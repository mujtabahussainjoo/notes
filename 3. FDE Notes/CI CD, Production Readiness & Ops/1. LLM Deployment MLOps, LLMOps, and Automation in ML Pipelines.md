# Simple Summary: DevOps, MLOps, and LLMOps

This topic explains how software, machine-learning models, and AI applications are built, tested, released, and monitored in real-world systems.

The main idea is:

> **DevOps manages software. MLOps manages machine-learning systems. LLMOps manages applications that use large language models.**

## 1. DevOps

**DevOps** is a way for developers, testers, and operations teams to work together.

Instead of building software for months and releasing it once, teams:

1. Build a small change.
2. Test it.
3. Release it.
4. Monitor it.
5. Improve it.
6. Repeat the process.

### Important DevOps ideas

- Teams work together instead of working separately.
- Code changes are stored and tracked using tools such as Git.
- Tests run automatically.
- New code can be released quickly.
- Applications are continuously monitored.
- Problems are detected early.

### CI and CD

**CI**, or Continuous Integration, means that new code changes are regularly added to a shared codebase and tested automatically.

**CD**, or Continuous Delivery or Deployment, means that tested code is sent to staging or production.

| Process | Meaning |
|---|---|
| Continuous Integration | Combine code changes and test them automatically |
| Continuous Delivery | Send tested code to staging; production release may need approval |
| Continuous Deployment | Automatically send tested code to production |

### Simple example

A developer changes the checkout code of an online store.

```text
Developer changes code
        ↓
Code is pushed to Git
        ↓
Automatic tests run
        ↓
If tests pass, code goes to staging
        ↓
After approval, code goes to production
```

This reduces manual work and catches errors earlier.

## 2. Why MLOps Is Different

**MLOps** means applying DevOps practices to machine-learning systems.

It helps teams deploy, manage, monitor, and update machine-learning models.

The main difference is that ordinary software mostly depends on **code**, while machine-learning systems depend on:

- Code.
- Training data.
- Model settings.
- Features.
- Infrastructure.
- Live production data.

### Software versus machine learning

| Traditional software | Machine-learning system |
|---|---|
| Mostly depends on code | Depends on code and data |
| Code is usually controlled | Real-world data constantly changes |
| Tests often check fixed results | Tests also check data and model quality |
| Code can remain useful for a long time | Model performance can become worse over time |
| Release a new code version | Release new code, data, and model versions |

### Simple example

Imagine a model that predicts whether a customer will buy a product.

It may work well when trained using old customer behavior. But later:

- Customer preferences change.
- New products are added.
- Shopping habits change.
- The economy changes.

The model may then make worse predictions. This is called **model decay**.

## 3. Main MLOps Problems

### Data quality

Data may contain:

- Missing values.
- Wrong values.
- Duplicate records.
- Unexpected fields.
- Outliers.
- Old or incomplete information.

Bad data usually leads to bad predictions.

### Data drift

Data drift happens when production data becomes different from the data used during training.

Example:

```text
Training data:
Customers mostly bought through desktop computers.

Production data:
Most customers now use mobile phones.
```

The model may no longer perform well because user behavior has changed.

### Model decay

Model decay means that model performance becomes worse over time.

The model may need to be:

- Monitored.
- Retrained.
- Replaced.
- Tested against a newer model.

### Model locality

A model trained for one group of users may not work equally well for another group.

For example, a recommendation model trained using United States customers may not give the best results for customers in India because customer behavior can be different.

### Other MLOps challenges

- Handling many users and requests.
- Managing model versions.
- Keeping training and production data consistent.
- Explaining why a model made a decision.
- Protecting private and sensitive data.
- Reproducing the same result for debugging.
- Updating models safely.

## 4. MLOps Workflow

A typical MLOps process looks like this:

```text
Collect data
    ↓
Clean and check data
    ↓
Split data into training and testing data
    ↓
Train the model
    ↓
Test and evaluate the model
    ↓
Store the model version
    ↓
Deploy the model
    ↓
Monitor live performance
    ↓
Retrain or replace the model when needed
```

MLOps adds another important activity to DevOps:

> **Continuous Training**

Continuous training means automatically training the model again when new data arrives or when model performance becomes poor.

## 5. Three Levels of MLOps

MLOps maturity shows how much of the machine-learning workflow is automated.

### Level 0: Manual process

Everything is done manually.

- Data scientists use notebooks and scripts.
- Data preparation is manual.
- Model training is manual.
- Testing is manual.
- Deployment is manual.
- Monitoring is limited.
- Retraining is manual.

This may be acceptable for experiments, but it becomes risky when models are used by many people.

### Level 1: Automated ML pipeline

The main machine-learning steps are automated.

- Data validation is automated.
- Data preparation is automated.
- Model training is automated.
- Model evaluation is automated.
- Retraining can happen on a schedule or after a warning.
- Deployment may still require manual work.

This level makes experiments faster and more reliable.

### Level 2: Fully automated process

The whole process is automated.

- Code changes trigger builds and tests.
- New data can trigger training.
- Models are automatically evaluated.
- Good models are deployed automatically.
- Production performance is monitored.
- Poor performance can trigger retraining.
- Older model versions can be restored if needed.

```text
New code or data
        ↓
Automatic validation
        ↓
Automatic training
        ↓
Automatic model testing
        ↓
Automatic deployment
        ↓
Production monitoring
        ↓
Retraining when required
```

## 6. Feature Store and Metadata Store

A **feature store** is a central place for storing and reusing prepared data features.

For example, an online store may use features such as:

- Number of previous orders.
- Average order value.
- Time since the last purchase.
- Frequently viewed product category.

Without a feature store, different teams may create slightly different versions of the same feature. This can create errors between training and production.

An **ML metadata store** keeps information about machine-learning experiments, such as:

- Which data was used.
- Which code version was used.
- Which settings were used.
- Which model was created.
- Which evaluation results were produced.
- Which model version is currently deployed.

This makes debugging and rollback easier.

## 7. What Is LLMOps?

**LLMOps** is a specialized form of MLOps for applications that use large language models.

Examples include:

- Chatbots.
- AI assistants.
- Document question-answering systems.
- Code-generation tools.
- Customer-support agents.
- RAG applications.

LLMOps helps teams build and operate these systems safely, reliably, and at a controlled cost.

## 8. Why LLMOps Needs Special Handling

LLM applications have problems that are different from traditional machine-learning systems.

### Prompts are part of the application

A prompt is an instruction given to the language model.

Example:

```text
You are a helpful customer-support assistant.
Answer using simple language.
If the answer is not in the provided documents, say that you do not know.
```

Prompts need to be:

- Stored and versioned.
- Tested.
- Reviewed.
- Approved.
- Reverted when a new version causes problems.

A small prompt change can produce a large change in the model’s answer.

### LLM answers are not always predictable

A normal classification model may answer:

```text
Cat or dog?
```

An LLM may answer a question in many different ways. Therefore, evaluation is more difficult.

LLM responses may need to be checked for:

- Correctness.
- Relevance.
- Clear language.
- Tone.
- Safety.
- Bias.
- Completeness.
- Use of trusted information.

### Hallucinations

A hallucination happens when an LLM confidently provides information that is false or unsupported.

Example:

```text
User: What was the exact sales figure for last month?

LLM: Sales were ₹25 lakh.
```

If the model did not receive the real sales data, this number may simply be invented.

LLMOps uses testing, monitoring, trusted data sources, and safety rules to reduce this problem.

### Cost and speed

LLM costs are often based on the amount of text sent to and received from the model.

Cost can increase because of:

- Long prompts.
- Large documents.
- Long answers.
- Too many requests.
- Using an expensive model for simple tasks.

LLMOps therefore monitors:

- Number of input tokens.
- Number of output tokens.
- Response time.
- Model usage.
- Cost per feature.
- Cache usage.

## 9. MLOps and LLMOps Compared

| Area | MLOps | LLMOps |
|---|---|---|
| Main focus | Machine-learning models | LLM-based applications |
| Important work | Feature engineering | Prompt engineering |
| Common data system | Feature store | Vector database |
| Main quality measures | Accuracy, precision, recall, F1 score | Helpfulness, correctness, safety, relevance |
| Common problem | Data drift and model decay | Hallucination, prompt injection, unsafe output |
| Training approach | Often train or retrain a model | Usually use an existing model and customize it |
| Main cost | Model training and infrastructure | Model usage and token consumption |
| Monitoring | Data changes and model performance | Answer quality, cost, latency, and safety |
| Extra controls | Model validation | Guardrails, output filters, prompt testing, and safety checks |

## 10. RAG and Vector Databases

LLM applications often use **RAG**, or Retrieval-Augmented Generation.

RAG allows an LLM to search trusted information before answering.

### Simple RAG flow

```text
User asks a question
        ↓
System searches company documents
        ↓
Relevant information is found
        ↓
Information is added to the LLM prompt
        ↓
LLM creates an answer using that information
```

A **vector database** stores documents in a form that helps the system find content with a similar meaning.

### Example

Suppose a customer asks:

```text
Can I return a product after 20 days?
```

Without RAG, the LLM may guess.

With RAG:

1. The system searches the store’s return policy.
2. It finds the correct section.
3. The policy is sent to the LLM.
4. The LLM answers using the policy.

This can reduce incorrect answers and makes the response more useful.

## 11. LLM Production Release Methods

LLM applications should not always be changed for every user at once.

### A/B testing

Two versions are shown to different user groups.

```text
50% of users → Model A
50% of users → Model B
```

The team compares their results.

### Canary release

The new version is first sent to a small group.

```text
95% of users → Old version
5% of users  → New version
```

If the new version works well, it is gradually released to more users.

### Blue-green release

Two complete environments are maintained:

- Blue: current working version.
- Green: new version.

After testing the green version, traffic is moved from blue to green.

## 12. Final Key Points

- **DevOps** improves the way software is built and released.
- **MLOps** adds data, model training, model testing, and model monitoring to DevOps.
- Machine-learning systems are harder to manage because real-world data changes.
- Models can become less accurate over time.
- Data, model, and code versions must be tracked.
- Continuous training helps models adapt to new data.
- **LLMOps** manages applications that use large language models.
- LLMOps must manage prompts, output quality, cost, speed, hallucinations, privacy, and safety.
- RAG helps an LLM answer using trusted external information.
- Good production systems continuously test, monitor, improve, and safely release changes.

### Easy memory trick

```text
DevOps  = Manage software
MLOps   = Manage software + data + models
LLMOps  = Manage software + prompts + LLM answers + safety + cost
```
