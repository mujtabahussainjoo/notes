# Simple Summary: Deploying and Managing LLMs

This course explains how to run large language models in real applications.

The main goal is to build LLM systems that are:

- Easy to use.
- Fast.
- Safe.
- Affordable.
- Reliable.
- Easy to update and maintain.

## 1. Ways to Deploy an LLM

Deployment means making an LLM available for an application or users.

### Managed API

A company provides the model through an API. You send a request and receive an answer.

```text
Your application → Model API → Answer
```

**Advantages:**

- Quick to start.
- No need to buy servers.
- The provider manages updates and scaling.
- Good for startups and changing traffic.

**Disadvantages:**

- Less control over private data.
- Long-term usage can become expensive.
- You depend on an external provider.

### On-premises or private deployment

The model runs inside your own data center or private cloud.

**Advantages:**

- Better control over security.
- More control over data.
- More control over customization.
- Useful for banks, hospitals, and regulated companies.

**Disadvantages:**

- Requires expensive hardware.
- Requires skilled people to manage it.
- Updates, security, and scaling are your responsibility.

### Simple choice

| Need | Suitable option |
|---|---|
| Quick setup | Managed API |
| Sensitive private data | Private or on-premises deployment |
| Full control | On-premises deployment |
| Changing traffic | Managed API or serverless |
| Heavy repeated workloads | Dedicated servers and GPUs |

## 2. Containers and Hardware

### Containers

A container packages the application, model, libraries, and settings together.

```text
Container
├── LLM model
├── Application code
├── Required libraries
└── Configuration
```

This helps the same application run consistently on:

- A developer’s laptop.
- A testing server.
- A cloud server.
- A production environment.

Containers also make it easier to:

- Run multiple copies.
- Update the service.
- Roll back after a failure.
- Move the application between environments.

### GPUs and CPUs

| Hardware | Best use | Main trade-off |
|---|---|---|
| GPU | Large models and fast responses | Faster but expensive and power-hungry |
| CPU | Small models and background work | Cheaper but usually slower |

### Example

For an online chatbot:

- Use a GPU when users need fast replies.
- Use a CPU for creating reports overnight.
- Use both when the application has different types of work.

## 3. Using Multiple Models

One model is not always best for every task.

A system can route requests to different models.

```text
User question
      ↓
Request router
 ┌────┴────┐
Small model   Large model
Simple task   Complex task
```

### Example

- “What are your store hours?” → Small and fast model.
- “Compare these five products and explain the differences.” → Larger and stronger model.
- Sensitive business question → Private model.

This approach can reduce cost and improve speed.

## 4. Packaging an LLM Pipeline

An LLM pipeline contains everything needed to receive a request and generate an answer.

Important parts include:

### Model weights

Model weights contain what the model has learned. They are like the model’s brain.

### Tokenizer

A tokenizer breaks text into smaller parts that the model can understand.

```text
"Hello world"
        ↓
["Hello", " world"]
```

The tokenizer must match the model. Using the wrong tokenizer can produce incorrect results.

### Prompt templates

A prompt template is a reusable instruction.

```text
You are a helpful support assistant.

Question:
{user_question}

Answer using simple language.
```

Templates make prompts consistent and easy to update.

### Configuration files

Configuration files store settings such as:

- Model name.
- Response limit.
- Temperature.
- Service settings.
- Environment values.

Private keys and passwords should not be written directly in source code.

### Model registry

A model registry stores model versions and related information.

```text
Model version 1 → Original model
Model version 2 → Improved model
Model version 3 → Bug-fixed model
```

It helps teams:

- Track changes.
- Compare versions.
- Roll back to an older version.
- Store test results.
- Know which model is in production.

## 5. API Patterns

An API allows another application to communicate with the LLM system.

### Synchronous API

The application sends a request and waits for the answer.

```text
Send request → Wait → Receive answer
```

This is useful for:

- Chatbots.
- Short questions.
- Fast answers.

### Asynchronous API

The application sends a request and continues doing other work. The answer arrives later.

```text
Send request → Continue working
                     ↓
              Answer arrives later
```

This is useful for:

- Large documents.
- Long-running tasks.
- Batch jobs.
- High traffic.

### Example

Creating a short product description can use a synchronous API.

Summarizing 100,000 documents should use an asynchronous or batch process.

## 6. Microservices

Microservices divide one large application into smaller services.

```text
User request
     ↓
Request service
     ↓
LLM service
     ↓
Database or vector search service
     ↓
Final answer
```

Each service performs one main job.

### Benefits

- Services can be updated separately.
- Teams can work independently.
- A failure in one service may not stop everything.
- Each service can be scaled as needed.
- Debugging becomes easier.

## 7. Batch, Streaming, and Serverless

### Batch processing

Many requests are collected and processed together.

Example:

```text
10,000 documents → Process overnight → Save summaries
```

Batch processing is useful when immediate answers are not needed.

### Streaming

The answer is sent little by little as it is created.

```text
The → answer → appears → gradually
```

Streaming is useful for chat applications because users see progress immediately.

### Serverless

With serverless deployment, the cloud provider starts resources when needed.

**Advantages:**

- No need to manage servers directly.
- Useful for changing traffic.
- You usually pay for actual usage.
- Easy to connect with other cloud services.

**Disadvantage:**

- The first request may be slower after a period of inactivity. This is called a cold start.

## 8. RAG: Giving the LLM Trusted Information

RAG means Retrieval-Augmented Generation.

It allows an LLM to search documents before answering.

```text
User question
      ↓
Search documents
      ↓
Find useful text
      ↓
Send text and question to LLM
      ↓
Generate answer
```

### Example

A company chatbot receives this question:

```text
Can I return a product after 30 days?
```

Instead of guessing:

1. The system searches the company return policy.
2. It finds the correct section.
3. It gives that section to the LLM.
4. The LLM answers using the policy.

RAG is useful when the information is:

- Private.
- Frequently updated.
- Specific to a company.
- Not included in the model’s original training.

## 9. Preparing Documents for RAG

### Chunking

Large documents are divided into smaller pieces called chunks.

```text
Large document
      ↓
Chunk 1
Chunk 2
Chunk 3
Chunk 4
```

Good chunks should keep related ideas together.

### Chunking styles

- **Fixed-size chunking:** Splits text into pieces of a similar size.
- **Semantic chunking:** Splits text according to meaning.
- **Hierarchical chunking:** Keeps relationships such as chapter, section, and paragraph.

A small overlap between chunks can help preserve context.

```text
Chunk 1: Text A + Text B
Chunk 2: Text B + Text C
```

### Metadata

Metadata adds useful labels to each chunk.

Examples:

- Document title.
- Section name.
- Date.
- Author.
- Product category.
- Country.
- Document type.

Metadata helps the system find better results.

## 10. Search Methods

### Keyword search

Finds exact words.

Example:

```text
Search: return policy
```

### Meaning-based search

Finds text with a similar meaning, even if the exact words are different.

Example:

```text
Question: How can I send an item back?
Document: Product return instructions
```

### Hybrid search

Combines keyword search and meaning-based search.

This usually gives better results because:

- Keyword search is good for exact names and codes.
- Meaning-based search is good for natural questions.

### Advanced retrieval

- **Multi-step retrieval:** Breaks a difficult question into smaller questions.
- **Cascading retrieval:** Starts with a broad search and then narrows the results.
- **Agentic RAG:** Allows an AI agent to decide what to search and which method to use.

## 11. Vector Databases

A vector database stores text as numbers that represent meaning.

```text
Text → Embedding numbers → Vector database
```

When a user asks a question:

1. The question is converted into numbers.
2. The system compares it with stored document numbers.
3. Similar documents are returned.

Vector databases are useful for semantic search.

They must be maintained by:

- Adding new document embeddings.
- Updating changed documents.
- Removing old documents.
- Rebuilding the index when needed.
- Applying filters such as date or product type.

An old or incorrect index can cause the LLM to retrieve outdated information.

## 12. Prompt, Context, and Feature Stores

### Prompt store

Keeps different prompt versions.

```text
Prompt v1 → Basic answer
Prompt v2 → More polite answer
Prompt v3 → More accurate answer
```

It helps teams compare results and restore an older prompt.

### Context store

Stores information needed for continuing conversations.

Examples:

- Previous user messages.
- User preferences.
- Earlier answers.
- Important facts.
- System instructions.

This helps an assistant remember the current conversation.

### Inference feature store

Stores information used during retrieval or prediction.

Examples:

- Document metadata.
- Embeddings.
- Product category.
- Customer type.
- Case jurisdiction.

## 13. Safety and Governance

LLM systems can create several risks.

### Harmful content

The model may produce:

- Offensive language.
- Dangerous instructions.
- Biased content.
- Inappropriate answers.

### Hallucinations

The model may invent facts that sound true.

### Data leakage

The model may expose:

- Passwords.
- Personal information.
- Customer records.
- Private company documents.

### Prompt injection

A user may try to trick the system into ignoring its rules.

## 14. Safety Techniques

### RLHF

RLHF means Reinforcement Learning from Human Feedback.

Human reviewers judge model answers. The model learns which answers are safer and more useful.

### DPO

DPO teaches the model directly from preferred and rejected answers.

```text
Preferred answer: Helpful and safe
Rejected answer: Incorrect or harmful
```

### Constitutional AI

The model follows a set of rules or principles.

Example rules:

- Respect privacy.
- Avoid hateful content.
- Do not invent facts.
- Refuse unsafe requests.

### Safety models

A separate safety system checks the input or output.

```text
LLM answer
    ↓
Safety check
    ↓
Allowed → User receives answer
Blocked → Answer is changed or rejected
```

### Output schema enforcement

The answer must follow a required format.

For example:

```json
{
  "answer": "string",
  "confidence": "high | medium | low",
  "source_found": true
}
```

If the output does not follow the required format, the system can reject it or ask the model to try again.

## 15. Making LLMs Faster and Cheaper

### Batching

Process several requests together.

This improves hardware usage and can reduce cost.

### Caching

Save common answers and reuse them.

```text
Same question → Return saved answer
```

This reduces repeated model calls.

### Model distillation

Create a smaller model that keeps much of the larger model’s useful behavior.

This smaller model usually needs less memory and responds faster.

### Quantization

Use smaller number formats for model weights.

It is similar to reducing a large image file while keeping it understandable.

Benefits include:

- Smaller model size.
- Lower memory use.
- Faster responses.
- Ability to run on cheaper hardware.

### Prompt compression

Remove unnecessary words from the prompt while keeping its meaning.

```text
Long prompt → Shorter useful prompt
```

This reduces processing time and token cost.

### Retrieval-based scaling

Instead of making the model larger, provide it with the right information from a database.

This can improve answers without using a very expensive model.

### Token budgeting

Set limits on input and output length.

```text
Maximum input: 2,000 tokens
Maximum answer: 300 tokens
```

This helps prevent unexpected costs.

### Resource forecasting

Use past usage to predict future needs.

For example, if traffic usually increases during a sale, the system can prepare more computing resources in advance.

## 16. CI/CD for LLM Applications

Traditional CI/CD mainly checks code. LLM CI/CD must check more things:

- Code.
- Model versions.
- Prompt versions.
- Data.
- Retrieved documents.
- Answer quality.
- Safety.
- Cost.
- Response speed.

### LLM testing

Tests should check whether:

- The answer is correct.
- The answer uses the right context.
- The prompt still works.
- The model follows instructions.
- The response is safe.
- The output format is valid.
- Costs remain within limits.

A simple test may look like this:

```python
def test_answer():
    answer = ask_llm("What is the return period?")
    assert "30 days" in answer
```

Real systems usually use more detailed checks than this, but the idea is the same.

### Canary release

Send a new model or prompt to a small group first.

```text
95% of users → Old version
5% of users  → New version
```

If the new version performs badly, roll it back quickly.

### Automated pipeline

```text
Code or prompt change
        ↓
Run tests
        ↓
Check model and answer quality
        ↓
Build container
        ↓
Deploy to a small user group
        ↓
Monitor results
        ↓
Release to everyone or roll back
```

## 17. Simple RAG API Example

The following example shows the basic idea of an API that receives a question and returns an answer.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Question(BaseModel):
    question: str

def get_rag_answer(question: str) -> str:
    # 1. Search the document database
    context = "Return products within 30 days with a valid receipt."

    # 2. Send the question and context to the LLM
    return f"Based on the policy: {context}"

@app.post("/ask")
def ask(question: Question):
    answer = get_rag_answer(question.question)
    return {"answer": answer}
```

### What happens here?

```text
Client sends question
        ↓
FastAPI receives it
        ↓
RAG searches useful information
        ↓
LLM creates an answer
        ↓
API returns JSON
```

In a real project, the document search, embeddings, vector database, safety checks, logging, authentication, and error handling would also be included.
