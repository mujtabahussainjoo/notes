# Spec-Driven Development

## 1. What is SDD?

**Spec-Driven Development (SDD)** is a software-development approach where the specification becomes the main source of truth.

Instead of starting with:

```text
Prompt → Code → Fix mistakes
```

SDD uses:

```text
Intent → Specification → Plan → Tasks → Code → Validation
```

The specification explains what the system should do, why it is needed, what constraints apply, and how success will be checked. Developers or AI coding agents then implement the feature against that specification. [web:31][web:32]

## 2. Why SDD is useful

AI coding tools can generate code quickly, but a vague request often produces a plausible implementation of the wrong problem.

A specification reduces guessing by defining:

- The user problem.
- The desired behavior.
- What is included and excluded.
- Data and API contracts.
- Error handling.
- Security and performance requirements.
- Acceptance criteria.

The main benefit is not simply writing code faster. It is reducing rework caused by unclear requirements and keeping implementation aligned with business intent. [web:34]

## 3. Core idea: what before how

A good SDD workflow separates two questions:

| Question | Example |
|---|---|
| What should the system do? | A customer can cancel an unpaid order. |
| How will it be implemented? | Add a REST endpoint and update the order service. |

The specification focuses first on **what** and **why**. The technical plan later explains **how**.

This separation gives the team a chance to correct the product behavior before investing in implementation details. GitHub's Spec Kit describes this as defining what and why before deciding how. [web:32][web:33]

## 4. SDD workflow

A practical workflow is:

```text
Constitution → Specify → Clarify → Plan → Tasks → Implement → Converge
```

Not every team needs every stage, but the stages are useful for production work.

### Stage 1: Constitution

The constitution contains project-wide rules that apply to every feature.

Examples:

- Use TypeScript with strict mode.
- All public APIs require authentication.
- Every feature must include automated tests.
- Do not expose customer data in logs.
- Use REST conventions already established by the project.
- Keep Magento service contracts backward compatible.

The constitution answers:

> What rules must every implementation follow?

GitHub Spec Kit recommends creating the constitution once per project, then running the feature workflow for each feature. [web:32]

### Stage 2: Specify

Write the feature specification in user and business terms.

Include:

- Problem statement.
- Goal.
- User stories.
- Functional requirements.
- Non-goals.
- Constraints.
- Edge cases.
- Acceptance criteria.

At this stage, avoid prematurely choosing frameworks, classes, or database tables unless they are already fixed constraints.

### Stage 3: Clarify

Review the specification for missing or ambiguous information.

Ask questions such as:

- What happens if the input is empty?
- Which users are authorized?
- What happens when an external API times out?
- Is the operation idempotent?
- What happens when two requests arrive at the same time?
- What is the expected behavior on mobile screens?
- What does the user see after a failure?

The goal is to remove assumptions before planning begins.

### Stage 4: Plan

Convert the approved behavior into a technical plan.

The plan can define:

- Architecture.
- Modules and components.
- Database changes.
- API endpoints.
- Events and queues.
- External integrations.
- Testing strategy.
- Observability requirements.
- Migration and rollback strategy.

This is where the team decides how to implement the specification.

### Stage 5: Tasks

Break the plan into small, verifiable tasks.

Each task should have:

- A clear outcome.
- A relationship to one or more requirements.
- Dependencies.
- Validation steps.
- A reasonable implementation size.

Example:

```text
T1. Add order-cancellation service contract.
T2. Validate order state before cancellation.
T3. Add authorization check.
T4. Persist cancellation reason.
T5. Add REST endpoint.
T6. Add unit and integration tests.
T7. Update API documentation.
```

### Stage 6: Implement

Developers or AI coding agents execute the tasks.

Implementation should refer back to:

- The specification.
- The technical plan.
- The task list.
- Project rules.
- Existing code patterns.

Do not treat generated code as automatically correct. Review the diff and run the required checks.

### Stage 7: Converge

Convergence means comparing the implementation with the intended behavior until the two match.

Check:

- Every requirement has an implementation.
- Every acceptance criterion has a test or verification step.
- No important behavior was added without approval.
- Error and security requirements are satisfied.
- Documentation reflects the final behavior.
- Tests, linting, static analysis, and CI pass.

Spec Kit describes repeating implementation and convergence until the work reaches a converged state. [web:32]

## 5. Anatomy of a good specification

A production-ready feature specification should contain the following sections.

### 5.1 Title and status

```markdown
# Cancel Unpaid Order

Status: Draft
Owner: Checkout Team
Last updated: 2026-09-19
```

### 5.2 Problem statement

Explain the user or business problem.

```text
Customers currently need support assistance to cancel an unpaid order. This creates unnecessary support work and delays corrections to accidental orders.
```

### 5.3 Goal

Describe the desired result.

```text
Allow an authenticated customer to cancel their own unpaid order from the account area.
```

### 5.4 Scope

State what the feature includes.

```text
In scope:
- Cancel unpaid orders.
- Show cancellation confirmation.
- Record a cancellation reason.
- Send an email notification.
```

### 5.5 Non-goals

State what the feature does not include.

```text
Out of scope:
- Cancelling paid orders.
- Cancelling shipped orders.
- Refund processing.
- Admin bulk cancellation.
```

Non-goals prevent an AI agent or developer from expanding the feature without approval.

### 5.6 Functional requirements

Write behavior in a testable way.

```text
FR-001: An authenticated customer can request cancellation of an order they own.

FR-002: The system must reject cancellation when the order is paid, shipped, complete, or already cancelled.

FR-003: The system must require a cancellation reason between 5 and 500 characters.

FR-004: A successful cancellation must record the user, timestamp, and reason.
```

### 5.7 Non-functional requirements

Include quality attributes.

```text
NFR-001: The endpoint must require authentication.

NFR-002: A customer must not be able to access another customer's order.

NFR-003: The operation should complete within 500 ms under normal load.

NFR-004: Logs must not contain payment details or personal data beyond the order identifier.
```

### 5.8 Integration contracts

Specify external interfaces precisely.

```text
POST /V1/orders/{orderId}/cancel

Request:
{
  "reason": "Ordered by mistake"
}

Success: HTTP 200
Failure: HTTP 400, 401, 403, or 409
```

Define:

- Request fields.
- Response fields.
- Status codes.
- Authentication.
- Retry rules.
- Timeout behavior.
- Idempotency behavior.

AI agents often invent integration details when the contract is missing, so this section is particularly important. [web:34]

### 5.9 Edge cases

```text
- The order does not exist.
- The order belongs to another customer.
- The order changes state while cancellation is processing.
- The reason is too short.
- The email service is unavailable.
- The request is repeated.
- The user refreshes after a successful cancellation.
```

### 5.10 Acceptance criteria

Acceptance criteria describe what “done” means.

```gherkin
Scenario: Customer cancels an unpaid order
  Given the customer owns an unpaid order
  When the customer submits a valid cancellation reason
  Then the order becomes cancelled
  And the cancellation reason is stored
  And the customer receives a confirmation message

Scenario: Customer tries to cancel a paid order
  Given the customer owns a paid order
  When the customer requests cancellation
  Then the request is rejected
  And the order remains paid
```

## 6. Example feature specification

```markdown
# Feature: Product FAQ Assistant

## Problem
Support agents repeatedly answer questions that are already covered by product manuals and store policies.

## Goal
Allow customers to ask questions and receive answers grounded in approved product and policy documents.

## In scope
- Search approved documents.
- Return a concise answer.
- Show document references.
- State when the answer is unavailable.

## Out of scope
- Product recommendations.
- Order changes.
- Refund processing.
- Searching private customer records.

## Functional requirements
- FR-001: The assistant must search the approved knowledge base for each product-policy question.
- FR-002: The assistant must answer only from retrieved content.
- FR-003: The assistant must show the source document name when an answer is available.
- FR-004: The assistant must say that it cannot find the answer when retrieval returns no relevant content.

## Non-functional requirements
- NFR-001: Retrieval must enforce store and tenant access rules.
- NFR-002: The system must log request ID and latency without logging sensitive customer content.
- NFR-003: The response should normally be returned within 5 seconds.

## Acceptance criteria
- A question about a known policy returns a grounded answer with a source.
- A question not covered by the documents returns an uncertainty message.
- A user cannot retrieve another store's private policy.
- A retrieval failure produces a safe error message.
```

## 7. SDD and AI coding agents

SDD is especially useful with AI coding agents because agents need clear context and boundaries.

A good agent input includes:

```text
Project rules
   +
Feature specification
   +
Technical plan
   +
Task list
   +
Relevant repository context
   ↓
AI coding agent
   ↓
Code, tests, and documentation
```

The agent should not be asked to “build something similar” without a contract. Give it explicit requirements and ask it to identify uncertainty instead of guessing.

### Useful agent instructions

```text
Implement only the tasks listed in tasks.md.
Do not change public APIs unless the specification requires it.
Use existing project patterns before introducing new abstractions.
Add tests for every acceptance criterion.
If a requirement is ambiguous, stop and ask for clarification.
Report files changed, tests run, and unresolved risks.
```

## 8. Spec-first, spec-anchored, and spec-as-source

There are different levels of adoption.

| Level | Description | Suitable for |
|---|---|---|
| Spec-first | Write a spec before implementation, but do not maintain it afterward | Small features and prototypes |
| Spec-anchored | Keep the specification updated with the code | Production applications |
| Spec-as-source | Humans mainly maintain the spec; code is generated or regenerated from it | Controlled greenfield systems |

Most existing production systems should begin with **spec-anchored** development. Full spec-as-source development can be difficult when the codebase contains legacy behavior and many manual integrations. [web:34]

## 9. SDD compared with other approaches

| Approach | Main source of direction | Typical workflow |
|---|---|---|
| Code-first | Existing code and developer decisions | Code → tests → documentation |
| Vibe coding | Conversational prompts | Prompt → generated code → repeated corrections |
| TDD | Tests | Test → implementation → refactor |
| BDD | User behavior scenarios | Scenario → implementation → acceptance test |
| SDD | Structured specification | Spec → plan → tasks → implementation → validation |
| Contract-driven development | Service contract | Contract → independent implementations |

SDD does not replace TDD or BDD. They can work together:

```text
Specification → Acceptance criteria → Tests → Implementation
```

## 10. SDD with brownfield projects

For an existing Magento, React, or API project, do not attempt to specify the entire codebase at once.

Use this approach:

1. Choose one feature or module.
2. Document current behavior first.
3. Identify existing APIs, events, database tables, and dependencies.
4. Write the desired behavior and non-goals.
5. Note compatibility constraints.
6. Create a plan that follows existing architecture.
7. Implement one small task at a time.
8. Compare the result with both current and desired behavior.

For legacy systems, include a section such as:

```markdown
## Existing behavior to preserve
- Existing checkout API response fields must remain backward compatible.
- Existing observers must continue to execute.
- Existing database data must remain readable.
```

This prevents an AI agent from “cleaning up” unrelated code and accidentally breaking compatibility.

## 11. Recommended repository structure

```text
project/
├── .specify/
│   ├── memory/
│   └── templates/
├── specs/
│   └── 001-cancel-unpaid-order/
│       ├── spec.md
│       ├── plan.md
│       ├── tasks.md
│       └── checklist.md
├── src/
├── tests/
├── docs/
└── README.md
```

A simpler structure also works:

```text
project/
├── docs/specs/
│   └── product-faq-assistant.md
├── src/
└── tests/
```

The important rule is that specifications must be versioned and easy to find near the implementation.

## 12. GitHub Spec Kit

GitHub Spec Kit is an open-source toolkit for starting SDD workflows with AI coding agents.

Its documented flow is:

```text
/speckit-constitution
/speckit-specify
/speckit-plan
/speckit-tasks
/speckit-implement
/speckit-converge
```

Additional clarification, checklist, and analysis steps can be used when more quality gates are needed. Spec Kit supports project rules, reusable templates, agent integrations, and workflows for new and existing projects. [web:32]

### Basic setup

The current repository instructions list Python 3.11+, `uv`, and a supported AI coding agent as prerequisites. [web:32]

```bash
uv tool install specify-cli
specify init my-project --integration copilot
cd my-project
```

The `/speckit-*` items are invoked inside the supported coding agent's chat, not necessarily as ordinary terminal commands. Always check the current project documentation for the supported integration and syntax. [web:32]

### Example Spec Kit sequence

```text
/speckit-constitution Define rules for maintainability, testing, and security.

/speckit-specify Add customer order cancellation for unpaid orders.

/speckit-plan Use the existing REST service contracts and preserve API compatibility.

/speckit-tasks

/speckit-implement

/speckit-converge
```

## 13. Quality gates

Use gates between stages instead of reviewing only the final code.

### Specification gate

- Is the problem clear?
- Are scope and non-goals defined?
- Are acceptance criteria testable?
- Are edge cases listed?
- Are external contracts documented?

### Planning gate

- Does the plan satisfy every requirement?
- Does it respect project architecture?
- Are security and performance addressed?
- Are migrations and rollback considered?

### Implementation gate

- Does every task map to a requirement?
- Are tests included?
- Is unrelated code unchanged?
- Were assumptions recorded?

### Release gate

- Do automated tests pass?
- Does manual acceptance pass?
- Are logs and metrics sufficient?
- Is the specification updated?
- Is the change safe to deploy and roll back?

## 14. Common mistakes

### Writing a vague specification

Bad:

```text
Add a better checkout experience.
```

Better:

```text
Allow a logged-in customer to save one default shipping address and select it during checkout.
```

### Mixing requirements and implementation too early

A requirement should describe observable behavior. The implementation plan can later choose services, classes, queues, or database changes.

### Forgetting non-goals

Without non-goals, the scope grows silently and the agent may implement unrelated features.

### Omitting failure behavior

Every important integration should define timeout, retry, validation, authorization, and error behavior.

### Treating the spec as disposable

If the requirement changes, update the specification before changing the code. Otherwise, future developers and agents will follow outdated intent.

### Letting the agent change too much

Use small tasks, restricted repository access, focused branches, and explicit instructions not to modify unrelated files.

### Measuring output instead of alignment

More generated code is not necessarily more progress. Measure acceptance criteria completed, defects, rework, review time, and production outcomes.

## 15. When SDD is a good fit

SDD is especially useful for:

- Production features with several integration points.
- AI-assisted implementation.
- APIs with clear contracts.
- Features requiring security and compliance review.
- Multi-developer teams.
- Long-lived modules.
- Brownfield changes where compatibility matters.
- Work that needs traceability from requirement to test.

## 16. When SDD may be excessive

A full workflow may add unnecessary overhead for:

- A quick experiment.
- A throwaway prototype.
- Visual exploration before the UX is settled.
- An urgent production incident.
- A small typo or isolated documentation update.
- Research where the main goal is learning rather than shipping.

Use the lightest process that prevents unacceptable risk.

## 17. Practical lab exercise

Build an order-cancellation feature for a small commerce application.

### Goal

Allow customers to cancel unpaid orders.

### Exercise

1. Write `spec.md` with problem, goal, scope, non-goals, requirements, edge cases, and acceptance criteria.
2. Review the specification with a checklist.
3. Write `plan.md` describing API, service, persistence, events, and tests.
4. Write `tasks.md` with small implementation tasks.
5. Implement one task at a time.
6. Add tests from the acceptance criteria.
7. Run static analysis and integration tests.
8. Review the final diff against `spec.md`.
9. Update the specification if the approved behavior changed.
10. Open a pull request containing the spec, plan, tasks, code, and test results.

### Example traceability table

| Requirement | Implementation | Test |
|---|---|---|
| FR-001: Customer can cancel own unpaid order | `CancelOrderService` | `test_customer_can_cancel_unpaid_order` |
| FR-002: Paid orders are rejected | State validation | `test_paid_order_cannot_be_cancelled` |
| FR-003: Reason is required | Request validator | `test_reason_validation` |
| NFR-002: Customer isolation | Authorization policy | `test_other_customer_cannot_cancel_order` |

## 18. Key takeaways

- SDD makes the specification the source of truth.
- It separates product intent from technical implementation.
- The common flow is specify, plan, create tasks, implement, and converge.
- Good specifications include requirements, non-goals, constraints, contracts, edge cases, and acceptance criteria.
- SDD works particularly well with AI coding agents because it reduces guessing.
- TDD and BDD complement SDD; they do not compete with it.
- For existing systems, start with one feature and preserve known behavior.
- Keep specifications versioned and update them when requirements change.
- Review the spec and plan before reviewing a large code diff.
- Use human approval for architecture, security, data access, and production changes.
