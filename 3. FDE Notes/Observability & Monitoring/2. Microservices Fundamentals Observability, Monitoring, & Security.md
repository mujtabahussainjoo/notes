# Microservices Observability, Monitoring, and Security

## Main idea

Microservices divide one large application into many smaller services.

For example, an online shop may have separate services for:

```text
Customer login
Product search
Shopping cart
Payment
Inventory
Delivery
```

This makes the system flexible, but it also makes problems harder to find.

To manage microservices safely, we need three things:

```text
Observability → Understand what is happening
Monitoring    → Detect problems early
Security      → Protect services and data
```

## What is observability?

Observability helps us understand the inside behavior of a system by looking at the information it produces.

It answers questions such as:

- Which service caused a delay?
- Why did a payment fail?
- Where did an error begin?
- How did one service affect another?

### Simple example

A customer clicks “Pay,” but the order takes 10 seconds.

```text
Customer
   |
   v
Order service
   |
   v
Payment service
   |
   v
Inventory service
   |
   v
Notification service
```

Observability helps follow the request through every service and find the slow step.

## Three main pillars

Observability uses three types of information.

| Pillar | Simple meaning | Example |
|---|---|---|
| Metrics | Numbers about system health | Error rate is 5% |
| Logs | Detailed records of events | Payment failed because of a timeout |
| Traces | The full path of one request | Payment service took 8 seconds |

### Easy memory trick

```text
Metrics = What is happening?
Logs    = What happened?
Traces  = Where did it happen?
```

Together, they provide a complete view of the system.

## Monitoring versus observability

| Monitoring | Observability |
|---|---|
| Detects known problems | Investigates known and unknown problems |
| Uses predefined limits | Uses metrics, logs, and traces |
| Tells you something is wrong | Helps explain why it is wrong |
| Sends alerts | Helps find the root cause |

### Simple example

```text
Monitoring:
Payment errors are above 5%.

Observability:
The payment database is slow, causing payment requests to fail.
```

Monitoring is the first warning. Observability is the deeper investigation.

## Types of monitoring

### Infrastructure monitoring

Checks the machines and network.

Examples:

- CPU usage.
- Memory usage.
- Disk space.
- Network traffic.
- Server health.

### Application monitoring

Checks how the software works.

Examples:

- Response time.
- Error rate.
- API performance.
- Database query time.
- Successful transactions.

### User-experience monitoring

Checks what real users experience.

Examples:

- Page loading time.
- Failed checkouts.
- Login problems.
- Broken screens.
- Slow mobile app actions.

Using all three gives a better understanding of system health.

## Proactive and reactive monitoring

### Proactive monitoring

Finds warning signs before a failure happens.

Example:

```text
CPU usage:
60% → 70% → 80% → 90%
```

The team receives a warning before the system becomes too slow.

### Reactive monitoring

Responds after a problem occurs.

Example:

```text
Payment service crashes
        |
        v
Alert is sent
        |
        v
Team starts fixing the problem
```

Both methods are useful:

```text
Proactive monitoring = Prevent problems
Reactive monitoring  = Recover quickly
```

## Metrics

Metrics are numerical measurements collected over time.

Common examples:

```text
CPU usage: 75%
Memory usage: 60%
Response time: 300 ms
Error rate: 2%
Requests per minute: 2,000
```

### Common metric types

| Metric type | What it measures | Example |
|---|---|---|
| Counter | Total number of events | Number of logins |
| Gauge | Current value | Current memory usage |
| Histogram | Distribution of values | Request-time ranges |
| Summary | Statistics about values | Average and percentiles |

### Collecting metrics

#### Push method

The application sends metrics to the monitoring system.

```text
Application → Monitoring system
```

#### Pull method

The monitoring system regularly asks the application for metrics.

```text
Monitoring system → Application
```

Pull collection keeps collection timing under central control and usually requires less monitoring logic inside the application.

#### Agent method

A small helper program runs near the application and collects the metrics.

```text
Application
     |
     v
Local monitoring agent
     |
     v
Monitoring system
```

## Collecting and analyzing metrics

A metric endpoint may provide data like this:

```text
http_requests_total 1500
memory_usage_percent 72
error_rate_percent 1.5
```

The monitoring system stores these values with timestamps.

It can then calculate:

- Total requests.
- Average response time.
- Highest value.
- Lowest value.
- Percentage of errors.
- Changes over time.
- Unusual spikes.

### Example

Instead of viewing every request time:

```text
120 ms, 130 ms, 125 ms, 900 ms, 140 ms
```

A summary may show:

```text
Average response time: 263 ms
Highest response time: 900 ms
```

This makes the data easier to understand.

## Logs

Logs are like a diary for a software system.

They record:

- What happened.
- When it happened.
- Which service was involved.
- Whether it was successful.
- What error occurred.
- Extra details needed for debugging.

### Common log types

| Log type | Purpose |
|---|---|
| Event log | Records actions such as login or payment |
| Error log | Records failures and errors |
| Access log | Records who accessed a service and when |
| Debug log | Provides detailed information for troubleshooting |

### Good log example

```text
2026-09-22 17:30:10
Service: payment
Level: ERROR
Order: 12345
Message: Database connection timeout
```

### Bad logging practice

Do not store sensitive information such as:

```text
Password
Full card number
Private access token
```

Logs should be useful without exposing private data.

## Centralized log management

In a microservices system, every service may create its own logs.

```text
Login logs       \
Payment logs      \
Order logs        ---> Central log system
Inventory logs   /
Delivery logs    /
```

Centralized logs make it easier to:

- Search all services together.
- Filter by time or error level.
- Follow one order.
- Find repeated problems.
- Create alerts from error patterns.

### Log storage levels

| Storage level | Use |
|---|---|
| Hot | Recent logs that need quick access |
| Warm | Older logs used sometimes |
| Cold | Historical or compliance records |

Retention rules automatically remove logs after a chosen period.

Example:

```text
Debug logs: 7 days
Application logs: 30 days
Audit logs: several years
```

## Distributed tracing

Tracing follows one request through many services.

It is like tracking a package through several delivery centers.

```text
Request starts
     |
     v
Login service       50 ms
     |
     v
Cart service        30 ms
     |
     v
Payment service    900 ms
     |
     v
Order service       40 ms
```

The total trace shows that the payment service is the slow part.

### Trace and span

- A **trace** represents the complete request.
- A **span** represents one step inside that request.
- A **trace ID** connects all steps to the same request.
- A **span ID** identifies one individual step.

```text
Trace ID: ABC123

Span 1: Login
Span 2: Cart
Span 3: Payment
Span 4: Order
```

### Context propagation

Each service must pass the trace information to the next service.

```text
Service A → Service B → Service C
    trace information continues
```

If a service does not pass it forward, the trace becomes incomplete.

## Security in microservices

Microservices communicate over networks, so every service becomes a possible entry point for an attacker.

Common risks include:

- Weak login protection.
- Unauthorized access.
- Unencrypted communication.
- Unsafe APIs.
- Outdated software.
- Denial-of-service attacks.
- Exposed sensitive data.
- Misconfigured services.

A problem in one service can sometimes spread to other services.

## Three important security controls

### 1. Encryption

Encryption protects data while it moves between services.

```text
Readable data → Encrypted data → Readable data
```

Transport Layer Security creates a protected connection.

Think of encryption as sending information inside a locked box.

### 2. Authentication

Authentication checks who the user or service is.

```text
Service A: Who are you?
Service B: Here is my approved identity token.
Service A: Identity confirmed.
```

Tokens and certificates can be used to prove identity.

### 3. Authorization

Authorization decides what an identified user or service is allowed to do.

```text
Authentication = Who are you?
Authorization  = What can you do?
```

Example:

```text
Admin service  → Read and update orders
Support service → Read orders
Customer       → Read only their own orders
```

Role-Based Access Control groups permissions by role.

## Important security principles

### Least privilege

Give each service only the access it needs.

```text
Payment service → Access payment data
Payment service → No access to employee records
```

This limits damage if the service is compromised.

### Defense in depth

Use several security layers together.

```text
Firewall
   +
Encryption
   +
Authentication
   +
Authorization
   +
Monitoring
```

If one layer fails, the others still provide protection.

### Continuous security checks

Security must be checked regularly.

Important activities include:

- Scan for weaknesses.
- Update old software.
- Protect exposed APIs.
- Review permissions.
- Monitor unusual behavior.
- Prepare an incident-response plan.
- Check third-party libraries.

## Observability tools

An observability system usually contains several parts.

```text
Application
    |
    v
Collect metrics, logs, and traces
    |
    v
Process and store data
    |
    v
Search and analyze data
    |
    v
Dashboards and alerts
```

### Common tool roles

| Tool role | Purpose |
|---|---|
| Collection tool | Gathers metrics, logs, and traces |
| Storage system | Saves the collected data |
| Query tool | Searches and analyzes data |
| Dashboard tool | Shows charts and system health |
| Alert tool | Notifies the team about problems |

OpenTelemetry is used to collect information in a common format. Prometheus is commonly used for metrics. Grafana is commonly used for dashboards and can bring metrics, logs, and traces together.

## Configuration as code

Instead of setting dashboards and alerts manually, store their settings as files in version control.

```text
Configuration files
        |
        v
Review changes
        |
        v
Automatically deploy monitoring setup
```

This approach helps with:

- Tracking changes.
- Reviewing updates.
- Restoring older versions.
- Keeping environments consistent.
- Automating deployment.

## Simple incident example

A customer says checkout is slow.

### Step 1: Monitoring detects the problem

```text
Checkout response time is above 5 seconds.
```

### Step 2: Metrics show the pattern

```text
Payment error rate increased.
Database usage is high.
```

### Step 3: Tracing follows the request

```text
Login: 40 ms
Cart: 30 ms
Payment: 4,800 ms
```

### Step 4: Logs explain the cause

```text
Payment service: Database connection timeout
```

### Step 5: Security checks the event

The team checks whether the unusual traffic came from an attack.

```text
Monitoring   → Finds the issue
Metrics      → Shows the pattern
Tracing      → Finds the slow service
Logs         → Explains the error
Security     → Checks for threats
```

## Final memory guide

Remember the whole topic with this sentence:

> Metrics show the numbers, logs record the events, traces follow the request, monitoring sends warnings, observability finds the cause, and security protects everything.

The main workflow is:

```text
Collect
  |
  v
Store
  |
  v
Analyze
  |
  v
Show on dashboard
  |
  v
Send useful alerts
  |
  v
Investigate and fix
```

For a safe and reliable microservices system:

```text
Observability + Monitoring + Security
              =
Reliable and protected services
```
