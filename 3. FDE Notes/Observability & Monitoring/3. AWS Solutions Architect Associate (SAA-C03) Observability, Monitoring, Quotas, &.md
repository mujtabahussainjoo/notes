# AWS Observability and Operations: Easy Summary

## Main idea

In cloud systems, especially systems built with small services, we need to know:

- Is the system working?
- What is going wrong?
- Where did the problem happen?
- What changed?
- How should we respond?

AWS observability uses four main signals:

```text
Metrics → What is happening?
Logs    → Why did it happen?
Traces  → Where did it happen?
Events  → What changed?
```

The goal is not just to collect data. The goal is to turn data into:

```text
Detection → Investigation → Action → Recovery
```

## The four observability signals

### 1. Metrics

Metrics are numbers collected over time.

Examples:

```text
CPU usage: 70%
Error rate: 2%
Response time: 400 ms
Lambda calls: 1,000
Queue size: 500
```

Metrics are useful for:

- Finding trends.
- Creating alarms.
- Checking service health.
- Measuring performance.
- Tracking business results.

### 2. Logs

Logs are detailed records of what happened.

Example:

```json
{
  "level": "ERROR",
  "service": "payment",
  "order_id": "12345",
  "message": "Database connection failed"
}
```

Logs help answer:

- What error occurred?
- Which service produced it?
- When did it happen?
- Which request was affected?
- What information can explain the failure?

### 3. Traces

A trace follows one request through many services.

```text
User request
    |
    v
API Gateway
    |
    v
Lambda
    |
    v
Database
    |
    v
Response
```

A trace can show:

- Which service was slow.
- Where an error happened.
- Which database or external API was involved.
- How long each step took.

### 4. Events

Events record changes in the environment.

Examples:

- A deployment happened.
- A server was scaled.
- A configuration changed.
- An AWS service had a problem.
- Maintenance was scheduled.

Events are important because a sudden system change may explain why the system started behaving differently.

## How the signals work together

```text
Metrics detect the problem
        |
        v
Logs explain the error
        |
        v
Traces locate the slow or failing step
        |
        v
Events show what changed
        |
        v
Team fixes the issue
```

### Example

An online shop becomes slow.

```text
Metrics:
Response time increased.

Logs:
Database timeout errors appeared.

Traces:
Most time was spent in the payment database call.

Events:
A new deployment happened ten minutes earlier.
```

Now the team has a much clearer idea of what happened.

## Important system health measures

Before creating dashboards and alarms, define what “healthy” means.

### Availability

Shows whether users can successfully use the system.

```text
Successful requests ÷ Total requests
```

Example:

```text
990 successful requests out of 1,000
Availability = 99%
```

### Latency

Shows how long a request takes.

Instead of looking only at the average, use percentiles:

- P90: 90% of requests are this fast or faster.
- P95: 95% of requests are this fast or faster.
- P99: 99% of requests are this fast or faster.

The average can hide very slow requests.

### Errors

Shows how often requests fail.

Examples:

- Server errors.
- Lambda errors.
- Failed payments.
- API failures.
- Throttling errors.

### Saturation

Shows how close the system is to its limits.

Examples:

- Lambda concurrency.
- Database connections.
- Queue size.
- Storage usage.
- API request limits.

### Business measures

Technical systems can look healthy while the business process is failing.

Track business values such as:

- Orders.
- Checkouts.
- Successful payments.
- Completed jobs.
- Sign-ups.

## Metrics design

### Namespaces

Namespaces group related metrics.

```text
AWS/Lambda
AWS/EC2
MyCompany/Checkout
MyCompany/Payments
```

This makes metrics easier to find and manage.

### Dimensions

Dimensions add context to a metric.

Example:

```text
Metric: Errors
FunctionName: payment-function
Environment: production
```

Use dimensions carefully. Too many unique values increase cost and create noise.

Avoid values such as:

```text
user_id
request_id
session_id
exact_timestamp
```

Prefer small, fixed groups:

```text
environment = dev, staging, production
region = east, west
service = payment, cart, catalog
```

## Choosing statistics

Use the right calculation for the job.

| Need | Useful calculation |
|---|---|
| Total requests | Sum |
| Total errors | Sum |
| Requests per second | Rate |
| Response-time behavior | Percentiles |
| Current CPU level | Average or maximum |
| Queue pressure | Maximum or average |

### Example

```text
Error rate = Errors ÷ Total requests
```

This is usually more useful than looking only at the raw number of errors.

## Static thresholds and anomaly detection

### Static threshold

Uses a fixed limit.

```text
If CPU > 80%, create an alarm.
```

Good when the system has stable behavior.

### Anomaly detection

Learns normal behavior and detects unusual changes.

Example:

```text
Normal traffic:
Low at night
High during the day

Anomaly:
Traffic suddenly becomes much higher than normal at night
```

Anomaly detection is useful when traffic changes by:

- Time of day.
- Day of week.
- Season.
- Business events.

## Avoiding noisy alarms

Too many alarms can cause alert fatigue. Teams may start ignoring alerts.

### Good alarm practices

- Alert on user impact.
- Use realistic limits.
- Require several bad periods before alerting.
- Define what missing data means.
- Add clear next steps.
- Give every alarm an owner.
- Review and remove useless alarms.
- Use lower-severity alerts for investigation details.

### Symptom and diagnostic alarms

```text
Symptom alarm:
Checkout error rate is high.

Diagnostic alarm:
Database connections are almost full.
```

The symptom alarm may notify the team immediately. The diagnostic alarm helps investigate the cause.

## Composite alarms

A composite alarm combines several alarms into one higher-level alarm.

Example:

```text
High latency
     AND
High error rate
     |
     v
Service health alarm
```

This reduces unnecessary notifications.

Instead of sending five separate alerts, the team receives one meaningful alert and checks the smaller alarms for details.

## Dashboards

A dashboard gives people a shared view of system health.

A useful dashboard should start with:

```text
Availability
Latency
Errors
Traffic
Saturation
```

Then show deeper details such as:

- Queue length.
- Throttles.
- Dependency health.
- Database performance.
- Service-specific metrics.

### Dashboard structure

```text
Top-level dashboard
        |
        v
Service overview
        |
        v
Detailed service dashboard
        |
        v
Logs and traces for investigation
```

Dashboards should be reviewed regularly because systems change over time.

## Lambda monitoring example

A Lambda dashboard may show:

```text
Invocations
Errors
Duration
Throttles
Concurrent executions
```

Example:

```text
Invocations: 9
Errors: 0
Average duration: 5.55 ms
Throttles: 0
```

A demonstration alarm might be:

```text
If invocations > 5 within 5 minutes:
    send a notification
```

In a real system, alarms should normally focus more on user-impacting problems such as errors, high latency, and throttling.

## CloudWatch Logs

### Log groups and streams

A log group is a container for related logs.

It can share settings such as:

- Retention period.
- Access permissions.
- Monitoring rules.

A log stream is one source of logs, such as:

- One Lambda function.
- One container.
- One server.
- One application process.

```text
Log group: Payment service
    |
    +---- Lambda stream
    +---- Container stream
    +---- API stream
```

### Log retention

Do not keep all logs forever by default.

Example:

```text
Debug logs: 7 days
Application logs: 30 days
Security logs: longer period
```

Important older logs can be moved to cheaper storage.

## Structured logs

Structured JSON logs are easier to search than plain sentences.

Good example:

```json
{
  "level": "ERROR",
  "service": "checkout",
  "trace_id": "abc123",
  "duration_ms": 8500,
  "message": "Payment request timed out"
}
```

Include useful fields such as:

- Log level.
- Service name.
- Request ID.
- Trace ID.
- Error type.
- Duration.
- Environment.

Never log:

- Passwords.
- Secret keys.
- Full payment-card numbers.
- Private personal information.

## Logs Insights queries

Log queries usually follow three simple actions:

```text
Filter → Summarize → Sort
```

### Find errors

```text
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

### Summarize errors by time

```text
fields @timestamp, @message
| filter @message like /ERROR/
| stats count() by bin(5m)
```

### Find slow requests

```text
fields @timestamp, duration_ms
| filter duration_ms > 1000
| sort duration_ms desc
| limit 20
```

To control query cost:

- Use a short time range.
- Search only needed log groups.
- Filter early.
- Avoid scanning unnecessary data.
- Keep result sets small.

## Metric filters and log subscriptions

### Metric filters

A metric filter turns a repeated log pattern into a metric.

```text
Log:
"Payment failed"

        |
        v

Metric:
PaymentFailureCount = 10

        |
        v

Alarm
```

This allows log patterns to appear on dashboards and trigger alarms.

### Subscription filters

Subscription filters send logs to other systems in near real time.

```text
CloudWatch Logs
       |
       +---- Lambda
       +---- Kinesis
       +---- Storage
       +---- Search system
```

They can be used for:

- Data processing.
- Real-time analysis.
- Long-term storage.
- Automated responses.
- Searching large amounts of logs.

## Distributed tracing with X-Ray

A trace represents one complete request.

A service may create a segment:

```text
API Gateway segment
Lambda segment
```

A downstream call may appear as a subsegment:

```text
Lambda
   |
   +---- Database subsegment
   +---- External API subsegment
```

### Service map

A service map displays:

- Services as nodes.
- Calls as connections.
- Latency.
- Errors.
- Dependencies.

```text
Client → API Gateway → Lambda → Database
```

It helps engineers quickly find the unhealthy or slow service.

### Sampling

Tracing every request may create too much data.

Sampling records only some requests.

This helps control:

- Storage.
- Processing cost.
- System overhead.

Critical requests, such as failed requests, may be given higher priority.

### Trace context

Trace information must travel from one service to the next.

```text
API Gateway
     |
     | trace ID
     v
Lambda
     |
     | same trace ID
     v
Database
```

If the trace ID is lost, the request story becomes incomplete.

## Troubleshooting workflow

Use a broad-to-detailed process:

```text
1. Metrics
2. Logs
3. Traces
4. Events
5. Fix and automate
```

### Example

```text
Metrics:
Latency is increasing.

Logs:
Many database timeout errors.

Traces:
Database call is the slowest step.

Events:
A configuration change happened recently.

Action:
Roll back the change and update the runbook.
```

## Quotas and throttling

A quota is a limit placed on a service.

Throttling happens when the limit is reached.

Common signs include:

```text
HTTP 429
TooManyRequests
Rate exceeded
ProvisionedThroughputExceeded
```

You may also see:

- Sudden latency increases.
- More retries.
- Growing queues.
- Timeouts.
- Cascading failures.

### Causes

- Sudden traffic growth.
- Too many requests.
- Low concurrency limits.
- Database capacity limits.
- New deployments.
- One customer using too many resources.

### Ways to reduce throttling

- Use queues to smooth traffic.
- Add caching.
- Batch requests.
- Spread work across partitions.
- Limit requests per customer.
- Use asynchronous processing.
- Increase capacity where possible.
- Request higher quotas in advance.

### Safe retries

Use:

- Exponential backoff.
- Random delay, called jitter.
- Maximum retry count.
- Request timeouts.
- Circuit breakers.
- Idempotent operations.

```text
Retry 1 → wait 1 second
Retry 2 → wait 2 seconds
Retry 3 → wait 4 seconds
```

Do not retry permanent errors forever.

## AWS Health and events

AWS Health provides information about issues affecting your account and resources.

Events may include:

- Service incidents.
- Maintenance.
- Scheduled changes.
- Advisories.
- Region-specific problems.
- Global problems.

EventBridge can route these events to:

```text
AWS Health event
       |
       v
EventBridge rule
       |
       +---- SNS notification
       +---- Lambda function
       +---- Automation workflow
       +---- Team chat
```

CloudTrail helps answer:

```text
Who changed something?
What was changed?
When was it changed?
```

Combining AWS Health, CloudTrail, metrics, logs, and traces gives a complete incident picture.

## Runbooks and automation

A runbook is a written list of steps for handling a common problem.

Example:

```text
Problem: Payment errors are increasing.

1. Check the payment dashboard.
2. Check payment-service logs.
3. Open the trace for a failed request.
4. Check database connection limits.
5. Roll back the recent deployment if needed.
6. Notify the support team.
```

Automation can perform safe steps automatically.

The goal is:

```text
Detect → Diagnose → Recover
```

with less manual work and less downtime.

## Final memory guide

Remember this sentence:

> Metrics show what is happening, logs explain why, traces show where, and events show what changed.

For good AWS operations:

```text
Choose useful metrics
        |
        v
Create simple dashboards
        |
        v
Set meaningful alarms
        |
        v
Search structured logs
        |
        v
Follow traces
        |
        v
Check events and changes
        |
        v
Use runbooks and automation
```

The final goal is not to collect everything. It is to collect the right information and turn it into quick, clear action.
