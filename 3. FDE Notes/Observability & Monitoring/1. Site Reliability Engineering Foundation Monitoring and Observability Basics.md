# Monitoring and Observability: Easy Summary

## Main idea

Monitoring and observability help us keep software systems healthy.

Think of an online shop:

- Monitoring tells us **that something is wrong**.
- Observability helps us understand **why it is wrong**.

```text
Monitoring     = Detect the problem
Observability  = Find the reason
```

Both are needed to keep applications reliable and reduce downtime.

## What is monitoring?

Monitoring means continuously collecting information about a system.

It checks things such as:

- How quickly the system responds.
- Whether the service is available.
- How many errors are happening.
- How much CPU and memory are being used.
- How many requests the system receives.

### Simple example

An online shop normally processes 100 orders per minute.

Suddenly, it processes only 10 orders per minute.

Monitoring notices this change and sends an alert.

```text
Normal: 100 orders per minute
Current: 10 orders per minute
              |
              v
          Alert sent
```

Monitoring is like the dashboard of a car:

- Speedometer shows speed.
- Fuel gauge shows fuel.
- Warning light shows a problem.

Monitoring gives us a quick view of the current system condition.

## Why monitoring is important

Monitoring helps teams:

- Find problems early.
- Reduce downtime.
- Protect customer experience.
- Check whether services meet reliability goals.
- Identify performance trends.
- Plan server and resource needs.
- Fix small issues before they become major failures.

Without monitoring, teams may discover a problem only after customers complain.

### Manual checks versus automatic monitoring

| Manual checking | Automatic monitoring |
|---|---|
| Happens occasionally | Runs continuously |
| Can miss problems | Detects problems quickly |
| Depends on human attention | Works day and night |
| Hard to manage at large scale | Works across many services |
| Uses personal judgment | Uses measured data |

Automatic monitoring collects the data. Human engineers still investigate the problem and decide what to do.

## What is observability?

Observability means understanding what is happening inside a system by studying the information it produces.

It helps answer questions such as:

- Why did the request fail?
- Which service caused the delay?
- Why are only some users affected?
- What happened before the error?
- How did one failure affect other services?

### Simple example

A video-streaming service reports:

```text
CPU: Normal
Memory: Normal
Service: Unavailable for many users
```

Monitoring may not find the reason because the usual system numbers look normal.

Observability helps investigate the complete request journey:

```text
User
  |
  v
Login service
  |
  v
Payment service
  |
  v
Recommendation service
  |
  v
Video service
```

It may show that the recommendation service overloaded the database, which then stopped video requests.

## Monitoring and observability together

| Monitoring | Observability |
|---|---|
| Finds known problems | Investigates known and unknown problems |
| Uses predefined checks | Allows deeper investigation |
| Tells us something is wrong | Helps explain why it is wrong |
| Sends alerts | Helps find the root cause |
| Gives a quick health view | Gives a detailed system picture |

### Easy memory trick

> Monitoring is the alarm. Observability is the investigation.

Monitoring and observability work together. Observability does not replace monitoring.

## The three main types of system information

### 1. Metrics

Metrics are numbers that change over time.

Examples:

```text
Response time: 250 milliseconds
Error rate: 2%
Requests per minute: 1,500
CPU usage: 70%
```

Metrics help us see trends and detect unusual behavior.

### 2. Logs

Logs are detailed records of events.

Example:

```text
2026-09-22 17:30
Payment request failed
Reason: Database connection timeout
Order ID: 12345
```

Logs help explain exactly what happened.

They can show:

- Error messages.
- Request details.
- User or order information.
- The order of events.
- Conditions during the failure.

### 3. Traces

A trace follows one request as it moves through different services.

Think of it like GPS tracking for a request.

```text
Request
  |
  v
Login: 20 ms
  |
  v
Cart: 30 ms
  |
  v
Payment: 900 ms
  |
  v
Order: 40 ms
```

This shows that the payment service caused most of the delay.

## The four Golden Signals

The four Golden Signals are important measurements for system health.

| Signal | Simple meaning | Example |
|---|---|---|
| Latency | How long a request takes | Page loads in 2 seconds |
| Errors | How many requests fail | 5% of payments fail |
| Traffic | How much work the system receives | 10,000 requests per minute |
| Saturation | How close resources are to their limit | Database is 90% full |

### Example

If an online shop has:

```text
Latency: High
Errors: Increasing
Traffic: Very high
Saturation: 95%
```

The system may be close to failure and needs attention.

## Cardinality: too many unique values

Cardinality means the number of unique values in a metric label.

A small number of fixed values is safe:

```text
environment = dev
environment = staging
environment = production
```

A large number of changing values is dangerous:

```text
user_id = 1001
user_id = 1002
user_id = 1003
...
```

If millions of users are used as metric labels, the monitoring system may create millions of separate time series.

### Why high cardinality is dangerous

Too many unique values can cause:

- High memory usage.
- More storage usage.
- Slow dashboards.
- Slow searches.
- Query timeouts.
- Monitoring system crashes.
- Loss of visibility during an outage.

The most dangerous labels often include:

- User IDs.
- Customer IDs.
- Request IDs.
- Trace IDs.
- Session tokens.
- IP addresses.
- Exact timestamps.
- Geographic coordinates.
- Transaction IDs.

### Bad example

```python
metric.labels(user_id=user_id).observe(response_time)
```

If every user has a different ID, the number of time series keeps growing.

### Better example

Group users into a small, fixed category:

```python
metric.labels(region="east").observe(response_time)
```

Or use a limited group:

```python
metric.labels(customer_type="premium").observe(response_time)
```

## How to control cardinality

Use these practices:

- Avoid user IDs and request IDs as metric labels.
- Use a small, fixed set of label values.
- Group data into useful categories.
- Combine detailed data before storing it.
- Use sampling for large amounts of trace data.
- Keep important error logs longer.
- Remove old or unused metrics.
- Watch cardinality growth.
- Set limits before the system becomes overloaded.

### Example

Instead of tracking every delivery address:

```text
Address: 14 Park Street, Kolkata
Address: 22 Lake Road, Kolkata
Address: 5 Main Road, Kolkata
```

Track by region:

```text
Region: Kolkata
Region: Delhi
Region: Mumbai
```

This provides useful information without creating millions of unique values.

## Logs and traces during an incident

Suppose customers cannot complete payments.

```text
Metrics:
Payment error rate is high.
```

This tells us what is happening.

```text
Logs:
Database connection timeout.
```

This gives a possible reason.

```text
Trace:
Payment service waited 5 seconds for the database.
```

This shows where the request was delayed.

Together:

```text
Metrics show the problem
Logs explain the event
Traces show the request path
```

## Centralized logging

Large applications have many services, and each service may produce separate logs.

Searching each server manually is slow.

Centralized logging collects logs into one searchable place.

```text
Mobile app logs       \
Payment service logs   \
Order service logs     ---> Central log store
Delivery service logs /
```

This makes it easier to:

- Search all services together.
- Match events by time.
- Follow an order from start to finish.
- Find repeated errors.
- Create alerts from error patterns.

## Dashboards

A dashboard displays important system information in one place.

A useful dashboard should show:

- Latency.
- Error rate.
- Traffic.
- Saturation.
- Availability.
- Important business actions.

### Good dashboard design

- Show important information first.
- Group related charts together.
- Use green for healthy, yellow for warning, and red for critical.
- Avoid too many charts.
- Show information that supports a decision.
- Keep loading speed in mind.
- Use useful, limited labels.

A dashboard should help someone understand the system within seconds.

## Alerts

Alerts notify the team when immediate action is needed.

Examples:

```text
Error rate is above 5%.
Payment response time is above 3 seconds.
Database storage is 90% full.
```

A useful alert should explain:

- What happened.
- Why it matters.
- What action may be needed.

### Bad alert

```text
Something is wrong.
```

### Better alert

```text
Payment failures are above 5% for 10 minutes.
Check the payment service and database connection.
```

## Avoiding alert fatigue

Alert fatigue happens when teams receive too many unnecessary alerts.

If people receive hundreds of low-value alerts, they may ignore an important one.

To avoid this:

- Alert only when action is needed.
- Use realistic limits.
- Focus on user impact.
- Remove duplicate alerts.
- Use dashboards for detailed investigation.
- Review alerts regularly.
- Group related failures into one alert.

```text
Dashboard = Detailed view
Alert     = Urgent warning
```

## Monitoring tools

Monitoring systems normally need three types of tools:

| Tool type | Purpose |
|---|---|
| Data collection and storage | Collects metrics and saves them |
| Dashboards and visualization | Displays charts and trends |
| Cloud monitoring services | Provides built-in monitoring for cloud resources |

A common setup may include:

```text
Applications
    |
    v
Metrics collection
    |
    v
Metrics storage
    |
    v
Dashboard
    |
    v
Alert
```

The exact tool is less important than choosing tools that:

- Work well together.
- Match the team’s skills.
- Support logs, metrics, and traces.
- Control data volume.
- Provide useful alerts.
- Scale with the application.

## Best practices

1. Monitor user-facing problems first.
2. Focus on important metrics instead of collecting everything.
3. Use the four Golden Signals.
4. Use metrics to detect problems.
5. Use logs to understand events.
6. Use traces to follow requests across services.
7. Keep logs structured and searchable.
8. Collect logs in one central place.
9. Make dashboards simple and useful.
10. Create alerts that require action.
11. Avoid user IDs and other unlimited values in metric labels.
12. Control cardinality before it becomes a problem.
13. Review dashboards and alerts regularly.
14. Test monitoring during normal and high traffic.
15. Update monitoring as the system changes.
