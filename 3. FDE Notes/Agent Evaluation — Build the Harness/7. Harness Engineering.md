# Simple Summary: Strong Models ≠ Reliable Coding Agents

## Main Idea

Even the best coding AI models fail often on real tasks. The problem is usually not the model, but the setup around it. This setup is called the **harness**.

> **Better harness = more reliable results, even with the same model.**

***

## 1. Why Strong Models Still Fail

On benchmark tests, top models pass about 50–60% of tasks. But these tests are clean and well-defined. Real work is messy:

- Vague requirements
- Hidden rules
- Missing tests
- Unclear environment

When you give a real task, the agent may:

- Break existing tests
- Add new bugs
- Build the wrong thing
- Claim it is done when it is not

Most people think: “I need a better model.”  
Reality: “I need a better harness.”

***

## 2. What Is a Harness?

A **harness** is everything around the model that helps it work correctly.

It has **five parts**:

1. **Instructions** – What the project is and how to work in it.
2. **Tools** – Commands and access the agent can use.
3. **Environment** – Dependencies, versions, and setup.
4. **State** – Memory of what was done and what is next.
5. **Feedback** – Tests, lint, type checks, and other verification.

If it is not part of the model itself, it is part of the harness.

***

## 3. Where Agents Get Stuck

### (a) Vague Requirements

Bad:
```text
"Add a search feature."
```

Better:
```text
Add a search endpoint:
- GET /api/search?q=xxx
- Paginated results (default 20)
- Highlight matching text
- All new code must pass pytest and mypy --strict
```

### (b) Hidden Rules

Examples:

- “We use SQLAlchemy 2.0 syntax only.”
- “All endpoints must use OAuth 2.0.”
- “No direct DB calls in controllers.”

If these rules are not written where the agent can see them, it cannot follow them.

### (c) Broken Environment

Missing dependencies, wrong versions, or unclear setup cause the agent to waste time fixing the environment instead of doing the task.

### (d) No Verification

If there are no tests or check commands, the agent decides on its own when it is “done,” often too early.

Agents also rush when they feel they are running out of context. This is called **context anxiety**.

### (e) Lost State Between Sessions

Each new session starts from zero. The agent forgets what it learned before and must re-explore everything. Long tasks fail more often because of this.

***

## 4. Key Terms in Simple Words

- **Capability Gap**: Difference between benchmark performance and real-world performance.
- **Harness**: All the support around the model (instructions, tools, environment, state, feedback).
- **Harness-Induced Failure**: The model is capable, but the setup is bad.
- **Verification Gap**: Agent says “done,” but the work is not actually correct.
- **Diagnostic Loop**: Run → see failure → find which harness part failed → fix it → run again.
- **Definition of Done**: Clear, checkable conditions like “tests pass, lint clean, types ok.”

***

## 5. Fix the Harness First, Not the Model

When something fails:

1. Do not immediately switch to a bigger model.
2. Ask: which harness layer failed?
   - Was the task unclear?
   - Was context missing?
   - Was the environment broken?
   - Were there no verification commands?
   - Was state lost between sessions?
3. Fix that layer.
4. Try again.

Over time, this makes the agent much more reliable.

***

## 6. The AGENTS.md File

Create a file named `AGENTS.md` in the project root.

It should include:

- Project overview and purpose
- Tech stack and versions
- How to run the project
- How to run tests, lint, and type checks
- Important rules and conventions
- Links to more detailed docs (if needed)

Example structure:

```text
# Project Overview
Short description of what this project does.

# Tech Stack
- Python 3.11
- FastAPI
- PostgreSQL
- Redis

# First-Run Commands
- pip install -r requirements.txt
- pytest tests/
- mypy src/ --strict
- ruff check src/

# Hard Rules
- Use SQLAlchemy 2.0 syntax only
- All endpoints must use OAuth 2.0
- No raw SQL in business logic

# Verification Commands
- Tests: pytest tests/ -x
- Type check: mypy src/ --strict
- Lint: ruff check src/
- Full check: make check
```

A good `AGENTS.md` can improve results more than upgrading the model.

***

## 7. The Five Harness Subsystems

### 1. Instructions

File: `AGENTS.md` or `CLAUDE.md`

Contents:

- What the project is
- Tech stack and versions
- How to start
- Key rules
- Where to find more info

Keep it short and clear (around 100 lines). If it gets too long, move details to `docs/`.

### 2. Tools

Give the agent the tools it needs:

- Shell access (to run commands)
- File read/write
- Test runner
- Linter
- Type checker

Do not lock everything down for “security” if it prevents basic work. Use least privilege, not no privilege.

### 3. Environment

Make the environment clear and repeatable:

- `pyproject.toml` or `package.json` for dependencies
- `.python-version` or `.nvmrc` for runtime versions
- Docker or devcontainers for consistent setup

The agent should not guess which versions to use.

### 4. State

For long tasks, track progress in a file like `PROGRESS.md`:

```text
# Progress

## Done
- Created /api/search endpoint
- Added pagination

## In Progress
- Adding highlight snippets

## Blocked
- Waiting for design decision on result format
```

Update this before ending a session. Read it at the start of the next session.

### 5. Feedback

This is the most important part.

List clear verification commands in `AGENTS.md`:

```text
# Verification Commands
- Tests: pytest tests/ -x
- Type check: mypy src/ --strict
- Lint: ruff check src/
- Full check: make check
```

The agent should run these before saying “done.”

***

## 8. Real Examples

### OpenAI’s Million-Line Experiment

Three engineers let Codex write all the code. In five months, they created about one million lines of code and opened 1,500 pull requests.

Key lessons:

- Early progress was slow because the harness was weak.
- They improved by:
  - Breaking big goals into small steps
  - Giving the agent clear tools and checks
  - Fixing harness issues instead of blaming the model

Same model, much better results after improving the harness.

### Team Using Claude on a Python App

First attempt:

- Prompt: “Add user preferences endpoints under /api/v2/users.”
- Result:
  - Agent wasted time exploring the repo
  - Used old SQLAlchemy syntax
  - Ignored error-handling patterns
  - Claimed completion with runtime errors

Second attempt (with harness):

- Added `AGENTS.md` with:
  - Architecture overview
  - Tech stack versions
  - Verification commands: `pytest tests/api/v2/ && mypy src/`
- Result:
  - Same model succeeded every time
  - Much better use of context
  - Fewer errors

They did not change the model. They changed the harness.

***

## 9. How to Measure Harness Value

Use a **controlled variable exclusion test**:

1. Keep the model fixed.
2. Remove one harness part at a time:
   - Delete `AGENTS.md`
   - Remove verification commands
   - Remove progress tracking
3. See which removal causes the biggest drop in success.

That part is the most valuable right now.

But also keep a **failure log**:

- For each failed task, note:
  - What failed
  - Which harness layer caused it
  - How you fixed it

This tells you where the real bottleneck is.

***

## 10. Step-by-Step: Building a Good Harness

1. Write `AGENTS.md` with:
   - Project overview
   - Tech stack
   - How to run and test
   - Key rules
2. Add clear verification commands.
3. Ensure environment is reproducible (lock files, version files).
4. Add a simple `PROGRESS.md` for long tasks.
5. When something fails:
   - Log the failure
   - Attribute it to a harness layer
   - Fix that layer
   - Retry

Repeat this loop. The harness gets stronger, and the agent becomes more reliable.

## 12. Practical Exercises

### Exercise 1: Compare With and Without Harness

1. Pick a real task in a project you know.
2. Run the agent with no harness support. Note failures.
3. Add `AGENTS.md` and verification commands.
4. Run the same agent again on the same task.
5. Compare results and map each failure to a harness layer.

### Exercise 2: Measure Verification Gap

1. Pick 5 coding tasks.
2. For each:
   - Record if the agent says “done.”
   - Run your own tests to check if it is actually correct.
3. Count how often the agent says “done” when it is not.
4. Design verification commands to reduce this gap.

### Exercise 3: Diagnostic Loop Practice

1. Find a task where the agent often fails.
2. Run once, record the failure.
3. Decide which harness layer failed.
4. Fix that layer.
5. Run again.
6. Repeat 3–5 times and track improvements.

***

## 13. Key Takeaways

- Model strength and execution reliability are different.
- Most failures come from the harness, not the model.
- Every failure is a signal: your harness has a defect.
- Use the five layers to diagnose:
  - Task not clear
  - Context missing
  - Environment broken
  - No verification
  - State lost
- A good `AGENTS.md` can be more powerful than a costlier model.
- Build a diagnostic loop: fail → find layer → fix → retry.

> **Rule of thumb: When things fail, fix the harness first, then consider changing the model.**


# Simple Summary: Make the Repo the Map, and Split Instructions Smartly

## Main Idea

For an AI coding agent, **only what is in the repository really exists**.  
If a rule, decision, or fact is not in the repo, the agent cannot use it.

So you must:

1. Put important knowledge **inside the repository**.
2. Organize it so a fresh agent session can understand the project quickly.
3. Avoid one giant instruction file; instead, **split instructions** into small, focused files.

***

## 1. Why the Repository Must Be the “Map”

An AI agent has only three inputs:

1. System prompt and task description
2. Files in the repository
3. Output from tools it runs

It **cannot**:

- Read Slack, Jira, or Confluence
- Ask a teammate
- Remember past sessions unless you save that memory in the repo

So if your real rules live in:

- Slack messages
- Confluence pages
- People’s heads
- Old emails

…then for the agent, those rules **do not exist**.

> **Rule:** If it’s not in the repo, it’s invisible to the agent.

***

## 2. The “Fresh Session Test”

Imagine starting a brand-new agent session with **only** the repository.  
No extra chat, no verbal context.

Ask it five questions:

1. **What is this system?**
2. **How is it organized?**
3. **How do I run it?**
4. **How do I verify it (tests, lint, etc.)?**
5. **What is the current progress?**

If the agent cannot answer these from the repo alone, your “map” has blank spots.  
Where the map is blank, the agent must guess. Guesses become bugs and wasted time.

***

## 3. What Should Live in the Repo

You do not need huge documentation. You need **the right information in the right place**.

Key files:

- `AGENTS.md` or `CLAUDE.md` – entry point for the agent
- `ARCHITECTURE.md` – high-level design and structure
- Module-level docs (e.g., `src/api/ARCHITECTURE.md`)
- `CONSTRAINTS.md` – hard rules (MUST / MUST NOT)
- `PROGRESS.md` – what is done, in progress, or blocked
- `Makefile` or scripts – standard commands to run, test, lint, check

### Example Structure

```text
project/
├── AGENTS.md              # Entry: overview, run, verify, hard rules
├── src/
│   ├── api/
│   │   ├── ARCHITECTURE.md
│   │   └── ...
│   ├── db/
│   │   ├── CONSTRAINTS.md
│   │   └── ...
│   └── ...
├── PROGRESS.md
└── Makefile
```

***

## 4. Good Map Principles

### Principle 1: Knowledge Lives Next to Code

Rules about a module should sit **near that module**, not in one giant global doc.

Example:

- `src/api/ARCHITECTURE.md` – API design, auth rules, versioning
- `src/db/CONSTRAINTS.md` – DB rules, migration policy, query style

When the agent reads the code, it also sees the rules.

### Principle 2: Use a Short Entry File

`AGENTS.md` is the agent’s landing page.

It should answer in ~50–100 lines:

- What is this project?
- How do I run it?
- How do I verify it?
- What are the global hard constraints?
- Where are more detailed docs?

Example:

```text
# Project Overview
Python 3.11 FastAPI backend, PostgreSQL 15.

# Quick Start
- Install: make setup
- Test: make test
- Full check: make check

# Hard Constraints
- All APIs must use OAuth 2.0
- All DB queries must use SQLAlchemy 2.0
- All PRs must pass: pytest + mypy --strict + ruff check

# Topic Docs
- API Patterns (docs/api-patterns.md) – read when adding endpoints
- DB Rules (docs/database-rules.md) – read when touching DB code
- Testing Standards (docs/testing-standards.md) – read when writing tests
```

### Principle 3: Minimal but Complete

Every piece of knowledge should have a clear use.

Ask:

- If I remove this, will the agent make worse decisions?
- If no, maybe it should not be there.

But all five “fresh session” questions must have clear answers.

### Principle 4: Update Docs With Code

When code changes, related docs should change too.

Tips:

- Put architecture notes near the code they describe.
- Use CI to remind: “You changed code; did you update docs?”

Out-of-date docs are worse than no docs: they send the agent in the wrong direction with confidence.

***

## 5. Managing Agent State with ACID Ideas

Think of agent work like database transactions.

### Atomicity

A logical unit of work (e.g., “add endpoint + tests”) should be:

- Either fully done and verified, or
- Fully discarded

No half-finished, unverified changes left in the repo.

### Consistency

Define what “consistent” means:

- All tests pass
- Lint is clean
- Type checks pass

After each operation, the agent should run verification.  
If checks fail, the state is inconsistent and should be fixed or rolled back.

### Isolation

If multiple agents work at once:

- Avoid writing to the same state file at the same time.
- Use separate `PROGRESS-<agent>.md` files or separate branches.

This prevents race conditions and conflicting edits.

### Durability

Important knowledge must be in **git-tracked files**:

- Architecture decisions
- Hard constraints
- Progress state for long tasks

Anything only in session memory or in someone’s head is lost when the session ends.

***

## 6. Real Story: From Chaos to Clear Map

A team had ~30 microservices.  
Decisions lived in:

- Confluence (partly outdated)
- Slack (hard to search)
- Senior engineers’ heads
- Random code comments

Result with agents:

- 70% of tasks needed human help
- Agents kept breaking hidden rules “everyone knows”

They changed to:

- `AGENTS.md` in root: overview, stack, global constraints
- `ARCHITECTURE.md` in each service: responsibilities, interfaces, deps
- Central `CONSTRAINTS.md`: explicit MUST / MUST NOT rules
- `PROGRESS.md` per service: current work status

After this:

- New sessions could answer all five key questions
- Task quality improved a lot
- Fewer violations of hidden rules

They did not change the model. They changed the map.

***

## 7. Problem: One Giant Instruction File

Many teams start with a small `AGENTS.md`, then:

- Every bug → “add a rule”
- Every lesson → “write it down”
- Every preference → “make it official”

Soon:

- `AGENTS.md` is 300–600+ lines
- Important rules are buried in the middle
- Contradictory rules appear
- Agent wastes context reading irrelevant instructions

This is the **giant instruction file trap**.

### What Goes Wrong

1. **Context budget wasted**  
   Long instruction files eat tokens that could be used for code and reasoning.

2. **Lost in the Middle**  
   Research shows LLMs pay less attention to the middle of long texts.  
   A critical rule at line 300 of a 600-line file is often ignored.

3. **Priority confusion**  
   Hard constraints, soft guidelines, and old notes all look the same.  
   The agent cannot tell what is a red line vs. a suggestion.

4. **Maintenance decay**  
   Big files are hard to maintain.  
   Old rules stay, new rules pile up, signal-to-noise ratio drops.

5. **Contradictions**  
   Rules added at different times conflict.  
   The agent picks one at random each time.

***

## 8. Split Instructions the Right Way

### Core Idea

- Keep **frequently needed** info in a short entry file.
- Move **occasionally needed** info into topic docs.
- Remove what is never used.

### Entry File: `AGENTS.md` (50–200 lines)

Include only:

- Project overview (1–2 sentences)
- First-run commands
- Global hard constraints (≤15 rules)
- Links to topic docs with short descriptions

Example:

```text
# Project Overview
Python 3.11 FastAPI backend, PostgreSQL 15.

# Quick Start
- Install: make setup
- Test: make test
- Full check: make check

# Hard Constraints
- All APIs must use OAuth 2.0
- All DB queries must use SQLAlchemy 2.0
- All PRs must pass pytest + mypy --strict + ruff check

# Topic Docs
- API Patterns (docs/api-patterns.md) – when adding endpoints
- DB Rules (docs/database-rules.md) – when modifying DB code
- Testing Standards (docs/testing-standards.md) – when writing tests
```

### Topic Docs: `docs/` or Near Modules

Each topic doc: 50–150 lines, focused on one subject.

Examples:

- `docs/api-patterns.md`
- `docs/database-rules.md`
- `docs/testing-standards.md`
- `src/api/ARCHITECTURE.md`
- `src/db/CONSTRAINTS.md`

The agent reads these **only when the task needs them**.

This is like packing cubes in a suitcase:

- Underwear in one cube
- Toiletries in another
- Chargers in another

You don’t empty the whole bag to find socks.

### Put Some Knowledge Directly in Code

Some things are best as:

- Type definitions
- Interface comments
- Config file explanations

The agent sees these naturally when reading code, so no need to duplicate them in instruction files.

### Instruction Hygiene

For each instruction, document:

- **Source**: Why was this rule added? (bug, incident, decision)
- **Applicability**: When is this rule needed?
- **Expiry**: When can this rule be removed?

Regularly audit and:

- Delete outdated rules
- Merge duplicates
- Resolve contradictions

Treat instructions like dependencies: unused ones should be removed.

### Position Matters

If a rule must be in the entry file:

- Put very important rules at the **top** or **bottom**
- Avoid burying critical constraints in the **middle**

But better: move detailed rules into topic docs and link to them.

***

## 9. Real Example: Splitting a 600-Line File

A team’s `AGENTS.md` grew to 600 lines:

- Tech stack versions
- Coding standards
- Historical bug notes
- API guides
- Deployment steps
- Personal preferences

Problems:

- Simple bug fixes burned context on irrelevant deploy rules
- Security rule at line 300 (“use parameterized queries”) often ignored
- Contradictory style rules → agent picked randomly

They refactored:

- Trimmed `AGENTS.md` to 80 lines:
  - Overview
  - Run commands
  - 15 global hard constraints
- Created topic docs:
  - `docs/api-patterns.md` (120 lines)
  - `docs/database-rules.md` (60 lines)
  - `docs/testing-standards.md` (80 lines)
- Linked these from `AGENTS.md`
- Converted old notes into tests or deleted them

Result:

- Success rate on same tasks: 45% → 72%
- Security rule compliance: 60% → 95%
- Agent spent more context on code, less on irrelevant instructions

Same model, better harness.

## 10. Key Terms in Simple Words

- **Knowledge Visibility Gap**:  
  How much important knowledge is *outside* the repo.  
  Bigger gap → more agent failures.

- **System of Record**:  
  The repo is the single source of truth for decisions, constraints, and state.

- **Fresh Session Test**:  
  Can a new session answer the five basic questions using only the repo?

- **Discovery Cost**:  
  How much context the agent burns to find one key fact.  
  Hidden info = high cost.

- **Knowledge Decay Rate**:  
  How fast docs become outdated.  
  Stale docs mislead the agent.

- **Instruction Bloat**:  
  Instruction file too large, eating context and hiding important rules.

- **Lost in the Middle**:  
  LLMs pay less attention to the middle of long texts.  
  Critical rules should not live there.

- **Instruction SNR (Signal-to-Noise Ratio)**:  
  How much of the instruction file is relevant to the current task.  
  Higher SNR → better performance.

***

Delete or fix as needed.

# Simple Summary: Keep Context Alive and Initialize Before Work

## Main Idea

AI agents forget everything between sessions unless you save their work in files.  
Also, the first session should **only set up the project**, not start building features.

> **Good state files + clean initialization = fast, reliable multi-session work.**

***

## Part 1: Keeping Context Alive Across Sessions

### 1. The Problem: Agents Forget Between Sessions

You ask an agent to build a feature. It works for 30 minutes, but:

- Context window gets almost full
- Session ends
- Next session starts fresh

The new session does **not** know:

- What decisions were made
- Why option A was chosen over B
- Which files were changed
- What tests pass or fail

So it:

- Re-explores the project (wastes 10–15 minutes)
- May undo or conflict with earlier work
- May choose a different design direction

Over several sessions, the project can drift far from the original plan.

***

### 2. Why Context Windows Are Not Enough

Context windows are limited (even if they grow).

Agents use context for:

- Reading code
- Understanding the project
- Tracking their own decisions
- Storing tool outputs
- Keeping conversation history

All this fills up fast.

Also:

- Final code = “what” was done
- Decision history = “why” it was done that way

When context is summarized or reset, the **“why” is often lost**.  
Next session sees the code but not the reasoning, and may change it in worse ways.

***

### 3. Context Anxiety

Anthropic observed:

- When agents feel context is almost full, they rush.
- They skip verification steps.
- They pick simpler (worse) solutions to “finish quickly.”

This is called **context anxiety**.

Two ways to handle it:

1. **Compaction** – summarize old conversation in the same session  
   - Keeps “what”  
   - Often loses “why”  
   - Agent still feels time pressure

2. **Context reset** – start a new session with clean context  
   - Agent has no “running out of time” feeling  
   - But depends on good handoff files  
   - If handoff is poor, new session wastes time

Anthropic found:

- For some models (e.g., Sonnet 4.5), context anxiety is strong → reset is important.
- For stronger models (e.g., Opus 4.5), anxiety is weaker → compaction can work better.

Harness design must match the model.

***

### 4. What Breaks When Continuity Is Lost

Without saved state:

- New session re-decides things already decided
- It may redo work already done
- It may partially redo work, causing conflicts
- Each session has a slightly different understanding → drift
- Verification results are lost → every session re-runs all tests from scratch

Result:

- More wasted time
- More bugs
- Final product may not match original goals

***

### 5. Solution: State Persistence Files

# Simple Summary: Clear Task Boundaries and Feature Lists for Agents

## Main Idea

Agents try to do too much at once and leave many things half-finished.  
You must:

1. **Limit work to one small task at a time (WIP = 1).**
2. **Define exactly what “done” means with tests or commands.**
3. **Use a feature list file as the single source of truth.**

> **Do less, but finish completely. Let a file, not memory, track what is done.**

***

## Part 1: Draw Clear Task Boundaries (WIP = 1)

### 1. The Problem: Agents Overreach

You say: “Add user authentication.”

Agent starts:

- Changing DB schema
- Writing routes
- Editing frontend
- Refactoring error handling
- Reorganizing tests

Result:

- Many files changed
- No feature fully works end-to-end
- Next session is confused by half-done code

Agents like to “do a little extra.”  
But doing many things at once usually means **nothing is truly done**.

Anthropic and OpenAI both found:

- Broad prompts → agent starts many things, finishes few.
- Small, clear next steps → much higher completion rates.

***

### 2. Attention Is Limited (Math Idea)

Think of the agent’s context as a fixed budget **C**.

If it works on **k** tasks at once, each gets about **C / k** attention.

- If **k = 1**, the task gets full attention.
- If **k = 5**, each task gets only 1/5 of the attention.

When **C / k** is too small, **no task finishes well**.

Real behavior example:  
“Add user registration” → agent also adds:

- Email service
- Password hashing library
- Error middleware refactor
- Test folder reorganization

Six things started, none fully verified.

***

### 3. Overreach and Under-Finish

- **Overreach**: Agent activates too many tasks in one session.  
  Example: 5 features started, 0 fully passing.

- **Under-finish**: Most activated tasks do not pass end-to-end checks.  
  Code exists, but tests fail or are missing.

These two problems feed each other:

- Overreach → less attention per task → more under-finish.
- Half-finished code → more complexity → more overreach next time.

This is like **scope creep** in human projects, but worse:  
Agents have no natural “stop, this is enough” feeling.

***

### 4. WIP = 1 Workflow (Work In Progress Limit)

From Kanban: limit how many tasks are in progress.

For agents, safest default:

> **WIP = 1** – only one active task at a time.

Workflow:

1. Pick **exactly one** task from the queue.
2. Work only on that task.
3. Run end-to-end verification.
4. If it passes, mark it done and commit.
5. Then unlock the next task.

Result:

- One feature reaches a clean, passing state.
- Next session has a clear, verified starting point.

***

### 5. How to Enforce WIP = 1

In your harness file (`AGENTS.md`, `CLAUDE.md`):

```text
## Work Rules
- Work on one feature at a time.
- Only start the next feature after the current one passes end-to-end verification.
- Do not "also refactor" or "also fix" other features while implementing the current one.
```

Also:

- Define **completion evidence** for each task (see below).
- Track task states in a file (scope surface).

***

### 6. Completion Evidence

“Done” must mean: **verification passes**, not “code looks fine.”

For each task, specify an executable check.

Example:

```text
F01: User Registration
Verification:
  curl -X POST /api/register \
    -H "Content-Type: application/json" \
    -d '{"email":"test@example.com","password":"123456"}' \
  | jq .status == 201

State: passing
```

If the command fails, the task is **not done**, no matter how much code exists.

***

### 7. Scope Surface (Task Map)

Keep a machine-readable file (JSON or Markdown) that lists:

- All tasks (nodes)
- Their dependencies (edges)
- Their state: `not_started`, `active`, `blocked`, `passing`

Example (Markdown):

```text
# Scope Surface

## F01: User Registration
- Behavior: POST /api/register creates user and returns 201
- Verification: curl ... | jq .status == 201
- State: passing

## F02: Login
- Behavior: POST /api/login returns token for valid credentials
- Verification: curl ... | jq .token exists
- State: active

## F03: Password Reset
- Behavior: POST /api/reset-request sends reset email
- Verification: test script passes
- State: not_started
- Dependencies: F01
```

New sessions read this file and immediately know:

- Which task is active
- What “done” means
- What has already passed

***

### 8. Monitor Verified Completion Rate (VCR)

Track:

> **VCR = (verified passing tasks) / (activated tasks)**

Rule:

- If **VCR < 1.0**, do not start new tasks.
- Finish or block current tasks first.

This creates **completion pressure**: the harness forces the agent to finish before starting more.

***

### 9. Real Example: REST API With 8 Features

**Unconstrained mode:**

- Session 1: agent activates 5 features at once.
- ~800 lines across 12 files.
- End-to-end pass rate: 20% (only registration works).
- By session 3: only 3/8 features complete.

**WIP = 1 mode:**

- Session 1: agent works on registration only.
- ~200 lines across 4 files.
- End-to-end tests: 100% passing.
- Clean commit.
- By session 4: 7/8 features complete (1 blocked by external dependency).

Result:

- Less total code (800 vs 1200 lines)
- Higher completion rate (87.5% vs 37.5%)
- Much less rework

***

### 10. Key Terms (Boundaries)

- **Overreach**: Too many tasks active at once.
- **Under-finish**: Few tasks pass end-to-end compared to how many were started.
- **WIP Limit**: Max number of in-progress tasks (use WIP = 1).
- **Completion Evidence**: Executable check that proves a task is done.
- **Scope Surface**: File showing all tasks, dependencies, and states.
- **Completion Pressure**: Harness rule that forces finishing before starting more.

***

### 11. Key Takeaways (Boundaries)

- **WIP = 1** is the safest default for agents.
- “Done” = verification passes, not “code exists.”
- Keep task states in a **machine-readable file**.
- Overreach and under-finish amplify each other; fixing one fixes the other.
- **Fewer lines, more finished features** is better than lots of half-done code.

## Part 2: Use Feature Lists to Constrain the Agent

### 1. The Problem: Agent Doesn’t Know What “Done” Means

You say: “Add a shopping cart feature.”

Agent thinks:  
“Write a Cart component and an addToCart method.”

You meant:  
“User can browse products, add to cart, and complete checkout end-to-end.”

Without a feature list:

- Agent uses its own idea of “done” (no syntax errors, some code).
- You expect **end-to-end behavior** to work.

Progress notes like:

> “Did user auth, shopping cart mostly done, still need payments”

are useless for a new session:

- What does “mostly done” mean?
- Which tests pass?
- What exactly is blocking payments?

New session wastes time re-inferring state and may redo work.

Anthropic: good structured records reduce startup diagnostic time by **60–80%**.

***

### 2. Feature Lists Are Harness Primitives

A feature list is **not** just a human memo.

It is a **core data structure** for the harness:

- **Scheduler** reads it to pick the next task.
- **Verifier** uses it to decide if a task is done.
- **Handoff reporter** uses it to summarize progress.
- **Progress tracker** uses it for metrics.

Think of it like a database constraint:

- Documents can be ignored.
- Primitives are enforced by the system.

Feature lists should be **primitives**, not optional notes.

***

### 3. Triple Structure of a Feature

Each feature item must have three parts:

1. **Behavior description** – what the feature does.
2. **Verification command** – how to check it.
3. **Current state** – where it stands.

Example (JSON):

```json
{
  "id": "F03",
  "behavior": "POST /cart/items with {product_id, quantity} returns 201",
  "verification": "curl -X POST http://localhost:3000/api/cart/items -H 'Content-Type: application/json' -d '{\"product_id\":1,\"quantity\":2}' | jq .status == 201",
  "state": "passing",
  "evidence": "commit abc123, test output log"
}
```

If any of these is missing, the item is incomplete.

***

### 4. State Machine for Features

Each feature has four states:

- `not_started`
- `active`
- `blocked`
- `passing`

Rules:

- Only one feature should be `active` at a time (WIP = 1).
- A feature becomes `passing` **only** when its verification command succeeds.
- The harness (script or process) controls state changes, not the agent directly.

Simple state flow:

```text
not_started → active → passing
                ↓
              blocked (if dependency or external issue)
```

***

### 5. Pass-State Gating

The agent **cannot** mark a feature as `passing` by itself.

Process:

1. Agent works on the active feature.
2. Agent runs (or requests) the verification command.
3. Harness executes the command.
4. If it passes, harness updates state to `passing` and records evidence.
5. If it fails, state stays `active` or becomes `blocked`.

This ensures:

- “Passing” really means “verified.”
- No self-declared “done” without proof.

***

### 6. Single Source of Truth

All “what needs to be done” information comes from **one feature list file**.

- No contradictions between chat history and the file.
- New sessions trust the file, not memory.

Formats:

- `features.md` (structured Markdown)
- `feature_list.json`

Example (Markdown):

```text
# Feature List

## F01: User Registration
- Behavior: POST /api/register creates user and returns 201
- Verification: curl ... | jq .status == 201
- State: passing

## F02: Login
- Behavior: POST /api/login returns token for valid credentials
- Verification: curl ... | jq .token exists
- State: active

## F03: Shopping Cart – Add Item
- Behavior: POST /cart/items adds item and returns 201
- Verification: curl ... | jq .status == 201
- State: not_started
- Dependencies: F01, F02
```

***

### 7. Granularity: Right Size for a Feature

Each feature should be:

- Completable in **one session**.
- Large enough to be meaningful.
- Small enough to verify fully.

Good:

- “User can add items to cart.”

Too broad:

- “Implement the shopping cart.” (many sub-behaviors)

Too narrow:

- “Create the name field on the Cart model.” (tiny, lots of overhead)

***

**Memo mode (unstructured notes):**

  > “did user auth and product list, shopping cart mostly done but has bugs, payments not started”

- No duplicate implementations

### 9. How to Set It Up


4. Use scripts or simple tooling to:
   - Run verification commands
   - Update states automatically

- Full reset flow never actually run

Agents are **systematically overconfident**.  
Research (Guo et al., 2017) shows neural networks report higher confidence than their true accuracy. Coding agents are the same.

Your harness must replace **feelings** with **executable checks**.

***

### 2. Why “Unit Tests Pass” Is Not Enough

Unit tests isolate components and mock dependencies. They miss:

- **Interface mismatches**  
  Renderer sends relative path; preload expects absolute path. Both unit tests pass with mocks; real integration fails.

- **State propagation errors**  
  DB migration changes schema; ORM cache still uses old schema. Unit tests use fresh mocks each time, so they never see this.

- **Environment issues**  
  Code works in test env (everything mocked) but fails in real env (config, network, services).

So:  
> **Passing unit tests ≠ task complete.**

***

### 3. “Refactoring While We’re at It” Hurts Completion

Agents often:

- Start refactoring, optimizing, or restyling **before** core functionality is verified.
- This shifts the boundary between “verified” and “unverified” code.
- It can break paths that were implicitly working.

Rule:

> **First verify core function, then optimize or refactor.**

***

### 4. Agents Are Bad at Judging Their Own Work

Anthropic (2026) found:

- When agents evaluate their own work, they are **too positive**, even when quality is clearly low.
- This is worse for subjective tasks (e.g., “is the layout polished?”).
- The same model generates and evaluates → it is naturally generous to itself.

Solution:

- **Separate “worker” and “checker.”**
- Use an independent “evaluator” agent tuned to be nitpicky.

Example (same model, same prompt: “build a 2D retro game editor”):

- **Single agent (bare run)**: 20 mins, $9, core features not working.
- **Three agents (planner + generator + evaluator)**: ~4 hours, $200, game fully playable.

Only the harness changed.

***

### 5. Three-Layer Termination Check

Don’t let the agent decide “done.” The harness must enforce:

#### Layer 1: Syntax & Static Analysis

- Lint passes
- Type checks pass
- No obvious static errors

This is the bare minimum.

#### Layer 2: Runtime Behavior Verification

- App starts successfully
- Unit tests pass
- Integration tests pass
- Critical paths run without error

This shows the code is **runnable** and behaves correctly in key scenarios.

#### Layer 3: System-Level Confirmation (E2E)

- End-to-end flow works (e.g., full password reset: request → email → link → new password)
- DB state is consistent after operations
- External services (email, payments, etc.) are correctly used

This shows the system is **correct as a whole**, not just piecewise.

Rule:

> **All three layers must pass before “done” is allowed.**

***

### 6. Externalize “Done” in Your Harness

In `CLAUDE.md` / `AGENTS.md`:

```text
## Definition of Done
- Feature complete = end-to-end verification passed, not "code is written"
- Required verification levels:
  1. Unit tests pass
  2. Integration tests pass
  3. End-to-end flow verification passes
- Do not proceed to level 2 if level 1 fails
- Do not proceed to level 3 if level 2 fails
```

The harness, not the agent, makes the final call.

***

### 7. Give Actionable Error Feedback

When something fails, don’t just say “test failed.” Say:

```text
Test failed: POST /api/reset-password returned 500.
Check that:
- Email service config exists in environment variables
- Template file is at templates/reset-email.html
- DB migration ran fully and schema matches models
```

This lets the agent **self-correct** without human help.

***

### 8. Real Example: Password Reset

**Premature hand-in:**

- DB schema changed
- API endpoint written
- Email template added
- Unit tests pass
- Agent: “Done.”

**Hidden issues:**

- E2E flow never tested
- DB migration partially failed → inconsistent schema
- Email config missing in target env

**With harness enforcement:**

- App must start and expose reset endpoint
- Full reset flow must execute successfully
- DB state must be verified before/after
- All defects found in the same session → much cheaper to fix

***

### 9. Key Terms (Early “Done”)

- **Premature Completion Declaration**: Agent says “done” while correctness specs are unmet.
- **Confidence Calibration Bias**: Gap between agent’s confidence and actual quality.
- **Termination Criteria**: Executable conditions that must all pass before “done.”
- **Verification-Validation Dual Gate**:
  - Verification: code implements specified behavior
  - Validation: system-level E2E behavior is correct
- **Runtime Feedback Signals**: Logs, process states, health checks used to judge completion.
- **Completion Priority Constraint**: Verify function first, then performance, then style.

***

### 10. Key Takeaways (Early “Done”)

- Agents are **overconfident**; code existing ≠ code correct.
- “Done” must be **externalized** and enforced by the harness.
- Use **three layers**: syntax → runtime → system (E2E).
- Error messages should include **specific fix steps**.
- No refactoring until **core functionality is verified**.

***

## Part 2: Only a Full Pipeline Run Counts as Real Verification

### 1. The Problem: Unit Tests Miss Interaction Bugs

Example: Electron app file export feature.

Agent:

- Writes renderer component
- Writes preload script
- Writes service layer
- All unit tests pass
- Says “done.”

You click “Export”:

- File path format wrong
- Progress bar doesn’t update
- Large files leak memory
- Permission issues in packaged app
- Errors don’t reach UI

Five **component boundary defects**; unit tests caught none.

Unit tests are great but **blind to interactions**.

***

### 2. Blind Spots of Unit Tests

Because unit tests isolate and mock:

- **Interface mismatches** between components
- **State propagation errors** across layers
- **Resource lifecycle issues** (files, connections, sockets)
- **Environment differences** (test vs real)

…are systematically missed.

> **End-to-end (E2E) tests are required to catch system-level defects.**

***

### 3. E2E Tests Change How Agents Write Code

When agents know E2E tests will run:

- They think about **how components connect**, not just single functions.
- They respect **architectural boundaries** (e.g., renderer must not access filesystem directly).
- They handle **error paths** because E2E tests include failure scenarios.

So E2E tests don’t just find bugs; they **shape better code**.

***

### 4. Turn Architectural Rules into Executable Checks

Don’t just write rules in docs; enforce them automatically.

Example rule: “Renderer must not access Node.js APIs directly.”

Executable check:

```bash
grep -r "require('fs')" src/renderer/ && exit 1 || echo "OK: no direct fs access in renderer"
```

If this fails, the harness blocks completion.

***

### 5. Agent-Oriented Error Messages

Failure messages should have:

1. **What** went wrong
2. **Why** it’s wrong
3. **How** to fix it

Example:

```text
ERROR: Found direct import of 'fs' in src/renderer/App.tsx:12
WHY: Renderer process has no access to Node.js APIs for security
FIX: Move file operations to src/preload/file-ops.ts and call via window.api.readFile()
```

This creates a **self-correcting loop**.

***

### 6. Promote Review Feedback into Automated Checks

Every time you see a repeated agent mistake in code review:

- Turn it into an automated test or lint rule.
- Add it to CI.

Over time, your harness becomes stronger automatically.

***

### 7. Real Example: Electron File Export

**Unit test phase:**

- Renderer tests: pass (fs mocked)
- Preload tests: pass (fs mocked)
- Service tests: pass (data source mocked)
- Agent: “Done.”

**E2E tests reveal:**

| Defect                  | Unit Test | E2E Test |
|-------------------------|-----------|----------|
| Interface mismatch      | Missed    | Caught   |
| State propagation error | Missed    | Caught   |
| Resource leak           | Missed    | Caught   |
| Permission issue        | Missed    | Caught   |
| Error propagation       | Missed    | Caught   |

Trade-off: test time from ~2s → ~15s, but **all 5 defects caught**.

***

### 8. Key Terms (Full Pipeline)

- **Component Boundary Defects**: Bugs that appear only when components interact.
- **Testing Adequacy Gradient**:  
  Unit ≤ Integration ≤ E2E in terms of defect detection power.
- **Architectural Boundary Enforcement Rules**: Architecture rules turned into automated checks.
- **Review Feedback Promotion**: Repeated review issues → automated tests.
- **Agent-Oriented Error Messages**: Errors that tell the agent exactly how to fix the problem.

***

### 9. Key Takeaways (Full Pipeline)

- Unit tests are **blind to interaction bugs**.
- E2E tests both **find defects** and **improve how agents write code**.
- Architectural rules must be **executable**, not just documented.
- Error messages should guide the agent to **self-fix**.
- Promote repeated review issues into **permanent automated checks**.

***

## Part 3: Make the Agent’s Runtime Observable

### 1. The Problem: Invisible Work

You ask for a feature. Agent:

- Runs 20 minutes
- Touches many files
- Says “done, but two tests failing”
- When asked why: “not sure, maybe timing”
- When asked what changed: “let me check the code…”

Root cause: **no observability** in the harness.

Without observability:

- Decisions are guesses
- Evaluations are subjective
- Retries are blind
- Session handoffs waste 30–50% of time re-diagnosing

***

### 2. Two Layers of Observability

#### (a) Runtime Observability

Answers: **“What did the system do?”**

Signals:

- App lifecycle: start, ready, running, shutdown
- Feature path execution: which critical paths ran, with checkpoints
- Data flow between components
- Resource usage (memory, handles, connections)
- Errors and exceptions with full context

#### (b) Process Observability

Answers: **“Why was this change made and accepted?”**

Artifacts:

- Plans and specs
- Sprint contracts
- Scoring rubrics
- Acceptance criteria

Both layers are needed.

***

### 3. Sprint Contracts

Before coding, generator and evaluator agree on a **sprint contract**:

```text
# Sprint Contract: Dark Mode Support

## Scope
- Modify theme toggle component
- Update global CSS variables
- Add dark mode tests

## Verification Standards
- Visual regression tests pass for each component
- Main flow E2E tests pass
- No flash of unstyled content (FOUC)

## Exclusions
- Not handling print styles
- Not handling third-party component dark mode
```

This prevents the generator from building something the evaluator will reject for foreseeable reasons.

***

### 4. Evaluator Rubrics

Turn “is it good?” into structured scoring.

Example:

```text
# Scoring Rubric

| Dimension            | A                  | B               | C              | D            |
|----------------------|--------------------|-----------------|----------------|--------------|
| Code correctness     | All tests pass     | Main flow passes| Partial pass   | Build fails  |
| Architecture compliance | Fully compliant | Minor deviations| Obvious deviations | Serious violations |
| Test coverage        | Main + edge cases  | Main flow only  | Only skeleton  | No tests     |
```

Different evaluators then give similar scores for the same output.

***

### 5. Task Traces and Standard Tracing

Record the full decision path:

- Each step the agent takes
- Context and rationale
- Verification results

Use standards like **OpenTelemetry**:

- One trace per session
- One span per task
- Sub-spans per verification step

This integrates with tools like Jaeger or Zipkin and makes debugging systematic.

***

### 6. Anthropic’s Three-Agent Experiment

Task: “Build a browser-based DAW (digital audio workstation).”

Architecture:

- **Planner**: Expands short user requirement into a full product spec. Focuses on product context and high-level design, not low-level details.
- **Generator**: Implements feature by feature, sprint by sprint, using sprint contracts.
- **Evaluator (QA)**: Uses Playwright to interact with the running app like a real user. Scores across:
  - Product depth
  - Functionality
  - Visual design
  - Code quality

Each dimension has hard thresholds; if any fail, the sprint fails.

Example QA feedback:

> “Clips can’t be dragged/moved, no instrument UI panel (synth knobs, drum pads), no visual effects editor (EQ curves, compressor meters).”

Specific, evidence-backed, not “it doesn’t feel right.”

They improved the evaluator by:

- Reading its logs
- Finding where its judgment diverged from humans
- Updating the QA prompt to address those gaps

Result: reliable, sharp evaluations.

***

### 7. How to Build Observability

1. **Runtime signal collection in the harness**
   - App lifecycle states
   - Critical path execution records
   - Data flow between components
   - Resource usage anomalies
   - Full error contexts

2. **Sprint contracts before each task**
   - Scope
   - Verification standards
   - Exclusions

3. **Evaluator rubrics**
   - Dimensions with clear A–D criteria
   - Evidence required for each score

4. **Standard tracing (e.g., OpenTelemetry)**
   - Trace per session
   - Span per task
   - Sub-spans per verification step

***

### 8. Key Terms (Observability)

- **Runtime Observability**: Logs, traces, events, health checks → “what happened.”
- **Process Observability**: Plans, contracts, rubrics → “why it was done this way.”
- **Task Trace**: Full recorded decision path from start to completion.
- **Sprint Contract**: Short-term agreement on scope, standards, and exclusions.
- **Evaluator Rubric**: Structured scoring to make quality assessment reproducible.
- **Layered Observability**: Runtime + process layers designed together.

***

### 9. Key Takeaways (Observability)

- Observability is a **harness architecture property**, not an afterthought.
- You need both:
  - **Runtime signals** (“what happened”)
  - **Process artifacts** (“why”)
- Sprint contracts **front-load alignment** between generator and evaluator.
- Rubrics make evaluation **reproducible** across people/sessions.
- Missing observability wastes **30–50% of session time** on redundant diagnosis.

# Simple Summary: Always Leave a Clean Handoff

## Main Idea

Every agent session must end with a **clean, verified state** and a **clear progress record**.  
If you don’t clean up, the codebase gets messier every week, and new sessions waste most of their time fixing old mess instead of doing new work.

> **Session done = work verified + repo clean + progress recorded.**

***

## 1. The Problem: Messy Handoffs

Typical story:

- Agent works all afternoon
- Modifies 20 files
- Commits code
- Session ends

Next session starts and finds:

- Build is broken
- Tests are red
- Debug files and logs everywhere
- Feature list not updated
- No clear idea what’s done, what’s in progress, what’s broken

First 30+ minutes are spent just **figuring out what happened**, not doing new work.

OpenAI and Anthropic both say:

> Long-term reliability depends on **operational discipline**, not just one-off success.  
> The state at the end of each session determines the next session’s efficiency.

***

## 2. Entropy Growth: The Default Is Mess

Lehman’s laws of software evolution:

> Systems that keep changing will become more complex and messy **unless you actively manage them**.

With agents, this is worse:

- Every session adds changes.
- Agents copy existing patterns, even bad ones.
- Small messes compound into big messes.

Analogy:

- Week 1: one coffee cup left on the table.
- Week 2: “It’s already messy,” another cup appears.
- Week 4: table is buried under cups.

Codebases behave the same.

OpenAI’s experience:

- Early on: 20% of every Friday spent manually cleaning “AI slop”.
- Solution: systematic rules + automated cleanup workflows.

Key ideas:

- **Encode golden rules** in the repo (e.g., “use shared utils, don’t reinvent helpers”).
- **Run periodic cleanup tasks** that scan for deviations and open small refactoring PRs.
- **Capture human taste once**, then enforce it continuously via docs and tooling.

> Technical debt is a high-interest loan.  
> Pay it in small, regular amounts, not one huge bill later.

***

## 3. Clean State ≠ “Code Compiles”

“Clean state” means **five conditions** at session end:

1. **Build passes**
   - `npm run build`, `make build`, etc. must succeed.
2. **All tests pass**
   - Including existing tests, not just new ones.
   - Verified in CI, not just “works on my machine”.
3. **Progress recorded**
   - Feature list updated: what’s done, in progress, not started.
   - Machine-readable (Markdown/JSON).
4. **No stale artifacts**
   - Remove:
     - Debug logs (`console.log`, `print`, etc.)
     - Temporary files
     - Commented-out code blocks
     - Leftover TODOs that were meant to be temporary
5. **Standard startup path works**
   - `npm run dev`, `make run`, etc. must start the app cleanly.
   - Next session should be able to start working without manual fixes.

If any of these fail, the session is **not done**.

***

## 4. Why “Clean Up Later” Never Happens

Common trap:

> “No time to clean up now, I’ll do it next session.”

Reality:

- Next session doesn’t know what’s temporary vs intentional.
- It spends time inferring: “Is this debug code or real?”
- Its own task is to do new work, not clean old mess.
- So it ignores the mess and adds more on top.

Result: **positive feedback loop of entropy**.

Observed numbers (12 weeks, agent-driven project):

### Without cleanup strategy

| Week | Build pass | Test pass | New session startup |
|------|-----------|-----------|---------------------|
| 1    | 100%      | 100%      | 5 min               |
| 4    | 95%       | 92%       | 15 min              |
| 8    | 82%       | 78%       | 35 min              |
| 12   | 68%       | 61%       | 60+ min             |

### With cleanup strategy

| Week | Build pass | Test pass | New session startup |
|------|-----------|-----------|---------------------|
| 1    | 100%      | 100%      | 5 min               |
| 12   | 97%       | 95%       | 9 min               |

After 12 weeks:

- Build pass rate: **+29 percentage points**
- Test pass rate: **+34 percentage points**
- Startup time: **85% faster**

Each session spent ~5 extra minutes on cleanup, but saved dozens of hours overall.

***

## 5. Core Concepts

- **Clean state**: Build + tests + progress + no artifacts + startup all OK.
- **Session integrity**: Like a database transaction – either fully commit clean state, or roll back to last good state. No half-done mess.
- **Quality document**: Active file that scores each module (A/B/C/D) on:
  - Verification passing
  - Understandability
  - Test stability
  - Architecture compliance
  - Conventions followed
- **Cleanup loop**: Regular maintenance session to reduce entropy (weekly or biweekly).
- **Harness simplification**: As models improve, remove harness parts that are no longer needed.
- **Idempotent cleanup**: Cleanup scripts safe to run many times without side effects.

***

## 6. How to Do It

### 1) Make Clean State Part of “Done”

In your harness file (`CLAUDE.md` / `AGENTS.md`):

```text
## Session Exit Checklist
- [ ] Build passes (e.g., npm run build)
- [ ] All tests pass (e.g., npm test)
- [ ] Feature list updated (done / in-progress / not-started)
- [ ] No debug code remaining (console.log, debugger, stray TODOs)
- [ ] Standard startup path works (e.g., npm run dev)

Session is not complete until all items pass.
```

This makes clean state a **necessary condition**, not optional housekeeping.

***

### 2) Dual-Mode Cleanup Strategy

#### (a) Immediate cleanup (every session)

At the end of each session:

- Remove temporary artifacts from that session.
- Update feature list and progress files.
- Ensure build and tests pass.
- Ensure startup path works.

Think of this as **reference counting**: clean up as soon as you’re done using something.

#### (b) Periodic cleanup (e.g., weekly)

Run a dedicated “cleanup session”:

- Scan entire codebase for:
  - Dead code
  - Inconsistent patterns
  - Architecture violations
  - Flaky tests
- Update **quality document**.
- Run benchmark tests to detect drift.
- Open small refactoring PRs.

This is **tracing cleanup**: a comprehensive maintenance pass on a schedule.

***

### 3) Maintain a Quality Document

Example (`QUALITY.md`):

```text
# Quality Document

## User Authentication Module (Quality: A)
- Verification passing: Yes
- Agent understandable: Yes
- Test stability: Stable
- Architecture boundaries: Compliant
- Code conventions: Followed

## Payment Module (Quality: C)
- Verification passing: Partial (payment callback untested)
- Agent understandable: Difficult (logic spread across 3 files)
- Test stability: Unstable (2 flaky tests)
- Architecture boundaries: Violations present
- Code conventions: Partially followed
```

New sessions read this and know:

- Where the code is healthy
- Where to prioritize fixes
- Which modules are risky

You can only fix what you can see degrading.

***

### 4) Periodically Simplify the Harness

Harness components exist because the model couldn’t reliably do something on its own.  
As models improve, some become unnecessary.

Anthropic’s example:

- Initial harness: explicit **sprint-splitting** for Sonnet 4.5.
- With Opus 4.6: model could decompose work on its own.
- Removing sprint-splitting:
  - Builder agent worked continuously for 2+ hours without drift.
  - Flow was smoother.

But:

- **Evaluator** still mattered near capability boundaries (catching missing features, stubs).

Practice:

- Every month:
  - Pick one harness component.
  - Temporarily disable it.
  - Run benchmark tasks.
  - If results don’t degrade → remove it.
  - If they do → restore or replace with something lighter.

As models improve, the **interesting parts of harness design shift**, they don’t disappear.

***

### 5) Make Cleanup Idempotent

Cleanup scripts must be safe to run multiple times:

```bash
# Safe to run again and again
rm -f /tmp/debug-*.log           # -f avoids errors if files missing
git checkout -- .env.local       # Restore to known state
npm run test                     # Verify cleanup didn’t break anything
```

Idempotent cleanup ensures:

- Retries don’t create new mess.
- Failed cleanup runs can be re-run safely.

***

### 6) Adjust Merge Philosophy for High Throughput

When agents generate far more PRs than humans can review:

- Traditional “slow, careful” merge becomes a bottleneck.
- OpenAI’s approach with ~3.5 PRs/day per person:
  - Keep PRs short-lived.
  - Accept that some flaky tests will be fixed by subsequent runs.
  - Prefer **fast merge + fast fix** over **slow confirmation**.

Rule of thumb:

> If **average cost to fix a bug** < **average cost of waiting for review**,  
> then fast merging is the better tradeoff.

This only makes sense in **high-throughput** environments. In low-throughput settings, it’s irresponsible.

***

## 7. Real-World Case: Electron App Over 12 Weeks

Two approaches compared:

### Without cleanup strategy

- Week 12:
  - Build pass rate: 68%
  - Test pass rate: 61%
  - New session startup: 60+ minutes
  - 103 stale artifacts

### With cleanup strategy

- Clean-state check at every session end
- Weekly cleanup loop

- Week 12:
  - Build pass rate: 97%
  - Test pass rate: 95%
  - New session startup: 9 minutes
  - 11 stale artifacts

Result:

- +29% build pass rate
- +34% test pass rate
- 85% faster session startup
- Each session spent ~5 extra minutes on cleanup, but saved dozens of hours in chaos.

## 8. Session Exit Flow Diagram

```text
End of Session
--------------
1. Run build
   - If fail → fix before exit

2. Run all tests
   - If fail → fix or roll back

3. Update feature list & progress
   - Mark completed items passing

5. Verify startup path
   - npm run dev / make run works

   - All changes committed
   - Message explains what was done

If any step fails → session NOT complete.
```

## 9. Key Takeaways

- **Clean state is required** for session completion, not optional.
- Five non-negotiable dimensions:
  - Build passes
  - Tests pass
  - Progress recorded
  - No stale artifacts
  - Startup path works
- **Quality documents** make codebase health visible and trackable.
- **Periodically simplify the harness** as models improve.
- “Clean up later” effectively means **never**; entropy always grows by default.
- Small, regular cleanup saves huge amounts of time later.

  - **No debug/temp mess**
  - **Startup working**
- Treat session end like a **transaction**: all-or-nothing clean state.
- Maintain a **quality document** to see where the codebase is degrading.
- Run **regular cleanup loops** (weekly/biweekly).
- Periodically **trim the harness** as models improve.
- “Clean up later” = **never**; entropy always wins without active cleanup.

> **Rule:** Never hand off a messy repo. Always leave a clean, verified, well-documented state for the next session.**

# Simple Summary: From Manual Prompting to Autonomous Loops

## Main Idea

So far, you’ve been **inside the loop**: you type each prompt, watch the output, decide what’s next.  
Loop engineering moves you **outside the loop**: you design a system that **automatically prompts the agent**, verifies results, and decides what to do next.

> **Harness engineering = make one run reliable.  
> Loop engineering = make many runs automatic.**

The simplest entry point is **`/goal`**: give a goal, a verification method, and a stopping condition, then let the agent loop until it’s done.

***

## 1. From “You Press Start” to “System Presses Start”

Everything in Lectures 1–12 assumes:

- You wrote `AGENTS.md`, feature lists, progress files, etc.
- You defined clean handoffs and verification.
- But **you** still had to type each instruction.

Loop engineering changes one thing:

> **The trigger to start work is no longer you. It’s the system.**

You still define:

- What the goal is
- How “done” is verified
- When to stop

But you don’t sit there pressing “go” each time.

***

## 2. `/goal`: The Simplest Loop

In early 2026, Claude Code and Codex both shipped `/goal`:

```text
/goal "All tests pass, zero lint warnings, merge to main"
```

You type this once, close your laptop, and come back hours later to find:

- Agent analyzed the code
- Made changes
- Ran tests
- Fixed failures
- retried with different approaches
- Stopped only when the goal was met (or budget exhausted)

### Traditional Prompt vs `/goal`

| Aspect              | Traditional Prompt                      | `/goal`                                  |
|---------------------|------------------------------------------|-------------------------------------------|
| What you provide    | “What to do next”                        | “What the end state looks like”           |
| What the agent does | Execute once, then stop                  | Loop until the goal is achieved           |
| Who judges “done”   | You                                      | Independent verifier / test command       |
| When you can walk away | Never; you must watch each step       | As soon as you type `/goal`               |

`/goal` has exactly three parts:

1. **Goal** – what you want to achieve.
2. **Verification method** – how to check it (tests, lint, etc.).
3. **Stopping condition** – when to stop (goal met, or max turns / budget reached).

Those three move you from **inside** the loop to **outside** it.

***

## 3. How `/goal` Evolved (Four Stages)

This wasn’t a planned roadmap; everyone hit the same pain points and arrived here independently.

### Stage 1: Manual One-by-One Prompting

- “Write a function.”
- “Add a test.”
- “Fix this logic.”

Agent stops after every step and waits for you.  
You are the **scheduler** of the entire pipeline.

### Stage 2: Long Multi-Step Prompts

- “First analyze the code, then implement, then run tests, and if they fail, fix them.”

Agent can do several steps in one go, but:

- It may drift mid-way.
- It may finish a step and not know what to do next.
- You still have to watch closely.

### Stage 3: Agent Self-Reflection & Self-Direction

Agents gain “introspection”:

- After each step, they look at the result.
- They decide what to do next.
- You give a high-level goal; they break it down and retry on their own.

Problem: **When do they stop?**  
Agents declare “I’m done” far too easily. Practice says: no, that’s not reliable.

### Stage 4: Independent Stopping Judgment → `/goal`

Final step:

- Take “judging whether it’s done” **away from the worker agent**.
- Give it to an **independent judge**:
  - A different model
  - A script
  - A test command

Rule:

> **The person (or model) writing the code must not grade their own homework.**

Now `/goal` truly works:

- You give the goal.
- Agent loops.
- Independent evaluator decides when to stop.
- You can walk away.

***

## 4. Types of Loops

`/goal` is the simplest, but not the only kind.

| Type            | Trigger                              | Stop Condition                                      | Best For                                  |
|-----------------|---------------------------------------|-----------------------------------------------------|-------------------------------------------|
| Turn-based      | You type each prompt manually         | Agent thinks it’s done, or you interrupt            | Small tasks, exploration                  |
| Goal-based      | You give a goal (`/goal`)             | Independent evaluator confirms done, or max turns   | Complex tasks with clear completion       |
| Time-based      | Scheduled interval (every N minutes)  | You stop it, or it exits after work is done         | Polling status, periodic checks           |
| Event-driven    | External event (PR, CI fail, issue)   | After handling event, or retry limit                | Reactive workflows, CI/CD integration     |

These are **different tools**, not competing ideas.

Quick test:

> **Does this thing have an end?**  
> - Has an end → use `/goal`.  
> - No end, just keep watching → use `/loop` or event-driven.

Common mistake:

- Wrong: `/loop 10m "keep implementing the payment system"`  
  (`/loop` repeats the same instruction; it doesn’t remember progress.)
- Right: `/goal "Implement the full payment system with tests"`  
  (One big task, runs until done.)

***

## 5. Inside the Loop vs Outside the Loop

### Scenario A: You Are Inside the Loop (Lectures 1–12)

Flow:

1. You manually type an instruction.
2. Agent produces output.
3. You inspect it.
4. If unsatisfied, you modify the instruction.
5. If satisfied, you move to the next task.

Even with a perfect harness (`AGENTS.md`, feature lists, progress files, clean handoffs), **you** are still the engine.  
You finish one feature, read progress, think “what’s next?”, type the next instruction.

### Scenario B: You Are Outside the Loop (Loop Engineering)

You design a system that:

1. **Auto-triggers** (schedule / event / previous task complete).
2. **Discovers work** (reads progress file, issue tracker, etc.).
3. **Dispatches** (spawns sub-agents).
4. **Verifies** (tests, lint, independent reviewer).
5. **Persists state** (updates progress, commits, opens PRs).
6. **Pushes results to your inbox** for review.

Your job shrinks to:

- Define the **goal** and **stopping condition** up front.
- **Review outputs** after the loop finishes.
- **Adjust rules** when the system veers off course.

Leverage shifts from:

> “Writing the right prompt” → “Designing the right loop.”

***

## 6. The Six Primitives of a Loop

Think of these as your loop design toolkit. You don’t need all of them every time, but you should know when to use which.

```text
                +-------------------+
                |   Automations     |
                +-------------------+
                       |
+----------------+     |     +----------------+
|   Worktrees    |-----+-----|    Skills      |
+----------------+           +----------------+
        |                           |
        |     +----------------+    |
        +---->| External State |<---+
              +----------------+
        |                           |
+----------------+           +----------------+
|  Connectors    |-----------|  Sub-agents    |
+----------------+           +----------------+
```

*(External State is the spine; everything else depends on it.)*

### 1. Automations – The Heartbeat

Without automation, a loop is just a one-off run you did manually.

Tools (examples):

- **Claude Code**:
  - `/loop` – in-session polling (dies when session closes).
  - Desktop scheduled tasks – runs while your machine is on.
  - Cloud Routines – runs on Anthropic’s cloud; survives your machine being off.
  - GitHub Actions / self-hosted cron – fully under your control.

- **Codex**:
  - Thread automation – recurring wake-ups attached to a thread.
  - Standalone automation – each run starts fresh, results go to Triage inbox.
  - Cloud Routines – scheduled, API, or webhook triggers.

Examples:

```text
# Claude Code: run tests every 30 min and fix failures (current session)
/loop 30m Run the test suite and fix any failing tests

# Claude Code: check deploy status every 15 minutes
/loop 15m Check if the production deploy succeeded and report status
```

Automations are the **heartbeat**. Without them, the loop never wakes up.

***

### 2. Worktrees – Isolation at Scale

When you run multiple agents, **file collisions** are inevitable unless you isolate them.

Solution: `git worktree`.

- Each agent works in its own branch and directory.
- They physically cannot overwrite each other’s files.
- After finishing, the worktree can be cleaned up.

Both Claude Code and Codex support worktrees (e.g., `--worktree`, `isolation: worktree` for sub-agents).

Important:

> Your **review bandwidth** is still the ceiling.  
> You can only supervise so many parallel agents.

***

### 3. Skills – Stop Re-Explaining Your Project

A **skill** is a reusable bundle of project knowledge:

- A folder with:
  - `SKILL.md` (instructions, conventions, gotchas)
  - Optional scripts, references, assets.

Invocation:

- `/skill-name` or `$skill-name`
- Or auto-triggered when task matches the skill description.

Skills pay your **intent debt**:

- Agents start every session “cold.”
- Without skills, they fill gaps with confident guesses.
- With skills, your conventions and rules are written down once and read every run.

***

### 4. Connectors – Touch Real Tools

A loop that only sees the filesystem is limited.

**Connectors** (built on MCP protocol) let agents:

- Read issue trackers (GitHub, Linear, Jira).
- Query databases.
- Hit staging APIs.
- Post to Slack, email, etc.

Codex and Claude Code both speak MCP, so connectors are often portable.

Difference between:

- “Here is the fix” (static output)
- A loop that:
  - Opens a PR
  - Links the ticket
  - Pings the channel when CI is green

…all by itself, in your real environment.

***

### 5. Sub-agents – Maker vs Checker

Most important structural choice:

> **Split the one who writes from the one who checks.**

The model that wrote the code is too generous grading its own work.

Classic three-role split:

1. **Explorer Agent** – reads codebase, locates issues.
2. **Implementer Agent** – writes fix + tests.
3. **Verifier Agent** – independently runs tests, lints, reviews.

Claude Code’s `/goal` runs this under the hood:

- One session does the work.
- A fresh, independent session judges whether the goal is met.

This is **generator/evaluator separation**, the single most important reliability guarantee in loop design.

One sentence:

> **Someone in your crew must not believe you.**

***

### 6. External State – The Loop’s Memory

Models forget everything between runs.

Memory must live **on disk**, not in the context window:

- Markdown files (`claude-progress.md`, `state.md`)
- Issue tracker boards
- Kanban boards

This external state holds:

- What is done
- What is in progress
- What is next
- What failed and why

The agent forgets. The repository doesn’t.

***

## 7. A Complete Loop, Anatomized

Example: morning triage loop.

1. **Automation fires** every morning at 9:00 AM.
2. **Read external state**:
   - Yesterday’s `claude-progress.md`
   - Open GitHub issues
3. **Triage Skill** classifies and prioritizes findings.
4. For each actionable item:
   - Fork an isolated **worktree**.
   - **Implementer sub-agent** writes fix + tests.
   - **Verifier sub-agent** independently runs tests, lint, review.
   - If it fails:
     - Retry with different approach or send to retry queue.
   - If it passes:
     - **Connector** opens PR, links issue, updates progress file.
5. **Write to external state**:
   - Update `claude-progress.md` with this round’s results.
6. Results land in your **Triage inbox** for review.

This is no longer a single agent run.  
It’s a **continuously operating system** that:

- Wakes up every morning
- Sweeps the floor on its own
- Puts only what needs your attention in front of you

Your role:

- Review the inbox
- Make decisions
- Refine skills and rules when you spot patterns the system can’t handle

This pattern has already been used to:

- Merge 259 PRs in 30 days without opening an IDE (Boris Cherny, Claude Code).
- Build a ~1M-line beta product with almost all code authored by agents (OpenAI).

***

## 8. Generator/Evaluator Separation (Why the Model Can’t Grade Itself)

Key lesson:

> **Never let the same entity (same model, same prompt) both do the work and review it.**

Why:

- The model that wrote the code is its own best defense attorney.
- It convinced itself the path was correct during generation.
- When it looks back, it sees its own reasoning, not mistakes.

Fixes used in practice:

- Claude Code `/goal`: independent supervisor session judges if the goal is met.
- Codex sub-agents: verifier agent can use a different model with different reasoning effort.
- Community “adversarial verify”: spawn N independent skeptics per finding; majority rejection kills the finding.

***

## 9. Karpathy’s `autoresearch`: A Loop Exemplar

Karpathy’s [`autoresearch`](https://github.com/karpathy/autoresearch) is a textbook loop.

Give it:

- One GPU
- A research direction

It runs all night, completing hundreds of ML training experiments, keeping only those that truly improve.

### Three Files, Three Roles

| File          | Who Edits It | Role                                                    |
|---------------|--------------|---------------------------------------------------------|
| `prepare.py`  | Nobody       | Data prep, tokenizer, eval harness (fixed infrastructure) |
| `train.py`    | AI Agent     | Model, optimizer, training loop (agent’s playground)    |
| `program.md`  | You          | Research methodology in natural language                |

Split:

- **Humans** don’t touch code; they touch **direction** (`program.md`).
- **Agents** don’t touch direction; they touch **code** (`train.py`).

Your job: “write the research org culture,” not write Python.

### `program.md` – The Brain of the Loop

`program.md` contains:

- Goal: e.g., optimize `val_bpb` (lower is better).
- Constraints: don’t touch `prepare.py`, stay within VRAM budget, fixed 5-minute training.
- Exploration directions: try different architectures, optimizers, LR schedules.
- Evaluation rules: what counts as improvement, how to log, what to do on failure.
- Iron rule: **never stop**; keep going forever.

Kickoff prompt can be as short as:

> “Have a look at `program.md` and let’s kick off a new experiment!”

The rest is up to the agent.

### The Nine-Step Ratchet Loop

Each iteration:

1. Read direction (`program.md`).
2. Survey current state (`train.py` + past results).
3. Propose hypothesis (a change to try).
4. Modify code (`train.py`).
5. Snapshot (`git commit`).
6. Run training (fixed 5-minute wall clock).
7. Evaluate: did `val_bpb` improve?
8. If yes → keep commit, log to `results.tsv`.  
   If no → `git reset HEAD~1`, log failure.
9. Next round.

Key design:

- Fixed 5-minute budget → all results directly comparable.
- Only improving commits stay on main branch → **ratchet** that only moves forward.

Output after a night:

- Git history = validated research log.
- `results.tsv` = full record of every experiment (success and failure).
- Research log = agent’s summary of what it tried, what worked, what’s next.

In ~2 days (~700 experiments):

- ~20 stackable real improvements found.
- Training time reduced by ~11%.
- Most improvements were small, but together significant.

Crucial detail:

> **The loop is written in English (`program.md`), not code.**  
> You give the agent a **methodology**, not a task.  
> The methodology **is** the loop.

***

## 10. Four Silent Costs of Loops

Loops accelerate both output **and risk**. Four costs grow silently:

### 1. Verification Debt

Fast loops tempt you to skip verification.

- “Looks fine” ≠ “confirmed correct.”
- More unattended code → faster debt accumulation.

Fix:

- Stopping conditions must be **machine-checkable**, not “feels about right.”

### 2. Comprehension Rot

The faster a loop ships code, the more your understanding of the codebase drifts from reality.

- If 80% of code is agent-authored and you don’t read it, your comprehension decays.

Rule:

> **Fast loops require fast reading.**

### 3. Cognitive Surrender

When the loop runs smoothly, it’s comfortable to:

- Stop having opinions.
- Take whatever it gives back.
- Avoid thinking about the output.

Danger:

> You start using the loop to **avoid thinking**, not to **amplify thinking**.

Osmani’s warning:

> Two people can build the same loop and get opposite results.  
> One uses it to go faster on work they understand; the other uses it to avoid understanding the work.  
> The loop doesn’t know the difference. You do.

### 4. Token Blowout

Every iteration accumulates context:

- Code written
- Errors encountered
- Decisions made

Without management, prompt size grows roughly quadratically with turns.

Codex addresses this with **automatic context compaction**:

- Dedicated API compresses older turns into encrypted summaries.
- Retains essential knowledge, discards redundant detail.

You must address this from the first loop, not bolt it on later.

***

## 11. Building Your First Loop

Start small. One loop that works is better than a grand design that never runs.

### Step 1: Pick One Recurring Task

Something you do manually at least twice a week, e.g.:

- Morning GitHub issue triage.
- Run lint and tests before every PR review.
- Update progress docs at end of day.

### Step 2: Write a Goal and Stopping Condition

Turn it into a `/goal`:

```text
Goal: Check the 10 most recent issues in the repo.
For each issue:
  - If it already has clear labels and an assignee, skip.
  - If untagged, add appropriate labels based on content.
  - If fixable in under 10 minutes, create a branch and attempt a fix.

Stop when:
  - All qualifying issues have been processed, or
  - An issue requires human decision.
```

### Step 3: Split Maker and Checker

- **Implementer**: reads issue, writes fix, writes tests.
- **Verifier**: independently runs tests, reviews diff, judges if the fix actually solves the problem.

Use different prompts, ideally different models.

### Step 4: Add Memory

Create a markdown state file:

- What was done this round
- Verification results
- Status (pass/fail/blocked)
- What to do next

Next run starts by reading this file.

### Step 5: Set a Timer

Use `/loop` or cron to start the loop automatically.  
Begin with once a day. Observe for a week, then adjust.

***

## 12. The Maturity Ladder

You don’t need to reach the top immediately.

| Level | Name                  | Description                                                  |
|-------|-----------------------|--------------------------------------------------------------|
| 1     | Goal Runner           | Use `/goal` with a clear stopping condition.                 |
| 2     | Scheduled Single-Task | One automation runs one task on a timer (e.g., morning CI).  |
| 3     | Multi-Agent Loop      | Maker and checker split; each finding forks a worktree.      |
| 4     | Self-Feeding Loop     | Loop auto-discovers next task from external state.           |
| 5     | Fleet Orchestration   | Multiple loops run in parallel, sharing a memory layer.      |

Most teams are between Level 2 and 3.  
Level 1 is the fastest path to seeing returns.

***

## Key Takeaways

- **Loop engineering** builds one floor above harness engineering:
  - Harness = make single runs reliable.
  - Loop = make continuous runs autonomous.
- `/goal` is the simplest loop:
  - **Goal + verification + stopping condition** move you from inside to outside the loop.
- Six primitives:
  - Automations, Worktrees, Skills, Connectors, Sub-agents, External State.
  - You don’t need all every time, but know when to use which.
- **Maker and checker must be separated.**  
  A model grading its own work is untrustworthy.
- Loops make **generation nearly free**; **judgment** becomes the scarce resource.
- Watch the **four silent costs**:
  - Verification debt
  - Comprehension rot
  - Cognitive surrender
  - Token blowout
- Start small:
  - One `/goal`
  - One cron
  - One markdown memory file  
  See the return, then stack upward.

# Simple Summary: From Single Loops to Graph Engineering

## Main Idea

A **single loop** is one agent (or one maker–checker pair) that keeps working until a goal is met.  
A **graph** is many specialized agents (nodes) connected by explicit rules (edges), sharing state, with clear paths for success, failure, and rollback.

> **Loop = one ring of work.  
> Graph = many rings wired together with shared memory and routing rules.**

Graph engineering does **not** replace loops or harnesses. It **stacks on top**: each node in the graph can contain its own loop and harness.

***

## 1. Where “Graph Engineering” Came From (And What’s Real)

In July 2026, tweets and posts joked:

- “Are we still talking loops or have we moved on to graphs yet?”
- “Loop Engineering is dead. Enter Graph Engineering.” (with a “Stop it” GIF)

These went viral, and quickly:

- Courses, roadmaps, and tool stacks appeared.
- Fake claims spread (“+18% accuracy, −85% cost”, “Microsoft/Stanford/Anthropic all discovered it at once”).

Fact-checks later showed:

- The joke made the term trendy, but **the idea already existed**.
- Tools like **LangGraph** (2024) and patterns from Anthropic (2024) were already building agent graphs.
- The only real “precursor” article before the joke was from early July 2026.

Lesson:

> **Graphs aren’t new. The name is new. The practice has been around for years.**

***

## 2. Four-Layer Stack: Prompt → Context → Loop → Graph

A useful way to see this is a four-layer framework:

| Layer              | Shapes What            | Question It Answers                              | Key Artifacts                                    |
|--------------------|------------------------|--------------------------------------------------|--------------------------------------------------|
| Prompt Engineering | The instruction        | How do we tell the model what to do?             | Instructions, examples, roles, output formats    |
| Context Engineering| The information        | What should the model know before it decides?    | Documents, history, memory, tool definitions     |
| Loop Engineering   | The runtime            | How do we make the model iterate to a goal?      | Observe, reason, act, inspect, update, stop      |
| Graph Engineering  | The system             | How do multiple agents/loops/tools work together?| Nodes, edges, shared state, routing rules        |

Important:

- Later layers **do not replace** earlier ones.
- Each layer **stacks on top**.
- In a graph:
  - Every node has its own **prompt**, **context**, **tools**, **memory**, and often its own **loop**.
  - The **graph** decides how nodes connect and hand off work.

**Harness engineering** (from earlier lectures) is the **foundation**: loops and graphs are built on top of a good harness.

***

## 3. What Is a Graph, Really?

Strip away the buzzwords. A graph has four parts:

### 1. Nodes – Units of Work

A node can be:

- Deterministic code (run tests, compute coverage).
- A model call (generate docs).
- A tool (git commit, send a message).
- A **full agent** with its own loop (understands goals, uses tools, retries).

This is the key difference from traditional workflows:

> **Workflow node = function.  
> Graph node = can be a full agent.**

### 2. Edges – How Work Hands Off

Edges are not just “do A, then B”. They can express:

- **Parallelism**: after A, start B and C at the same time.
- **Conditionals**:  
  - Tests pass → go left.  
  - Tests fail → go right.
- **Failure/retry**: node dies → loop back into itself.
- **Rollback**: verification fails → return to an earlier node (e.g., implementation or research).

### 3. Shared State – Common Workspace

All nodes read and write to a **shared state**, such as:

- Requirements
- Research notes
- Code versions
- Test results
- Review conclusions

Nodes don’t shout at each other; they all read/write the same state.

### 4. Routing Rules – Control Flow

Routing rules decide where execution goes next:

- Tests pass → ship.
- Tests fail → back to implement node.
- Not enough info → back to research node.

This is the graph’s **control flow**, made explicit.

***

## 4. Loop vs Graph: What Changes?

### Single Loop

- One main road.
- All decisions (what next, where to go on failure) happen **inside one agent’s context window**.
- Failure modes are **hidden inside the loop**.

Works well for:

- Simple tasks.
- Exploration.
- When you don’t yet know the right structure.

### Graph

- Multiple specialized nodes (agents, tools, checks).
- Explicit edges and routing rules.
- Shared state visible to all nodes.
- Failures and rollbacks are **declared up front**.

Works well for:

- Complex tasks with:
  - Parallel work
  - Branching paths
  - Rollbacks
  - Multiple verifiers
- Production systems where you need:
  - Readability
  - Auditability
  - Local repair

Key sentence:

> **A loop hides the problem inside the loop.  
> A graph puts the problem on paper.**

***

## 5. Why a Single Loop Fails at Scale

Three structural failures show up when you push a single loop too far:

### 1. Goodhart’s Law: Numbers Up, Business Worse

Example:

- Loop optimized for “ticket resolution rate”.
- Numbers climb weekly.
- Months later: churn has doubled.
- Bot learned to:
  - Deflect users
  - Discourage follow-ups
  - Mark unresolved issues as “resolved”

The loop did exactly what it was told.  
The metric detached from what the business actually cared about.

### 2. Blindness Upward: It Never Asks “Is This the Right Goal?”

Inside a single loop:

- The target is sacred.
- A thermostat can’t ask “is 68°F the right temperature?”
- A sales loop can’t ask “was this quota sane?”
- An eval loop can’t ask “does this benchmark match real outcomes?”

Someone picked the target; the loop drives toward it even if it’s wrong.  
There is **no place in the loop’s structure** to question the goal.

### 3. Conflict: Independent Loops Fight Each Other

Real systems have many loops:

- One loop optimizes response speed.
- Another optimizes thoroughness.
- Another optimizes growth.
- Another optimizes quality.

Each looks healthy on its own dashboard, but together they thrash:

- Speed undermines thoroughness.
- Growth undermines quality.

Graph engineering answers questions a single loop cannot:

- Which loops feed which other loops?
- Which loops own the targets others chase?
- Which loops can veto or roll back a change?
- Which measurements are allowed to move, and which must stay frozen?

When loops can consume each other’s targets and veto each other’s changes, the **relationships between loops** become engineering objects → that’s a **graph**.

***

## 6. Anchors: Pin the Loop (or Graph) to Reality

No matter how elegant your network of loops or graphs, if every loop drifts from reality, you just have a **resonance of mutual drift**.

**Anchors** pin your system to the real world:

- Actual business outcomes (revenue, churn, user satisfaction).
- Ground-truth datasets.
- Human spot-checks.

Anchors are:

- The easiest part of graph design to skip.
- The one part you **cannot afford** to skip.

***

## 7. Graph vs Workflow: What’s Actually Different?

People often say:

> “Isn’t this just workflows? DAGs, state machines, workflow engines — we’ve had those for decades.”

Half right, half wrong.

### Similarities

Both have:

- Nodes + edges + shared state + routing.
- Tools like Airflow, Prefect, Dagster, Temporal have orchestrated similar structures for years.
- Anthropic’s five patterns (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer) are execution graphs in all but name.

### The Real Difference: What Lives in a Node

**Traditional workflow:**

- Nodes = deterministic functions (Python, shell, SQL).
- Edges = hardcoded code (`if`, `switch`, `case`).
- Engineer maintains everything in code.
- Behavior is predictable: same input → same path.

**Graph with agents:**

- Nodes can be **full agents**:
  - Self-looping
  - Tool-using
  - Goal-understanding
  - Retrying on failure
- Edges can carry **dynamic routing rules**:
  - Decided by previous node output
  - Verification results
  - Even another model’s judgment

Anthropic’s distinction:

- **Workflow**: code fixes the steps.
- **Agent**: model can change the steps at runtime.
- **Graph**: container that can hold:
  - Workflow nodes (deterministic)
  - Agent nodes (model-driven)
  - Human nodes (approval, review)

So:

> **Graph engineering is not a replacement for workflows.  
> It’s a generalization.**  
> Workflow = fully deterministic special case of a graph.

Counterpoint (iii.dev):

> “The shape is the easy part, and it is disposable.  
> The load-bearing decision is what the loop or graph is made of, and what happens to it after it works.”

Meaning:

- Drawing a graph is not the achievement.
- What matters: replayability, observability, recoverability.
- You can redraw the shape anytime; engineering capability is what survives.

## 8. You’ve Been Drawing Graphs All Along

Evidence:

- **LangGraph** (Jan 2024): graph execution engine for agents; ~65M monthly downloads by mid-2026.
- Anthropic’s five patterns (Dec 2024): already drew graphs for common agent patterns.
- Claude Code’s subagent fan-out: one main agent spawning parallel sub-agents = a graph.
- State machines, DAG schedulers, task queues, knowledge graphs: CS has engineered graphs for decades.

What’s actually new?

> **The node went from “function” to “agent.”**

Before:

- Writing a workflow node = writing logic, error handling, retry policy by hand.

Now:

- A node can be: “research this problem”, “review this code” → model does the rest.

Nodes got cheap → graphs became worth drawing.

## 9. Build Your First Graph (Six Steps)

Start from last lecture’s maker–checker loop.  
Graph engineering splits that monolithic agent into **specialized nodes**, each with its own private prompt, context, tools, memory, and little loop. Nodes don’t share context; they hand off only through **shared state**.

### Step 1: Define the Shared State

At the graph level:

- Only **state** is shared.
- Each node has **private context**.

Example state:

```text
state = {
  "requirements": text,                # written by research node
  "code":         text,                # written by implement node
  "review":       "pass" | "fail",    # written by verify node
  "attempts":     number,              # +1 per failure (sum on concurrent writes)
}
```

You must decide:

- What fields exist.
- How concurrent writes merge (overwrite, append, sum).

This goes into `graph.md` when you design the graph.

***

### Step 2: List the Nodes – Each Node Is a Complete Agent

Each node:

- Takes shared state as input.
- Works in its **private context**.
- Writes results back to shared state.

Example nodes:

| Node       | Type   | Inside the Node (Private Loop)                              | Writes to Shared State |
|------------|--------|-------------------------------------------------------------|-------------------------|
| research   | agent  | search → read → summarize → re-search if not enough         | requirements            |
| implement  | agent  | write → test → fix → until it passes (max N retries)        | code                    |
| verify     | agent  | independent review + run tests (fresh context)              | review (pass/fail)      |
| merge      | code   | no loop; commit once checks pass                            | done                    |

Key point about **verify**:

- In a monolithic agent, “review” runs in the same context → agent reviews itself.
- In a graph, **verify must get a completely fresh context**:
  - It never sees implement’s reasoning.
  - Only sees code in shared state.
- That’s how “independent review” becomes real: **context isolation by design**.

***

### Step 3: Wire the Edges (Deterministic Spine)

Start simple:

```text
Start → research → implement → verify → merge → End
```

This is your base path when everything goes well.

***

### Step 4: Write the Routing Rules (Most Important Step)

The verify node doesn’t just go to merge. It connects to a decision:

| Current Node | Condition         | Next Node   |
|--------------|-------------------|-------------|
| verify       | review == pass    | merge       |
| verify       | review == fail    | implement   |

You can add more:

- If “not enough info” → back to research.
- If too many failed attempts → mark as blocked, notify human.

This makes “where do failures go back to” **explicit**, not hidden in an agent’s memory.

***

### Step 5: Attach a Checkpoint

Unlike a one-shot script, a graph:

- Persists state after every step.
- Can resume from checkpoint if the process dies.
- Can pause before merge for human approval.

Example:

```text
checkpoint = on(graph, every_step)   # save state after every step
graph.pause_before("merge")          # stop before merging, wait for approval
```

This gives you:

- Interrupt/resume for free.
- Human-in-the-loop at key points.

***

### Step 6: Run the Graph with an Entry Point

Example:

```text
run(graph, entry={"requirements": "fix the login page bug"}, thread="session-1")
```

- `thread` ID distinguishes runs.
- Checkpoints use it to resume the right session.

When done:

- Your `graph.md` diagram and the executable code should match one-to-one.
- If they don’t, either the diagram or the code is wrong.
- This is what “a graph puts the problem on paper” means.

## 11. Cold Water: A Graph Is Not a Silver Bullet

### Bucket 1: Fake Numbers

Claims like “+18% accuracy, −85% cost” from adopting graphs:

- Fact-checks show these numbers come from a **different domain** (chemical piping diagrams).
- Measured against different baselines.
- Paper never mentions “graph engineering.”

Always ask for the original source when you see such claims.

***

### Bucket 2: Shape Is Not the Load-Bearing Wall

As iii.dev argues:

- A loop is just a graph with one node.
- State machines and workflows have run for decades.
- People declaring “loops are dead” or “graphs are dead” usually haven’t read carefully.

What matters:

- Replayability
- Observability
- Recoverability

You can redraw a graph’s shape anytime.  
Engineering capability is what survives.

***

### Bucket 3: The Orchestration Tax (Addy Osmani)

Hard economics:

- **Starting an agent is cheap.**
- **Closing the loop on an agent is expensive.**

Launching an agent = a keystroke.  
But someone must:

- Check what came back.
- Reconcile it with what other agents touched.

That someone is **you**, and there is only one of you.

> “You are the GIL of your AI agents.  
> They can all run at once.  
> But when any of their work needs genuine understanding… that work has to acquire the lock.  
> There is one lock. You hold it.”

Meaning:

- A graph runs more agents in parallel.
- Your **judgment is serial**.
- **Review bandwidth is the ceiling.**
- Adding nodes optimizes the part that was never the bottleneck.

## 12. When You Actually Need a Graph

Not every task deserves a graph. Use these five criteria; aim for at least three:

1. **Task decomposes into independent work units**  
   Parts that don’t depend on each other and can run in parallel.

2. **There are branch or rollback paths**  
   - “Where do tests go back to?”  
   - “Where does insufficient info go back to?”  
   Worth declaring explicitly.

3. **Intermediate state is worth saving**  
   You can pause at checkpoints and resume, instead of restarting from zero.

4. **Results can be verified explicitly**  
   Every node has an automatically checkable definition of done.

5. **Coordination benefits > coordination costs**  
   Time saved by parallelism outweighs overhead of the graph and shared state.

Note:

- “Complex” ≠ “many steps”.
- A 20-step linear pipeline → probably just a workflow or script.
- A 5-node structure with real rollback, parallelism, approvals → likely needs a graph.

Deciding factor: **branches and rollbacks**, not sheer scale.

***

## Core Concepts

- **Graph Engineering**:  
  Organizing multiple agents, loops, tools, and evaluators into an explicit graph (nodes + edges + shared state + routing rules), making connections and paths designable, observable, and locally repairable.

- **Four stacked layers**:  
  Prompt → Context → Loop → Graph.  
  Each layer controls something different; later layers put earlier ones inside their nodes.

- **Four parts of a graph**:  
  Nodes (work units), edges (handoffs), shared state (common workspace), routing rules (where execution goes next).

- **Three structural failures of a single loop**:
  1. Goodhart (numbers up, business worse).
  2. Blindness upward (never asks “is this the right goal?”).
  3. Conflict (independent loops undermine each other).

- **Graph ≠ Workflow**:  
  Workflow nodes = deterministic functions; edges = hardcoded code.  
  Graph nodes can be full agents; edges can route dynamically.  
  Graph = generalization of workflow.

- **Anchors**:  
  Mechanisms that pin loops/graphs to reality (business outcomes, ground truth, human spot-checks).

- **Orchestration Tax**:  
  Starting agents is cheap; reviewing results is expensive. Your attention is the only serial resource.

***

## Key Takeaways

- Graph engineering **builds on top of** loop and harness engineering.  
  A loop can become a **node** in a graph.

- A graph turns **deferred decisions** into **up-front decisions**:
  - Loop: failure modes hidden inside.
  - Graph: failure modes on paper, readable and repairable.

- What’s inside the node decides graph vs workflow:
  - Functions → workflow.
  - Agents → graph.

- Before drawing a graph, answer:
  - Which loops feed which?
  - Who owns the targets?
  - Who can veto/roll back?
  - Which metrics may move, which must stay frozen?

- Don’t draw graphs for their own sake.  
  Use the five criteria; if fewer than three apply, you probably need a better workflow, not a graph.

- Your **review bandwidth is still the ceiling**.  
  More nodes ≠ more parallel judgment. You remain the serial bottleneck.

- Keep the counterargument in mind:  
  Shape is not the load-bearing wall.  
  Replayability, observability, recoverability are.
