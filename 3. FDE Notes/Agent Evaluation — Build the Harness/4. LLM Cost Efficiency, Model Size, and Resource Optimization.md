# LLM Cost and Resource Use

This course explains how to use LLMs without wasting money, hardware, or energy.

The main idea is:

> **Use the smallest model and the least amount of computing power that can still do the job well.**

## 1. Model Size and Cost

LLMs can be small, medium, or large.

| Model size | Strength | Cost and resource use |
|---|---|---|
| Small | Fast and affordable | Needs less memory and hardware |
| Medium | Good balance | Moderate cost and performance |
| Large | Best for complex tasks | Expensive and resource-heavy |

### Simple example

```text
Simple FAQ chatbot → Small model
Business assistant → Medium model
Complex legal research → Large model
```

A larger model may give better answers, but the improvement may not justify its extra cost.

## 2. Main Costs of an LLM

Running an LLM costs more than just calling the model.

### Compute cost

This is the cost of using CPUs, GPUs, or TPUs.

It applies to:

- Training.
- Fine-tuning.
- Generating answers.
- Running many users at the same time.

### Storage cost

Storage is needed for:

- The model.
- Training data.
- Checkpoints.
- Logs.
- Embeddings.
- Backups.

### Network cost

Moving data between servers or cloud regions can cost money.

```text
Data enters the system
       ↓
Model processes it
       ↓
Data leaves the system
```

Sending large amounts of data repeatedly can increase the bill.

### Idle cost

A server that stays active when nobody is using it still costs money.

## 3. Cloud and On-Premises Options

### Public cloud or API

You use a model hosted by another company.

**Advantages:**

- Low starting cost.
- Quick setup.
- No need to buy hardware.
- Easy to scale.
- Provider manages much of the system.

**Disadvantages:**

- Monthly or usage charges.
- Costs can grow with traffic.
- Less control over private data.
- Possible provider lock-in.
- Unexpected charges may appear.

### In-house deployment

Your company owns and runs the model.

**Advantages:**

- Better control over data.
- More privacy.
- More customization.
- Useful for healthcare, finance, and other sensitive work.
- No external API fee for every request.

**Disadvantages:**

- High hardware cost.
- High electricity cost.
- Requires skilled staff.
- Your team manages security and updates.
- Hardware can fail and needs maintenance.

| Need | Better option |
|---|---|
| Quick experiment | Public cloud or API |
| Small budget | Public model |
| Sensitive private data | In-house or private cloud |
| Large and steady workload | In-house may become cheaper over time |
| Unpredictable traffic | Cloud with auto-scaling |

## 4. Model Optimization

Optimization means making the model cheaper and faster while keeping acceptable quality.

### Pruning

Remove parts of the model that are not very useful.

```text
Large model
   ↓ remove unnecessary parts
Smaller and faster model
```

### Quantization

Use smaller number formats inside the model.

Benefits:

- Smaller model size.
- Lower memory use.
- Faster responses.
- Lower hardware cost.

### Knowledge distillation

Teach a smaller model to copy a larger model’s useful behavior.

```text
Large teacher model
        ↓
Small student model
```

### Transfer learning

Use an already trained model and adjust it for a new task.

This is cheaper than training from the beginning.

### Caching

Save answers to repeated questions.

```text
Same question → Return saved answer
```

This avoids unnecessary model calls.

### Batch processing

Process several requests together.

This improves resource usage for background jobs.

## 5. Fine-Tuning for Lower Cost

Fine-tuning changes an existing model for a specific task.

### Example

```text
General language model
          ↓
Company product data
          ↓
Company support model
```

Fine-tuning can improve accuracy without building a new model from zero.

### Cost-saving fine-tuning methods

- Use a smaller learning rate.
- Train only for the required number of rounds.
- Stop when the model stops improving.
- Use good, clean data.
- Reuse a pre-trained model.
- Use mixed-precision training.
- Tune settings automatically.
- Use only the data needed for the task.

## 6. Important Training Settings

### Learning rate

Controls how quickly the model changes during training.

- Too high: the model may learn badly.
- Too low: training may take too long.

### Batch size

Controls how many examples are processed together.

- Larger batch: better hardware use.
- Smaller batch: lower memory use.

### Number of training rounds

More rounds do not always mean better results.

Stop when improvement stops.

### Output length

Longer answers need more time and money.

```python
settings = {
    "max_new_tokens": 50,
    "temperature": 0.2
}
```

A shorter output limit can reduce cost for simple tasks.

## 7. Cloud Cost-Saving Options

### Spot instances

Use spare cloud capacity at a lower price.

Best for work that can stop and restart.

Examples:

- Model training.
- Experiments.
- Non-urgent batch work.

### Reserved instances

Commit to using resources for a longer period in exchange for a discount.

Best for workloads that run regularly.

### Serverless

Run the model only when needed.

```text
No request → No active processing cost
New request → Resource starts
```

### Auto-scaling

Automatically add or remove resources.

```text
Low traffic  → 1 server
High traffic → 5 servers
Traffic drops → 1 server
```

### Cost alerts

Set alerts when spending crosses a limit.

```text
Monthly budget: ₹50,000
Alert at: ₹40,000
```

## 8. Small, Medium, and Large Models

The course gives a general way to think about model sizes:

| Size | Approximate parameter range | Typical use |
|---|---:|---|
| Small | Below 10 billion | Simple classification and chatbots |
| Medium | About 10–70 billion | Enterprise applications |
| Large | Above 100 billion | Complex reasoning and creativity |

These ranges are only general guidance. Actual performance depends on the model design, data, and task.

## 9. Choosing the Right Model Size

Ask these questions:

1. What task must the model perform?
2. How accurate must it be?
3. How quickly must it respond?
4. How many users will use it?
5. Is the data private?
6. What hardware or cloud budget is available?
7. How often will the model be used?
8. Will traffic increase in the future?
9. Are there legal or compliance requirements?
10. Is energy use important?

### Example

A small company needs a support chatbot.

```text
Task: Answer common product questions
Traffic: Moderate
Privacy: Normal business data
Budget: Limited
Speed: Important
```

A small or medium public model may be the best choice.

A large in-house model would probably cost more than necessary.

## 10. Cost and Performance Trade-Off

```text
Larger model
   ↓
Better complex-task performance
   ↓
More hardware
   ↓
Higher cost
   ↓
More energy use
   ↓
Possible slower responses
```

More model size does not always create equal improvement.

This is called **diminishing returns**.

### Simple example

```text
Small model accuracy: 80%
Medium model accuracy: 88%
Large model accuracy: 90%
```

If the large model costs ten times more but improves accuracy by only 2%, it may not be worth using.

## 11. Scaling LLM Deployments

Scaling means supporting more requests without wasting resources.

### Vertical scaling

Use a stronger machine.

```text
One normal GPU → One stronger GPU
```

### Horizontal scaling

Add more machines.

```text
One server → Three servers → Ten servers
```

### Hybrid scaling

Use both methods.

```text
Private servers for normal traffic
Cloud servers during busy periods
```

### Problems during scaling

- Higher cost.
- More memory requirements.
- Network delays.
- Data synchronization.
- Difficult system management.
- Idle resources when traffic drops.

## 12. Distributed Training

Large models can be trained using several machines.

### Data parallelism

Each machine processes different data.

```text
Machine 1 → Data group A
Machine 2 → Data group B
Machine 3 → Data group C
```

### Model parallelism

The model itself is divided across machines.

```text
Machine 1 → Model part 1
Machine 2 → Model part 2
Machine 3 → Model part 3
```

### Pipeline parallelism

Different parts of the model process different stages of the work.

These methods can reduce training time but require fast networking and careful coordination.

## 13. Resource Management

Good resource management includes:

- Monitor CPU and GPU use.
- Avoid keeping unused servers active.
- Use automatic scaling.
- Share resources where possible.
- Keep data movement low.
- Use efficient containers.
- Plan for future growth.
- Test the system under heavy traffic.
- Keep backup resources available.

## 14. Practical Cost Analysis

When estimating the cost of a model, include:

```text
Compute
+ Storage
+ Data transfer
+ Training
+ Fine-tuning
+ Inference
+ Monitoring
+ Security
+ Maintenance
= Total cost
```

Do not compare models only by their API price.

A cheap model may become expensive if it:

- Needs many calls.
- Produces long answers.
- Requires more retries.
- Needs heavy post-processing.
- Performs poorly and requires human correction.

## 15. Simple Cost Example

```python
hours_used = 100
price_per_hour = 0.50
storage_cost = 20
network_cost = 10

total_cost = (hours_used * price_per_hour) + storage_cost + network_cost

print("Estimated cost:", total_cost)
```

Output:

```text
Estimated cost: 80.0
```

This is a simple estimate. Real cloud pricing may include many additional charges.

## 16. Best Practices

- Start with a small model.
- Test it on real examples.
- Increase model size only when needed.
- Measure quality, speed, and cost.
- Fine-tune instead of training from zero.
- Use pruning and quantization.
- Limit input and output length.
- Cache repeated results.
- Use spot resources for interruptible work.
- Use reserved plans for steady workloads.
- Use auto-scaling for changing traffic.
- Set budget alerts.
- Monitor cloud usage regularly.
- Keep the system portable to reduce provider lock-in.
- Check that cost savings do not damage accuracy or safety.

## 18. Final Memory Guide

- **Small model:** Cheap and fast.
- **Large model:** Powerful but expensive.
- **Compute:** Processing power used by the model.
- **Storage:** Space used for models and data.
- **Network cost:** Cost of moving data.
- **Pruning:** Remove unnecessary model parts.
- **Quantization:** Use smaller number formats.
- **Distillation:** Teach a small model from a large model.
- **Fine-tuning:** Adapt an existing model for a special task.
- **Auto-scaling:** Add or remove resources automatically.
- **Spot instance:** Cheaper temporary cloud resource.
- **Reserved instance:** Discount for long-term commitment.
- **Diminishing returns:** Bigger models may give only small extra improvements.

> **The goal is not to use the biggest model. The goal is to use the model that gives enough quality at the lowest practical cost and resource use.**
