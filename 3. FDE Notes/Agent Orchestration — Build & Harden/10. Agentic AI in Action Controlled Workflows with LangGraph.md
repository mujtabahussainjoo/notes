# LangGraph: Easy Summary

## What is LangGraph?

LangGraph is a way to build AI workflows with clear steps and decisions.

A normal AI program may call different prompts in a less organized way. LangGraph gives the process a clear structure:

```text
Start
  |
  v
Do one task
  |
  v
Check the result
  |
  v
Choose the next task
  |
  v
Finish
```

It is useful when an AI system must:

- Perform many steps.
- Remember information between steps.
- Choose different paths.
- Use tools or APIs.
- Handle errors.
- Show how it reached a result.

### Simple example

Imagine a customer-support assistant:

```text
Customer message
       |
       v
Understand the message
       |
       v
Is it a greeting, question, or complaint?
       |
       +---- Greeting ----> Send welcome message
       |
       +---- Question ----> Search help documents
       |
       +---- Complaint ---> Send to support team
```

LangGraph controls this process.

## The four main parts

LangGraph has four important parts.

| Part | Easy meaning | Example |
|---|---|---|
| StateGraph | The complete workflow container | The whole customer-support process |
| Node | One task or step | Search documents |
| Edge | A connection between steps | Move from search to answer |
| State | Shared information | User question, search results, final answer |

### Diagram

```text
                 StateGraph
        +---------------------------+
        |                           |
        |  Node A ---- Edge ----> Node B
        |    |                       |
        |    +------ State ----------+
        |                           |
        +---------------------------+
```

### 1. StateGraph

The StateGraph is the main container. It holds:

- Nodes.
- Edges.
- The state.
- The starting point.
- The ending point.

It controls the order in which steps run.

### 2. Nodes

A node is a normal function that performs one job.

Examples:

```python
def search_documents(state):
    # Search company documents
    return {"document_results": "Found policy information"}
```

Other possible nodes:

- Search the web.
- Read a document.
- Analyze data.
- Call an API.
- Check an order.
- Create a response.
- Save information.

A good node should usually have one clear responsibility.

### 3. Edges

Edges connect nodes and decide what happens next.

A normal edge is simple:

```text
Node A → Node B → Node C
```

A conditional edge makes a decision:

```text
If the question is about weather:
    go to weather node

If the question is about an order:
    go to order node

Otherwise:
    go to general-help node
```

### 4. State

State is the shared data that moves through the workflow.

It works like a shared notebook. Every node can read information from it and add new information.

Example:

```text
Start:
query = "What are the latest AI trends?"
web_results = empty
document_results = empty
final_answer = empty

After web search:
web_results = "New AI tools are becoming more popular"

After document search:
document_results = "The company is testing AI assistants"

After final step:
final_answer = "The main AI trends are..."
```

## Defining state with Python

`TypedDict` defines what information the workflow is allowed to store.

```python
from typing import TypedDict

class ResearchState(TypedDict):
    query: str
    web_results: str
    document_results: str
    final_answer: str
    step_count: int
```

This tells us:

- `query` stores the user’s question.
- `web_results` stores web findings.
- `document_results` stores company-document findings.
- `final_answer` stores the final response.
- `step_count` tracks progress.

Using clearly defined fields makes the workflow easier to understand and safer to maintain.

## How state changes

There are three common ways to update state.

### Replace

The new value replaces the old value.

```python
{"step_count": 3}
```

If the old value was `2`, it becomes `3`.

Useful for:

- Current step.
- Status.
- Progress.
- Final answer.

### Accumulate

New information is added to existing information.

```text
Old findings:
- Result A

New finding:
- Result B

Final findings:
- Result A
- Result B
```

Useful for:

- Search results.
- Messages.
- Notes.
- Multiple findings.

Example:

```python
from typing import Annotated
import operator

class ResearchState(TypedDict):
    findings: Annotated[list[str], operator.add]
```

The `operator.add` instruction tells LangGraph to add new list items instead of replacing the old list.

### Merge

Different pieces of information are combined.

```text
Old details:
name = Mujtaba
city = Kolkata

New details:
role = Developer

Merged details:
name = Mujtaba
city = Kolkata
role = Developer
```

Merge is useful for dictionaries or grouped information.

## Linear workflows

A linear workflow always follows the same path.

```text
Start
  |
  v
Fetch data
  |
  v
Clean data
  |
  v
Analyze data
  |
  v
Create report
  |
  v
End
```

Use a linear workflow when:

- The steps never change.
- Every input follows the same process.
- Simple and predictable behavior is preferred.
- Easy debugging is important.

### Example: monthly report

```text
Read sales data
      |
      v
Calculate totals
      |
      v
Create charts
      |
      v
Create PDF report
```

This is linear because the same steps happen every time.

## Conditional workflows

A conditional workflow chooses a path based on the input or state.

```text
User question
      |
      v
Classify question
      |
      +---- Current news? ----> Web search
      |
      +---- Company policy? --> Document search
      |
      +---- Both needed? -----> Web + document search
```

Use a conditional workflow when:

- Different questions need different actions.
- The system must make decisions.
- Some tasks need web search and others do not.
- You want to avoid unnecessary work.

### Simple routing function

```python
def decide_path(state: ResearchState) -> str:
    query = state["query"].lower()

    if "latest" in query or "current" in query:
        return "web_search"

    if "company" in query or "policy" in query:
        return "document_search"

    return "both"
```

This function checks the question and returns the name of the next node.

## Building a StateGraph

A basic LangGraph workflow looks like this:

```python
from typing import TypedDict
from langgraph.graph import StateGraph, END

class AgentState(TypedDict):
    user_input: str
    result: str

def input_node(state):
    return {
        "user_input": state["user_input"]
    }

def process_node(state):
    text = state["user_input"].lower()

    if "hello" in text or "hi" in text:
        answer = "Hello! How can I help you?"
    elif "weather" in text:
        answer = "I would check the weather service."
    else:
        answer = "I received your question."

    return {
        "result": answer
    }

def output_node(state):
    return {
        "result": state["result"]
    }

workflow = StateGraph(AgentState)

workflow.add_node("input", input_node)
workflow.add_node("process", process_node)
workflow.add_node("output", output_node)

workflow.set_entry_point("input")
workflow.add_edge("input", "process")
workflow.add_edge("process", "output")
workflow.add_edge("output", END)

app = workflow.compile()
```

Run the workflow:

```python
result = app.invoke({
    "user_input": "Hello",
    "result": ""
})

print(result["result"])
```

Output:

```text
Hello! How can I help you?
```

### What happens internally?

```text
Initial state
   |
   v
Input node reads the message
   |
   v
Process node decides what it means
   |
   v
Output node returns the final result
   |
   v
End
```

## Compilation

After defining the nodes and edges, the graph is compiled.

```python
app = workflow.compile()
```

Compilation changes the workflow design into something that can actually run.

Think of it like building a machine:

```text
Functions + connections = Blueprint
Compile = Build the machine
Invoke = Use the machine
```

Compilation also helps check whether:

- Nodes are connected.
- The starting point exists.
- The ending point exists.
- Conditional destinations are valid.
- The graph structure is complete.

## LLM-based routing

Instead of using simple keywords, an AI model can classify the user’s message.

For example, it can classify messages as:

- Greeting.
- Question.
- Command.
- Feedback.
- Unclear.

```text
User message
      |
      v
AI classifies the message
      |
      v
Router chooses a handler
      |
      +---- Greeting ----> Greeting handler
      |
      +---- Question ----> Question handler
      |
      +---- Command -----> Command handler
      |
      +---- Feedback ----> Feedback handler
      |
      +---- Unclear ------> Ask for clarification
```

### Example

```text
"Hi! Can you explain how neural networks work?"
```

Although the message starts with “Hi,” its main purpose is a question. An AI router can understand this and send it to the question handler.

This is better than checking only for the word “Hi.”

## Confidence-based routing

The AI router can also return a confidence score.

```text
Category: QUESTION
Confidence: 0.95
Reason: The user is asking for an explanation.
```

If the confidence is low, the system should ask the user to clarify instead of guessing.

```python
if confidence < 0.6:
    return "fallback"
```

This makes the system safer.

## Error handling

Real systems can fail because:

- An API is unavailable.
- The AI returns an unexpected answer.
- The user sends an empty message.
- A search returns no results.
- A required field is missing.

A node should handle these cases clearly.

```python
def safe_process(state):
    try:
        result = do_some_work(state)
        return {"result": result}
    except Exception:
        return {
            "result": "Sorry, I could not complete that request."
        }
```

The system should fail politely instead of crashing.

## Important best practices

1. Start with a simple linear workflow.
2. Add conditional paths only when needed.
3. Give every node one clear job.
4. Use meaningful node names.
5. Define state fields clearly.
6. Use typed state instead of random fields.
7. Test every possible route.
8. Handle empty, unclear, and unexpected input.
9. Keep decision logic easy to read.
10. Store useful reasoning and status information for debugging.
11. Do not assume that users always provide perfect input.
12. Show errors in a friendly way.
