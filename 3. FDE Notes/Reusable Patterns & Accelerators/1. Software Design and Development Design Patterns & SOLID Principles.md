# Design Patterns and SOLID Principles

## Main Idea

Good software design makes code:

- Easier to understand.
- Easier to test.
- Easier to change.
- Easier to reuse.
- Less likely to break when new features are added.

Two important tools help achieve this:

1. **Design patterns** – common plans for solving common programming problems.
2. **SOLID principles** – simple rules for organizing classes and code.

***

## 1. What Is a Design Pattern?

A design pattern is a **general plan**, not ready-made code.

Think of it like a house blueprint:

```text
Blueprint = General design
House     = Final solution made for a specific situation
```

The same blueprint can be changed to build different houses.  
In the same way, the same design pattern can be adapted to different software projects.

### Example

Suppose many applications need:

- User login.
- Shopping carts.
- Payment processing.
- Notifications.
- File saving.

Developers have solved similar problems many times. A design pattern gives you a proven way to approach them instead of starting from zero.

### Benefits

Design patterns:

- Save development time.
- Give developers a shared language.
- Make code easier to maintain.
- Encourage reusable solutions.
- Help teams communicate clearly.

Example:

> “Use an adapter here.”

A developer who knows the adapter pattern immediately understands that two incompatible parts need help working together.

### Important warning

Do not use a design pattern just because it exists.

Ask:

- Does this problem really need a pattern?
- Does the pattern fit this project?
- Does the programming language already provide a simpler solution?
- Will the pattern make the code more complicated?

A pattern is a tool, not a rule.

***

## 2. Three Main Types of Design Patterns

The original “Gang of Four” book described 23 patterns in three groups.

```text
Design Patterns
       │
 ┌─────┼─────┐
 │     │     │
Create Structure Behavior
objects objects  communication
```

### A. Creational patterns

These explain how to create objects.

### B. Structural patterns

These explain how to connect objects and classes.

### C. Behavioral patterns

These explain how objects communicate and share responsibilities.

***

# 3. Creational Patterns

Creational patterns control **when and how objects are created**.

## Factory Pattern

A factory creates the correct object for you.

### Real-world example

A restaurant kitchen receives an order:

```text
"Pizza"  → Create Pizza object
"Burger" → Create Burger object
"Salad"  → Create Salad object
```

The customer does not need to know how the food is prepared.

### Simple example

```python
class NotificationFactory:
    def create(self, notification_type):
        if notification_type == "email":
            return EmailNotification()
        if notification_type == "sms":
            return SMSNotification()
```

The rest of the program asks the factory for a notification instead of creating every object directly.

## Singleton Pattern

A singleton ensures that only one instance of an object exists.

### Example

A program may need only one:

- Configuration manager.
- Application logger.
- Database connection manager.

```python
class Logger:
    _instance = None

    @classmethod
    def get_instance(cls):
        if cls._instance is None:
            cls._instance = Logger()
        return cls._instance
```

### Warning

Singletons can create hidden shared state and make testing harder. Use them only when one shared object is truly needed.

## Prototype Pattern

Prototype creates a new object by copying an existing object.

### Example

Instead of building every product from the beginning:

```text
Original product
       ↓ copy
Similar product
```

This is useful when object creation is expensive or complicated.

# 4. Structural Patterns

Structural patterns explain how objects are combined into larger systems.

## Adapter Pattern

An adapter helps two incompatible parts work together.

### Real-world example

A travel plug adapter allows a device with one plug type to work in another country.

```text
Old interface → Adapter → New interface
```

### Software example

One weather service expects a city name:

```python
weather.get_by_city("Delhi")
```

Your application only has a postal code:

```python
weather.get_by_postal_code("110001")
```

An adapter converts the postal code into the format the old service expects.

## Facade Pattern

A facade gives a simple interface to a complicated system.

### Real-world example

A hotel receptionist hides the complexity of:

- Room booking.
- Housekeeping.
- Restaurant reservations.
- Payment.

You simply ask the receptionist for help.

```text
User → Simple Facade → Many complex services
```

### Software example

```python
class OrderFacade:
    def place_order(self, product):
        inventory.reserve(product)
        payment.charge()
        shipping.create_label()
        email.send_confirmation()
```

The customer-facing code calls one simple method instead of managing every service separately.

## Decorator Pattern

A decorator adds features to an object without changing its original class.

### Example

Start with a plain coffee:

```text
Coffee
```

Add features:

```text
Coffee
  + Milk
  + Sugar
  + Whipped cream
```

### Software example

```python
class Coffee:
    def cost(self):
        return 5

class MilkCoffee:
    def __init__(self, coffee):
        self.coffee = coffee

    def cost(self):
        return self.coffee.cost() + 2
```

The original coffee class remains unchanged.

## Bridge Pattern

The bridge pattern separates two parts so they can change independently.

### Example

A remote control and a television are separate:

```text
Remote control → Device
```

The same remote design can work with:

- Television.
- Music system.
- Projector.

This avoids creating a separate class for every combination of remote and device.

# 5. Behavioral Patterns

Behavioral patterns explain how objects communicate and divide work.

## Command Pattern

A command turns an action into an object.

### Example

A button may perform:

- Save.
- Print.
- Delete.
- Undo.

Instead of hardcoding every button, each action becomes a command.

```python
class SaveCommand:
    def execute(self):
        document.save()
```

This makes actions easier to store, repeat, queue, or undo.

## Mediator Pattern

A mediator helps objects communicate without directly depending on one another.

### Real-world example

An air traffic controller coordinates airplanes.

```text
Plane A ─┐
Plane B ─┼→ Air traffic controller
Plane C ─┘
```

The airplanes do not need to communicate directly with every other airplane.

## Iterator Pattern

An iterator lets you go through a collection without knowing how it is built.

```python
for product in products:
    print(product.name)
```

You do not need to know whether `products` is stored as:

- An array.
- A list.
- A database result.
- Another collection type.

## Chain of Responsibility

A request moves through a chain until one object handles it.

### Example

A support request moves through:

```text
Frontline agent → Team leader → Manager → Specialist
```

Each person decides:

- Can I handle it?
- If not, pass it to the next person.

## Memento Pattern

A memento saves an earlier state so it can be restored later.

### Example

The undo button in a text editor:

```text
Current document
       ↓ save
Previous version
       ↓ restore
Undo
```

## Observer Pattern

Observers are notified when something changes.

### Example

When you subscribe to a video channel:

```text
New video published
        ↓
All subscribers receive notification
```

This is commonly used for:

- Notifications.
- Event systems.
- User interface updates.
- Stock price changes.

## State Pattern

An object behaves differently depending on its current state.

### Example

A game character may be:

```text
Healthy → Injured → Defeated
```

Each state allows different actions.

This is usually cleaner than using many large `if-else` statements.

## Strategy Pattern

The strategy pattern lets you choose between different methods of solving a problem.

### Example

A delivery system may choose:

```text
Standard delivery
Express delivery
Same-day delivery
```

```python
class Order:
    def __init__(self, delivery_strategy):
        self.delivery_strategy = delivery_strategy

    def deliver(self):
        return self.delivery_strategy.calculate_cost()
```

The order does not need to know how every delivery method works.

## Template Method Pattern

A parent class defines the general steps, while child classes fill in specific details.

### Example

Logging always follows:

```text
Prepare message
Write message
Close file
```

But different loggers may write to:

- A text file.
- A database.
- A cloud service.

## Visitor Pattern

A visitor adds an operation to existing objects without heavily changing those objects.

### Example

A game may have:

- Player objects.
- Enemy objects.
- Treasure objects.

A scoring visitor can calculate points for each without putting all scoring logic inside every class.

## Null Object Pattern

Instead of checking repeatedly for `null`, use an object that safely does nothing.

### Example

```python
class EmptyLogger:
    def log(self, message):
        pass
```

The program can call `log()` without repeatedly checking whether a logger exists.

# 6. SOLID Principles

SOLID is a memory word for five design rules.

```text
S = Single Responsibility
O = Open/Closed
L = Liskov Substitution
I = Interface Segregation
D = Dependency Inversion
```

## S — Single Responsibility Principle

A class should have **one main job**.

### Bad example

```python
class Order:
    def calculate_total(self):
        pass

    def save_to_database(self):
        pass

    def send_email(self):
        pass
```

This class is doing three jobs:

- Calculating.
- Saving.
- Sending email.

### Better design

```python
class Order:
    def calculate_total(self):
        pass

class OrderRepository:
    def save(self, order):
        pass

class EmailService:
    def send_confirmation(self, order):
        pass
```

### Easy memory rule

> One class, one main reason to change.

Benefits:

- Easier testing.
- Easier debugging.
- Less code confusion.
- Smaller changes.

***

## O — Open/Closed Principle

Software should be:

- Open for adding new behavior.
- Closed for changing working code unnecessarily.

### Example

Instead of modifying one large payment class every time a new payment method is added, create separate payment methods.

```python
class PaymentMethod:
    def pay(self, amount):
        raise NotImplementedError

class CardPayment(PaymentMethod):
    def pay(self, amount):
        print("Paid by card")

class WalletPayment(PaymentMethod):
    def pay(self, amount):
        print("Paid by wallet")
```

To add a new payment method, create another class instead of changing old code.

***

## L — Liskov Substitution Principle

A child class should work wherever its parent class is expected.

### Simple example

If a program expects an `Animal` that can make a sound, every child animal should behave correctly when used as an `Animal`.

A child class should not:

- Break the parent’s promises.
- Remove expected behavior.
- Produce surprising results.

### Easy memory rule

> A child should be a safe replacement for its parent.

***

## I — Interface Segregation Principle

Do not force a class to use functions it does not need.

### Bad example

```python
class Machine:
    def print(self):
        pass

    def scan(self):
        pass

    def fax(self):
        pass
```

A simple printer may be forced to implement scanning and faxing even though it cannot do those things.

### Better design

```python
class Printer:
    def print(self):
        pass

class Scanner:
    def scan(self):
        pass

class FaxMachine:
    def fax(self):
        pass
```

### Easy memory rule

> Give each class only the controls it actually needs.

***

## D — Dependency Inversion Principle

High-level code should not depend directly on low-level details.

Instead, both should depend on a general interface.

### Bad example

```python
class Report:
    def __init__(self):
        self.logger = FileLogger()
```

The report is tightly connected to one specific logger.

### Better example

```python
class Report:
    def __init__(self, logger):
        self.logger = logger

    def generate(self):
        self.logger.log("Report created")
```

Now the report can use:

```python
Report(FileLogger())
Report(DatabaseLogger())
Report(CloudLogger())
```

### Easy memory rule

> Depend on an agreement, not on one specific tool.

Benefits:

- Easier testing.
- Easier replacement of services.
- Less tight connection between classes.
- More reusable code.

# 7. Important Software Practices

## KISS: Keep It Simple

Do not make a solution more complicated than necessary.

```text
Simple solution → Easier to understand
Complex solution → More places for errors
```

Before using a pattern, ask whether a simple function or class would be enough.

## DRY: Don’t Repeat Yourself

Do not copy the same logic into many places.

### Bad example

```python
# In three different files
total = price + tax
```

### Better example

```python
def calculate_total(price, tax):
    return price + tax
```

Now the calculation has one shared location.

## Separation of Concerns

Keep different responsibilities separate.

```text
User interface
      ↓
Business logic
      ↓
Database
```

For example:

- The user interface displays information.
- Business logic makes decisions.
- Database code saves and retrieves data.

## Composition Over Inheritance

Composition means building a class by giving it other objects to use.

```python
class Car:
    def __init__(self, engine):
        self.engine = engine
```

The car uses an engine instead of inheriting all engine behavior.

Composition is often easier to change than a deep inheritance tree.

## Write Pseudocode First

Before writing real code:

1. Understand the problem.
2. List the steps.
3. Write the solution in plain language.
4. Discuss it with teammates.
5. Then write code.

Example:

```text
Get order
Check payment
Check stock
Create shipment
Send confirmation
```

## Document Decisions

Record:

- Why a design was chosen.
- Which pattern was used.
- What limitations exist.
- Which requirements were considered.

Documentation helps future developers understand the system.

## Check Functional and Non-Functional Requirements

### Functional requirements

What the program must do.

Examples:

- Calculate an invoice.
- Allow users to log in.
- Process a payment.

### Non-functional requirements

How the program should work.

Examples:

- Be fast.
- Be secure.
- Support many users.
- Follow privacy laws.
- Stay within budget.

Both types matter.

# 9. Design Patterns vs SOLID

| Design patterns | SOLID principles |
|---|---|
| Reusable plans for common problems | General rules for organizing code |
| Solve particular design situations | Guide the whole design |
| Examples: Factory, Adapter, Observer | Examples: SRP, OCP, DIP |
| More specific | More general |
| Can be used when appropriate | Should guide everyday design decisions |

They work together:

```text
SOLID principles → Good structure
Design patterns  → Proven solutions inside that structure
```

***

# 10. Final Memory Guide

### Design patterns

- **Creational**: How are objects created?
- **Structural**: How are objects connected?
- **Behavioral**: How do objects communicate?

### SOLID

- **S**: One class, one main job.
- **O**: Add new behavior without breaking old code.
- **L**: Child classes should safely replace parent classes.
- **I**: Do not force classes to use unnecessary functions.
- **D**: Depend on general interfaces, not specific tools.

### Best practices

- Keep code simple.
- Do not repeat logic.
- Separate different responsibilities.
- Prefer composition when suitable.
- Write pseudocode first.
- Document decisions.
- Test and review the design.
- Use patterns only when they solve a real problem.

> **Good software design is not about using as many patterns as possible. It is about making the code easy to understand, easy to change, and safe to reuse.**
