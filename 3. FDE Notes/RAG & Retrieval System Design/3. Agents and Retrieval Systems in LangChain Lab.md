# Agents and Retrieval Systems in LangChain Lab

## 1. What this lab teaches

This lab explains how to build applications that combine:

- **Agents**: LLM-powered systems that decide what action to take.
- **Tools**: Functions that let an agent use external systems.
- **Retrieval**: Finding useful information from documents or databases.
- **RAG**: Giving retrieved information to an LLM so it can generate a grounded answer.

In simple terms:

> An agent decides what to do, and a retrieval system finds the information needed to do it.

LangChain provides reusable components for loaders, splitters, embeddings, vector stores, retrievers, models, and tools. [web:1][web:6]

## 2. What is an agent?

An agent uses a language model to decide which steps are required to complete a task.

A normal LLM only generates text. An agent can also:

- Call a search tool.
- Query a database.
- Read a document.
- Call an API.
- Perform calculations.
- Use the result of one tool call to decide the next step.

### Agent loop

An agent usually follows this loop:

1. Receive the user's question.
2. Decide whether a tool is needed.
3. Select and call a tool.
4. Read the tool result.
5. Decide whether more work is required.
6. Return the final answer.

This is commonly described as a **ReAct-style loop**: reasoning, action, and observation. [web:6]

## 3. What are tools?

A tool is a normal function that an agent is allowed to call.

Examples:

- `search_docs(query)`
- `get_product_price(sku)`
- `query_orders(customer_id)`
- `calculate_tax(amount, country)`
- `fetch_url(url)`

In LangChain, the `@tool` decorator can convert a Python function into an agent tool. The function name and description help the model understand when to use it. [web:6]

```python
from langchain_core.tools import tool

@tool
def get_shipping_status(order_id: str) -> str:
    """Return the shipping status for an order."""
    return f"Shipping status for {order_id}: dispatched"
```

A good tool should have:

- A clear name.
- A precise description.
- Typed input parameters.
- A predictable return value.
- Error handling.
- Permission and security checks.

## 4. What is retrieval?

Retrieval means finding relevant information from an external knowledge source at query time.

LLMs have two important limitations:

- They cannot read an unlimited amount of data in one request.
- Their built-in knowledge may be old or may not include your private data.

Retrieval solves this by searching your documents, database, or another source and returning relevant content. [web:1]

Example:

```text
User question:
What is the return policy for damaged products?

Retriever result:
Damaged products can be returned within 30 days with proof of purchase.

LLM answer:
You can return a damaged product within 30 days if you have proof of purchase.
```

## 5. What is RAG?

**Retrieval-Augmented Generation**, or RAG, combines search with text generation.

The general process is:

```text
Documents
   ↓
Load documents
   ↓
Split into chunks
   ↓
Create embeddings
   ↓
Store vectors
   ↓
Search for relevant chunks
   ↓
Send chunks to the LLM
   ↓
Generate an answer
```

RAG helps an application produce answers that are more relevant to a private or changing knowledge base. It does not automatically guarantee correctness; retrieval quality and prompt design still matter.

## 6. Main retrieval components

### 6.1 Document loaders

Document loaders import data from external sources and convert it into LangChain `Document` objects.

A `Document` generally contains:

```python
Document(
    page_content="The product can be returned within 30 days.",
    metadata={"source": "return-policy.pdf", "page": 2}
)
```

Possible sources include:

- PDF files.
- Text and Markdown files.
- Web pages.
- Google Drive.
- Slack.
- Notion.
- SQL databases.
- APIs.

### 6.2 Text splitters

Large documents are divided into smaller chunks before indexing.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
)

chunks = splitter.split_documents(documents)
```

- `chunk_size` controls the approximate chunk length.
- `chunk_overlap` repeats some text between neighboring chunks.
- Overlap helps preserve context across chunk boundaries.

Poor chunking can cause incomplete retrieval. Start with a simple splitter, then test chunk size and overlap using real questions.

### 6.3 Embeddings

An embedding model converts text into a vector of numbers.

Texts with similar meaning should have vectors that are close together. This allows semantic search.

```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
query_vector = embeddings.embed_query("How long can I return a product?")
```

The same embedding model should normally be used for both indexed documents and user queries.

### 6.4 Vector stores

A vector store saves document embeddings and supports similarity searches.

Common choices include:

- FAISS for local experiments.
- Elasticsearch for production search and vector retrieval.
- MongoDB Atlas for applications already using MongoDB.
- Pinecone for managed vector search.
- PostgreSQL with a vector extension.

```python
from langchain_community.vectorstores import FAISS

vector_store = FAISS.from_documents(chunks, embeddings)
```

### 6.5 Retrievers

A retriever accepts a query and returns relevant `Document` objects.

```python
retriever = vector_store.as_retriever(
    search_kwargs={"k": 3}
)

docs = retriever.invoke("What is the return policy?")
```

The retriever hides the details of the underlying search system. This makes it easier to replace one vector store with another. [web:1][web:6]

## 7. Three RAG architectures

| Architecture | How it works | Advantages | Limitations | Suitable for |
|---|---|---|---|---|
| 2-Step RAG | Always retrieve first, then generate | Simple, fast, predictable | Less flexible | FAQ and documentation bots |
| Agentic RAG | Agent decides when and how to retrieve | Flexible and supports multiple tools | More complex and less predictable | Research assistants |
| Hybrid RAG | Adds query rewriting and validation | Better quality control | More processing and latency | Production domain assistants |

### 7.1 2-Step RAG

```text
Question → Retrieve documents → Generate answer
```

Use this when every question should be answered from the same knowledge base.

### 7.2 Agentic RAG

```text
Question → Agent decides
              ├─ Answer directly
              ├─ Search documentation
              ├─ Query a database
              └─ Call another tool
```

The agent only needs access to one or more tools that can fetch external knowledge. [web:1]

### 7.3 Hybrid RAG

A hybrid workflow may:

1. Rewrite an unclear question.
2. Retrieve documents.
3. Check whether the documents are relevant.
4. Search again if necessary.
5. Generate an answer.
6. Check whether the answer is supported by the retrieved context.

This is useful when accuracy is more important than minimum latency.

## 8. Simple agent example

The current LangChain style uses `create_agent` to combine a model, tools, and a system prompt. [web:1]

```python
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def search_catalog(query: str) -> str:
    """Search the product catalog for matching products."""
    return "Found: Magento-compatible payment extension"

agent = create_agent(
    model="your-model-name",
    tools=[search_catalog],
    system_prompt=(
        "Use search_catalog when the user asks about products. "
        "Do not invent catalog information."
    ),
)

response = agent.invoke({
    "messages": [
        {"role": "user", "content": "Find a payment extension."}
    ]
})
```

The agent can decide whether it should call `search_catalog` before answering.

## 9. Retrieval agent template

The LangChain retrieval-agent template demonstrates a retrieval chat bot with two graphs:

- **Index graph**: Adds documents to a user-specific index.
- **Retrieval graph**: Searches documents using the conversation and generates an answer.

The template supports retriever providers such as Elasticsearch, MongoDB Atlas, and Pinecone. It also supports configurable models, embeddings, search parameters, prompts, and additional tools. [web:4]

The important design idea is user isolation:

```text
Document → user_id = user-123 → searchable only for user-123
```

This prevents one user's documents from being returned to another user.

## 10. Agentic RAG vs normal RAG

| Feature | Normal 2-Step RAG | Agentic RAG |
|---|---|---|
| Retrieval | Always happens | Agent decides |
| Number of searches | Usually fixed | May vary |
| Latency | More predictable | Variable |
| Tool usage | Usually one retrieval pipeline | Multiple tools possible |
| Implementation | Easier | More complex |
| Best use | Stable FAQ or docs | Multi-step research or operations |

## 11. Common problems

### Wrong documents are retrieved

Possible causes:

- Chunks are too large or too small.
- The query is vague.
- The embedding model is unsuitable.
- The `k` value is too low.
- Metadata filters are missing.

Possible improvements:

- Add query rewriting.
- Use hybrid keyword plus vector search.
- Add metadata filters.
- Rerank retrieved documents.
- Evaluate retrieval separately from answer generation.

### The answer contains unsupported claims

Use a prompt such as:

```text
Answer only from the supplied context.
If the context does not contain the answer, say that the information is unavailable.
Do not invent details.
```

Also show source metadata and test groundedness.

### The agent calls tools unnecessarily

Improve the tool descriptions and system prompt. Define clear rules for when a tool must or must not be used.

### Sensitive documents are exposed

Apply authorization before retrieval, not only after generation. Filter by tenant, user, role, store, or document permissions before returning documents to the LLM.

## 12. Practical project structure

```text
app/
├── agents/
│   ├── product_agent.py
│   └── prompts.py
├── retrieval/
│   ├── loaders.py
│   ├── chunking.py
│   ├── embeddings.py
│   ├── vector_store.py
│   └── retriever.py
├── tools/
│   ├── catalog.py
│   └── orders.py
├── evaluation/
│   └── test_questions.json
└── main.py
```

Keep ingestion separate from query-time retrieval. Index documents asynchronously or on a schedule; do not rebuild the complete index for every user question.

## 13. Suggested lab exercise

Build a product-support assistant:

1. Load product manuals and return-policy documents.
2. Split them into chunks.
3. Create embeddings.
4. Store the chunks in FAISS or Elasticsearch.
5. Create a retriever that returns the top three chunks.
6. Build a 2-Step RAG chain.
7. Add a product-search tool.
8. Convert the chain into an agentic RAG assistant.
9. Add a `customer_id` or `store_id` metadata filter.
10. Test the system with questions that are both answerable and unanswerable.

Example questions:

- “Can I return a damaged item?”
- “Which payment methods are supported?”
- “Find products compatible with Magento 2.”
- “What is the policy for a product not mentioned in the documents?”

## 14. Key takeaways

- An agent chooses actions; tools perform actions.
- Retrieval finds relevant external information.
- RAG gives that information to an LLM for answer generation.
- Loaders, splitters, embeddings, vector stores, and retrievers are the main retrieval building blocks.
- 2-Step RAG is predictable; Agentic RAG is flexible; Hybrid RAG adds validation.
- Use metadata filters for tenant and user isolation.
- Evaluate retrieval quality and answer quality separately.
- For production systems, add logging, retries, access control, tracing, and cost monitoring.
