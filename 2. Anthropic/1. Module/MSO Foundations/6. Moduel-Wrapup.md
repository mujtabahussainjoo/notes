Not necessarily, the model samples each next token from a probability distribution, so wording can vary even when both answers are correct. [ibm](https://www.ibm.com/think/topics/zero-shot-prompting)

### Question 3  
**Correct answer: B**  
Adds token cost on every call for little or no gain. [ibm](https://www.ibm.com/think/topics/zero-shot-vs-few-shot-prompting)

**Why:**  
If zero-shot already gives the right answer for a simple, well-specified task, adding three examples:
- Increases the number of tokens in every request (higher cost).
- Usually does not improve accuracy much, because the task is already clear.  
Best practice: add examples only when you need them to fix structure or edge cases. [ibm](https://www.ibm.com/think/topics/zero-shot-vs-few-shot-prompting)

### Question 4  
**Correct answer: C**  
Batch submission with polling. [learnprompting](https://learnprompting.org/docs/basics/few_shot)

**Why:**  
For thousands of offline inputs with no user waiting:
- **Batch API** lets you send many requests together.
- It can take longer (up to hours), but costs less per token.

## Exercise: Predict the Behavior

### Scenario 1  
**Correct answer: A**  

At low temperature, the model concentrates probability on the most likely tokens, so repeated runs return the same label far more consistently, though never with guaranteed determinism, even at temperature 0. At high temperature, the distribution spreads out, so wording and even the chosen label can vary. For a classifier you want the low-temperature, repeatable behavior. [ibm](https://www.ibm.com/think/topics/zero-shot-prompting)

**Why:**  
- **Temperature** controls randomness.
- Low temperature → more focused on top choices → more consistent outputs.
- High temperature → more spread-out choices → more varied outputs.
- Even at temperature 0, outputs are not strictly guaranteed to be identical every time. [ibm](https://www.ibm.com/think/topics/zero-shot-prompting)

***

### Scenario 2  
**Correct answer: B**  

Adding two or three correct input-output examples shows the model the exact structure to match, which usually fixes a structure problem that more instruction text did not. The cost is extra tokens on every call, so add the fewest examples that make the output reliable. [ibm](https://www.ibm.com/think/topics/zero-shot-vs-few-shot-prompting)

**Why:**  
- **Zero-shot** = only instructions.
- **Multi-shot** = instructions + examples.
- When the structure keeps coming wrong, examples often fix it faster than longer instructions.
- Trade-off: more tokens (cost) per call. [ibm](https://www.ibm.com/think/topics/zero-shot-vs-few-shot-prompting)

***

### Scenario 3  
**Correct answer: C**  

The batch pattern fits: submit the requests in a batch and poll for completion, accepting longer latency for a lower per-token cost. A synchronous loop would hit rate limits and tie up the application, and streaming buys nothing because no user is watching. [learnprompting](https://learnprompting.org/docs/basics/few_shot)

**Why:**  
- 50,000 documents overnight → huge volume, no user waiting.
- **Batch API** is designed for this: lower cost, higher latency.
- Synchronous or streaming would be slower, more expensive, and risk rate limits. [learnprompting](https://learnprompting.org/docs/basics/few_shot)

### Scenario 4  
**Correct answer: B**  

The context window is a fixed token budget; as history and tool results accumulate it fills. An input that is already oversized is rejected with an error before generation, while a request that fits on input but reaches the ceiling mid-generation comes back with truncated output and a `model_context_window_exceeded` stop reason. The symptom is a session that ran fine in testing failing once inputs grow, which is why the application must trim or summarize history. [parloa](https://www.parloa.com/knowledge-hub/zero-shot-vs-few-shot/)

**Why:**  
- **Context window** = maximum tokens the model can see in one request.
- As conversation history grows, you can:
  - Get an error if the input is too big before generation starts.
  - Get truncated output if it exceeds the limit while generating.
- The app must manage history (trim, summarize, drop old turns) to stay within this fixed budget. [parloa](https://www.parloa.com/knowledge-hub/zero-shot-vs-few-shot/)

## Quick Recap in Plain Words

1. **Tokens** = the unit of text the model reads, writes, and charges for. Think in tokens, not words. [parloa](https://www.parloa.com/knowledge-hub/zero-shot-vs-few-shot/)
2. **Context window** = a fixed token budget for one request. Too big → error or cut-off answer. You must manage conversation history. [parloa](https://www.parloa.com/knowledge-hub/zero-shot-vs-few-shot/)
3. **Sampling** = the model uses randomness, so same prompt can give different answers. Testing on exact text is unreliable. [ibm](https://www.ibm.com/think/topics/zero-shot-prompting)
4. **Model choice vs reasoning mode** = different controls. Pick the smallest model and simplest mode that pass your tests, then add only if needed. [ibm](https://www.ibm.com/think/topics/few-shot-prompting)
5. **How you call Claude** = usually via SDK over REST API. Choose sync, streaming, async, or batch based on:
   - Is a user waiting?
   - Is it a real-time or bulk offline job? [learnprompting](https://learnprompting.org/docs/basics/few_shot)
