LLMs like Claude work with **tokens** inside a fixed **context window**, and they generate text using **sampling**, which makes outputs **non‑deterministic** (not exactly repeatable). Understanding these four ideas explains why costs, limits, and test strategies look the way they do. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

***

## Tokens: the basic unit

- Claude doesn’t see “characters” or “words”; it sees **tokens**, small chunks of text. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)
- Everything counts in tokens: your system prompt, user messages, conversation history, tool definitions, tool results, and Claude’s reply. Tokens are the unit for both **pricing** and **context budget**. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Different models can break text into tokens slightly differently, so “X characters per token” is only an approximation; for serious work you should check how many tokens your typical inputs actually use at build time. [platform.claude](https://platform.claude.com/docs/en/about-claude/glossary)

**Easy example:**  
Think of tokens as **mobile data MBs**, not individual letters. Your plan (model) bills and limits in MBs (tokens). Whether a message is 100 or 120 characters doesn’t matter directly; what matters is how many MBs (tokens) it consumes.

***

## Context window: a fixed token budget

- The **context window** is the maximum number of tokens a model can handle in one request; it includes system prompt, whole conversation so far, documents you add, tool outputs, and the model’s reply itself. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)
- If your **input alone** is larger than the window, the API rejects the request before generation with a “prompt too long” style error. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)
- If the input fits, but during generation the sum of input + output hits the limit, Claude stops and returns what it has so far with a `model_context_window_exceeded` stop reason instead of an exception. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)
- In real apps, long chats and large documents fill this window fast, so you must **trim or summarize** older history before each call to keep the session alive. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

**Easy example:**  
Imagine a **whiteboard** with limited space. You write instructions, examples, and notes (input), then Claude writes its answer on the same board (output). When the board is full, Claude must stop; it cannot write more until you erase or summarize some content.

***

## Sampling: why answers can differ

- At each step, Claude doesn’t pick one fixed next token; it creates a **probability distribution** over possible next tokens, then **samples** one of them. [platform.claude](https://platform.claude.com/docs/en/about-claude/glossary)
- **Temperature** and similar parameters (when allowed) control how “spread out” this distribution is:  
  - Low temperature → more weight on the most likely tokens → more repeatable, safer outputs.  
  - High temperature → more spread → more variety and creativity, but more randomness. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)
- Because of sampling, running **the same prompt twice** can produce different wording, even when both answers are correct. [platform.claude](https://platform.claude.com/docs/en/about-claude/glossary)
- On newer Claude models (for example Sonnet 5 and some others), non‑default values for `temperature`, `top_p`, or `top_k` are not accepted; trying to set them returns a 400 error, so you steer behavior mainly via **prompting**, not sampling knobs. [platform.claude](https://platform.claude.com/docs/en/models/sonnet-5/whats-new-sonnet-5)
- Even where temperature is supported, setting it to 0 only makes outputs **more repeatable**, not perfectly identical every time. [platform.claude](https://platform.claude.com/docs/en/about-claude/glossary)

**Easy example:**  
Think of a **storyteller** with a script outline. You say, “Tell me a story about a cat and a dog.” The outline keeps the story consistent, but the storyteller can choose slightly different sentences each telling. Turning temperature down is like telling them “stick very closely to your usual wording,” but they may still change small phrases.

## Non-determinism: what it means for tests and evals

- **Non‑determinism** means that **identical inputs do not guarantee identical outputs**; the model may phrase things differently each time while still being correct. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)
- This breaks traditional tests that assert **exact strings**, because even a perfect answer may use different words. Instead, you assert on **properties**:  
  - A required field exists in the JSON.  
  - A numeric value is within an allowed range.  
  - The output parses as valid JSON or matches a schema. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)
- When you need to judge **meaning** instead of structure (for example, “Is this reasoning correct?” or “Is this answer helpful?”), you run **evals** using a model to grade other model outputs, which the course treats as the standard way to know if a feature behaves correctly. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)

**Easy example:**  
If Claude generates invoices, you don’t test “is this exact text identical?”; you test “does every invoice have customer name, date, items, and correct totals?”. The exact sentence like “Thank you for your purchase” can vary; the **structure and values** must not.

## One simple “all together” example

Suppose you build a **question–answering feature** for a help desk:

1. The user’s question, some previous messages, and a few knowledge base snippets are converted into **tokens**, which all count toward your cost and your context window. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)
2. All those tokens share the **context window** with Claude’s upcoming answer; if you stuff too much history or too many docs, the request may fail or be cut short. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)
3. Claude answers using **sampling**, so two runs of the same ticket may differ slightly in wording, especially at higher temperature. [platform.claude](https://platform.claude.com/docs/en/about-claude/glossary)
4. Because of this **non‑determinism**, your tests don’t check for one exact sentence; they check whether:  
   - The answer mentions the right policy.  
   - The JSON response has all required keys.  
   - The tone stays polite and within your rules. [dev](https://dev.to/yashnigam/claude-certified-developer-foundations-certification-overview-4n07)

This is exactly the behavior the module wants you to internalize: think in tokens, respect the context window, expect sampled (slightly variable) wording, and design tests and evals for properties instead of exact strings. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## Simple diagram (mental model)

```text
                1) INPUT → TOKENS → CONTEXT WINDOW

        Your system prompt
        + user messages
        + history
        + tools & docs
        ----------------------------
                 ↓ tokenized

        ┌───────────────────────────────┐
        │  Context window (fixed size) │  ← measured in tokens
        └───────────────────────────────┘
                 ↑ everything must fit

                2) MODEL GENERATION → SAMPLING

        For each next token:
          - Model computes probabilities
          - Samples one token (not a fixed choice)
          - Repeats until stop condition

                3) OUTPUT

        Output tokens (also counted in the window)
        → detokenized into text you see

Non-determinism:
  Same input
      ↓
  Sampling chooses slightly different tokens
      ↓
  Different, but still valid, answers
```
