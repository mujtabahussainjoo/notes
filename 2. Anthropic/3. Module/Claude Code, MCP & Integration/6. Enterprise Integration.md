### Summary: Connecting Claude to Enterprise Systems and Secure Authentication

#### Introduction
This summary discusses how to connect Claude Code to enterprise systems, focusing on secure authentication practices. It explains the differences between building a prototype and preparing for production, covering authentication patterns, secret management, and compliance requirements.

### Key Points

1. **Understanding Enterprise Integration**
   - **Prototype vs. Production:** A prototype shows that a connection works, but when working in a regulated environment (like finance or healthcare), you must answer more questions:
     - Who is the model acting as, and is that identity logged?
     - What data can it access, and where does that data go?
     - Can an administrator lock the configuration to prevent unauthorized changes?
     - Can access be logged for compliance audits?

   **Example:** In a prototype, you might connect to a database without much thought, but in production, you need to ensure that the connection is secure and complies with regulations.

2. **Authentication Patterns by Service Type**
   - **Remote Services with User Identity:** Use **OAuth**. This method involves a user signing in through a web browser, and after approval, a token is issued for access.
   - **Remote Services with Service Identity:** Use **API keys** stored in environment variables. This method ensures that sensitive keys are not included in configuration files.
   - **Local Services:** Use file system permissions. No secret is needed for local services, as access is controlled by permissions.

   **Example:** If you connect to a cloud service like GitHub, you typically use OAuth, while for an internal API, you might use an API key stored securely.

3. **Managing Secrets After Authentication**
   - **Separation of Secrets:** Never keep sensitive information like API keys in configuration files. Store them in environment variables or use a secret manager to keep them safe.
   - **Rotation of Secrets:** Regularly change your credentials to enhance security. If a key is leaked, it should be replaced immediately.

   **Example:** Instead of writing an API key directly in a config file, you would reference it like this:
   ```json
   {
     "headers": {
       "Authorization": "Bearer ${API_KEY}"
     }
   }
   ```
   This way, the key remains secure and is not exposed in version control.

4. **Enterprise Requirements for Authentication**
   - **Audit Logs:** Use hooks to log every action taken by the system. This is crucial for compliance reviews.
   - **Data Residency:** Ensure that data is processed in a specific location to meet regulatory requirements.

   **Example:** If a company has rules about where data can be processed, you would set up the server so that it only operates within the approved region.

5. **Using OAuth: A Concrete Example**
   - The **GitHub MCP server** uses OAuth for user authentication. You must register the correct redirect URIs for production to work, as these are specific to each environment.

   **Example of OAuth Failure:**
   - If you register your OAuth app for staging but forget to add the production URI, sign-in attempts will fail, as the server won't recognize the production host.

6. **Best Practices for Secure Connection**
   - **Avoid Hardcoded Secrets:** Always reference secrets using environment variables.
   - **Test on a Clean Machine:** Before distributing your setup, test it on a clean environment to ensure there are no hidden dependencies.

### Conclusion
Connecting Claude Code to enterprise systems requires careful planning and adherence to security practices. By using proper authentication methods, managing secrets securely, and setting up audit logs, you can ensure your integration is robust and compliant with regulations.
