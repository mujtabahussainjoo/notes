# Testing and Tracing

An eval gives you a score, but it does not tell you **where** the problem happened.

For example, an eval may say:

> “The answer is wrong.”

But it does not automatically tell you whether the problem came from:

- Retrieval.
- Prompt building.
- The model.
- Output parsing.
- A broken connection between two steps.

That is why an AI system needs both:

1. Different levels of tests.
2. Traces that show every step of a run.

A trace records model calls, tool calls, intermediate results, timing, and errors, making it easier to find the exact failing step. [oracle](https://www.oracle.com/a/ocom/docs/applications/fusion-apps-ai-agents-observe-eval-guide.pdf)

## Four levels of testing

Each test level checks a different part of the system.

| Test level | What it checks | Simple example |
|---|---|---|
| Unit | One small function | Does the date parser convert text into a date? |
| Functional | One AI call or feature behavior | Does the model return the required fields? |
| Integration | Two or more components working together | Does retrieved content reach the model correctly? |
| End-to-end | The complete user journey | Does the user receive the correct answer from start to finish? |

### 1. Unit test

A unit test checks one function by itself.

Example:

```python
parse_date("March 3")
```

The test checks whether the function returns the correct date.

It is:

- Fast.
- Cheap.
- Easy to understand.
- Good for finding errors inside one function.

But it cannot tell you whether that function works correctly with the rest of the application.

### 2. Functional test

A functional test checks one feature or model call.

For example, it may check whether the model returns:

```json
{
  "primary_date": "March 3",
  "issue": "delayed order"
}
```

It can verify:

- Required fields exist.
- Values have the expected type.
- The response is valid JSON.
- The output can be parsed.

However, it may use clean, prepared input. It may not catch problems in retrieval, prompt construction, or other surrounding steps.

### 3. Integration test

An integration test checks whether two connected components communicate correctly.

Example:

```text
Retriever → Prompt builder → Model
```

This is very important because each component can work correctly alone while the connection between them is broken.

A retrieval function may return:

```python
[
    {"content": "Refunds are processed within 30 days."}
]
```

But the prompt builder may expect:

```python
"Refunds are processed within 30 days."
```

Both parts may pass their own tests:

- The retriever correctly returns a list of dictionaries.
- The prompt builder correctly handles a string.

But together they fail because nobody converts the dictionary list into the expected text.

Integration tests are designed to catch this kind of handoff problem. Integration testing specifically checks whether separate modules exchange data correctly. [atlassian](https://www.atlassian.com/continuous-delivery/software-testing/types-of-software-testing)

### 4. End-to-end test

An end-to-end test runs the complete flow as a real user would.

Example:

```text
User asks: “Where is my refund?”
      ↓
System searches documents
      ↓
Prompt is created
      ↓
Model answers
      ↓
User sees the final response
```

This test catches problems that appear only when the whole system runs together.

Its disadvantages are:

- It is slower.
- It costs more.
- It can be harder to maintain.
- It tells you that something failed, but not always where.

A good testing strategy normally uses many fast lower-level tests, fewer integration tests, and a smaller number of important end-to-end tests. [momentic](https://momentic.ai/blog/software-testing-pyramid-guide)

## What is tracing?

A trace is a timeline of everything that happened during one request.

It may record:

- The original user input.
- Retrieval queries.
- Retrieved documents.
- Prompt contents.
- Tool calls.
- Model inputs and outputs.
- Parsing steps.
- Token usage.
- Latency.
- Errors.
- The final result.

Example:

```text
Step 1: retrieve(query)       OK      42 ms   → 3 chunks
Step 2: build_prompt(chunks)  OK       1 ms   → prompt created
Step 3: model.call(prompt)    OK     980 ms   → answer generated
Step 4: parse(answer)         FAIL     2 ms   → missing field: amount
```

Without a trace, you only know:

> “The eval failed.”

With a trace, you know:

> “The parser failed because the model did not return the `amount` field.”

That can turn a long debugging session into a quick fix.

Traces are especially useful for AI agents because they show the full chain of model calls, tool calls, decisions, and intermediate results. [oracle](https://www.oracle.com/a/ocom/docs/applications/fusion-apps-ai-agents-observe-eval-guide.pdf)

## The important handoff failure

Consider this trace:

```text
retrieve(q)        OK → [{"content": "Refunds take 30 days."}]
build_prompt(...)  OK → chunks inserted without reading .content
model.call(...)    OK → answer ignores the documents
final check        FAIL → “30 days” missing
```

The retrieval step worked.

The model call also worked technically.

The failure happened between retrieval and prompt creation.

The retriever returned:

```python
[{"content": "..."}]
```

But the prompt builder expected plain text.

The model therefore received badly formatted context and answered from its general knowledge instead of the retrieved policy.

## Correct fix

The correct solution is to align the data format and add an integration test:

```python
context = "\n".join(c["content"] for c in chunks)
prompt = build_prompt(question, context)
```

Then test the complete handoff:

```text
retrieve() → build_prompt() → model.call()
```

The correct answer is therefore:

> **Option C: Align the handoff and add an integration test.**

The other options are wrong:

- Fixing the parser does not help because the parser already passes.
- Rewording the prompt does not help because the retrieved content never reached the prompt correctly.

## Routing simple and complex searches

Not every question needs the same retrieval strategy.

A simple question may need one lookup:

> “What is the refund period?”

A complex question may need several searches:

> “Compare the refund policy, identify exceptions, and explain what happens if the customer paid through multiple methods.”

You can use a small router:

```python
def route(query):
    kind = classify(query)

    if kind == "lookup":
        return fetch_once(query)

    return agentic_search(query)
```

The router chooses between:

- **Single lookup:** Fetch information once.
- **Multi-step search:** Search across several rounds.

This can reduce cost and response time because simple questions do not use expensive iterative search.

However, if all your questions have the same shape, skip the router and use one fixed strategy.

## Retrieval strategy

| Query type | Recommended approach |
|---|---|
| Single fact, stable documents | Fetch once |
| Multi-part question | Search across multiple rounds |
| Frequently changing information | Use current or repeated retrieval |
| Simple, predictable traffic | Avoid an extra routing call |

The router itself costs money and adds a small delay, so use it only when your traffic contains both simple and complex questions.

## Simple memory trick

Remember the testing levels like this:

- **Unit:** Does one part work?
- **Functional:** Does one feature produce the right output?
- **Integration:** Do the parts work together?
- **End-to-end:** Does the whole user journey work?

Remember tracing like this:

> **Tests tell you that something broke. Traces tell you where it broke.**

## Main takeaway

A passing unit test does not prove that the full system works.

A passing model call does not prove that the model received the correct context.

A passing end-to-end test does not easily reveal which step failed.

For reliable AI systems:

1. Test individual functions.
2. Test individual model or feature calls.
3. Test the connections between components.
4. Test the complete user flow.
5. Record a trace for every important run.
6. When a test fails, inspect the trace to find the exact broken step.
7. Add an integration test whenever a failure occurs at a component boundary.

In the example, the parser and model were both fine. The real problem was the broken data handoff between retrieval and prompt construction. That is exactly the kind of failure an integration test and a trace are meant to catch.
