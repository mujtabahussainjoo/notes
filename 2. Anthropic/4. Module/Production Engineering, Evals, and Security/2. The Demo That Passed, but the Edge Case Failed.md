# The Demo That Passed, but the Edge Case Failed

The main lesson is:

> A feature can pass many manual tests and still be wrong in real life if you do not test unusual or confusing inputs.

Checking whether the output has the correct **format** is not the same as checking whether it contains the correct **meaning** or value. Structured AI output needs both format validation and value validation. [aclanthology](https://aclanthology.org/2025.emnlp-industry.32.pdf)

## What happened?

A team built an AI feature that extracted information from customer messages.

They manually tested about twelve messages. Every result looked correct, so they shipped the feature.

The feature already checked that:

- The message was not empty.
- The extracted date field was present.
- The date was valid.
- The date was not impossible or malformed.

For two weeks, everything appeared to work.

Then a customer sent:

> “I placed my order on March 3 but did not receive it until April 12.”

The system extracted:

> April 12 as the order date.

The correct order date was:

> March 3.

## Why did all checks pass?

Both dates were valid dates:

- March 3 is a valid date.
- April 12 is a valid date.
- The output field was not empty.
- The date had the correct format.

Therefore, the validation checks passed.

But the system still selected the **wrong date**.

This shows an important difference:

| Check | Question it answers |
|---|---|
| Format validation | “Is this a valid date?” |
| Field validation | “Did the system return a date?” |
| Meaning validation | “Did it return the correct date from the message?” |

The feature checked the first two but not the third.

## The real root cause

The problem was not necessarily a bad model or a broken prompt.

The real problem was that the team never tested the situation where one message contained two dates.

Their test examples only used simple messages like:

> “I placed my order on March 3.”

They did not define what should happen when a message says:

> “I ordered it on March 3 but received it on April 12.”

Because there was no graded test case for this situation:

- Nobody noticed the problem before launch.
- There was no holdout test set.
- There was no measurement showing that the feature could confuse different dates.
- The manual demonstrations created false confidence.

A **holdout set** is a separate group of test cases kept aside to check whether the system works on examples it did not see during development.

## What fixed the problem?

The eval did not directly fix the extraction.

The eval did something different:

1. It exposed the failure.
2. It documented the correct expected behavior.
3. It turned the failure into a permanent test case.
4. It prevented the same problem from returning after future changes.

The two-date message became a regression test.

The prompt or extraction logic could then be changed to say something clearer, such as:

> “Extract the date when the order was placed, not the delivery or receipt date.”

After the change, the eval could check whether the output was now correct.

## Important lesson about validation

Validation is useful, but it has limits.

Validation can check:

- Whether the response is valid JSON.
- Whether required fields exist.
- Whether a date has the correct format.
- Whether a number is inside an allowed range.
- Whether code can be parsed.
- Whether a tool returned the expected data type.

Validation cannot automatically know whether:

- The correct date was selected.
- The correct person was identified.
- The summary preserved the original meaning.
- The extracted value came from the correct sentence.
- The answer used the right interpretation.

A response can be perfectly valid JSON and still contain completely incorrect values. Research on structured extraction also shows that schema-valid output can hide semantic value errors, so format checks should be combined with content or grounding checks. [themoonlight](https://www.themoonlight.io/en/review/the-structured-output-benchmark-a-multi-source-benchmark-for-evaluating-structured-output-quality-in-large-language-models)

## How to find edge cases early

Before launch, ask:

> “What unusual inputs could make this feature choose the wrong answer?”

You can ask another model to generate possible failure cases.

For a date-extraction feature, useful edge cases include:

- Two dates in one sentence.
- No date in the message.
- A relative date, such as “next Tuesday.”
- A date written in different formats.
- A date with no year.
- A date range, such as “March 3–5.”
- A delivery date and an order date together.
- A date that is mentioned only in quoted text.
- Conflicting dates in different parts of the message.
- A date referring to a previous order.

Do not automatically trust generated cases. A human should review them and write down the expected answer.

## Build a graded test case

For the example above, the test case could be:

```json
{
  "input": "I placed my order on March 3 but did not receive it until April 12.",
  "expected": {
    "order_date": "March 3"
  },
  "reason": "The system must extract the order date, not the delivery date."
}
```

The test should check the actual value, not just whether the returned value is a valid date.

A useful extraction eval may check:

- Is the output valid JSON?
- Are all required fields present?
- Is each value the correct value?
- Is the value supported by the input?
- Did the system distinguish between similar fields?
- Did it correctly return “unknown” when information was missing?

## Turn every production failure into a test

Whenever a real customer finds a bug:

1. Save the original input.
2. Write down the correct expected output.
3. Add it to the eval dataset.
4. Fix the prompt, code, retrieval, or model.
5. Run the complete eval.
6. Keep the case permanently for regression testing.

This creates a growing collection of real-world examples.

Over time, your test set should include:

- Normal inputs.
- Common customer requests.
- Ambiguous inputs.
- Missing or incomplete inputs.
- Long inputs.
- Malformed inputs.
- Adversarial or unsafe inputs.
- Every important production failure.

Golden test sets are most useful when they cover real use cases and known failure modes, rather than containing only many easy examples. They should also be version-controlled with the prompts and code they test. [arxiv](https://arxiv.org/html/2601.22025v2)

## Easy way to remember

Remember this sentence:

> **Valid shape does not mean correct meaning.**

Or use the three-step rule:

1. **Format:** Is the output shaped correctly?
2. **Value:** Is the selected value correct?
3. **Meaning:** Does it match what the user actually meant?

For the date example:

- “April 12” has the correct format.
- It is a real date.
- But it is the wrong value for the order-date field.

## Final takeaway

The team did not fail because they tested too little manually. They failed because all their tests were too similar.

A dozen easy demos are not enough. Before shipping, deliberately test the cases that are:

- Ambiguous.
- Unusual.
- Incomplete.
- Conflicting.
- Long.
- Similar to real production mistakes.

The eval is not the thing that fixes the model. Its job is to reveal hidden failures, record the correct expected behavior, and protect the system from regression in the future.
