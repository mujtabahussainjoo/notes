# Evals and a Calibrated Judge

The main idea is simple:

> Do not decide that your AI feature is “done” because it looked correct a few times. Create a repeatable test, give it a score, and track that score whenever you change the prompt, tools, or model.

An **eval** turns “I think it works” into measurable evidence. A **judge** is another model that checks the quality of the answer when simple code checks are not enough.

## 1. Write a design document first

Before writing production code, create a short Markdown design document. It should explain four things:

### 1. Success criteria

Describe exactly what the system must produce.

Avoid vague goals:

> “Summarize the conversation.”

Use a goal that can be checked:

> “Create a two-sentence summary that includes every action item and names the person responsible for each one.”

Good success criteria should tell you:

- What the output must contain.
- What format it should use.
- What makes the answer correct.
- What representative examples should pass.

These criteria later become the basis for your eval cases.

### 2. Failure handling

List the problems that can happen and explain what the system should do.

For every failure, decide whether it is:

- **Retriable:** Try again because the problem may be temporary.
- **Terminal:** Stop because trying again will not help.

Example:

| Failure | Type | System behavior |
|---|---|---|
| Temporary API rate limit | Retriable | Wait and retry with backoff |
| Invalid tool arguments | Possibly retriable | Correct the arguments or ask the model again |
| Missing required information | Terminal | Ask the user for the missing information |
| Permission denied | Terminal | Tell the user the action cannot be completed |
| Unsafe requested action | Terminal | Refuse or require approval |

Also explain what the user sees when recovery is impossible. Planning this before production prevents you from discovering that you have no error path during a real incident.

### 3. Cost and latency budget

Decide the limits before choosing the architecture.

Write down:

- Maximum cost per request.
- Maximum monthly cost.
- Target response time.
- Maximum acceptable latency.
- Minimum reliability or success rate.

For example:

- Cost: no more than ₹1 per request.
- Latency: response within 5 seconds for 95% of requests.
- Reliability: at least 95% successful task completion.
- Monthly budget: no more than ₹10,000.

These numbers help you decide whether a larger model, extra tool call, or judge call is affordable.

### 4. Trust boundary

Decide what information is untrusted and what the agent is allowed to do.

Untrusted information may include:

- User-provided text.
- Emails.
- Documents.
- Web pages.
- GitHub issues or pull requests.
- Database content written by other users.

The agent should treat this content as **data**, not as instructions it must blindly follow.

Also list the smallest set of permissions the agent needs. For example:

- It may read selected files.
- It may search documentation.
- It may create a draft.
- It cannot send an email without approval.
- It cannot delete production data.
- It cannot access unrelated repositories.

This is the principle of **least privilege**: give the agent only the access and actions it truly needs.

## 2. What is an eval?

An eval is a collection of test cases used to check an AI feature.

Each test case contains:

1. An input.
2. The expected behavior.
3. The actual output.
4. A score.

The basic process is:

```text
Load test cases
      ↓
Run the AI feature
      ↓
Grade every answer
      ↓
Calculate the overall score
      ↓
Inspect individual failures
```

A simple eval might look like this:

```python
def run_test_case(test_case):
    output = run_prompt(test_case)
    score = grade(test_case, output)

    return {
        "test_case": test_case,
        "output": output,
        "score": score,
    }


def run_eval(dataset):
    results = [run_test_case(case) for case in dataset]
    average = sum(item["score"] for item in results) / len(results)

    return {
        "average_score": average,
        "results": results,
    }
```

The first score does not need to be excellent. For example, a first version might score 5 out of 10. The important thing is that later changes can be compared against that number.

Change only one major thing at a time:

- Change the prompt.
- Run the eval.
- Record the result.
- Then change the tools or model separately.

If you change the prompt, examples, tools, and model together, you will not know which change caused the improvement or regression.

## 3. Choose the right grader

There are three main ways to grade an AI response.

| Output type | Best grader | Example |
|---|---|---|
| One exact answer | Exact match | `approved`, `rejected`, or a known number |
| Structured output | Code check | Valid JSON, required fields, valid Python |
| Open-ended answer | LLM judge | Summary quality, correctness, completeness |

### Exact or string match

Use this when there is only one correct answer.

Example:

```text
Expected: approved
Actual: approved
Result: Pass
```

It is cheap and reliable, but it is too strict for answers that can be written in different ways.

For example, these answers may both be correct:

- “Paris, France”
- “The capital of France is Paris.”

An exact string comparison may incorrectly mark one of them as wrong.

### Code-graded checks

Use code when you can describe correctness with a clear rule.

Examples:

- Is the response valid JSON?
- Does it contain the required fields?
- Is a number within the correct range?
- Is the generated code syntactically valid?
- Does the response contain all required cities?
- Did the agent call the correct tool?
- Did it avoid a forbidden action?

Example:

```python
import json

def validate_json(text):
    try:
        json.loads(text.strip())
        return 10
    except json.JSONDecodeError:
        return 0
```

Code checks are usually fast, cheap, and consistent. However, they only tell you whether the output follows the required structure. They do not tell you whether the content is meaningful or high quality.

A response can be valid JSON and still contain completely wrong information.

### LLM-as-judge

Use another language model when the answer is open-ended and quality is difficult to check with code.

Examples:

- Is the summary faithful to the original text?
- Did the answer follow the user’s instructions?
- Is the explanation complete?
- Is the recommendation supported by the retrieved information?
- Is the answer helpful and safe?
- Did the agent choose an appropriate tool?

A judge should not return only a number. It should also explain the decision.

A useful judge response contains:

- Strengths.
- Weaknesses.
- Short reasoning.
- Score.
- Evidence from the answer.

Example:

```json
{
  "strengths": [
    "Includes all three action items"
  ],
  "weaknesses": [
    "Does not identify the owner of one action item"
  ],
  "reasoning": "The summary is mostly faithful but incomplete because one action item has no owner.",
  "score": 7
}
```

The reasoning makes the score easier to understand and helps prevent the judge from giving every answer a safe middle score, such as 6.

## 4. Calibrate the judge

A judge is not automatically trustworthy just because it is another AI model.

**Calibration** means checking whether the judge agrees with human reviewers.

Use this process:

1. Collect representative examples.
2. Ask one or more human reviewers to score them.
3. Run the AI judge on the same examples.
4. Compare the human scores with the judge’s scores.
5. Examine disagreements.
6. Improve the rubric and examples.
7. Run the comparison again.

Your examples should include:

- Clearly correct answers.
- Clearly incorrect answers.
- Borderline answers.
- Short and long answers.
- Common failures.
- Edge cases.
- Examples from real usage when possible.

If the judge disagrees with humans frequently, its score cannot yet be trusted. A number may look precise while actually being meaningless.

### How to improve a weak judge

If the judge is unreliable:

- Define each score more clearly.
- Explain exactly what a score of 1, 5, and 10 means.
- Add good and bad examples to the judging prompt.
- Require the judge to cite evidence from the answer.
- Use a structured JSON response.
- Add an “insufficient evidence” or “needs human review” option when appropriate.
- Test the judge on a separate holdout set.
- Recalibrate when the judge model or prompt changes.

Do not use the same model to judge itself when possible. A different model or model family can provide a more independent evaluation. Also remember that judges can have biases, such as preferring longer answers, certain writing styles, or answers that sound confident.

For important systems, track not only average agreement but also whether the judge produces:

- False passes: bad answers marked as good.
- False failures: good answers marked as bad.
- Different performance across task types.
- Bias toward short, long, technical, or polite answers.

## 5. Use coverage, not just a perfect rubric

A small test set can give you false confidence.

Three easy examples may all pass while the system fails on:

- Long inputs.
- Missing information.
- Strange formatting.
- Conflicting instructions.
- Empty results.
- Tool failures.
- Prompt injection.
- Unusual user requests.

A larger and more varied dataset usually finds more real problems than a tiny “perfect” dataset.

Start with a small labeled set, then add cases covering:

- Common user requests.
- Known failures.
- Edge cases.
- Different input lengths.
- Different tool outcomes.
- Security and permission boundaries.

Generated test cases can help increase coverage, but review them manually so that unrealistic or incorrect cases do not pollute the eval.

For an agent, evaluate more than the final answer. Also check:

- Whether it selected the correct tool.
- Whether the tool arguments were correct.
- Whether it took unnecessary steps.
- Whether it recovered properly from failures.
- Whether it respected permissions.
- Whether the overall task was completed safely.

## 6. The improvement loop

A practical development loop looks like this:

1. Write the success criteria.
2. Create the initial test dataset.
3. Build the first prompt or feature.
4. Run the eval.
5. Read the failed cases.
6. Identify the failure category.
7. Change one thing.
8. Run the eval again.
9. Keep the change only if it improves the result without breaking important cases.

The failure category usually suggests the next fix:

| Failure | Possible cause |
|---|---|
| Invalid JSON | Output instructions or schema problem |
| Wrong retrieved fact | Retrieval or context problem |
| Failure on long input | Context-window or truncation problem |
| Wrong tool selected | Tool description or routing problem |
| Unsafe action | Missing trust boundary or permission check |
| Correct content but poor tone | Prompt or communication instructions |

Always inspect individual test results, not just the average. An average score can hide an important regression:

- Three cases improved.
- Three critical cases became worse.
- The average stayed the same.

That is why you need both:

- Overall score.
- Per-case results and failure reasons.

## 7. When to use each method

Use the cheapest reliable method first:

- Use exact matching for one fixed answer.
- Use code checks for structure, syntax, fields, ranges, and tool behavior.
- Use an LLM judge only for meaning and quality that code cannot measure.
- Use human review for high-risk or high-impact decisions.

A judge adds another model call for every test case. That increases:

- Cost.
- Latency.
- System complexity.
- Score variability.

A practical setup is:

- Run exact and code-based checks on every code change.
- Run the more expensive LLM judge on a scheduled or release evaluation.
- Keep human review for critical cases.

## The main lesson

A production-ready AI feature needs more than a successful manual demo.

You should be able to answer:

- What exactly must the feature do?
- What failures can happen?
- What happens when recovery is impossible?
- How much may each request cost?
- How fast must it respond?
- What information is untrusted?
- What actions is the agent allowed to take?
- How is the output graded?
- Has the judge been checked against human decisions?
- Which cases fail today?

An eval is like a thermometer: it does not improve the system by itself, but it gives you a measurement you can trust. The design document defines what “good” means, the eval measures it, and the calibrated judge helps evaluate quality when simple code checks are not enough.
