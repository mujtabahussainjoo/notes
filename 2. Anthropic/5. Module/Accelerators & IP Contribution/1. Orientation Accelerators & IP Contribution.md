# Module 5 — Accelerators and IP Contribution

## 1. Purpose and Overview

This module addresses what happens **after a Claude-based solution works**.

Earlier development work may produce a functioning production agent, Claude Code configuration, MCP integrations, and evaluation suite. But a working build is not automatically reusable, maintainable, deployable, or defensible during security and procurement review.

The central problem is:

> **How do you turn a successful one-off build into an asset that another team can configure, maintain, deploy, and trust?**

The module teaches developers to move from **building solutions** to **productizing and operationalizing those solutions**.

The major themes are:

1. **Reusable accelerators** — package working solutions so future engagements configure them instead of rebuilding them.
2. **Contribution and shared infrastructure** — turn useful internal patterns, tools, and fixes into contributions that maintainers can review and accept.
3. **Deployment choices** — decide where Claude workloads should run, including the first-party API, Amazon Bedrock, Google Vertex AI, and other platforms.
4. **Versioning and change management** — prevent model or prompt changes from silently breaking production behavior.
5. **Procurement and compliance** — evaluate platforms according to latency, cost, security, residency, and compliance requirements rather than convenience alone.
6. **Multi-deployment applications** — coordinate several Claude deployments while maintaining clear identity, data, and security boundaries.

The module's broader production mindset is therefore:

**A successful prototype is the beginning of production engineering, not the end.**

# 2. Key Terms and Concepts

The supplied module assumes concepts introduced in earlier modules. The following definitions provide the production-oriented context needed to understand the material.

| Term                    | Definition                                                                                                  | Practical example                                                                                       |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Prompt**              | Instructions and information provided to a model to guide its response or behavior.                         | `"Classify this support ticket as billing, technical, or account."`                                     |
| **Tool**                | A capability an AI system can invoke to perform an operation outside the model itself.                      | A `get_order_status(order_id)` function that queries an order database.                                 |
| **Agent**               | An AI system that can reason through a task and use available tools or steps to accomplish it.              | A support agent that identifies a customer's order, checks its status, and prepares a response.         |
| **Context**             | The information available to the model for producing its current response.                                  | System instructions + conversation history + customer/order information + tool results.                 |
| **Memory**              | Information stored outside the immediate model context so it can be retrieved later.                        | Saving a customer's preferred communication language and retrieving it during a later interaction.      |
| **Accelerator**         | A reusable technical asset that reduces the amount of work required on future engagements.                  | A parameterized agent template with configurable prompts, tools, permissions, and evaluations.          |
| **MCP**                 | A protocol for connecting AI applications to external tools and data sources in a standardized way.         | Connecting an agent to an approved internal documentation or ticketing system.                          |
| **Model version**       | A specific model release/configuration used by an application.                                              | Pinning an application to a known Claude model version rather than silently accepting upstream changes. |
| **Deployment platform** | The infrastructure through which a model is accessed and operated.                                          | Anthropic's API, Amazon Bedrock, or Google Vertex AI.                                                   |
| **Trust boundary**      | The point where responsibility, identity, permissions, or data ownership changes between systems.           | Customer data entering a third-party service through an authenticated API.                              |
| **Eval suite**          | A repeatable collection of tests used to determine whether an AI application continues to behave correctly. | Running 500 representative support questions after changing a prompt.                                   |

### Why these concepts matter together

A production Claude application is rarely just:

**user → prompt → model → response**

Instead, it becomes something closer to:

**user → application → authentication → context → model → tools/data → model → validation → response → monitoring**

Each additional component creates another place where reliability, security, cost, and compatibility have to be considered.

# 3. Challenges in Productionizing AI

A proof of concept usually answers:

> **"Can we make this work?"**

Production engineering asks substantially harder questions:

> **"Can other people use it safely, repeatedly, predictably, and economically?"**

The module identifies several recurring gaps.

## 3.1 A working build may not be reusable

An agent created for one engagement may contain:

* hard-coded customer information
* fixed prompts
* environment-specific configuration
* assumptions about available tools
* developer-specific setup
* undocumented dependencies

Another team then has to reconstruct the original developer's decisions.

### Production response

Package the solution as a **parameterized accelerator**.

Instead of:

```text
Agent → Customer A configuration
```

create:

```text
Reusable Agent
     │
     ├── Customer configuration
     ├── Prompt configuration
     ├── Tool configuration
     ├── Environment configuration
     └── Evaluation configuration
```

The next engagement should primarily **configure the asset**, not recreate it.

---

## 3.2 A useful private fix is not automatically shared infrastructure

A developer may solve a recurring problem locally. That solution becomes much more valuable if other teams can reuse it.

But maintainers need to be able to understand:

* what changed
* why it changed
* how to reproduce it
* how it was tested
* what assumptions it makes
* whether it introduces compatibility or security concerns

The module therefore treats contribution as an engineering activity, not simply as "uploading some code."

A contribution needs to be **documented, testable, understandable, and maintainable**.

---

## 3.3 Model changes can become production changes

AI applications have an additional dependency that conventional applications often do not have in the same form: **model behavior can change independently of application code**.

A prompt that works well against one model release may behave differently after a model update.

This creates a dangerous situation:

```text
Application code unchanged
        ↓
Model/prompt changes
        ↓
Behavior changes
        ↓
Production regression
```

The module's answer is to **version what ships**.

That includes treating important prompts, model selections, configurations, and evaluations as controlled production artifacts rather than informal strings or settings.

---

## 3.4 Platform selection is an architectural decision

The easiest platform for a developer to use is not necessarily the platform a customer can approve.

Platform selection can depend on:

* latency requirements
* cost
* compliance
* data residency
* security requirements
* customer's existing cloud infrastructure
* procurement requirements
* operational constraints

Therefore, choosing a model platform should be treated as an architectural and organizational decision.

---

## 3.5 Multiple deployments create multiple boundaries

An application may use more than one Claude deployment.

For example:

```text
Application
   │
   ├── Claude deployment A
   │
   ├── Claude deployment B
   │
   └── Internal services
```

This creates additional questions:

* Which identity is used for each deployment?
* Which data can each deployment access?
* Where is customer data stored?
* Which environment is allowed to call which service?
* Are credentials isolated?
* Can data unintentionally cross organizational boundaries?

The module emphasizes explicitly **scoping these trust boundaries** so that the architecture can survive security and compliance review.

# 4. Core Production Techniques

## 4.1 Prompt Engineering with Fixed Output Formats

### What it is

Designing prompts so the model produces responses in a predictable structure rather than unconstrained prose.

For example, an application could request:

```json
{
  "category": "billing",
  "priority": "high",
  "requires_human": true
}
```

instead of relying on a developer to parse arbitrary natural-language output.

### Why it matters

Predictable output makes downstream software easier to build and test.

For example:

```text
Claude
  ↓
Structured result
  ↓
Application validation
  ↓
Business logic
```

is generally easier to operate than:

```text
Claude
  ↓
Free-form paragraph
  ↓
String parsing
  ↓
Hope the expected information is present
```

### Effective implementation

Define:

* required fields
* allowed values
* expected types
* validation rules
* fallback behavior

Then test the format as part of the evaluation suite.

### Pitfalls

Avoid assuming that a prompt alone is a complete validation mechanism.

Application code should still validate model-generated data before using it for consequential operations.

## 4.3 Controlled and Secure Tool Calls

A tool turns a model from a system that only generates text into one that can interact with external systems.

Example:

```text
User:
"Where is my order?"

Agent:
  ↓
get_order_status(order_id)
  ↓
Database/API
  ↓
Tool result
  ↓
Claude
  ↓
Customer response
```

### Why this matters

Tools introduce real-world side effects and access to sensitive systems.

A production system therefore needs to consider:

* authentication
* authorization
* least privilege
* input validation
* output validation
* logging
* data boundaries
* failure handling

### Example

A tool that reads an order might be allowed:

```text
read_order(order_id)
```

while a dangerous operation should require stronger controls:

```text
cancel_order(order_id)
```

The second operation may require additional authorization or human approval.

---

## 4.4 Full Tool Action Loops

A robust agent workflow is often iterative:

```text
User request
    ↓
Model decides whether a tool is needed
    ↓
Tool call
    ↓
Tool result
    ↓
Model evaluates result
    ↓
Another action or final response
```

For example, an order-support agent might:

1. Identify the customer.
2. Retrieve the order.
3. Check shipment status.
4. Determine whether the order is delayed.
5. Retrieve the relevant policy.
6. Explain the result to the customer.

The key production concern is preventing uncontrolled tool use.

Tool execution should have:

* explicit permissions
* bounded scope
* validated arguments
* appropriate authentication
* failure handling
* auditability

---

## 4.5 Live / Streamed Response Handling

The supplied module text **does not explain response streaming in detail**.

In a general Claude application, streaming means receiving model output progressively rather than waiting for the entire response.

Conceptually:

```text
Request
  ↓
Model
  ↓
token/chunk 1
token/chunk 2
token/chunk 3
...
final response
```

This can improve perceived responsiveness, but production implementations must account for:

* interrupted connections
* incomplete output
* UI cancellation
* partial responses
* retries
* duplicate processing

These implementation details are not covered in the supplied module and should not be attributed to it.

## 4.6 Robust Error and Interruption Handling

Production AI systems must assume things will fail.

Potential failures include:

* model/API errors
* network failures
* tool failures
* authentication failures
* invalid tool arguments
* timeouts
* user cancellation
* deployment-specific errors

A useful architecture separates failures:

```text
Model failure
     ├── retryable
     └── non-retryable

Tool failure
     ├── retry
     ├── fallback
     └── human review

Application failure
     └── safe error response
```

### Important production principle

Never assume:

> "The model returned something, therefore the workflow succeeded."

The application should verify important operations independently.

---

## 4.7 Context Window Management

**Context** is the information supplied to the model for a particular request.

As conversations become longer, context can grow:

```text
System instructions
+ conversation history
+ retrieved documents
+ tool results
+ current request
```

This creates practical concerns around:

* context limits
* latency
* cost
* irrelevant historical information
* duplicated information

A common strategy is to retain important information while reducing unnecessary history.

For example:

```text
100 previous messages
       ↓
summarize older discussion
       ↓
retain recent messages
       ↓
retrieve important facts when needed
```

The supplied module does not give a detailed algorithm for trimming or summarization, so this should be treated as general production guidance rather than module-specific instruction.

---

## 4.8 Agent Architectures for Multi-Step Tasks

An agent becomes useful when a task requires multiple operations rather than one model response.

A simple workflow might be:

```text
Request
  ↓
Plan/decide
  ↓
Retrieve information
  ↓
Use tool
  ↓
Evaluate result
  ↓
Take next action
  ↓
Final response
```

Production agent design should make the workflow understandable and bounded.

A reusable accelerator can package this architecture so future projects configure:

* available tools
* prompts
* policies
* deployment settings
* evaluation cases

rather than rebuilding the architecture.

---

## 4.9 Memory Storage and Recall

**Memory** differs from immediate context.

Context is available **now**.

Memory is information stored so it can potentially be retrieved **later**.

Example:

```text
Conversation 1:
Customer prefers email.

        ↓
Stored memory

Conversation 2:
Agent retrieves preference.

        ↓
"Would you like me to send this by email?"
```

Production memory requires careful decisions about:

* what should be stored
* how long it should be retained
* who can access it
* how it is updated
* how it is deleted
* whether storing it is appropriate

The supplied module does not provide detailed memory-storage implementation guidance.

---

## 4.10 Human-in-the-Loop Review

Some actions should not happen automatically simply because an agent can technically perform them.

A useful pattern is:

```text
Agent proposes action
       ↓
Risk check
       ↓
Low risk ─────────→ automatic execution
       │
       └─ High risk → human approval
```

For example:

| Action                               | Possible handling               |
| ------------------------------------ | ------------------------------- |
| Explain an order status              | Automatic                       |
| Search documentation                 | Automatic                       |
| Draft a refund                       | Automatic draft                 |
| Issue a large refund                 | Human approval                  |
| Modify sensitive account information | Additional authorization/review |

Human review creates a deliberate control boundary around consequential actions.

---

## 4.11 Batch / Background Processing

Not every AI task needs to happen synchronously while a user waits.

For large workloads, a background workflow can be more appropriate:

```text
Input dataset
     ↓
Queue
     ↓
Workers
     ↓
Claude processing
     ↓
Validation
     ↓
Stored results
     ↓
Report / downstream system
```

This approach is useful for workloads such as:

* document classification
* large-scale summarization
* offline evaluation
* data enrichment

The supplied module does not provide detailed batch-processing implementation instructions, so the architecture above should be understood as a general production pattern rather than a direct module procedure.

# 5. Reusable Accelerators

The most module-specific concept is the **accelerator**.

An accelerator packages work that has already been solved.

Instead of starting each project with:

```text
New project
   ↓
Design
   ↓
Implement
   ↓
Configure
   ↓
Test
```

you aim for:

```text
Existing accelerator
       ↓
Customer-specific configuration
       ↓
Evaluation
       ↓
Deployment
```

## Possible accelerator forms

### Parameterized agent template

Contains reusable:

* agent structure
* prompts
* tool definitions
* configuration
* permissions
* evaluation cases

Customer-specific values are supplied separately.

### Configurable MCP server

Instead of creating a new integration for every engagement, provide a reusable server with controlled configuration.

### Portable evaluation suite

A collection of representative tests that can travel with the application.

For example:

```text
Accelerator
├── Agent
├── Configuration
├── Tools
├── Security policy
├── Evaluation suite
└── Documentation
```

The objective is not merely code reuse.

It is **decision reuse**.

The next developer should inherit the previous team's tested patterns and constraints.

# 6. Contribution and Shared Infrastructure

A private solution becomes organizational infrastructure when it can be maintained by people other than its original author.

A good contribution should make it possible for a maintainer to answer:

1. What problem does this solve?
2. How does it work?
3. How do I reproduce it?
4. How was it tested?
5. What dependencies does it have?
6. What security implications exist?
7. What compatibility assumptions does it make?
8. How should future developers use it?

This transforms:

```text
"I fixed this for my project."
```

into:

```text
"Here is a documented, tested, reusable solution."
```

That distinction is central to the module.

# 7. Choosing Where Claude Runs

The module explicitly calls out several deployment choices:

* Anthropic's first-party API
* Amazon Bedrock
* Google Vertex AI
* third-party platforms

There is no universally correct deployment location.

The correct choice depends on the customer's requirements.

## Decision dimensions

| Dimension          | Questions to ask                                                                    |
| ------------------ | ----------------------------------------------------------------------------------- |
| **Latency**        | Where will requests originate, and what response time is required?                  |
| **Compliance**     | What regulatory and contractual requirements apply?                                 |
| **Data residency** | Where is customer data permitted to be processed or stored?                         |
| **Security**       | What identity, networking, and access controls are required?                        |
| **Cost**           | What pricing model fits the workload?                                               |
| **Cloud strategy** | Does the customer already standardize on AWS, Google Cloud, or another environment? |
| **Operations**     | Who owns monitoring, credentials, deployment, and incident response?                |
| **Procurement**    | What platforms and vendors can the organization approve?                            |

The important lesson is to make the decision **explicit and defensible**.

# 8. Version What Ships

Versioning is a key protection against silent behavioral changes.

A production AI release should not be thought of as only:

```text
application-code-v12
```

It can involve multiple important components:

```text
Application
+ model version
+ prompts
+ tools
+ configuration
+ evaluation suite
```

A useful release record might conceptually look like:

```text
Release 3.2

Application: 3.2
Model: approved version
Prompt set: 7
Tool schema: 4
Evaluation suite: 12
```

Then a model or prompt change becomes an explicit engineering decision.

Instead of:

> "Something seems different."

the team can ask:

> "What changed between release 3.1 and 3.2?"

This is especially important because AI systems are probabilistic and behavior can depend heavily on model and prompt configuration.

# 9. Multi-Deployment Claude Applications

A larger application may coordinate several Claude deployments.

For example:

```text
                    ┌── Deployment A
                    │
Application ────────┼── Deployment B
                    │
                    └── Internal services
```

The architecture must explicitly define:

### Identity

Which credentials or service identities are used?

### Data

What information can each deployment receive?

### Permissions

Which deployment can call which tools?

### Boundaries

Where does customer data cross between systems?

### Auditability

Can the organization determine:

* who initiated an operation
* which system performed it
* which data was provided
* what external systems were accessed

This allows security and compliance teams to review the architecture based on concrete boundaries rather than assumptions.

# 10. Practical Example: E-Commerce Support Accelerator

Consider an e-commerce company that wants an AI support agent.

## Step 1 — Build the initial solution

A customer asks:

> "Where is my order?"

The application authenticates the customer and supplies the agent with the relevant request.

```text
Customer
   ↓
Support application
   ↓
Authentication
   ↓
Claude agent
```

---

## Step 2 — Give the agent controlled tools

The agent can use:

```text
get_order(order_id)
get_shipping_status(order_id)
get_return_policy(product_id)
```

It cannot arbitrarily access the company's entire database.

This establishes a narrow permission boundary.

---

## Step 3 — Execute the workflow

The agent determines that order information is required.

```text
User request
     ↓
Agent
     ↓
get_order()
     ↓
Order information
     ↓
get_shipping_status()
     ↓
Shipping information
     ↓
Agent response
```

---

## Step 4 — Validate important operations

Suppose the customer instead asks:

> "Cancel my order and refund me."

The system should distinguish between **answering** and **performing a consequential action**.

A safer workflow is:

```text
Customer request
      ↓
Agent determines requested action
      ↓
Check authorization
      ↓
Check cancellation policy
      ↓
Determine risk
      ↓
Human approval if required
      ↓
Execute cancellation
      ↓
Confirm result
```

The agent should not treat natural-language intent as sufficient authorization.

---

## Step 5 — Package the solution

Once the system works, the team turns it into an accelerator.

```text
E-commerce Support Accelerator
├── Agent workflow
├── Prompt templates
├── Tool definitions
├── Security configuration
├── Evaluation suite
├── Deployment configuration
└── Documentation
```

A second customer can now configure:

```text
Customer A
  order API = A
  policies = A
  deployment = A

Customer B
  order API = B
  policies = B
  deployment = B
```

without rebuilding the entire agent.

---

## Step 6 — Create evaluations

The accelerator should include representative scenarios such as:

* valid order lookup
* nonexistent order
* unauthorized order lookup
* delayed shipment
* return request
* cancellation request
* tool timeout
* unavailable backend
* ambiguous customer request
* high-risk refund request

These tests provide a reusable safety net when prompts, models, or tools change.

---

## Step 7 — Select deployment

The customer's architecture team evaluates available deployment options according to:

```text
Latency
+ compliance
+ residency
+ security
+ cost
+ existing cloud strategy
+ procurement
```

The choice is therefore based on documented requirements rather than developer preference.

---

## Step 8 — Version the release

The final production artifact records the versions of:

```text
Agent
Prompt configuration
Model
Tools
Application
Evaluations
```

A future change can then be tested before release.

---

## Step 9 — Prepare the contribution

If the team discovers a reusable improvement—for example, a safer tool-authorization pattern—it can be prepared for broader reuse.

The contribution should contain enough documentation and tests for a maintainer to understand and validate it without reconstructing the original project.

# 11. Production Mindset

The module's underlying progression can be represented as:

```text
Prototype
   ↓
Working build
   ↓
Tested build
   ↓
Documented build
   ↓
Reusable accelerator
   ↓
Versioned deployment
   ↓
Security/compliance review
   ↓
Maintainable production asset
```

Each stage addresses a different failure mode.

| Stage                | Question                                                |
| -------------------- | ------------------------------------------------------- |
| Prototype            | Can it work?                                            |
| Working build        | Does the implementation function?                       |
| Tested build         | Does it behave correctly across representative cases?   |
| Documented build     | Can another developer understand it?                    |
| Reusable accelerator | Can another engagement configure it?                    |
| Versioned deployment | Can changes be tracked and reproduced?                  |
| Security review      | Are identity, data, and permissions controlled?         |
| Production asset     | Can the organization operate and maintain it over time? |

The crucial transition is from **developer knowledge** to **explicit engineering artifacts**.

If the original developer must explain everything personally, the solution has not yet become a durable organizational asset.

---

# 12. Main Takeaway and Mindset

The central lesson of this module is:

> **A build that works is not the finished product. The real engineering work begins when you make that build reusable, reviewable, versioned, deployable, and maintainable.**

For developers, that means thinking beyond implementation.

When finishing a Claude application, ask:

### Reuse

* Can another team configure this without rebuilding it?
* Which parts should become parameters?

### Documentation

* Can a maintainer understand the architecture without asking me?

### Evaluation

* Do we have tests that detect behavioral regressions?

### Versioning

* Can we identify exactly which model, prompts, tools, and application version shipped?

### Deployment

* Why are we using this platform?
* Does it satisfy the customer's latency, compliance, security, residency, and cost requirements?

### Security

* What identities and permissions exist?
* Where do data and trust boundaries cross?

### Change management

* What happens if the model or prompt changes?

### Contribution

* Could this solution become shared infrastructure rather than remaining a one-off project?

The mature production mindset is therefore:

**Don't just make the agent work. Make the solution something another team can safely reuse, a maintainer can confidently accept, a security team can review, and an organization can operate over time.**
