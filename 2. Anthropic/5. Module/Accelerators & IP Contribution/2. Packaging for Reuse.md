# Packaging a Working Build into a Reusable Accelerator

## 1. Purpose

This section explains how to turn a **working Claude build into a reusable asset** so the next customer or engagement starts from a proven foundation instead of a blank repository.

The key idea is:

> **Build once, package the reusable parts, and make future teams configure rather than rebuild.**

This matters because rebuilding the same engineering solution repeatedly consumes expensive developer time. Packaging immediately after a successful build is also easier than trying to reconstruct the original design decisions months later.

---

## 2. What Is an Accelerator?

An **accelerator** is a packaged solution that gives a future engagement a working foundation.

A normal one-off build might look like:

```text
Customer A
    ↓
Custom code
    ↓
Working solution
```

A reusable accelerator changes that into:

```text
Reusable accelerator
        ↓
Customer-specific configuration
        ↓
Customer A solution
```

The accelerator contains the parts that are already proven, while customer-specific differences become **parameters**.

### Example

Suppose an agent contains:

```python
customer_name = "Acme"
support_path = "/acme/support"
max_refund = 500
```

Instead of shipping those hard-coded values, package the agent around configuration:

```text
customer_name → configuration
support_path  → configuration
max_refund    → configuration
```

The agent's core loop remains unchanged.

The next team therefore **configures the asset instead of editing the implementation**.

---

# 3. The Three Main Accelerator Types

The module identifies three common reusable asset types.

| Asset                  | What it contains                        | What should be configurable?                                                 |
| ---------------------- | --------------------------------------- | ---------------------------------------------------------------------------- |
| **Agent Template**     | System prompt, tool schemas, agent loop | Domain-specific prompts, paths, scopes, credentials by reference, thresholds |
| **MCP Server Package** | Tools exposed by the server             | Scopes, credentials by reference, customer-specific paths                    |
| **Eval Suite**         | Graded tests and judge rubric           | Dataset paths and environment-specific thresholds                            |

Choosing the correct asset type matters.

A collection of scripts may technically work, but if every future customer has to modify those scripts manually, it is **not effectively reusable**.

---

# 4. Agent Template

An **agent template** packages the reusable architecture of a working agent.

It typically includes:

```text
Agent Template
├── System prompt
├── Tool schemas
├── Agent loop
├── Configuration
└── Evaluation
```

### What stays reusable?

The fundamental behavior:

* agent loop
* tool structure
* prompt architecture
* validation patterns
* reusable logic

### What becomes configuration?

Anything that changes between engagements, such as:

* customer-specific prompts
* paths
* scopes
* credentials by reference
* thresholds

### Good design

```text
                    Agent Template
                          │
              ┌───────────┴───────────┐
              │                       │
       Reusable logic          Configuration
              │                       │
        agent loop              customer values
        tool schemas             paths/scopes
        prompt structure         thresholds
```

The next customer should modify the configuration rather than the core implementation.

---

# 5. MCP Server Package

An **MCP server package** turns a working collection of tools into something another environment can install and configure.

The package should clearly define:

* what tools are available
* what inputs each tool expects
* what scope each tool has
* which credentials are required
* which paths or resources can vary

For example:

```text
MCP Server
├── search_documents(query)
├── get_document(id)
└── create_ticket(data)
```

The implementation stays reusable, while the installing organization controls things such as:

```text
scope = customer's approved resources
credentials = customer's credential reference
paths = customer's environment
```

### Important principle

**Do not make customers edit the server code just to configure its environment.**

Configuration should represent environmental differences.

---

# 6. Portable Eval Suite

An **eval suite** packages the evidence that demonstrates that an AI asset works.

It contains two particularly important things:

1. **The graded test dataset**
2. **The judge/rubric that determines whether results pass**

For example:

```text
Eval Suite
├── test_cases.json
├── grading_rubric
└── baseline_score
```

This makes the evaluation portable.

A new team can run the same evaluation against its own deployment and determine whether the accelerator still behaves as expected.

---

## Eval as a Deployment Gate

The eval isn't only documentation.

It can also become a **release gate**.

For example:

```text
New model version
       ↓
Run pinned evaluation
       ↓
Compare against baseline
       ↓
Meets threshold?
    ↙       ↘
  Yes        No
   ↓          ↓
Deploy     Investigate
```

This is particularly important when promoting a new model version.

Instead of assuming:

> "The new model should work."

the team has a measurable baseline:

> "The new model must meet the established evaluation threshold before production deployment."

# 7. Parameterization: The Core Packaging Technique

**Parameterization** means identifying values that vary between environments and moving them out of the reusable implementation.

Think of it as separating:

```text
WHAT THE ASSET DOES
```

from:

```text
WHERE / FOR WHOM / UNDER WHAT LIMITS IT RUNS
```

### Agent example

Instead of:

```text
Agent code
 ├── Customer A prompt
 ├── Customer A path
 ├── Customer A scope
 └── Customer A threshold
```

use:

```text
Agent code
       +
Configuration
 ├── Customer prompt
 ├── Customer path
 ├── Customer scope
 └── Customer threshold
```

This prevents the next customer from copying and modifying the original implementation.

---

# 8. What Should Be Documented?

Code tells someone **how the system behaves**.

Documentation needs to explain what cannot reliably be inferred from the code.

At minimum, document:

### Environment assumptions

What does the asset expect to exist?

Examples:

* required services
* supported environments
* required permissions
* required dependencies

### Expected inputs

What does the asset accept?

For an MCP tool:

```text
tool: get_order
input:
    order_id: string
```

### Failure modes

What happens when something goes wrong?

For example:

```text
API unavailable → retry/failure response
Invalid input → validation error
Unauthorized request → access denied
```

### Evaluation criteria

Explain:

* what is being tested
* how it is graded
* what the score means
* what baseline must be maintained

Without this documentation, the accelerator becomes a **black box**.

And when developers don't understand a reusable asset, they tend to rebuild it.

---

# 9. Auditability Is Part of the Package

The module makes an important production point:

> **An accelerator is not complete if it cannot survive security or regulatory review.**

A reviewer may need to know:

### What data does it touch?

For example:

```text
Customer profile
Order history
Support tickets
```

### Which identity does it act under?

For example:

```text
service-account-support-agent
```

### What did it actually do?

The package should preserve or expose the relevant audit information.

Conceptually:

```text
Request
   ↓
Identity
   ↓
Agent
   ↓
Tool
   ↓
Data
   ↓
Action
   ↓
Audit log
```

This turns auditability from something reconstructed later into part of the asset itself.

---

# 10. Packaging Checklist

A useful way to package an accelerator is to make three decisions for every asset:

| Asset              | Parameterize                                              | Document                                                     | Bundle for audit                            |
| ------------------ | --------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------- |
| **Agent template** | Prompts, paths, scopes, credential references, thresholds | Environment assumptions, inputs, failure modes, working eval | Data touched, acting identity, activity log |
| **MCP server**     | Scopes, credential references, customer paths             | Tool inputs, scope boundaries, failure modes                 | Data touched, acting identity, activity log |
| **Eval suite**     | Thresholds and dataset paths                              | Rubric, score meaning, baseline                              | Data touched, acting identity, activity log |

This checklist helps prevent a common mistake: focusing only on code packaging while forgetting operational and audit information.

---

# 11. The Wrong Approach: Loose Scripts

A common failure pattern is:

```text
agent.py
tools.py
customer_config.py
prompt.py
eval.py
```

Everything runs, so it appears reusable.

But imagine the next developer opens the repository and discovers:

```text
prompt.py → contains customer-specific instructions
tools.py → contains customer-specific paths
agent.py → contains hard-coded thresholds
config.py → contains environment assumptions
```

The next team now has to understand and modify several files.

They eventually copy the repository:

```text
Original
   ↓
Copy
   ↓
Customer B modifications
   ↓
Divergence
```

Now there are two versions of essentially the same solution.

That is the opposite of the accelerator model.

---

# 12. The Better Approach

Instead:

```text
Reusable Agent
       +
Customer Configuration
       +
Portable Evaluation
       +
Documentation
       +
Audit Information
```

The customer-specific information is explicit.

For example:

```yaml
customer:
  name: "Customer B"

paths:
  support: "/customer-b/support"

scopes:
  orders: "read"

thresholds:
  refund_limit: 500
```

The exact configuration format is not the important part.

The important design principle is that **environmental variation is represented as configuration rather than scattered code modifications**.

---

# 13. When Packaging Pays Off

Packaging has an upfront cost.

The first build takes longer because you must:

* separate reusable and customer-specific components
* parameterize values
* write documentation
* prepare evaluations
* package audit information

So there is a trade-off.

### For reusable work

```text
First engagement
      ↓
Additional packaging effort
      ↓
Future engagements
      ↓
Much less rebuilding
```

This is worthwhile when the pattern will be reused.

### For a genuine one-off

If a customer will never reuse the solution and there is no reasonable expectation of another similar engagement, packaging everything may add unnecessary complexity.

The module therefore explicitly allows a different approach:

> **For a one-off that will never be reused, ship the build and move on.**

The goal isn't to package everything.

The goal is to **package things whose reuse justifies the investment**.

---

# 14. What "Good" Looks Like

A well-packaged accelerator should allow the next team to answer these questions quickly:

### Configuration

* What do I need to change for my environment?
* Where do I provide those values?
* Which defaults are safe?

### Operation

* What does the asset do?
* What tools does it use?
* What inputs does it expect?

### Failure handling

* What failures are already handled?
* What failures require intervention?

### Evaluation

* How do I prove it works?
* What score is considered acceptable?
* What baseline am I comparing against?

### Security and audit

* What data does it access?
* Which identity does it use?
* What actions does it perform?
* Where are those actions logged?

If the answers require contacting the original developer, the asset is not sufficiently packaged.

---

# 15. Main Takeaway

The most important production lesson here is:

> **Don't package just the code. Package the reusable design, configuration boundaries, documentation, evaluation, and audit information.**

A successful working build becomes an accelerator when:

```text
Working build
     ↓
Separate reusable vs. customer-specific parts
     ↓
Parameterize differences
     ↓
Document assumptions and failure modes
     ↓
Bundle evaluations
     ↓
Bundle audit information
     ↓
Reusable accelerator
```

The goal is not merely to save files for later.

The goal is to make the **next engagement start from a known, tested, understandable asset** rather than from the original developer's memory.

That is what turns one delivery into reusable engineering infrastructure.


## Checkpoint 1 — Fix the Broken Accelerator Template

### Problem

The template is supposed to be reusable, but one **customer-specific value is hardcoded** inside the function.

The problematic line is:

```python
repo_path="/home/acme/checkout-service"
```

`/home/acme/checkout-service` is specific to the **Acme customer repository**, so another team should not have to edit the source code to use a different repository.

### What should change?

Make `repo_path` a function parameter.

**Before:**

```python
def build_review_agent():
```

**After:**

```python
def build_review_agent(repo_path):
```

Then replace the hardcoded value:

**Before:**

```python
repo_path="/home/acme/checkout-service"
```

**After:**

```python
repo_path=repo_path
```

### Corrected version

```python
def build_review_agent(repo_path):
    return Agent(
        model="claude-opus-4-8",
        system_prompt=SYSTEM_PROMPT,
        tools=[read_file, run_linter],
        repo_path=repo_path,
    )
```

### Why this matters

The reusable part is the **code-review agent**, while the repository is **customer-specific configuration**.

So the next team can do:

```python
build_review_agent("/home/customer-b/checkout-service")
```

without modifying the template itself.

### Note

The same principle would apply to the other customer-specific values mentioned in the postmortem:

* **Repository path** → parameterize
* **Model name** → configuration/version selection
* **Review thresholds** → parameterize
* **Customer-specific prompt fragments** → configuration

**Production lesson:** A template is reusable only when the values that change between engagements are explicitly exposed as configuration rather than hidden inside the implementation.
