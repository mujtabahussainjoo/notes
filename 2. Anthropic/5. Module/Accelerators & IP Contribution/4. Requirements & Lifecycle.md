# From Business Requirements to Production-Ready Claude Systems

This part of the module connects the earlier **accelerator/contribution work** to the next major concern: **choosing and defending a deployment architecture**.

The central idea is:

> **Do not choose a deployment platform first and then try to justify it. Start with requirements, translate them into measurable constraints, and let those constraints drive the architecture and platform decision.**

---

# 1. Purpose and Overview

A Claude application may work perfectly as a prototype and still be unsuitable for production.

For example, a business may say:

> “We want an AI agent that helps support staff work faster.”

That statement is useful as a **business goal**, but it isn't specific enough to design or test.

A production team needs to turn it into requirements such as:

* The agent classifies each ticket into one of four queues.
* The agent drafts a response using relevant company policy.
* A human must approve the response before it is sent.
* Customer data must remain within a particular geographic region.
* Each request must be associated with an auditable identity.
* Responses must meet a specified latency target.
* The system must support a specified request volume.

Now those requirements can drive:

**Business problem → Functional requirements → Infrastructure requirements → Architecture → Platform → Build → Test → Deploy → Operate**

The module therefore treats deployment as part of a broader **systems lifecycle**, rather than as a final technical choice.

# 2. Key Terms and Concepts

Although this particular section focuses primarily on requirements and lifecycle, the broader Claude application terminology is useful.

| Term                           | Meaning                                                                                       | Example                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Prompt**                     | Instructions and information given to Claude to guide its response                            | “Summarize this customer complaint using these three fields.”          |
| **Tool**                       | A capability Claude can invoke to interact with an external system                            | `get_order_status(order_id)`                                           |
| **Agent**                      | A system where Claude can reason through a task and potentially use tools over multiple steps | Claude reads a support request → checks order data → drafts a response |
| **Context**                    | The information available to Claude during a request                                          | Conversation history, documents, tool results, system instructions     |
| **Memory**                     | Information deliberately stored for possible use across separate interactions                 | A customer's preferred language stored in a customer profile           |
| **Functional requirement**     | Something the system must **do**, expressed so it can be checked                              | “A human approves every summary before storage.”                       |
| **Infrastructure requirement** | A constraint on **how/where/under what conditions** the system operates                       | “Transcript data must be processed in the EU.”                         |
| **Gate**                       | A decision point that must be satisfied before moving to the next lifecycle phase             | Don't promote a new model until its evaluation passes                  |
| **Eval**                       | A repeatable test/evaluation used to determine whether the AI behaves acceptably              | 500 support questions with expected quality criteria                   |
| **Residency**                  | The geographic/legal location where data is processed or stored                               | Customer transcripts must remain within the EU                         |
| **Identity**                   | The account/credential under which an operation occurs                                        | The agent accesses a database using a specific service identity        |

### Functional vs. infrastructure requirements

This distinction is especially important.

**Functional:**

> What must the application do?

**Infrastructure:**

> What constraints must the system satisfy while doing it?

For example:

```text
Business goal:
Help bank support agents process calls faster.

Functional:
→ Generate a summary of every call.
→ Human approves the summary.
→ Approved summary is stored.

Infrastructure:
→ Transcript processing stays within the EU.
→ Operations use an auditable identity.
→ Response meets a defined latency target.
```

# 3. Turning a Business Problem into Requirements

## Step 1 — Start with the business problem

Suppose the requirement is:

> “Help support agents answer customers faster.”

This isn't yet sufficiently precise.

There are several unanswered questions:

* What exactly should the AI do?
* What information should it use?
* What actions can it take?
* Which actions require approval?
* How quickly must it respond?
* How much traffic must it handle?
* Where can customer data be processed?
* Who is allowed to access the data?
* What needs to be logged?

---

## Step 2 — Extract functional requirements

A **functional requirement** should describe observable behavior.

For example:

```text
The system must:
1. Classify each support ticket into one of four queues.
2. Draft a response using the relevant policy.
3. Include the relevant policy reference.
4. Require human approval before sending.
```

Each statement can become something that engineering and QA can verify.

This is the important transition:

```text
Vague goal
    ↓
Specific behavior
    ↓
Testable requirement
    ↓
Eval / acceptance criterion
```

A requirement such as:

> “The AI should be accurate.”

is difficult to test.

A requirement such as:

> “The system must classify each ticket into one of four predefined queues.”

is much easier to turn into an evaluation.

---

# 4. Deriving Infrastructure Requirements

Infrastructure requirements are often **implicit** in the business problem.

The team has to actively ask the questions that the business requirement creates.

## The four major questions highlighted by this module

### 1. Latency

> How quickly must the system respond?

And importantly:

> **Where is latency measured?**

For an interactive support agent, a 30-second response may be unacceptable even if the model produces excellent output.

---

### 2. Scale

> How many requests will the system receive?

Don't only consider average traffic.

Consider:

```text
Normal traffic
      ↓
Peak traffic
      ↓
Unexpected spikes
```

A system that works for 10 requests/minute may behave very differently at 1,000 requests/minute.

---

### 3. Residency

> Where is data allowed to be processed?

This becomes especially important for regulated workloads.

Example:

```text
Requirement:
Customer transcripts must remain in the EU.

Architecture implication:
Choose a deployment architecture capable of satisfying
the required geographic/data-processing boundary.
```

---

### 4. Identity

> Who is performing the operation?

An AI application shouldn't be thought of simply as:

```text
Claude → database
```

Instead, you need to understand:

```text
User
  ↓
Application
  ↓
Agent
  ↓
Service identity / credentials
  ↓
Database
```

You need to know:

* what identity is being used,
* what permissions it has,
* what data it can access,
* and what activity is auditable.

---

# 5. Documenting Requirements

Requirements need to be written down because the people making the eventual deployment decision may **not be the people who originally gathered them**.

A useful requirements record might look like:

| Category   | Requirement                           | Reason                       |
| ---------- | ------------------------------------- | ---------------------------- |
| Functional | Human approves summary before storage | Business/process requirement |
| Functional | Agent summarizes every transcript     | Business workflow            |
| Latency    | Response must meet defined target     | User experience              |
| Scale      | Support expected peak request volume  | Capacity                     |
| Residency  | Processing must remain in EU          | Regulation                   |
| Identity   | Access must use auditable identity    | Security/compliance          |

This gives the architecture team a defensible chain:

```text
Requirement
    ↓
Constraint
    ↓
Architecture decision
    ↓
Platform choice
```

Instead of:

```text
“We chose platform X because we're familiar with it.”
```

# 6. Checkpoint 3 — Extract the Requirements

Scenario:

> A regulated EU bank wants an agent that summarizes customer call transcripts for its support team, with summaries reviewed before being stored in the EU.

## Question 1

**Which is a valid functional requirement?**

### Answer: **B — The agent produces a summary that a human approves before it is stored.**

Why?

It describes **system behavior**:

```text
Transcript
   ↓
Generate summary
   ↓
Human approval
   ↓
Store
```

The others belong to different categories:

* **A — “fast and accurate”** → too vague to be a precise functional requirement.
* **C — approved cloud provider** → infrastructure/deployment constraint.
* **D — data must not leave the EU** → infrastructure/residency requirement.

---

## Question 2

**Which is a valid infrastructure requirement?**

### Answer: **C — Transcript data is processed in the EU.**

Why?

It describes a **deployment/data-processing constraint**, not something the agent itself does.

Compare:

```text
Functional:
Human reviews every summary.

Infrastructure:
Transcript processing occurs in the EU.
```

### Checkpoint 3 answers

| Question | Answer | Reason                                          |
| -------- | ------ | ----------------------------------------------- |
| Q1       | **B**  | Defines observable application behavior         |
| Q2       | **C**  | Defines a geographic/data-processing constraint |

# 7. Systems Lifecycle for Claude Applications

The module then places these requirements into a complete engineering lifecycle.

```text
Requirements
     ↓
Design
     ↓
Build
     ↓
Test
     ↓
Deploy
     ↓
Operate
     ↓
Iterate
     ↺
Requirements
```

The important insight is that Claude development isn't just:

```text
Prompt → Claude → Response
```

It's a complete engineered system.

---

## Phase 1 — Requirements

Determine:

* What must the system do?
* What constraints must it satisfy?
* What regulations apply?
* What latency is acceptable?
* What scale is required?
* What identity/security model is required?
* Where may data be processed?

**Artifact:** requirements record.

---

## Phase 2 — Design

Decide:

* Which deployment platform?
* Which model?
* What tools?
* What trust boundaries?
* What data can cross those boundaries?
* What permissions does the agent have?

For example:

```text
Requirements:
EU residency
+ auditable identity
+ expected workload
        ↓
Architecture design
        ↓
Deployment platform selection
```

The platform decision should follow the requirements.

---

## Phase 3 — Build

Now implement:

* Agent
* Prompts
* Tools
* Application logic
* Authentication
* Configuration
* Integrations

This is where the actual Claude application is constructed.

---

## Phase 4 — Test

Test multiple layers:

```text
Unit tests
    ↓
Integration tests
    ↓
AI evaluations
    ↓
End-to-end tests
```

The important idea from the module is that **an AI application should not be promoted simply because the code runs**.

---

## Phase 5 — Deploy

Deployment should involve controlled promotion.

For model changes:

```text
New model/version
       ↓
Run evaluation
       ↓
Compare against pinned baseline
       ↓
Pass?
   ↙       ↘
 Yes       No
 ↓          ↓
Promote    Investigate
```

This prevents a model update from silently changing production behavior.

---

## Phase 6 — Operate

Once deployed, monitor the actual system.

Important operational signals include:

* Latency
* Token usage/cost
* Errors
* Tool failures
* Application failures
* Guardrail violations
* Production behavior

Production operation generates information that isn't available during development.

---

## Phase 7 — Iterate

Production findings feed back into requirements.

For example:

```text
Production:
Tool calls are slower than expected.

        ↓

New requirement:
Support response must complete within X seconds.

        ↓

Design change:
Caching / architecture / platform change

        ↓

New implementation + evaluation
```

This makes the lifecycle continuous rather than a one-time process.

---

# 8. Gating Between Phases

A **gate** is a deliberate decision point before advancing to the next lifecycle phase.

This is particularly important for regulated systems.

For example:

### Design → Build

Don't begin implementation until the architecture satisfies required residency constraints.

```text
Does proposed architecture satisfy EU residency?
             ↓
        Yes → Build
        No  → Redesign
```

### Test → Deploy

Don't promote a model simply because the application technically works.

```text
New version
    ↓
Evaluation
    ↓
Compare with pinned baseline
    ↓
Pass?
    ↓
Deploy
```

This provides a controlled engineering process.

---

# 9. Checkpoint 4 — Place the Work in the Right Phase

## (a) Pinning the full model ID and keeping the prior version

### **Answer: Deploy**

The deployment process should pin the exact model version and retain the previous version so the production system isn't silently changed.

---

## (b) Gating promotion on the eval result before a version goes to production

### **Answer: Deploy**

The evaluation is the gate that determines whether a version can be promoted.

Conceptually:

```text
Candidate version
      ↓
Eval
      ↓
Compare against baseline
      ↓
Promotion decision
```

---

## (c) Deciding data must be processed in a specific region

### **Answer: Requirements**

This is an infrastructure requirement.

For example:

```text
Requirement:
Customer data must be processed in the EU.
```

That requirement later influences the architecture and deployment platform.

---

## (d) Instrumenting token cost and latency per call in production

### **Answer: Operate**

This is production observability.

You are measuring how the deployed system behaves in the real environment.

---

## (e) Choosing Amazon Bedrock because the customer holds its compliance posture there

### **Answer: Design**

This is an architecture/deployment-platform decision based on the requirements.

The reasoning is:

```text
Customer requirements
        ↓
Compliance / residency / security constraints
        ↓
Platform evaluation
        ↓
Choose deployment platform
```

### Checkpoint 4 answers

| Activity                                                | Phase            |
| ------------------------------------------------------- | ---------------- |
| (a) Pin full model ID + retain prior version            | **Deploy**       |
| (b) Gate promotion on eval                              | **Deploy**       |
| (c) Require processing in a specific region             | **Requirements** |
| (d) Instrument production token cost + latency          | **Operate**      |
| (e) Choose Bedrock based on customer compliance posture | **Design**       |

# 10. Production Challenges

The requirements/lifecycle material reveals why a simple Claude prototype isn't enough.

## Prototype mindset

```text
Does it produce a good answer?
        ↓
Yes
        ↓
Ship
```

## Production mindset

```text
Does it work?
    +
Is the behavior defined?
    +
Can it be evaluated?
    +
Can it operate within required latency/scale?
    +
Can data remain within required boundaries?
    +
Is identity controlled and auditable?
    +
Can model changes be detected?
    +
Can production behavior be monitored?
        ↓
Then consider promotion
```

The major challenge is therefore **turning an impressive model interaction into a controlled engineering system**.

# 11. How the Broader Production Techniques Fit

The prompt asks about several techniques—streaming, tool loops, memory, batch processing, etc. **Those implementation details are not actually described in the supplied section of the module.** They should therefore be treated as broader production concepts rather than claims about what this specific excerpt teaches.

Their relationship to the lifecycle is:

| Technique            | Lifecycle relevance           |
| -------------------- | ----------------------------- |
| Fixed output formats | Build / Test                  |
| Tool calls           | Design / Build                |
| Tool loops           | Design / Build                |
| Streaming            | Build / Operate               |
| Error recovery       | Build / Test / Operate        |
| Context management   | Design / Build                |
| Agent workflows      | Design / Build                |
| Memory               | Design / Build                |
| Human-in-the-loop    | Requirements / Design / Build |
| Batch processing     | Design / Deploy / Operate     |

For example, if the requirement says:

> “A human must approve every summary before storage.”

then **human-in-the-loop** isn't merely an implementation detail. It becomes an architectural requirement.

# 12. Practical Example — E-Commerce Support Agent

Consider an e-commerce company building a Claude support agent.

## Step 1 — Business problem

> Customers need faster answers about orders and returns.

Not enough to start coding yet.

---

## Step 2 — Functional requirements

Translate the goal into concrete behavior:

```text
1. Identify the customer's request.
2. Retrieve order information when necessary.
3. Explain the relevant return policy.
4. Draft a response.
5. Require approval before performing sensitive actions.
```

---

## Step 3 — Infrastructure requirements

Ask what the business problem implies:

```text
Latency:
How quickly should support staff receive the answer?

Scale:
How many conversations occur per minute?

Residency:
Where can customer/order data be processed?

Identity:
Which service identity can access order information?

Audit:
Which tool calls and actions must be logged?
```

---

## Step 4 — Design

Choose:

* Claude deployment platform
* Model
* Tool architecture
* Database access
* Authentication
* Trust boundaries
* Human approval workflow

For example:

```text
Support agent
     ↓
Claude
     ↓
Tool: get_order()
     ↓
Order service
     ↓
Return information
     ↓
Claude drafts response
     ↓
Human approval
     ↓
Customer
```

---

## Step 5 — Build

Implement:

* System prompt
* Tool schemas
* Agent workflow
* Authentication
* Logging
* Configuration
* Approval mechanism

---

## Step 6 — Test

Create evaluations such as:

```text
Input:
"My package hasn't arrived."

Expected behavior:
→ Identify order issue
→ Retrieve order status
→ Explain status
→ Do not invent tracking information
```

Also test failure cases:

```text
Database unavailable
        ↓
Agent should not fabricate order information.
```

---

## Step 7 — Deploy

Pin the production model version and evaluate any new version against the existing baseline.

```text
Production v1
     ↓
Candidate v2
     ↓
Run same evaluation suite
     ↓
Compare
     ↓
Promotion gate
```

---

## Step 8 — Operate

Monitor:

* Response latency
* Token consumption
* Tool errors
* Database failures
* Incorrect responses
* Human approval rates
* Production traffic

---

## Step 9 — Iterate

Suppose production reveals that order lookups are frequently slow.

That becomes new engineering information:

```text
Production observation
        ↓
Latency requirement refined
        ↓
Architecture reconsidered
        ↓
Implementation changed
        ↓
Re-test
        ↓
Deploy
```

This demonstrates why the lifecycle ends with **iterate → requirements**, rather than simply ending at deployment.

# 13. Key Design Pattern: Requirements Drive Platform Choice

One of the most important patterns in this section is:

```text
             BUSINESS PROBLEM
                    ↓
          FUNCTIONAL REQUIREMENTS
                    ↓
       INFRASTRUCTURE REQUIREMENTS
                    ↓
                 DESIGN
                    ↓
        PLATFORM / MODEL / BOUNDARIES
                    ↓
                  BUILD
                    ↓
                   TEST
                    ↓
                 DEPLOY
                    ↓
                 OPERATE
                    ↓
                 ITERATE
                    ↺
```

Notice what **doesn't** happen:

```text
“We usually use platform X.”
        ↓
Let's find reasons to justify X.
```

Instead:

```text
Requirement
   ↓
Constraint
   ↓
Architecture consequence
   ↓
Platform decision
```

That makes the deployment decision **defensible to reviewers, security teams, compliance teams, and future maintainers**.

# 14. Production Checklist

Before treating a Claude application as production-ready, ask:

### Requirements

* [ ] Are functional behaviors explicitly defined?
* [ ] Are infrastructure constraints documented?
* [ ] Are regulatory requirements identified?
* [ ] Are latency and scale requirements known?
* [ ] Is the identity model defined?

### Design

* [ ] Does the deployment platform satisfy the requirements?
* [ ] Are trust/data boundaries explicit?
* [ ] Are model and platform choices documented?

### Build

* [ ] Are prompts and tools clearly defined?
* [ ] Are customer-specific values parameterized?
* [ ] Are sensitive operations protected?

### Test

* [ ] Are there repeatable evaluations?
* [ ] Are failure cases tested?
* [ ] Is there a pinned baseline?

### Deploy

* [ ] Is the exact model version pinned?
* [ ] Is promotion gated by evaluation?
* [ ] Is the previous version available for rollback?

### Operate

* [ ] Are latency and token costs monitored?
* [ ] Are errors and tool failures observable?
* [ ] Are security/audit events recorded?

### Iterate

* [ ] Do production findings feed back into requirements?
* [ ] Can the system evolve without losing its safety and evaluation guarantees?

# 15. Main Takeaway

The deeper lesson of this section is that **production AI engineering starts before the first prompt is written**.

A business request must first become something engineering can reason about:

```text
Business goal
     ↓
Checkable behavior
     ↓
Infrastructure constraints
     ↓
Architecture
     ↓
Implementation
     ↓
Evaluation
     ↓
Controlled deployment
     ↓
Production monitoring
     ↓
Iteration
```

The production mindset is therefore:

> **Don't ask only “Can Claude do this?” Ask “What exactly must the system do, under what constraints, how will we verify it, and what controls allow us to operate it safely after deployment?”**

That mindset connects this section directly to the earlier accelerator material: a reusable Claude build is not merely code that works—it is an engineered asset with **clear requirements, explicit assumptions, evaluations, controlled deployment, and operational boundaries**.
