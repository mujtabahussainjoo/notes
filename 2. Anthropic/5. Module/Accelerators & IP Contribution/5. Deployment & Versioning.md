# Choosing Where a Claude Workload Runs and Versioning What Ships

This section moves from **requirements and lifecycle** into two concrete production decisions:

1. **Where should the Claude workload run?**
2. **How do you make sure the model version in production doesn't silently change?**

The key idea is that deployment is not simply a technical preference. It is constrained by the customer's existing **cloud, identity, compliance, and data-residency environment**, while versioning determines whether model changes are deliberate and reversible. 

---

# 1. Purpose and Overview

A packaged Claude application is still just code until it is deployed.

At deployment time, two new questions appear:

```text
Where does it run?
        +
Exactly what version runs?
```

These decisions matter because an application can break **without anyone changing its application code**.

For example:

```text
Application code
      ↓
model = "opus"
      ↓
Alias moves to newer model
      ↓
Output changes
      ↓
Parser breaks
      ↓
Production incident
```

The solution is to make both deployment and versioning explicit:

```text
Customer requirements
       ↓
Deployment platform
       ↓
Pinned model version
       ↓
Evaluation gate
       ↓
Production
```

# 2. Key Terms and Concepts

| Term                    | Meaning                                                              | Example                                             |
| ----------------------- | -------------------------------------------------------------------- | --------------------------------------------------- |
| **Prompt**              | Instructions/context given to Claude                                 | “Summarize this support ticket using these fields.” |
| **Tool**                | An external capability Claude can invoke                             | `get_order_status(order_id)`                        |
| **Agent**               | Claude-based workflow that can perform multiple reasoning/tool steps | Read request → query order → draft response         |
| **Context**             | Information available during a request                               | System instructions + conversation + tool results   |
| **Memory**              | Information deliberately retained between interactions               | Customer's saved preferences                        |
| **Deployment platform** | Environment where the Claude workload runs                           | Anthropic API, Bedrock, Vertex AI                   |
| **Model alias**         | A convenient name that can point to a changing model version         | `"opus"`                                            |
| **Pinned model ID**     | A reference to a specific model snapshot                             | A full model ID                                     |
| **Model snapshot**      | A fixed version of a model                                           | The exact version selected for production           |
| **Residency**           | Where data is processed/stored geographically                        | EU-only processing                                  |
| **Identity**            | The credentials/account under which operations run                   | AWS identity                                        |
| **Eval**                | Repeatable test used to evaluate model/application behavior          | Support-ticket evaluation suite                     |
| **Rollback**            | Returning production to a known-good previous version                | Revert from model V2 to V1                          |
| **Promotion gate**      | A condition that must pass before a version reaches production       | New model must pass eval                            |

# 3. Choosing the Deployment Platform

The module's central rule is:

> **The customer's existing cloud environment usually determines the deployment platform.**

The question isn't simply:

> “Which platform has the best model?”

Instead, consider:

* Where does the customer already operate?
* Which identity system do they use?
* What compliance agreements already exist?
* What data-residency constraints apply?
* What Claude capabilities are required?
* What versioning mechanism does the platform provide?

The source specifically notes that identity and data location are largely determined by the deployment platform rather than by application code. 

---

# 4. Deployment Platform Options

## First-party Claude API

Useful when:

* There is no binding cloud requirement.
* There is no special residency constraint.
* The customer wants the newest capabilities.

Identity and terms are based around Anthropic.

For production:

```text
Use:
Full model ID
+
Retain previous version
```

---

## Claude Platform on AWS

This is accessed through the customer's AWS account, but the source distinguishes it from inference actually running inside the customer's AWS boundary: inference is Anthropic-operated.

It can make sense when the customer:

* Operates on AWS.
* Wants Anthropic model IDs/lifecycle.
* Wants first-party API feature parity.

The important distinction is:

```text
AWS account access
≠
Inference necessarily running inside AWS
```

That distinction matters for compliance and residency discussions. 

---

## Claude in Amazon Bedrock

Bedrock provides a Claude integration through AWS.

The source describes:

* Messages API at `/anthropic/v1/messages`
* Broad feature parity with the first-party API
* AWS identity
* Customer AWS boundary
* AWS compliance posture

Feature-specific requirements should still be checked against current Bedrock documentation. 

This is especially relevant when:

```text
Customer
   ↓
Already operates heavily in AWS
   ↓
Has AWS compliance/security controls
   ↓
Wants Claude within that environment
```

---

## Google Vertex AI

For a Google Cloud customer, Vertex AI provides:

* Google Cloud identity
* IAM
* Google Cloud billing
* Regional/global endpoints depending on requirements

The module positions this as an option when the customer already operates on Google Cloud and has its compliance posture there. 

---

## Third-party platforms

Some customers already operate a platform that embeds Claude.

The important point is that you must understand **how that particular platform hosts Claude**.

The supplied material uses Microsoft Foundry as an example and specifically distinguishes between:

* **Hosted on Azure**
* **Hosted on Anthropic**

Those hosting forms have different infrastructure/residency implications, so a regulated customer requires verification at build time.

# 6. Why Model Aliases Are Dangerous in Production

This is the core incident from the section.

The application originally used:

```python
model = "opus"
```

That worked because `"opus"` pointed to the recommended model.

But an alias is a **moving target**.

Conceptually:

```text
Today:

"opus"
   ↓
Model A
```

Later:

```text
"opus"
   ↓
Model B
```

The application code hasn't changed.

But the behavior potentially has.

---

# 7. The Production Incident

The trace tells the story:

```text
deploy: model="opus"
        ↓
alias advanced
        ↓
new opus version
        ↓
response shape changed
        ↓
parser failed
        ↓
rollback attempted
        ↓
no pinned previous version
        ↓
hotfix required
```

The critical problem wasn't merely that the new model behaved differently.

The bigger problem was:

> **There was no known-good pinned version available to roll back to.**

The source describes this as an **untracked production change** caused by the unpinned deployment. 

---

# 8. Alias vs. Pinned Model ID

## Moving alias

```text
model = "opus"
```

Conceptually:

```text
"opus"
   ↓
Current recommended version
```

The target can change without an application code change.

### Advantages

* Convenient
* Automatically receives newer versions
* Good for experimentation

### Production problem

The application can change behavior without your release process changing.

---

## Pinned model

```text
model = "claude-haiku-4-5-20251001"
```

Conceptually:

```text
Full model ID
       ↓
Fixed snapshot
```

The model remains unchanged until **you deliberately change the reference**.

The supplied material notes that model-ID pinning conventions depend on the model generation, so developers should verify the current convention at build time. 

---

# 9. Version the Prompt and Asset Too

Pinning the model alone isn't the complete versioning strategy.

The module says to version:

```text
Model
Prompt
Asset / application
```

For example:

```text id="6fqk6m"
Application v3
├── Model: pinned version
├── Prompt: v7
├── Tool schemas: v4
└── Eval suite: v5
```

This makes it easier to determine exactly what produced a production result.

---

# 10. Retain the Previous Version

Pinning gives you a known version.

**Retention gives you a rollback path.**

Imagine:

```text
Production
    ↓
Model V1
```

You release:

```text
Candidate
    ↓
Model V2
```

If V2 causes problems:

```text
V2
 ↓
Regression
 ↓
Rollback
 ↓
V1
```

Without V1:

```text
V2
 ↓
Regression
 ↓
???
 ↓
Hotfix
```

That's exactly what happened in the incident.

---

# 11. Promotion Through the Eval

A pinned model should not automatically go straight into production.

The module describes an evaluation-based promotion process:

```text
Pinned candidate
       ↓
Run eval suite
       ↓
Compare with pinned baseline
       ↓
Partial traffic / controlled rollout
       ↓
Evaluate result
       ↓
Promote OR rollback
```

This changes the role of an eval.

It isn't merely:

> “A test we ran during development.”

It becomes:

> **A deployment gate.**

The source explicitly describes the eval as becoming the gate for promotion rather than being only a one-time test. 

---

# 12. The Complete Production Versioning Pattern

A robust deployment therefore looks like:

```text
                 ┌──────────────────┐
                 │ Pinned baseline  │
                 │     Model V1     │
                 └────────┬─────────┘
                          │
                    Candidate V2
                          ↓
                    Run evaluation
                          ↓
                  Compare with V1
                          ↓
                 ┌────────┴────────┐
                 │                 │
               Pass              Fail
                 │                 │
                 ↓                 ↓
            Promote V2         Reject/Rollback
                 │
                 ↓
          Retain V1 for rollback
```

This is much safer than:

```text
"opus"
  ↓
Whatever version happens to be current
  ↓
Production
```

# 13. Key Production Challenges

## Challenge 1 — Silent upstream changes

Your code can remain unchanged while model behavior changes.

**Solution:** pin the model.

---

## Challenge 2 — No rollback path

If you overwrite or discard the previous version, a regression becomes a hotfix problem.

**Solution:** retain the prior pinned version.

---

## Challenge 3 — Treating evals as development-only tests

A model can pass tests during development but still require controlled promotion.

**Solution:** make evaluation part of the deployment gate.

---

## Challenge 4 — Platform assumptions

A customer's cloud provider doesn't automatically mean every Claude hosting option has the same residency or identity properties.

**Solution:** understand the exact platform/hosting model and verify current requirements.

# 14. Practical Example — Regulated E-Commerce Customer

Imagine an e-commerce company operates primarily on AWS and requires customer data to remain within its configured AWS environment.

### Requirements

```text
Cloud: AWS
Identity: AWS identity
Residency: AWS boundary
Need: Claude support agent
Rollback: Required
```

### Design

The team evaluates deployment options and selects the appropriate AWS-based Claude integration according to the customer's requirements.

Then:

```text
AWS identity
      ↓
Claude deployment
      ↓
Pinned model ID
      ↓
Support agent
      ↓
Eval suite
```

### Release

Current:

```text
Model V1
```

Candidate:

```text
Model V2
```

Run the evaluation:

```text
V2 vs V1
```

If the candidate passes:

```text
V2 → production
V1 → retained for rollback
```

If it fails:

```text
V2 → rejected
V1 → remains production
```

The exact platform/model identifiers should be verified against current platform documentation at build time, as the supplied material explicitly warns.

# 15. Checkpoint 5 — Correct Configuration

Scenario:

> A customer runs AWS, has a data-residency requirement, and needs rollback capability.

You need one choice from each group.

### Platform Group

**Answer: Amazon Bedrock**

Reason: the scenario specifically establishes an AWS customer with a residency/compliance requirement, and the module describes Bedrock as operating within the customer's configured AWS boundary. 

### Identity Group

**Answer: AWS identity reference**

Bedrock uses AWS identity rather than an Anthropic API key.

### Model Reference Group

**Answer: A pinned full model ID**

A moving alias can change without an application release.

### Rollback Group

**Answer: Retain the prior pinned version**

You need a known-good version to return to if the candidate fails.

### Final Checkpoint 5 Answer

```text
Platform:
Amazon Bedrock

Identity:
AWS identity reference

Model:
Pinned full model ID

Rollback:
Retain the prior pinned version
```

# 16. Prototype vs. Production

| Prototype                       | Production                                   |
| ------------------------------- | -------------------------------------------- |
| Moving alias can be convenient  | Pin exact model version                      |
| Latest version automatically    | New versions deliberately promoted           |
| No rollback may be acceptable   | Previous version retained                    |
| Manual testing                  | Repeatable eval gate                         |
| Platform chosen for convenience | Platform chosen from requirements            |
| Minimal release process         | Controlled release process                   |
| “It works”                      | “It is controlled, testable, and reversible” |

The source explicitly allows a moving alias for a **throwaway prototype that never reaches production**. The stricter versioning requirements apply to what actually ships.

# 17. Developer Production Checklist

Before deploying a Claude workload:

### Platform

* [ ] Identify the customer's primary cloud.
* [ ] Check identity requirements.
* [ ] Check data-residency requirements.
* [ ] Check compliance requirements.
* [ ] Verify platform-specific Claude feature requirements.

### Versioning

* [ ] Use a pinned full model ID.
* [ ] Don't rely on a moving alias for production.
* [ ] Version the prompt alongside the model.
* [ ] Version the application/asset.

### Evaluation

* [ ] Maintain a pinned baseline.
* [ ] Run the candidate against the baseline.
* [ ] Gate promotion on evaluation results.
* [ ] Consider controlled/partial rollout.

### Rollback

* [ ] Retain the previous pinned version.
* [ ] Know how to restore it.
* [ ] Test the rollback procedure where appropriate.

### Verification

* [ ] Verify current model-ID conventions.
* [ ] Verify current platform capabilities.
* [ ] Verify residency/hosting assumptions at build time.

# 18. Main Takeaway

The incident demonstrates a fundamental production principle:

> **An upstream model update should be a deliberate deployment event—not a surprise production change.**

The safe chain is:

```text
Customer requirements
        ↓
Choose appropriate deployment platform
        ↓
Pin exact model version
        ↓
Version prompt + application
        ↓
Run evaluation
        ↓
Promote deliberately
        ↓
Retain previous version
        ↓
Rollback if necessary
```

The biggest mindset shift is:

**Don't think of the model as a dependency that automatically updates. Think of it as a versioned production component that your release process controls.**

That turns a model regression from:

```text
Production incident
→ emergency hotfix
```

into:

```text
Evaluation failure
→ don't promote
```

or, if already promoted:

```text
Production regression
→ rollback to known-good version
```

That is the difference between a Claude application that merely **works today** and one that can be **operated safely over time**.
