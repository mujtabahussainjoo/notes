# Moving an Asset from Private Reuse to Shared Infrastructure

## 1. Purpose

Once an accelerator has been packaged for internal reuse, the next step is deciding whether it can become **shared infrastructure**.

The important transition is:

```text
Working build
    ↓
Internal reusable asset
    ↓
Contribution-ready asset
    ↓
Shared infrastructure
```

Packaging solves the **reuse problem**.

Contribution preparation solves the **maintainer and ownership problem**.

A maintainer who did not build the original asset must be able to understand, install, test, and verify it without reconstructing the original developer's intent.

---

# 2. Match the Asset to the Right Contribution Channel

Not every contribution belongs in the same place.

The module highlights the **Claude Cookbook** as a repository for focused reference implementations, while open-source MCP servers and tools generally have their own repositories and contribution conventions.

### The key rule

> **Put the contribution in the channel designed for that kind of contribution.**

For example:

| Contribution                          | Appropriate channel                                                |
| ------------------------------------- | ------------------------------------------------------------------ |
| Focused Claude implementation/pattern | Claude Cookbook                                                    |
| MCP server                            | That server's repository                                           |
| MCP tool/fix                          | Relevant tool/server repository                                    |
| Large multi-component application     | Its appropriate project/repository, not a focused Cookbook example |

### Why this matters

Imagine you built a complete customer-support platform containing:

```text
Agent
+ MCP server
+ frontend
+ database
+ authentication
+ deployment scripts
```

Trying to submit the entire application as a Cookbook example creates a mismatch.

The Cookbook is intended for **focused patterns**, so reviewers would have to understand an entire application before evaluating the example.

A better contribution extracts the reusable pattern:

```text
Large customer application
        ↓
Remove customer-specific components
        ↓
Isolate reusable pattern
        ↓
Focused example
        ↓
Example + test + assumptions
```

# 3. What a Maintainer Needs to Verify

The goal isn't to impress the maintainer with sophisticated code.

The goal is to make verification **easy**.

The module identifies four requirements.

## 3.1 The Code Does One Thing

A contribution should have a clear purpose.

Bad:

```text
customer-support-platform/
├── agent/
├── billing/
├── authentication/
├── frontend/
├── database/
├── analytics/
└── deployment/
```

Better:

```text
conversation-handling-pattern/
├── implementation
├── example
├── test
└── README
```

The second version gives the maintainer a clear question:

> "Does this implementation demonstrate the claimed conversation-handling pattern?"

They don't need to reconstruct the architecture of an entire customer application.

---

# 4. Include a Runnable Example

A maintainer should be able to **see the contribution working**.

Don't make the reviewer build a custom harness just to discover what the code does.

A useful structure might look like:

```text
pattern/
├── example.py
├── implementation.py
├── test_example.py
└── README.md
```

The example should demonstrate the intended behavior end to end.

Conceptually:

```text
Install
   ↓
Run example
   ↓
Observe expected behavior
```

This is much stronger than:

> "This code demonstrates a reusable conversation pattern."

The example provides evidence.

---

# 5. Include a Test

The runnable example demonstrates the behavior.

The **test verifies it**.

For example:

```python id="n4jpxw"
def test_conversation_handler():
    result = handle_conversation(test_input)

    assert result.category == "support"
```

The exact test depends on the contribution, but the principle is the same:

> **A maintainer should be able to verify the behavior without reproducing your reasoning process.**

This is especially important for AI applications because the implementation may depend on prompts, tools, model behavior, and configuration.

The test provides a concrete verification point.

---

# 6. Document the Assumptions

A maintainer needs to know what the contribution assumes about its environment.

For example:

```text
Assumptions:
- Python version X
- Claude API access
- Required environment variable
- Tool X available
- Input follows schema Y
```

Also document important limitations or failure conditions.

Without this information:

```text
Contribution
    ↓
Maintainer runs it
    ↓
Something fails
    ↓
Maintainer investigates
```

The maintainer has effectively inherited the original developer's debugging work.

With explicit assumptions:

```text
Contribution
    ↓
Documented prerequisites
    ↓
Maintainer reproduces expected environment
    ↓
Example runs
    ↓
Test passes
```

# 7. Rights and Attribution Come First

Technical correctness isn't enough.

Before contributing code from a customer engagement, determine whether you actually have the **right to contribute it**.

Customer work may contain:

* proprietary code
* customer-specific logic
* confidential information
* contractual restrictions
* third-party code with licensing requirements

Therefore:

```text
Technical readiness
        +
Rights clearance
        ↓
Contribution-ready
```

### Attribution matters too

If the contribution builds upon existing work, that prior work needs to be properly attributed according to its applicable terms.

The module's key point is that **licensing and attribution are gates**, not cleanup tasks to perform after submission.

# 8. Remove Customer-Specific Information

The example in this module is a customer-service agent developed during an engagement.

Before contributing it, the developer needs to turn:

```text
Customer-specific implementation
```

into:

```text
General reusable pattern
```

For example, remove:

* customer names
* proprietary business rules
* internal URLs
* credentials
* private data
* customer-specific prompts
* confidential workflows

Then preserve the general technical pattern.

Conceptually:

```text
Customer service agent
        ↓
Remove customer details
        ↓
General conversation-handling pattern
        ↓
Runnable example
        ↓
Test
        ↓
Documentation
        ↓
Contribution
```

# 9. Contribution-Readiness Checklist

The module's readiness bar can be summarized as follows:

| Requirement          | Question for the developer                                                    |
| -------------------- | ----------------------------------------------------------------------------- |
| **Focused code**     | Does the contribution do one clear thing?                                     |
| **Correct channel**  | Am I submitting it to the repository/channel designed for this type of asset? |
| **Runnable example** | Can the maintainer run it and observe the behavior?                           |
| **Test**             | Is there a test that proves the intended behavior?                            |
| **Assumptions**      | Have I documented prerequisites and important limitations?                    |
| **Rights**           | Do I have permission to contribute this code?                                 |
| **Attribution**      | Have I properly credited prior work?                                          |
| **Customer data**    | Have customer-specific/confidential details been removed?                     |

---

# 10. Private Accelerator vs. Shared Contribution

These are related but different finishing states.

| Private accelerator                    | Shared infrastructure                                     |
| -------------------------------------- | --------------------------------------------------------- |
| Designed for another internal team     | Designed for maintainers and broader users                |
| Configuration is documented            | Installation and contribution expectations are documented |
| Eval demonstrates behavior             | Example + test allow independent verification             |
| Internal assumptions may be acceptable | Assumptions must be explicit                              |
| Internal ownership is known            | Licensing and attribution must be cleared                 |
| Reusable within the organization       | Suitable for acceptance and maintenance                   |

So:

> **Reusable does not automatically mean contribution-ready.**

A private accelerator is optimized for reuse by your organization.

A contribution must additionally satisfy the requirements of the destination project and its maintainers.

---

# 11. What Happens When Licensing Cannot Be Cleared?

Sometimes the technical work is excellent but cannot legally or contractually be contributed.

The correct response is **not to submit it anyway**.

Instead:

```text
Potential contribution
       ↓
Rights check
       ↓
Can rights be cleared?
   ↙          ↘
 Yes           No
  ↓             ↓
Prepare       Escalate
contribution  to owner
```

The module explicitly recommends escalating to the owner when an engagement licensing constraint cannot be cleared.

This protects both the contributor and the receiving project.

# 12. Practical Example: Customer-Service Agent

Suppose a team built this during a customer engagement:

```text
Customer Support Agent
├── Conversation handling
├── Customer-specific policies
├── Internal API integration
├── Private prompts
└── Customer data
```

The team identifies that the **conversation-handling pattern** is generally useful.

### Step 1 — Isolate the reusable pattern

```text
Conversation handling
```

### Step 2 — Remove customer-specific material

Remove:

* customer data
* private API endpoints
* proprietary policies
* credentials
* confidential prompts

### Step 3 — Prepare a focused implementation

```text
conversation-pattern/
├── handler.py
├── example.py
├── test_handler.py
└── README.md
```

### Step 4 — Add the runnable example

The example demonstrates the pattern from input to output.

### Step 5 — Add the test

The test verifies the expected behavior.

### Step 6 — Document assumptions

Explain required configuration, dependencies, expected inputs, and limitations.

### Step 7 — Check rights and attribution

Confirm the team is permitted to contribute the implementation and properly attribute any prior work.

### Step 8 — Submit through the appropriate channel

Because the contribution is a focused Claude pattern, the relevant reference channel can be the Cookbook; if it were an MCP server or tool, its own repository would be the appropriate destination.

# 13. What Makes a Contribution "Maintainer-Friendly"?

Think about the reviewer's experience.

### Difficult contribution

```text
"Here is 5,000 lines from our customer project.
It worked for us."
```

The maintainer has to figure out:

* what it does
* what parts matter
* how to run it
* what dependencies exist
* what assumptions exist
* whether it is legally usable
* how to test it

### Maintainer-friendly contribution

```text
"This demonstrates pattern X."

Implementation
     ↓
Runnable example
     ↓
Test
     ↓
Assumptions
     ↓
Licensing/attribution
```

The reviewer can understand the contribution quickly and verify it independently.

That is the actual goal.

---

# 14. Main Takeaway

The progression is:

```text
Working solution
      ↓
Reusable accelerator
      ↓
Focused contribution
      ↓
Runnable example
      ↓
Test
      ↓
Documented assumptions
      ↓
Rights + attribution cleared
      ↓
Maintainer can verify
      ↓
Shared infrastructure
```

The central lesson is:

> **Don't just contribute code that worked for you. Contribute an asset that someone else can understand, run, test, and legally accept.**

For a Developer, contribution readiness means four technical things are clear:

**focused code + runnable example + test + assumptions**

And before any of that reaches a maintainer, there is an additional gate:

**rights and attribution.**

That is what turns a private accelerator into infrastructure that other developers can confidently build on.


# Checkpoint 2 — Choose the Contribution Channel and Readiness Fix

## Match 1: Case → Contribution Channel

| Case                                                      | Correct channel                                                                            | Why                                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| **Case A** — Focused tool wrapping a single API           | **The tool's own repository**                                                              | It is a standalone tool, so it belongs with that tool's source and contribution conventions.                            |
| **Case B** — Full customer-service application            | **The Cookbook, but only after the reusable pattern is stripped out as a focused example** | The Cookbook is for focused reference implementations, not an entire application with UI and deployment infrastructure. |
| **Case C** — One-line fix to an existing Cookbook example | **The Cookbook example's own repository**                                                  | The fix belongs with the example it modifies.                                                                           |

### Answer

```text
Case A → The tool's own repository

Case B → The Cookbook, but first reduce it to a focused reusable pattern

Case C → The Cookbook example's own repository
```

---

# Match 2: Case → Missing Readiness Item

| Case                                 | Missing readiness item                     | Why                                                                                                        |
| ------------------------------------ | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| **Case A** — Focused tool            | **A test that proves the wrapper behaves** | The implementation is already focused; the maintainer needs something they can run to verify its behavior. |
| **Case B** — Full application        | **Reduction to a single focused pattern**  | The contribution is too broad for a Cookbook-style focused review.                                         |
| **Case C** — Customer-engagement fix | **The rights check**                       | Even a tiny change originating from an engagement needs permission/rights clearance before contribution.   |

### Answer

```text
Case A → A test that proves the wrapper behaves

Case B → Reduction to a single focused pattern

Case C → The rights check
```

---

## Final Answer

### Match 1

* **A → Tool's own repository**
* **B → Cookbook, after stripping it down to a focused reusable pattern**
* **C → Cookbook example's own repository**

### Match 2

* **A → Test that proves the wrapper behaves**
* **B → Reduce to a single focused pattern**
* **C → Rights check**

### Production lesson

The contribution has to pass **two different tests**:

```text
Is it in the right place?
        +
Can the maintainer verify and legally accept it?
        ↓
Contribution-ready
```

A contribution can be technically correct and still stall if the reviewer has to **reverse-engineer the intent, reproduce the setup, or resolve ownership questions** themselves.
