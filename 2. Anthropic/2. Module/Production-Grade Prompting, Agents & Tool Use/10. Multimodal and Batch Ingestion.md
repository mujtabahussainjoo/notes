## Simple Summary

This topic has two main parts:

1. **Images and PDFs use context space** before Claude even reads your written question.
2. **Batch processing** is for thousands of offline jobs; it is not for users waiting for an immediate answer.

Think of it like this:

```text
Images and PDFs
→ Use space in Claude’s working memory

Thousands of files
→ Use Batch API, not one-by-one normal API calls
```

***

## Images Use Tokens Too

Claude does not see an image like a human eye. It breaks an image into many small squares called **patches**.

```text
Image
   ↓
Broken into small 28 × 28 pixel squares
   ↓
Each square = 1 visual token
   ↓
More/larger squares = more token cost
```

The image-token formula is:

\[
\text{Image tokens} =
\left\lceil \frac{\text{width}}{28} \right\rceil
\times
\left\lceil \frac{\text{height}}{28} \right\rceil
\]

Claude’s vision documentation uses 28 × 28 pixel patches for visual tokens. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/vision)

### Easy Example

A 1,000 × 1,000 pixel image:

\[
\left\lceil \frac{1000}{28} \right\rceil
\times
\left\lceil \frac{1000}{28} \right\rceil
=
36 \times 36
=
1{,}296
\]

So one 1,000 × 1,000 image uses about:

```text
1,296 visual tokens
```

Ten similar screenshots can use roughly:

```text
10 × 1,296 = 12,960 visual tokens
```

That is a large amount of context before you add your system prompt, user question, tools, PDFs, or conversation history.

***

## Resize Images Before Sending

Large images may cost more, slow requests, and fill the context window.

```text
Large screenshot
      ↓
More image tokens
      ↓
Higher cost
      ↓
Less room for instructions and answer
```

If the full high resolution is not needed, resize the image first.

### Example

Suppose you want Claude to read a website error screenshot.

```text
Original image:
4000 × 3000 pixels
```

If the screenshot only needs to show an error message and one form field, resize it before sending:

```text
Resized image:
1400 × 1050 pixels
```

This often gives Claude enough detail while using much less context.

### Simple Python Resize Example

```python
from PIL import Image

image = Image.open("large-screenshot.png")

# Keep the image size reasonable.
image.thumbnail((1400, 1400))

image.save("smaller-screenshot.jpg", quality=85)
```

Simple flow:

```text
Original image
      ↓
Resize to useful size
      ↓
Send to Claude
      ↓
Lower token use and faster request
```

Current limits vary by model. Anthropic documentation lists a high-resolution tier with a 2,576-pixel maximum long edge and 4,784 visual-token limit, and a standard tier with a 1,568-pixel long edge and 1,568 visual-token limit; oversized images are downscaled before processing. Check the model documentation when you build. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/vision)

## Three Ways to Send Images

| Method | Simple meaning | Best use |
|---|---|---|
| Inline Base64 | Put image data directly inside the API request | One-time small image |
| Image URL | Give Claude a reference to an image URL | Image already hosted and safely accessible |
| Files API | Upload once, receive a `file_id`, reuse it later | Same image used many times |

Claude supports image content blocks using Base64 data, a URL reference, or a `file_id` from the Files API. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/vision)

***

## 1. Send Image as Base64

Use this when the image is one-time and small enough that uploading first is not worth the extra step.

```python
import base64

with open("error-screenshot.jpg", "rb") as file:
    image_base64 = base64.b64encode(file.read()).decode("utf-8")

response = client.messages.create(
    model=model,
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "image",
                    "source": {
                        "type": "base64",
                        "media_type": "image/jpeg",
                        "data": image_base64
                    }
                },
                {
                    "type": "text",
                    "text": (
                        "Read the visible error message. "
                        "Return JSON with fields: error_code, error_message, "
                        "and suggested_next_step."
                    )
                }
            ]
        }
    ]
)
```

### When It Is Good

```text
User uploads one photo
      ↓
You analyze it once
      ↓
You do not need it again
```

### Limitation

The full image data travels again every time you send it.

```text
Same Base64 image in 10 requests
      ↓
Sent 10 times
      ↓
More request size and latency
```

***

## 2. Send Image by URL

Use a URL when the image is already stored somewhere accessible.

```python
response = client.messages.create(
    model=model,
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "image",
                    "source": {
                        "type": "url",
                        "url": "https://example.com/product-image.jpg"
                    }
                },
                {
                    "type": "text",
                    "text": "Describe the product in three short bullet points."
                }
            ]
        }
    ]
)
```

Use this only when:

- The URL is accessible to the API.
- You are permitted to share the image.
- The image does not expose sensitive data through a public URL.
- URL availability is reliable.

For private files or repeated internal use, the Files API is usually safer and more reliable.

***

## 3. Use Files API for Reuse

Use the Files API when the same image or PDF will be used again.

```text
Upload file once
      ↓
Receive file_id
      ↓
Use file_id in future requests
      ↓
Avoid repeatedly sending Base64 file data
```

Claude’s Files API lets you upload once and reference files later with a `file_id`. Files used in messages still count as input tokens, but you avoid repeated file encoding/upload overhead. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/vision)

### Example: Upload an Image Once

```python
with open("product-photo.jpg", "rb") as file:
    uploaded_file = client.beta.files.upload(
        file=("product-photo.jpg", file, "image/jpeg")
    )

image_file_id = uploaded_file.id
```

Later, use the image:

```python
response = client.messages.create(
    model=model,
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "image",
                    "source": {
                        "type": "file",
                        "file_id": image_file_id
                    }
                },
                {
                    "type": "text",
                    "text": "Check whether this product image contains a visible defect."
                }
            ]
        }
    ]
)
```

## Sending PDFs

For PDFs, use a **document block**, not an image block.

```text
Image file
→ type: image

PDF file
→ type: document
```

A PDF may contain:

- Normal text
- Tables
- Charts
- Scanned pages
- Images
- Forms
- Invoices
- Contracts

PDFs use context budget based on extracted text and visual page content. Anthropic’s PDF guidance says text-heavy PDF pages typically use about 1,500–3,000 tokens per page, with image token costs applied to page images too. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/pdf-support)

### Base64 PDF Example

```python
import base64

with open("invoice.pdf", "rb") as file:
    pdf_base64 = base64.b64encode(file.read()).decode("utf-8")

response = client.messages.create(
    model=model,
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "document",
                    "source": {
                        "type": "base64",
                        "media_type": "application/pdf",
                        "data": pdf_base64
                    },
                    "title": "invoice.pdf"
                },
                {
                    "type": "text",
                    "text": (
                        "Extract invoice number, invoice date, seller name, "
                        "total amount, and currency. "
                        "Return only JSON."
                    )
                }
            ]
        }
    ]
)
```

Expected result:

```json
{
  "invoice_number": "INV-1042",
  "invoice_date": "2026-09-20",
  "seller_name": "Example Supplies Pvt Ltd",
  "total_amount": 12500.00,
  "currency": "INR"
}
```

PDFs and text files use `document` content blocks, and a `file_id` can be used after uploading them through the Files API. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/files)

## Better Prompt for Images and PDFs

Do not only say:

```text
Describe this image.
```

This may produce a broad answer.

Instead, say exactly what you need.

### Example: Error Screenshot

```text
Read this screenshot carefully.

Return only JSON with these fields:
- visible_error_code
- visible_error_message
- affected_page
- suggested_next_step

If the text is unclear, use "NOT_READABLE".
Do not guess missing text.
```

### Example: Product Image

```text
Check this product image for visible damage.

Look for:
- cracks
- scratches
- missing parts
- loose packaging
- water damage

Return:
{
  "damage_found": true or false,
  "damage_type": "string",
  "confidence": "LOW | MEDIUM | HIGH",
  "notes": "short sentence"
}

If an object is partly hidden, say that it is partly hidden.
Do not claim damage when the image is unclear.
```

### Example: Invoice PDF

```text
Read the attached invoice.

Extract:
- invoice number
- invoice date
- seller name
- buyer name
- subtotal
- tax
- total
- currency

Rules:
- Return valid JSON only.
- Use null when a value is missing.
- Do not guess unclear values.
- Do not include extra fields.
```

The same prompt rules apply to text, images, and PDFs:

```text
Clear task
      +
Clear output format
      +
Rule for unclear information
      =
More reliable result
```

## Batch API: For Thousands of Jobs

The normal synchronous API is good when a user is waiting.

```text
User asks question
      ↓
Send request
      ↓
Wait for answer
      ↓
Show answer immediately
```

But it is not ideal for thousands of background jobs.

### Wrong Approach

```python
for ticket in tickets:
    response = client.messages.create(
        model=model,
        messages=[...]
    )
```

If you have 5,000 tickets, this still makes 5,000 separate synchronous API calls.

```text
5,000 tickets
      ↓
5,000 API requests
      ↓
Rate limits
      ↓
Slow application
      ↓
Many connections or retries
```

Splitting the list into small chunks does not make it a true batch job if you still call the normal API one item at a time.

***

## What Real Batch Processing Means

The Message Batches API lets you submit many requests together.

```text
Prepare 5,000 requests
        ↓
Send one batch submission
        ↓
Receive batch_id
        ↓
Your application continues other work
        ↓
Check batch status later
        ↓
Download results when complete
```

Claude’s Message Batches API supports up to **100,000 requests** or **256 MB** in one batch, whichever limit is reached first. It can take up to **24 hours**, though many batches complete sooner; official documentation says most complete within about one hour. Batch requests offer 50% lower token cost than standard processing. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

***

## When to Use Normal API vs Batch API

| Situation | Use | Why |
|---|---|---|
| User uploads one product photo and wants immediate answer | Normal synchronous API | User is waiting |
| Chatbot reply | Normal synchronous or streaming API | Must respond quickly |
| Check a single invoice | Normal synchronous API | Small real-time task |
| Nightly classification of 5,000 support tickets | Message Batches API | Offline, high volume, lower cost |
| Analyze 2,000 PDFs for an internal report | Message Batches API | No user waiting |
| Test a prompt against 10,000 examples | Message Batches API | Evaluation work is offline |
| Classify images overnight | Files API + Message Batches API | Reuse assets and process at scale |

***

## Batch Example: Classify Support Tickets

Suppose you need to classify 5,000 tickets overnight.

Each ticket must become:

```json
{
  "category": "BILLING | TECHNICAL | ESCALATION",
  "urgency": "LOW | MEDIUM | HIGH"
}
```

### Step 1: Create Batch Requests

```python
batch_requests = []

for ticket in tickets:
    batch_requests.append({
        "custom_id": f"ticket-{ticket['id']}",
        "params": {
            "model": model,
            "max_tokens": 256,
            "system": (
                "You are a support ticket classifier. "
                "Return only JSON with category and urgency."
            ),
            "messages": [
                {
                    "role": "user",
                    "content": ticket["message"]
                }
            ]
        }
    })
```

The `custom_id` is important because results may come back in a different order from the submitted requests. [platform.claude](https://platform.claude.com/docs/en/api/messages/batches)

### Step 2: Submit One Batch

```python
batch = client.messages.batches.create(
    requests=batch_requests
)

batch_id = batch.id

print(batch_id)
```

Now your application gets a batch ID:

```text
msgbatch_01XYZ...
```

Store it in your database so you can check later.

### Step 3: Poll for Completion

```python
import time

while True:
    batch_status = client.messages.batches.retrieve(batch_id)

    if batch_status.processing_status == "ended":
        break

    time.sleep(60)
```

Simple meaning:

```text
Submit batch
      ↓
Wait one minute
      ↓
Check status
      ↓
Still processing? Wait again
      ↓
Finished? Download results
```

### Step 4: Read Results

```python
for result in client.messages.batches.results(batch_id):
    ticket_id = result.custom_id

    if result.result.type == "succeeded":
        claude_message = result.result.message

        print(ticket_id, claude_message.content)
    else:
        print(ticket_id, "Failed:", result.result.type)
```

The result order is not guaranteed, so use `custom_id` to connect the answer back to the original ticket. [platform.claude](https://platform.claude.com/docs/en/api/messages/batches)

## Batch Example: Process Product Images Overnight

Suppose an e-commerce company has 10,000 product images and wants to check for poor-quality images.

### Goal

```text
For each image:
- Check for blur
- Check for missing product
- Check for visible watermark
- Check whether background is clean
- Return machine-readable result
```

### Good Design

```text
1. Upload reusable product images with Files API
        ↓
2. Save file_id against each product
        ↓
3. Build batch requests using file_id
        ↓
4. Submit one Message Batch
        ↓
5. Poll batch status
        ↓
6. Match results using product custom_id
        ↓
7. Store result in product-quality table
```

### Request Shape Example

```python
batch_requests.append({
    "custom_id": f"product-{product_id}",
    "params": {
        "model": model,
        "max_tokens": 256,
        "messages": [
            {
                "role": "user",
                "content": [
                    {
                        "type": "image",
                        "source": {
                            "type": "file",
                            "file_id": product_image_file_id
                        }
                    },
                    {
                        "type": "text",
                        "text": """
Check this product image.

Return only JSON:
{
  "product_visible": true,
  "blur_level": "LOW | MEDIUM | HIGH",
  "watermark_found": true,
  "background_quality": "GOOD | POOR",
  "notes": "short explanation"
}

Do not guess if the image is unclear.
"""
                    }
                ]
            }
        ]
    }
})
```

This is a good fit because:

```text
Many images
      +
No user waiting
      +
Same task for every image
      +
Need structured output
      =
Files API + Batch API
```

## Important Batch Rules

### 1. Batch Is Not for Live Users

Do not use a batch job for this:

```text
User uploads a damaged-item photo
        ↓
User expects answer now
```

Batch can take minutes or hours. Use normal synchronous API or streaming instead.

### 2. Batch Results May Be Out of Order

This is why each request needs a unique `custom_id`.

```text
Submitted:
ticket-1
ticket-2
ticket-3
```

Results may return as:

```text
ticket-3
ticket-1
ticket-2
```

Never rely on result position. Match using `custom_id`. [platform.claude](https://platform.claude.com/docs/en/api/messages/batches)

### 3. Chunking a Loop Is Not Batch Processing

This is still normal synchronous work:

```python
for chunk in chunks:
    for ticket in chunk:
        client.messages.create(...)
```

It still creates one request per ticket.

Real batch processing means:

```python
client.messages.batches.create(
    requests=many_requests
)
```

One batch submission contains many individual message requests. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

### 4. Batch Is Cheaper but Slower

```text
Normal API:
Fast result
Higher cost
Good for user waiting

Batch API:
Slower result
Lower cost
Good for offline work
```

Batch processing offers lower token pricing, but it is asynchronous and can take up to 24 hours. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

## Images + PDFs + Batch Together

This combination is useful for offline, repeated work.

### Example: Invoice Processing Pipeline

```text
10,000 invoice PDFs
        ↓
Upload PDFs once using Files API
        ↓
Store file_id with invoice record
        ↓
Create batch requests
        ↓
Ask Claude to extract invoice details
        ↓
Use JSON output
        ↓
Poll for completed batch
        ↓
Save results to database
```

Expected extracted output:

```json
{
  "invoice_number": "INV-1042",
  "invoice_date": "2026-09-20",
  "vendor_name": "Example Supplies Pvt Ltd",
  "total": 12500.00,
  "currency": "INR"
}
```

### Why It Works

```text
PDFs are reusable
→ Files API

Thousands of records
→ Batch API

Database needs reliable fields
→ JSON / structured output

No user waiting
→ Batch delay is acceptable
```

## What Can Go Wrong

| Problem | Why it happens | Better approach |
|---|---|---|
| Context fills quickly | Too many large images/PDFs in one request | Resize images, split work, send only relevant files |
| Requests are slow | High-resolution files use many tokens | Resize and compress before sending |
| Rate-limit errors | Thousands of normal API calls in a loop | Use Message Batches API |
| User waits too long | Batch used for real-time request | Use synchronous or streaming API |
| Results matched to wrong record | Code assumes result order matches input order | Use `custom_id` |
| Same file repeatedly uploaded | Base64 sent every request | Upload once with Files API |
| Wrong or inconsistent output | Prompt does not define expected structure | Use clear JSON output rules or structured output |
| Claude guesses unclear image/PDF text | Prompt does not tell it what to do when unclear | Add “use `NOT_READABLE` / `null`; do not guess” |

## Main Takeaway

Remember these simple rules:

```text
Large image
→ More visual tokens

Large PDF
→ More context tokens

Same file used many times
→ Upload once with Files API

One user waiting now
→ Normal API or streaming

Thousands of offline jobs
→ Message Batches API

Batch results out of order
→ Always use custom_id
```

Before building, test with real production image sizes, real PDFs, and realistic batch volume. This helps you avoid context-limit failures, unexpected cost, rate-limit errors, and slow user experiences.


## Correct Matches

| Scenario | Correct choice | Why |
|---|---|---|
| A reference product diagram used in every pipeline request | **Files API: upload once, reference `file_id` in each request** | The same diagram is reused repeatedly. Uploading once avoids repeatedly sending the full file data with every request.  [platform.claude](https://platform.claude.com/docs/en/build-with-claude/files) |
| A one-off UI bug screenshot from a support engineer | **Inline Base64: encode and include directly in the message block** | The screenshot is used only once. Adding a separate upload step gives little benefit for a single request.  [platform.claude](https://platform.claude.com/docs/en/build-with-claude/vision) |
| A job classifying 5,000 customer-feedback responses | **Message Batches API: submit all requests in one batch call, poll for completion** | This is high-volume, offline work. Batch processing is designed for many requests, costs less, and avoids thousands of normal synchronous calls.  [platform.claude](https://platform.claude.com/docs/en/build-with-claude/batch-processing) |

## Easy Rule

```text
Same file used again and again
→ Files API

One file used once
→ Inline Base64

Thousands of separate jobs, no user waiting
→ Message Batches API
```

## Important Difference

The first two choices decide **how to send a file**:

```text
Inline Base64
or
Files API
```

The third choice decides **how to submit many API requests**:

```text
Message Batches API
```

So a real high-volume image workflow can use both:

```text
Upload reusable images/PDFs
→ Files API

Classify thousands of them overnight
→ Message Batches API
```
