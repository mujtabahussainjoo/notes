## Simple Summary

This topic is about **agent memory**: what Claude should remember after one session ends and a new session starts.

The main decision is simple:

```text
What should the agent remember later?
        ↓
Where should that information be kept?
        ↓
How much will it cost to keep and retrieve it?
```

If you keep too much old conversation inside the prompt, every API call becomes more expensive and slower. If you save too little information outside the prompt, the agent forgets important things when the session ends. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

***

## Memory Types

| Memory type | What stays remembered | Best use | Main downside |
|---|---|---|---|
| In-context memory | Current chat messages and tool results | Short, one-session tasks | Grows every turn; lost when session ends |
| External storage | Data saved in DB, Redis, files, CRM, etc. | Multi-day work, shared state, user preferences | Needs database code and adds lookup time |
| Summarized memory | Short notes from an earlier long conversation | Continuing long tasks without replaying all history | Details may be lost |
| Stateless | Nothing is remembered | Independent one-time jobs | No follow-up memory |

***

## In-Context Memory

In-context memory means Claude remembers only what is inside the active conversation.

```text
System prompt
      +
User messages
      +
Claude answers
      +
Tool results
      =
Current session memory
```

### Example

```text
User:
“Investigate why guest checkout is failing.”

Agent:
1. Reads error logs.
2. Checks recent deployment.
3. Reads payment configuration.
4. Finds likely cause.
5. Gives an answer.
```

During this session, Claude can remember previous messages and tool results. But after a new session starts:

```text
New session
      ↓
Old chat history is gone
      ↓
Claude does not remember the prior investigation
```

### Use It When

- The task is short.
- The task completes in one session.
- The user does not need to continue tomorrow.
- Tool output is small.
- You do not need long-term memory.

### Problem

Every extra turn increases context size:

```text
More messages
      ↓
More tokens sent again on later calls
      ↓
More cost
      ↓
More latency
      ↓
Eventually context window fills
```

Context includes prompts, messages, tool definitions, tool calls, tool results, and generated output. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## External Storage

External storage means saving important information outside the Claude conversation.

Possible places:

```text
PostgreSQL
MySQL
Redis
MongoDB
S3 / file storage
Vector database
CRM
Magento customer data
Application database
```

### Example: Support Case Memory

Suppose a customer comes back after two days.

Instead of sending every old chat message, save important facts:

```json
{
  "case_id": "CASE-4821",
  "customer_id": "C-10024",
  "issue": "Guest checkout payment failure",
  "confirmed_findings": [
    "Logged-in checkout works",
    "Guest checkout fails after payment authorization",
    "Failure started after payment module update"
  ],
  "current_status": "Waiting for staging test",
  "next_step": "Compare guest token logic with previous module version"
}
```

When the next session begins, retrieve only useful state:

```text
<case_memory>
Case: CASE-4821
Issue: Guest checkout payment failure.

Confirmed:
- Logged-in checkout works.
- Guest checkout fails after payment authorization.
- Problem started after payment module update.

Current status:
Waiting for staging test.

Next step:
Compare guest token logic with previous module version.
</case_memory>
```

Now Claude can continue the case without receiving 50 pages of old conversation and logs.

### Use External Storage When

- The agent must remember information across days or weeks.
- Users return in later sessions.
- Several agents need shared state.
- You need audit records.
- A task must survive restarts or deployments.
- You need to store user preferences or case progress.

### Trade-off

```text
Database read/write
      +
Access-control checks
      +
Encryption
      +
Retention policy
      +
Extra engineering work
      =
More complexity
```

But it is usually much cheaper than sending full conversation history forever.

## Summarized Memory

Summarized memory means turning a long conversation into short, useful notes.

```text
Full chat history:
50,000 tokens
        ↓
Summary:
1,500 tokens
        ↓
Use summary in next session
```

### Example

Bad summary:

```text
The agent investigated a checkout issue and found some possible causes.
```

This is too vague.

Better technical summary:

```text
<investigation_summary>
Goal:
Fix guest checkout payment failure.

Confirmed findings:
- Logged-in checkout works.
- Guest checkout fails after payment authorization.
- Failure began after Vendor_Payment version 2.4.3 deployment.
- Error occurs in GuestTokenValidator.php.
- Production payment endpoint differs from staging.

Failed attempts:
- Redis flush did not fix the issue.
- Reindexing did not fix the issue.

Files checked:
- app/code/Vendor/Payment/Model/GuestTokenValidator.php
- app/code/Vendor/Payment/Plugin/CheckoutPlugin.php

Next steps:
- Compare guest-token logic with version 2.4.2.
- Test endpoint correction in staging.
- Do not edit production configuration without approval.
</investigation_summary>
```

### Good Summarizer Prompt

```text
Create a compact memory for the next agent session.

Keep:
- The current task goal
- Confirmed facts
- Important decisions
- File names and paths
- Important tool results
- Errors and root causes
- Fixes tried and their outcomes
- Pending work
- Safety rules and approval requirements

Remove:
- Repeated explanations
- Low-value exploration
- Casual discussion
```

### Risk

Anything missing from the summary is gone for the next session.

```text
Not included in summary
        ↓
Not available to Claude later
```

Use summarized memory when you need continuity but do not need every original detail.

## Stateless Agents

A stateless agent remembers nothing after finishing a request.

```text
New input
      ↓
Agent does job
      ↓
Returns result
      ↓
Session ends
      ↓
No memory is saved
```

### Example: Ticket Classification

```text
Input:
“My API key stopped working after rotation.”

Output:
{
  "category": "TECHNICAL",
  "urgency": "HIGH"
}
```

The next ticket does not need anything from this ticket.

### Best Uses

- Ticket classification
- Field extraction
- JSON formatting
- Translation
- Invoice processing
- Batch jobs
- One-time document analysis

### Benefit

```text
No old context
      ↓
Low cost
      ↓
Simple code
      ↓
No growing context problem
```

## Easy Decision Guide

```text
Does the task need memory from an earlier session?
        │
        ├── No
        │     ↓
        │   Use a stateless agent
        │
        └── Yes
              ↓
Does it only need a short current-session history?
        │
        ├── Yes
        │     ↓
        │   Use in-context memory
        │
        └── No
              ↓
Does it need exact facts, user preferences, or shared state?
        │
        ├── Yes
        │     ↓
        │   Use external storage
        │
        └── It mainly needs progress from earlier work
              ↓
            Use summarized memory,
            usually stored externally
```

In real production systems, combine approaches:

```text
Current task messages
→ In-context memory

Long-term case/customer/project data
→ External storage

Previous long conversation
→ Summary memory

Large documents and manuals
→ Retrieve only when needed
```

## Why Memory Must Be Designed Early

A common mistake is:

```text
Store full chat history in messages[]
        ↓
Send it again on every Claude request
        ↓
Prototype works
        ↓
Production traffic and long sessions arrive
        ↓
Token cost grows
        ↓
Context fills
        ↓
Agent fails or becomes unreliable
```

This may work during development because developers test one short or continuous session.

Production may be very different:

```text
Session 1: User starts case
Session 2: User returns later
Session 3: More logs and files are added
Session 4: Full old history is injected again
```

By Session 4, the agent can start with tens of thousands of tokens before doing useful work.

### Example Failure

```text
Old conversation history: 40,000 tokens
System prompt and tool schemas: 5,000 tokens
--------------------------------------------
Before first new tool call: 45,000 tokens
```

Then new tool outputs arrive:

```text
More logs
      +
More tool results
      +
More messages
      ↓
Context budget runs out
      ↓
Incomplete answers or worse tool routing
```

The agent may look as if it is selecting the wrong tool, but the real issue may be too much old memory in context.

The correct fix is:

```text
Full old history
      ↓
Move to external storage
      ↓
Keep only relevant facts and a short summary
      ↓
Inject the minimum needed memory for this session
```

## Skills: Reusable Instructions

A **Skill** is different from memory.

```text
Memory:
“What happened earlier?”

Skill:
“How should Claude perform this type of task?”
```

A Skill is a reusable folder containing a `SKILL.md` file. It has:

```text
1. Name
2. Description
3. Instructions
```

Claude can load a Skill only when the user request matches the Skill description. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/skills-guide)

### Example: Magento Module Review Skill

```markdown
---
name: magento-module-review
description: Review Adobe Commerce or Magento 2 modules for security, performance, API, and coding-standard problems.
---

# Magento Module Review

When reviewing a Magento module:

1. Check for direct ObjectManager usage.
2. Review plugins and preferences.
3. Check database queries and collections.
4. Review cache invalidation.
5. Check ACL and API authorization.
6. Check for unsafe customer-data exposure.
7. Return results under these headings:

## Critical issues
## Performance concerns
## Security concerns
## Suggested fixes
```

Folder structure:

```text
.claude/
  skills/
    magento-module-review/
      SKILL.md
```

When you ask:

```text
“Review this Magento payment module for security and performance problems.”
```

Claude can load this Skill.

When you ask:

```text
“Write a product description for running shoes.”
```

The Magento review Skill does not need to load.

This reduces context cost because full Skill instructions are loaded only for relevant tasks. Agent Skills are modular instruction/resource bundles, and their description is used to decide whether they should be loaded. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/skills-guide)

***

## Skills vs CLAUDE.md

| Pattern | When it loads | Best use | Context impact |
|---|---|---|---|
| Skill (`SKILL.md`) | Only when relevant | Specialized review checklists, domain workflows, special output formats | Low until needed |
| `CLAUDE.md` | Every session | Team rules, coding conventions, project-wide constraints | Fixed cost every session |
| In-context instructions | Every turn in current session | Short temporary work | Grows with chat history |

### Use `CLAUDE.md` For Always-On Rules

```markdown
# Project Rules

- Use TypeScript strict mode.
- Do not use `any`.
- Follow Magento coding standards.
- Add tests for changed business logic.
- Do not change database schema without migration files.
- Do not deploy production changes without approval.
```

These rules matter for every task in the project.

### Use Skills for Special Tasks

```text
Magento code review
Payment integration checklist
Security audit
Deployment review
Incident response
Performance investigation
```

Do not put all specialized instructions in `CLAUDE.md`; otherwise every unrelated session pays for them.

In the Agent SDK, filesystem sources such as `CLAUDE.md` and Skills are controlled through `settingSources` / `setting_sources`; configure this explicitly rather than relying on an assumed default. [code.claude](https://code.claude.com/docs/en/agent-sdk/claude-code-features)

## Important Rule for Subagents

Subagents start with separate context.

```text
Parent agent
        ↓
Delegates task
        ↓
Subagent starts with its own context
```

Do not assume a subagent automatically receives:

- Parent conversation history
- Parent Skill instructions
- Previous summaries
- Relevant documents

Give the subagent exactly what it needs.

### Example

```text
Task:
Review Magento payment module for security problems.

Subagent receives:
- Module path
- Read-only code-search tools
- Magento security review Skill
- Expected output format
- Stop after prioritized findings
```

This avoids missing instructions and unnecessary context.

## Main Takeaway

Remember this:

```text
In-context memory
→ Short-term memory during one session

External storage
→ Long-term memory across sessions

Summarized memory
→ Small notes from a large old conversation

Stateless
→ No memory; every job starts fresh

Skills
→ Reusable task instructions

CLAUDE.md
→ Rules that apply to every project task
```

The best production agent does not send every old conversation forever. It stores long-term facts outside the prompt, retrieves only what matters for the current task, summarizes old work carefully, and loads special instructions only when needed.

## Correct Matches

| Agent use case | Correct memory scope | Why |
|---|---|---|
| A customer support agent helps the same user through daily check-ins for two weeks | **External storage: write state to a database at session end, then read it back at session start** | The agent must remember case details, earlier findings, customer preferences, pending tasks, and prior decisions across separate sessions and days. In-context chat history disappears when a session ends. |
| A document formatter receives a file, transforms it, returns the output, and ends | **No persistent memory (stateless): each session starts fresh** | Every file job is independent. Saving old conversation state would add cost and complexity without helping the next document. |
| A coding assistant works with a developer for several hours in one session, then stops permanently | **In-context memory: all state lives in the active conversation** | The assistant needs to remember the current code discussion, files reviewed, decisions, and tool results during the active session, but nothing needs to survive after it ends. |

## Easy Memory Rule

```text
Needs to remember across separate sessions?
→ External storage

Each job is separate and independent?
→ Stateless

Needs memory only during one current session?
→ In-context memory
```

For the two-week support agent, a strong real-world design would use both a database and a short summary:

```text
Database:
- Customer ID
- Case ID
- Preferences
- Confirmed facts
- Current case status
- Open tasks
- Approval history

Prompt at new session:
- Current user request
- Relevant retrieved case data
- Short summary of previous progress
```

That avoids sending two weeks of full chat history on every API request while still allowing the agent to continue where it stopped.
