## Simple Summary

A **production agent** is an AI system that can take several steps, use tools, remember useful task state, and keep working until it reaches a goal.

But agents are not always the right choice. Start with the simplest solution:

```text
One Claude request
        ↓
Workflow with fixed steps
        ↓
Agent with flexible tool choices
```

Use an agent only when you cannot reliably write all the steps in advance. Workflows follow code-defined paths; agents decide which available tools and steps to use based on the current goal and context. [anthropic](https://www.anthropic.com/engineering/building-effective-agents)

***

## Workflow vs Agent

The first question is:

```text
Can I write the exact steps in normal code?
```

If the answer is yes, use a **workflow**. If the answer is no because every user request may need a different path, use an **agent**.

| Choose a workflow when | Choose an agent when |
|---|---|
| Steps are known in advance | Goal is known, but the path is not |
| Every request follows the same order | User requests can vary a lot |
| You need strict control and predictable actions | The AI must choose between tools dynamically |
| Mistakes are expensive and each step needs fixed checks | Some non-deterministic behavior is acceptable |
| Standard logs and debugging are sufficient | You can observe full agent transcripts and tool calls |
| Example: order return process | Example: investigate an unknown production issue |

### Workflow Example: Return an Order

A return process can usually be written as fixed code:

```text
1. Verify user login
2. Find order
3. Check return window
4. Check product return eligibility
5. Create return request
6. Send confirmation
```

This should be a workflow:

```python
if user_is_authenticated():
    order = get_order(order_id)

    if within_return_window(order) and is_returnable(order):
        create_return_request(order)
        send_confirmation()
```

There is no need to let an AI decide the process.

### Agent Example: Investigate Checkout Failure

A production issue may be unclear:

```text
“The checkout is failing sometimes.”
```

The right path depends on what Claude finds:

```text
Read error logs
        ↓
Check recent deployment history
        ↓
Inspect payment-module configuration
        ↓
Review failed API calls
        ↓
Compare guest checkout versus logged-in checkout
        ↓
Suggest safe next action
```

The exact order cannot always be known in advance. This is where an agent can be useful.

## Basic Agent Loop

Every single-agent system follows the same core loop:

```text
1. User gives a goal
        ↓
2. Claude decides whether it needs a tool
        ↓
3. Claude requests a tool call
        ↓
4. Your application runs the tool
        ↓
5. Your application returns the result
        ↓
6. Claude decides the next step
        ↓
7. Repeat until task is done
```

The Agent SDK documentation describes this as a repeated cycle: receive prompt, evaluate, request or return tools, execute tools, return results, and repeat until Claude completes the task. [code.claude](https://code.claude.com/docs/en/agent-sdk/agent-loop)

### Simple Example: Store Support Agent

```text
User:
“My checkout is failing. Can you find the cause?”
```

Possible agent loop:

```text
Claude:
“I need recent checkout errors.”
        ↓
Tool:
get_checkout_errors()
        ↓
Result:
500 error after payment authorization
        ↓
Claude:
“I need the latest payment-module deployment.”
        ↓
Tool:
get_recent_deployments()
        ↓
Result:
Payment module updated 30 minutes ago
        ↓
Claude:
“I should inspect configuration differences.”
        ↓
Tool:
compare_payment_config()
        ↓
Result:
Production API endpoint is missing
        ↓
Claude:
“Likely root cause: missing payment API endpoint after deployment.”
```

This is agent behavior because the next tool is chosen based on previous results.

## Three Ways to Build Agents

The agent loop is the same, but you can choose how much infrastructure you build yourself.

| Path | Who runs the loop? | Best when | What you own |
|---|---|---|---|
| Raw Messages API | Your application | You need complete control | Loop, tool execution, retries, history, context, errors, exit rules |
| Agent SDK | Your application process, with SDK support | You want production help but still need local control | Your tools, permissions, application integration, deployment controls |
| Claude Managed Agents | Anthropic-managed environment | Long-running work, managed execution, managed sandbox | Agent definition, event handling, integration, governance decisions |

### 1. Raw Messages API

You write all logic yourself:

```python
while True:
    response = client.messages.create(
        model=model,
        messages=messages,
        tools=tools
    )

    messages.append({
        "role": "assistant",
        "content": response.content
    })

    if response.stop_reason != "tool_use":
        break

    tool_results = run_requested_tools(response.content)

    messages.append({
        "role": "user",
        "content": tool_results
    })
```

**Good when:**
- You need maximum control.
- You have special deployment or compliance needs.
- You want to understand every part of the loop.
- You need custom state, retries, approval flows, or observability.

**Cost:** you must implement and test everything.

***

### 2. Agent SDK

The Agent SDK gives you a ready-made agent structure, including an agent loop, tools, permissions, and context-management support. You still decide which tools to expose and what the agent is allowed to do. [code.claude](https://code.claude.com/docs/en/agent-sdk/agent-loop)

**Good when:**
- You want to build inside your own Python or TypeScript application.
- You need more control than a fully hosted agent.
- You want SDK-provided help for loop management and tool handling.
- You want to use permissions or hooks to inspect, modify, or block tool calls.

The SDK provides hooks that can intercept, modify, or block calls before they run—useful for approval checks and policy enforcement. [code.claude](https://code.claude.com/docs/en/agent-sdk/agent-loop)

***

### 3. Claude Managed Agents

Managed Agents is a hosted option where Anthropic runs the agent loop, session, and execution environment. Your application creates an agent configuration, starts a session, sends user events, and receives streamed results. [platform.claude](https://platform.claude.com/docs/en/managed-agents/quickstart)

```text
Your app
      ↓
Managed Agent configuration
      ↓
Anthropic runs loop and sandbox
      ↓
Your app receives streamed progress and final result
```

**Good when:**
- Tasks can run for minutes or hours.
- You do not want to build and secure an execution sandbox.
- You do not want to maintain the full agent loop.
- A hosted, stateful session fits your data requirements.

Managed Agents is documented as a beta feature, with an API flow where you define an agent and then run sessions against it. [platform.claude](https://platform.claude.com/docs/en/managed-agents/quickstart)

**Important data constraint:** because Managed Agents sessions are stateful and server-managed, confirm current retention, zero-data-retention, HIPAA/BAA, regional, and other compliance eligibility before using them with regulated or sensitive data. For PHI, privileged legal content, or strict zero-retention requirements, choose an approved architecture and endpoint with your compliance team rather than selecting a hosted path only for convenience. [support.claude](https://support.claude.com/en/articles/15425996-data-retention-practices-for-covered-models)

## Agent Loop Checklist

No matter which wiring path you choose, verify these five things.

| Check | What it means |
|---|---|
| Tools registered | Every needed tool exists; no unnecessary tools are exposed |
| System prompt scoped | The prompt states the exact job, safety rules, and allowed tool purpose |
| Tool loop works | Every tool call gets a correct matching tool result |
| Human approval exists | Risky actions pause for a user or operator decision |
| Exit conditions exist | Agent stops when the task is done or limit is reached |

### Minimal Agent System Prompt

```text
You are a checkout-incident investigation agent.

Your job is to identify likely causes of checkout failures and
produce a safe investigation summary.

Available tools:
- get_checkout_errors: retrieves recent checkout errors
- get_recent_deployments: retrieves recent deployment information
- get_payment_config: retrieves current payment configuration
- compare_configs: compares staging and production configuration

Rules:
- Use read-only tools only.
- Do not modify files, deployment settings, orders, or customer data.
- State uncertainty when evidence is incomplete.
- Stop after identifying the most likely root cause and recommended next step.
```

A narrow system prompt improves tool routing because Claude knows its exact goal and tool boundaries.

***

## Exit Conditions Matter

Without clear exit conditions, an agent may keep calling tools even after it has enough information.

Bad design:

```text
Agent keeps exploring until Claude decides it is finished.
```

Better design:

```text
Stop when:
- Root cause has evidence from at least two sources, or
- No additional tool can produce relevant evidence, or
- Maximum of five tool rounds is reached, or
- A human approval decision is required, or
- A tool error requires manual action.
```

Example in code:

```python
MAX_TOOL_ROUNDS = 5
tool_rounds = 0

while tool_rounds < MAX_TOOL_ROUNDS:
    response = call_claude()

    if response.stop_reason == "end_turn":
        break

    if response.stop_reason != "tool_use":
        break

    run_tools_and_return_results()
    tool_rounds += 1

if tool_rounds == MAX_TOOL_ROUNDS:
    return "Investigation paused: tool-call limit reached. Human review needed."
```

This prevents accidental loops, surprise cost, and repeated unnecessary tool calls.

## Human-in-the-Loop (HITL)

**Human-in-the-loop** means the agent pauses before a risky step and asks a human to approve, reject, or modify the action.

The main question is:

```text
What is the worst thing that could happen if this tool runs automatically?
```

If the damage could be serious or difficult to reverse, require approval.

| Where to add approval | When to use it | Example |
|---|---|---|
| Before destructive action | Tool can change, delete, send, publish, or spend money | Delete records, deploy production code, send email, cancel order |
| After plan creation | Wrong plan could cause harmful work even if each action is valid | Database migration, infrastructure update, customer account remediation |
| On unusual tool result | Tool errors, unexpected values, empty data, out-of-range result | Payment refund amount is unusually high |
| Before external communication | Agent will contact a customer, vendor, or team | Send a support reply, create public issue, publish announcement |

### Unsafe File-Editing Agent

```text
Agent:
1. Reads production configuration file
2. Detects incorrect value
3. Edits file
4. Runs validate_config
5. Validation passes
6. Agent stops
```

This may appear correct, but it can still harm production.

For example:

```text
Agent changes rate_limit from 1000 to 100
        ↓
Configuration syntax is valid
        ↓
validate_config returns PASS
        ↓
Real application traffic is throttled
        ↓
Production outage
```

The file was valid, but the business and operational effect was harmful.

### Safer Design

```text
Agent:
1. Reads configuration
2. Detects possible problem
3. Creates proposed change
4. Validates proposed change
5. Pauses for human approval
6. Human approves or rejects
7. Only after approval, write_file runs
8. Validate again
9. Monitor outcome
```

```text
Propose change
      ↓
Validate proposal
      ↓
Human approval
      ↓
Commit write
```

A validation check confirms that a file follows rules. It does **not** guarantee that the change is safe for a real production system.

***

## Example: HITL in Code

```python
proposal = {
    "file": "/etc/app/config.yaml",
    "change": {
        "rate_limit": {
            "old_value": 1000,
            "new_value": 100
        }
    },
    "reason": "Current value violates the configured limit.",
    "risk": "Reducing this value may throttle production traffic."
}

approval = request_human_approval(proposal)

if approval.status != "approved":
    return {
        "status": "stopped",
        "message": "No production change was made."
    }

write_file(
    path=proposal["file"],
    changes=proposal["change"]
)
```

For irreversible or high-impact actions, the agent should have permission to **propose**, not automatically **commit**.

## Tool Orchestration: Avoid Too Many Tools

Giving an agent every available tool “just in case” can lower reliability.

```text
Too many overlapping tools
        ↓
Claude has more similar choices
        ↓
Wrong tool selection becomes more likely
        ↓
More prompt/context tokens
        ↓
Higher cost and slower decisions
```

### Bad Tool Set

```text
search_docs
find_docs
lookup_docs
query_help
get_info
search_knowledge_base
```

These tools overlap too much.

### Better Tool Set

```text
search_knowledge_base
get_current_session_summary
get_order_status
get_recent_deployments
create_support_ticket
```

Each tool has a separate purpose.

For a checkout-incident agent, start with only:

```text
get_checkout_errors
get_recent_deployments
get_payment_config
compare_configs
```

Add another tool only after you identify a real missing capability.

## Production Design Example

### Goal

```text
Find why checkout is failing after a deployment.
```

### Tools

```text
get_checkout_errors()
get_recent_deployments()
get_payment_config()
compare_configs()
create_incident_ticket()
```

### Safe System Prompt

```text
You are a read-only checkout incident investigation agent.

Goal:
Identify the most likely cause of a checkout failure after a deployment.

Use only these read-only tools:
- get_checkout_errors
- get_recent_deployments
- get_payment_config
- compare_configs

Rules:
- Do not change configuration.
- Do not deploy or roll back code.
- Do not access unrelated customer data.
- Use no more than five tool rounds.
- Stop when evidence supports one likely root cause.
- If evidence is insufficient, return a short list of next manual checks.
- Before create_incident_ticket, present the ticket draft for human approval.
```

### Agent Flow

```text
User reports checkout failure
        ↓
Agent checks errors
        ↓
Agent checks latest deployment
        ↓
Agent compares configuration
        ↓
Agent identifies likely cause
        ↓
Agent creates proposed incident summary
        ↓
Human approves ticket creation
        ↓
Agent creates ticket
        ↓
Agent stops
```

## Compliance and Data Path

For regulated or sensitive data, decide the approved data route **before** building the agent.

This is not mainly a prompt decision. It affects:

```text
API endpoint
      +
Cloud region
      +
Credentials
      +
Logging destination
      +
Data retention
      +
Tool execution environment
      +
Vendor approval
```

Examples of requirements that can change the architecture:

- Legal privilege or confidential legal documents
- Patient health information
- EU data residency
- Government/FedRAMP workloads
- Internal cloud-vendor restrictions
- Audit and logging requirements

The correct approach is:

```text
Name the data constraint first
        ↓
Select an approved endpoint and cloud route
        ↓
Configure credentials and region
        ↓
Route application logs to approved storage
        ↓
Then build prompts, tools, memory, and the agent loop
```

For these cases, confirm the exact supported configuration with your organization’s security/compliance team and the current provider documentation. Anthropic’s trust guidance notes that eligibility for data controls and covered products can vary by product, account configuration, and access route. [support.claude](https://support.claude.com/en/articles/15425996-data-retention-practices-for-covered-models)

## Key Takeaways

```text
Known fixed steps?
→ Build a workflow.

Goal known, path unknown?
→ Consider an agent.

Need total control?
→ Use raw Messages API loop.

Need SDK help but local control?
→ Use Agent SDK.

Need managed loop and sandbox for long-running work?
→ Consider Managed Agents, after checking data constraints.

Can the agent send, write, delete, deploy, cancel, refund, or publish?
→ Add human approval before the action.

Agent picks a valid path but keeps working forever?
→ Add explicit exit conditions.

Tool routing becomes confused?
→ Reduce the exposed tool set and clarify descriptions.
```

The safest production agent is not the one with the most tools or the most autonomy. It is the one with the smallest useful tool set, clear boundaries, controlled context, clear stop rules, and human approval before any action that can harm users, systems, money, or data.

## Gap 1: `update_record` Tool Description

Use a description that clearly says **when Claude should use it** and **when it must not use it**. Because this tool changes customer data, it must only run after human approval.

```python
"description": (
    "Use this tool to update one specified field in an existing customer "
    "record after the requested change has been reviewed and explicitly "
    "approved by a human. Use it only when a valid customer_id, field name, "
    "and new value are available. Do not use it to read customer data, search "
    "for a customer, make multiple updates at once, delete a record, or make "
    "any change without human approval. Returns the updated field and its "
    "new value."
),
```

This description gives Claude a clear boundary:

```text
Read customer data?
→ Use read_record

Change one approved customer field?
→ Use update_record

No approval yet?
→ Do not execute update_record
```

## Gap 2: HITL Checkpoint Code

Insert this inside the `if block.type == "tool_use":` section, **before** `execute_tool(...)`.

```python
if block.name == "update_record":
    approval_request = {
        "action": "update_record",
        "customer_id": block.input["customer_id"],
        "field": block.input["field"],
        "new_value": block.input["new_value"]
    }

    approved = request_human_approval(approval_request)

    if not approved:
        tool_results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "is_error": True,
            "content": (
                "The requested customer record update was not approved by "
                "a human. Do not make the update."
            )
        })
        continue
```

The full relevant part becomes:

```python
for block in response.content:
    if block.type == "tool_use":

        if block.name == "update_record":
            approval_request = {
                "action": "update_record",
                "customer_id": block.input["customer_id"],
                "field": block.input["field"],
                "new_value": block.input["new_value"]
            }

            approved = request_human_approval(approval_request)

            if not approved:
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "is_error": True,
                    "content": (
                        "The requested customer record update was not approved "
                        "by a human. Do not make the update."
                    )
                })
                continue

        result = execute_tool(block.name, block.input)

        tool_results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": result
        })
```

## Why This Is Correct

`read_record` is a read-only action:

```text
Read data
→ Lower risk
→ Usually no approval needed
```

`update_record` changes customer data:

```text
Update data
→ Could be wrong or irreversible
→ Human approval required before execution
```

The approval must happen **before** this line:

```python
result = execute_tool(block.name, block.input)
```

Otherwise, the update may already have been made before anyone reviews it.

If approval is rejected, the application sends a matching `tool_result` with:

```python
"is_error": True
```

That lets Claude know the tool was not executed, so it can safely tell the user that the requested update was not approved or ask for a different action. Tool calls must receive matching tool-result blocks, including when a tool is blocked or fails. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
