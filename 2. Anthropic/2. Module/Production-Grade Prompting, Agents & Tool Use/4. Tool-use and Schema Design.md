## Simple Summary

**Tool use** means Claude can ask your application to perform an action, such as checking an order, searching documentation, reading a database, or creating a ticket. Claude does **not** run the tool itself; it selects a tool and supplies inputs, while **your code** executes the real action and sends the result back. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

Think of Claude as a smart receptionist:

```text
User asks a question
       ↓
Claude chooses the correct department/tool
       ↓
Your application does the real work
       ↓
Your application sends the result to Claude
       ↓
Claude explains the result to the user
```

***

## Tool-Use Loop

A tool loop always follows this pattern:

```text
1. You define available tools
          ↓
2. User asks a question
          ↓
3. Claude selects a tool and returns tool_use
          ↓
4. Your backend runs the tool
          ↓
5. Your backend returns tool_result
          ↓
6. Claude uses the result and replies,
   or asks to use another tool
```

Claude returns `stop_reason: "tool_use"` when it needs your application to run a client-side tool. Your app then makes a new API request containing the previous messages, Claude’s full response, and the matching tool result. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

### Example: Order Status

```text
User:
“Where is my order 10001234?”

Claude decides:
“I need the order-status tool.”

Your backend:
Calls Magento / Adobe Commerce order API.

Tool result:
Order is shipped. Courier: BlueDart.
Expected delivery: 28 September.

Claude:
“Your order has been shipped through BlueDart and is expected
to arrive on 28 September.”
```

Claude does not connect to Magento by itself. Your secured backend decides whether it is allowed to read that order and then performs the API call.

## Main Tool Parts

Every tool definition has three important parts:

| Part | Meaning | Example |
|---|---|---|
| `name` | Short technical name for the tool | `get_order_status` |
| `description` | Explains what it does, when to use it, and when not to use it | “Use for a current order status. Do not use for order cancellation.” |
| `input_schema` | Defines which input data the tool needs | `order_id` must be a string |

Claude chooses tools mostly from their **name and description**. A vague description can make Claude select the wrong tool even when the JSON fields are valid. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

## Good vs Bad Tool Schema

### Bad Tool

```json
{
  "name": "get_data",
  "description": "Use this to find information.",
  "input_schema": {
    "type": "object",
    "properties": {
      "id": {
        "type": "string"
      }
    }
  }
}
```

Problems:

- `get_data` does not explain what data it gets.
- “Find information” is too broad.
- Claude does not know when **not** to use it.
- `id` has no meaning: order ID, customer ID, ticket ID, or product ID?
- Missing required fields may cause Claude to guess.

### Good Tool

```json
{
  "name": "get_order_status",
  "description": "Use this tool to retrieve the current shipping and delivery status for a specific customer order. Use it when the user asks where an existing order is, whether it has shipped, or when it will arrive. Do not use it to cancel an order, modify an order, view product stock, or search orders when no order ID is available. Returns order status, courier name, tracking number, and estimated delivery date.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "The customer order number, for example 10001234."
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

Why this is better:

```text
Specific name
      +
What it does
      +
When to call it
      +
When not to call it
      +
Expected result
      +
Clear required input
      =
Better tool selection
```

Tool descriptions should help Claude distinguish tools that sound similar. The official docs note that Claude decides when a tool is needed based on the user’s request and the tool description. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

## Required vs Optional Fields

Do not mark every field as required.

### Required Field

Make a field required when the tool cannot work without it.

```json
"required": ["order_id"]
```

An order-status tool cannot usually find a specific order without an order ID.

### Optional Field

Make a field optional when the tool has a sensible default or can operate without it.

```json
{
  "name": "search_products",
  "description": "Search the product catalog by keyword. Use when a customer wants to find products. Do not use for checking the status of an existing order.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "Words to search for, for example 'black running shoes'."
      },
      "page_size": {
        "type": "integer",
        "description": "Maximum number of products to return. Default is 10."
      }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

Here:

```text
query     → Required, because searching needs words
page_size → Optional, because the backend can use 10 by default
```

If you mark optional fields as required, Claude may invent a value just to satisfy the schema.

## Tool Call and Result Blocks

Tool conversations use **structured blocks**, not only plain text.

| Block | Sent by | Contains | Key rule |
|---|---|---|---|
| `text` | Claude | Normal written response | Preserve it in message history, even if Claude also calls a tool |
| `tool_use` | Claude | Tool name, unique ID, input arguments | Must receive a matching tool result |
| `tool_result` | Your app, inside a user message | Result of the real tool execution | Must use the exact matching `tool_use_id` |
| `thinking` | Claude, if extended thinking is enabled | Reasoning-related block | Must be returned unchanged on the next turn |

For every `tool_use` block, your next user message must include a `tool_result` block with the exact matching ID. Tool results must immediately follow the assistant tool-use turn; do not insert another message between them. The API validates this structure. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/build-a-tool-using-agent)

## Full Example: One Tool Call

### Step 1: Define Tool

```python
tools = [
    {
        "name": "get_order_status",
        "description": (
            "Use this tool to retrieve the current delivery status of a "
            "specific order. Use it when the user asks where an order is, "
            "whether it shipped, or its expected delivery date. "
            "Do not use it for cancellations, returns, or product searches."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "order_id": {
                    "type": "string",
                    "description": "Order number, for example 10001234."
                }
            },
            "required": ["order_id"],
            "additionalProperties": False
        }
    }
]
```

### Step 2: Send User Message

```python
messages = [
    {
        "role": "user",
        "content": "Where is my order 10001234?"
    }
]

response = client.messages.create(
    model="claude-model",
    max_tokens=1024,
    tools=tools,
    messages=messages
)
```

### Step 3: Claude Requests Tool Use

Claude may return something like:

```json
{
  "stop_reason": "tool_use",
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_01ABC",
      "name": "get_order_status",
      "input": {
        "order_id": "10001234"
      }
    }
  ]
}
```

Your code must save the **complete** `response.content`, not only the tool call. A Claude response may include text, tool calls, and—when enabled—thinking blocks together. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)

### Step 4: Your Backend Runs the Tool

```python
order = get_order_status(order_id="10001234")
```

Example backend result:

```python
{
    "status": "shipped",
    "courier": "BlueDart",
    "tracking_number": "BD123456789",
    "estimated_delivery": "2026-09-28"
}
```

In a real Adobe Commerce application, also verify:

```text
- Is the customer logged in?
- Does the order belong to this customer?
- Is the requested data safe to reveal?
```

A valid Claude tool call does not replace authorization checks in your application.

### Step 5: Return Tool Result

```python
messages.append({
    "role": "assistant",
    "content": response.content
})

messages.append({
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": "toolu_01ABC",
            "content": """
            {
              "status": "shipped",
              "courier": "BlueDart",
              "tracking_number": "BD123456789",
              "estimated_delivery": "2026-09-28"
            }
            """
        }
    ]
})
```

The `tool_use_id` must exactly match the original tool-call ID. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/build-a-tool-using-agent)

### Step 6: Ask Claude to Continue

```python
final_response = client.messages.create(
    model="claude-model",
    max_tokens=1024,
    tools=tools,
    messages=messages
)
```

Claude can now answer:

```text
Your order has been shipped through BlueDart and is expected
to arrive on 28 September 2026.
```

## Handling Tool Errors

Tools can fail because of a timeout, bad input, missing data, or external API errors. Return an error result rather than pretending the tool succeeded.

```python
messages.append({
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": "toolu_01ABC",
            "is_error": True,
            "content": "Order 10001234 was not found."
        }
    ]
})
```

Claude can then ask the user for a correct order number instead of inventing an answer. The tool-result format supports an `is_error` flag for this purpose. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

## Multiple Tools: Parallel vs Sequential

Claude can ask for more than one tool in the same response. Whether your code runs them together depends on whether the tools depend on each other.

### Parallel: Independent Work

User asks:

```text
“Check my order 10001234 and tell me whether the black running
shoes are in stock.”
```

Possible tool calls:

```text
get_order_status(order_id="10001234")
search_products(query="black running shoes")
```

These calls are independent, so your backend can run both at the same time:

```text
Claude requests two tools
          ↓
Run both concurrently
          ↓
Return both tool results together
          ↓
Claude creates one final answer
```

When returning parallel results, return **one matching `tool_result` for every `tool_use` block**, together in the next user message. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)

```python
messages.append({
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": "toolu_order",
            "content": "{\"status\": \"shipped\"}"
        },
        {
            "type": "tool_result",
            "tool_use_id": "toolu_stock",
            "content": "{\"in_stock\": true, \"qty\": 8}"
        }
    ]
})
```

### Sequential: Dependent Work

User asks:

```text
“Find my most recent order and tell me its delivery status.”
```

Claude cannot check status until it knows the order ID.

```text
1. find_recent_order(customer_id)
          ↓
2. Result gives order_id = 10001234
          ↓
3. get_order_status(order_id="10001234")
          ↓
4. Claude answers the user
```

This must happen in separate turns because the second tool input depends on the first result.

**Easy rule:**

```text
Tool B needs result from Tool A
→ Run in sequence

Tools do not need each other
→ Run in parallel
```

Claude documentation describes parallel tool-use support and requires every parallel call to have its corresponding result returned in the next user message. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)

## Avoid Wrong Tool Selection

Imagine two poorly described tools:

```text
search_knowledge_base:
“Use this to find information.”

get_cached_result:
“Use this to find information.”
```

Claude has almost no useful way to choose between them.

### Better Versions

```text
search_knowledge_base:
“Use this to search the knowledge base for current information
when the user asks a question not already answered in this session.
Do not use this if an earlier search in the same conversation
already returned relevant information.”

get_cached_result:
“Use this to retrieve information already fetched earlier in the
current conversation. Use it only when a previous knowledge-base
search covers the same question. Do not use it to perform a new search.”
```

Now Claude has a decision rule:

```text
Need new information?
→ search_knowledge_base

Need an already-found result?
→ get_cached_result
```

If two tools keep needing longer and longer descriptions to separate them, consider merging them into one tool.

### Example of Merging Similar Tools

Instead of:

```text
get_billing_faq()
get_technical_faq()
get_shipping_faq()
```

Use:

```json
{
  "name": "search_help_center",
  "description": "Search the help center for a customer question. Use for billing, technical, shipping, returns, and account questions.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string"
      },
      "topic": {
        "type": "string",
        "enum": ["BILLING", "TECHNICAL", "SHIPPING", "RETURNS", "ACCOUNT"]
      }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

This reduces the number of near-identical choices Claude must reason about.

## MCP: Reuse Existing Tool Servers

**MCP** means Model Context Protocol. It is a standard way to connect AI applications to external tools and services.

Without MCP, you may need to build and maintain every tool yourself:

```text
Your app
   ├── GitHub tool schema
   ├── GitHub API execution code
   ├── Issue tool schema
   ├── Pull-request tool schema
   ├── Repository tool schema
   └── Ongoing maintenance as GitHub API changes
```

With a suitable MCP server:

```text
Your app
      ↓
MCP server for GitHub
      ↓
Tools for repositories, issues, pull requests, etc.
```

The tool-use cycle remains the same:

```text
Claude selects tool
      ↓
Tool runs through MCP server
      ↓
Result returns
      ↓
Claude uses result
```

The difference is that the MCP server owns the service connection and tool definitions, rather than your application manually defining every schema. Claude’s API can connect directly to remote MCP servers and lets you configure or limit exposed tools. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

***

## MCP Context Cost

Every tool definition uses context space. If you connect many MCP servers, Claude may receive many tools and descriptions before the user even asks the first question.

```text
More MCP servers
      ↓
More tool schemas
      ↓
More context tokens
      ↓
Higher cost and less room for conversation
```

For the Claude API MCP Connector, you can:

- Disable tools you do not need with `enabled: false`
- Delay loading large tool definitions with `defer_loading: true`
- Expose only the specific tools needed for the task

The `enabled` option controls whether a tool is available, and `defer_loading` prevents its description from being sent to the model initially; the latter works with tool search. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)

**Example MCP configuration idea:**

```json
{
  "type": "mcp_toolset",
  "mcp_server_name": "github",
  "default_config": {
    "enabled": false,
    "defer_loading": true
  },
  "configs": {
    "get_issue": {
      "enabled": true,
      "defer_loading": false
    },
    "create_issue": {
      "enabled": true,
      "defer_loading": false
    }
  }
}
```

This means:

```text
GitHub server is connected
       ↓
Most tools stay unavailable
       ↓
Only get_issue and create_issue are shown to Claude
       ↓
Lower context cost and fewer wrong tool choices
```

## Important Production Rules

1. **Claude chooses; your code executes.** Never assume the model directly runs your database query, API request, email send, or Magento action. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

2. **Treat tool input as untrusted input.** Even if schema-valid, validate permissions, ownership, business rules, rate limits, and security on the backend.

3. **Keep the full assistant content array.** Do not keep only the tool-call block. Text and thinking blocks may be required for a correct next turn. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

4. **Return results immediately in the next user turn.** Every tool call needs one matching result using the exact `tool_use_id`. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/build-a-tool-using-agent)

5. **Use `is_error: true` for failures.** This lets Claude handle an unavailable service or missing data honestly instead of guessing. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

6. **Use parallel calls only for independent tasks.** If a later tool needs output from an earlier tool, make separate sequential turns. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)

7. **Keep tools distinct.** Clear names, concise descriptions, “when to use” conditions, and “when not to use” conditions improve routing. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

8. **Use MCP when it saves real maintenance work.** Use manual schemas when you need exact control or no suitable maintained MCP server exists. For broad MCP tool sets, restrict visible tools to protect context budget. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)

```text
Claude decides what to call.
```

## Rule That Was Broken

Every `tool_use` block returned by Claude must receive a matching `tool_result` block in the **immediately following user turn**.

```text
Claude sends:
tool_use id = toolu_01
        ↓
Your app must send:
tool_result tool_use_id = toolu_01
```

The ID must match exactly. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

## Easy Rule to Remember

```text
Tool call ID in Claude response
           =
Tool result ID sent by your application
```

If they do not match exactly, Claude’s API cannot connect the result to the tool call, so the next request fails validation.
