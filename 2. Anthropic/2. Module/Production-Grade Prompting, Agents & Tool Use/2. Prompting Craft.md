## Simple Summary

A prompt that works once in a chat may fail in a real application because real users give unexpected inputs. The right fix is usually **not** “write a longer prompt”; first identify what failed, then add the one missing prompt technique.

The four main techniques are:

1. **System prompt** — sets permanent rules for Claude.
2. **XML tags** — clearly separate instructions, examples, user input, code, and documents.
3. **Few-shot examples** — show Claude exactly what a correct answer looks like.
4. **Output constraints** — clearly state the required output format, such as one label or valid JSON.

***

## Which Problem Needs Which Fix?

| What goes wrong | What is missing | Best fix |
|---|---|---|
| You expect one label, but receive a sentence or extra explanation | Output format rule | Add an output constraint |
| Claude slowly changes tone, role, scope, or rules across a conversation | Clear permanent instructions | Improve the system prompt |
| Claude understands the task but invents its own response layout | A clear example | Add one or more few-shot examples |
| It works for simple test data but fails on unusual inputs | A rule or example for that special case | Add an edge-case constraint or example |
| Claude mixes instructions with user data, code, or documents | Clear boundaries | Add XML tags |

**Simple rule:** name the failure first. Then add the matching technique. Do not keep adding random extra instructions.

***

## The Four Techniques Explained

### 1. System Prompt: The Permanent Rules

A system prompt is the main instruction that stays active for the whole conversation. It tells Claude:

- Its role
- What it should and should not do
- The allowed output format
- The tone and scope
- Important rules that must remain unchanged

**Example:**

```text
You are a customer-support ticket classifier.

Classify every ticket into exactly one category:
BILLING, TECHNICAL, or ESCALATION.

Return only the category name.
Do not add explanations.
```

This is better than repeating the same rules in every user message.

Use a system prompt when Claude:
- Starts answering questions outside its job
- Changes tone or rules after several messages
- Gives overly broad answers
- Forgets an important output rule

***

### 2. XML Tags: Clear Separation

XML tags are simple labels such as:

```text
<instructions>
...
</instructions>

<ticket>
...
</ticket>
```

They help Claude understand what is an instruction and what is only data to analyze. Anthropic recommends using clear, descriptive, consistent tag names, especially when a prompt has multiple documents, examples, instructions, or inputs.

**Bad prompt:**

```text
Classify this support request.

My account shows two charges.

Return only BILLING, TECHNICAL, or ESCALATION.
```

Claude can still understand this, but longer prompts become confusing.

**Better prompt:**

```text
<instructions>
Classify the support ticket into exactly one category:
BILLING, TECHNICAL, or ESCALATION.

Return only the category.
</instructions>

<ticket>
My account shows two charges.
</ticket>
```

**Useful tag names:**

```text
<instructions>
<rules>
<examples>
<sample_input>
<ideal_output>
<ticket>
<user_query>
<documentation>
<my_code>
<product_data>
```

There are no special “official” tag names you must use. Use names that make sense for your content. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

***

### 3. Few-Shot Examples: Show, Don’t Only Tell

Few-shot prompting means giving Claude a few correct examples.

Use examples when writing instructions is not enough to explain:
- Exact casing, such as `BILLING` rather than `Billing`
- Exact JSON structure
- Special formatting
- How to handle confusing or unusual cases
- The tone and style you expect

**Example:**

```text
<instructions>
Classify each support ticket.
Return only one of:
BILLING, TECHNICAL, ESCALATION.
</instructions>

<examples>
  <example>
    <sample_input>
    My account shows two charges for April.
    </sample_input>

    <ideal_output>
    BILLING
    </ideal_output>
  </example>

  <example>
    <sample_input>
    The API returns a 429 error.
    </sample_input>

    <ideal_output>
    TECHNICAL
    </ideal_output>
  </example>
</examples>

<ticket>
I was charged twice for the same month.
</ticket>
```

Expected result:

```text
BILLING
```

The examples teach Claude the exact expected pattern. Anthropic’s prompting guidance recommends making examples relevant to the actual task and wrapping them clearly so they do not get confused with instructions or live input. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

**Important:** examples use input tokens on every API request, so use the fewest examples that reliably solve the issue.

***

### 4. Output Constraints: Protect Your Code

An output constraint tells Claude exactly what it must return.

Without it, Claude may give a helpful but unusable answer:

```text
This appears to be a billing-related issue.
```

But your program may require this:

```text
BILLING
```

**Simple constraint:**

```text
Return exactly one value:
BILLING, TECHNICAL, or ESCALATION.

Return no explanation.
Return no punctuation.
Return no extra text.
```

For JSON, be precise about:

- Field names
- Field types
- Allowed values
- Maximum length
- Missing information
- Whether extra fields are allowed
- Whether introductory text is forbidden

**Example:**

```text
Return only JSON.

Use exactly this structure:

{
  "category": "BILLING | TECHNICAL | ESCALATION",
  "priority": "LOW | MEDIUM | HIGH",
  "summary": "maximum 120 characters"
}

If priority cannot be determined, use "MEDIUM".
Do not add Markdown code fences.
Do not add explanation before or after the JSON.
```

This helps, but a written prompt is still an instruction that the model might fail to follow on an unusual input.

***

## Stronger Protection: Structured Outputs

For production applications, do not rely only on “Return valid JSON” in a prompt when malformed JSON could break your code.

Claude supports **structured outputs**: you send a JSON Schema to the API, and the API constrains generation so the output must match that schema. This prevents invalid JSON or unexpected field names before your code receives the answer. [docs.cloud.google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/structured-outputs)

### Prompt-only approach

```text
Return JSON with category and priority.
```

Possible failure:

```text
Sure! Here is the JSON:

{
  "ticket_category": "billing"
}
```

Your parser may fail because:
- There is extra text before JSON.
- Field name is wrong.
- Value casing is wrong.
- Required field is missing.

### Structured-output approach

```json
{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["BILLING", "TECHNICAL", "ESCALATION"]
    },
    "priority": {
      "type": "string",
      "enum": ["LOW", "MEDIUM", "HIGH"]
    }
  },
  "required": ["category", "priority"],
  "additionalProperties": false
}
```

With a schema like this, Claude’s output is constrained to valid JSON with exactly the fields and values your application expects. [docs.cloud.google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/structured-outputs)

## Strict Tool Use

Structured outputs protect Claude’s final text response. **Strict tool use** protects the arguments Claude sends to your tools.

For example, imagine your Magento application has this tool:

```text
get_order_status(order_id)
```

You do not want Claude to call it with broken data such as:

```json
{
  "orderNumber": "maybe-order-123"
}
```

Instead, define a tool schema and enable:

```json
"strict": true
```

Then Claude’s tool name and input must follow your declared JSON Schema. Anthropic describes this as grammar-constrained sampling: the model is restricted to schema-valid tool inputs while generating the call. [claude](https://claude.com/blog/structured-outputs-on-the-claude-developer-platform)

**Example tool schema:**

```json
{
  "name": "get_order_status",
  "description": "Get the current status of an order belonging to the logged-in customer.",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "The customer order ID"
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

This ensures the tool receives the expected `order_id` field. It does **not** replace your backend security checks. Your backend must still verify that:
- The user is authenticated.
- The order belongs to that user.
- The AI is allowed to call the action.
- The action is safe to perform.

## Production Prompt Pattern

Here is a simple reusable pattern for a support-ticket classifier:

```text
<system_rules>
You are a support-ticket classifier.

Choose exactly one category:
BILLING, TECHNICAL, ESCALATION.

Return only the category name in uppercase.
Do not explain your choice.
</system_rules>

<examples>
  <example>
    <sample_input>
    I was charged twice for the same subscription.
    </sample_input>

    <ideal_output>
    BILLING
    </ideal_output>
  </example>

  <example>
    <sample_input>
    My API request always returns a 429 error.
    </sample_input>

    <ideal_output>
    TECHNICAL
    </ideal_output>
  </example>
</examples>

<ticket>
{{customer_ticket}}
</ticket>
```

What each part does:

```text
System prompt/rules → Keeps Claude within its job
XML tags            → Separates rules, examples, and live user data
Examples            → Shows exact label format and casing
Output constraint   → Prevents explanations or unexpected text
JSON Schema          → Enforces machine-readable output in production
```

## Practical Debugging Loop

When an answer is wrong, use this process:

```text
1. Look at the failure.
          ↓
2. Identify the failure type.
          ↓
3. Add only the missing structural piece.
          ↓
4. Test with normal and unusual inputs.
          ↓
5. Keep the prompt small and precise.
```

### Example diagnosis

| Failure | Wrong reaction | Better fix |
|---|---|---|
| Claude returns a full sentence instead of `BILLING` | “Please be more careful” | Add “Return only one uppercase label” or use a schema |
| Claude mixes documentation with user instructions | Repeat instructions more loudly | Wrap each section in XML tags |
| Claude uses `billing`, `Billing`, and `BILLING` | Add many paragraphs about casing | Add an exact example with `BILLING` |
| It fails when no order ID exists | Keep rewording the happy-path prompt | Add a rule: “If no ID exists, return `MISSING_ORDER_ID`” |
| JSON parsing fails sometimes | Retry the request repeatedly | Use structured JSON output |

***

## Important Limits

Structured outputs significantly improve reliability, but your code must still handle some cases:

- **Refusal:** Claude may refuse a request for safety reasons.
- **Truncation:** The response may stop if it reaches the `max_tokens` limit.
- **Schema first-use delay:** A new schema can add extra latency on its first use because the API prepares it; repeated use of the same schema is typically more efficient.
- **Input token cost:** the format/schema instructions add some input-token usage.
- **No shortcut for security:** schema-valid data can still be unauthorized or logically wrong, so validate permissions and business rules in your backend. [docs.cloud.google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/structured-outputs)

## Main Takeaway

Use the **smallest structural fix** that solves the actual failure:

```text
Wrong long-term behavior  → System prompt
Mixed prompt sections     → XML tags
Exact pattern unclear     → Few-shot example
Wrong output form         → Output constraint
Machine-readable result   → Structured JSON output
Safe tool arguments       → Strict tool use
```

That is the production mindset: do not endlessly make prompts longer. Diagnose the failure, add the missing control, test it with realistic edge cases, and let your application validate everything that can affect users or data.

## What Went Wrong

The task was simple:

```text
Read a support ticket
        ↓
Return exactly one category:
BILLING, TECHNICAL, or ESCALATION
```

But the first prompt was too open:

```text
You are a support classifier. Classify the ticket.
```

Claude understood the ticket, but it had freedom to answer in different ways:

```text
This appears to be a billing issue.
Billing
billing
billing/technical
```

A human can understand all of these answers. But a program may only accept:

```text
BILLING
```

That difference is the main issue: **correct meaning is not enough if the output format breaks the code.**

## The Six Passes Explained

| Pass | What the developer did | Why it did not fully work |
|---|---|---|
| 1 | Asked Claude to classify as billing, technical, or escalation | Claude returned full sentences instead of one label |
| 2 | Added “Be concise” and “Use only the category name” | Claude still changed casing: `Billing` or `billing` |
| 3 | Added long explanations of each category | The model understood more, but still returned two labels for unclear tickets |
| 4 | Added “Never return two categories” | Helped sometimes, but Claude still gave explanations for difficult cases |
| 5 | Added even more rules and edge-case text | Prompt became very long; output became long too; cost and latency increased |
| 6 | Used a strict JSON format and clear examples | Output became reliable, short, and easy for the parser to use |

The key problem was not that Claude did not understand billing or technical issues. The key problem was that the developer never clearly enforced the exact output shape until the final pass.

***

## Two Different Failures

### Failure 1: Prompt Design Failure

The developer added more **descriptions** instead of adding a better **constraint**.

For example, this is too vague:

```text
Classify this ticket as billing, technical, or escalation.
Be concise.
Use only the category name.
```

It does not clearly define:

- Exact casing
- Whether a sentence is allowed
- Whether more than one label is allowed
- What to do for an unclear ticket
- Whether punctuation is allowed

A better version is:

```text
Return exactly one of these uppercase labels:

BILLING
TECHNICAL
ESCALATION

Return no explanation.
Return no punctuation.
Return no other text.
If more than one category may apply, choose the most likely category.
```

This is short, but much stronger.

***

### Failure 2: Engineering Failure

By Pass 5, the prompt became very long.

Long prompts can cause problems:

- More input tokens → higher cost
- More words for Claude to process → slower response
- Long instructions can encourage long answers
- Important rules become harder to notice
- Accuracy may not improve at all

The prompt reached more than 2,000 characters, and Claude started giving long and unfocused answers. This increased latency without improving classification quality.

Simple idea:

```text
Long prompt
     ↓
More tokens
     ↓
More cost and slower response
     ↓
Possibly longer output
     ↓
No guaranteed accuracy improvement
```

So a verbose prompt can create a performance problem even when the original classification problem is already mostly solved.

## Better Prompt Pattern

Here is a much better prompt for this use case:

```text
System:
You are a support-ticket classifier.

Classify each ticket into exactly one of:
BILLING, TECHNICAL, ESCALATION.

Return only one uppercase label.
Do not return an explanation, sentence, punctuation, or Markdown.
If multiple categories seem possible, select the most likely category.

<sample_input>
My account shows two charges for April.
</sample_input>

<ideal_output>
BILLING
</ideal_output>

<sample_input>
The API keeps returning a 429 error.
</sample_input>

<ideal_output>
TECHNICAL
</ideal_output>

<ticket>
I was charged twice for the same month.
</ticket>
```

Expected response:

```text
BILLING
```

### Why this works

```text
System instructions  → Define the fixed rules
Output constraint    → Forces one uppercase label only
XML tags             → Separate examples from actual ticket data
Few-shot examples    → Show exact casing and expected style
Ambiguity rule       → Prevents `BILLING/TECHNICAL`
```

## Best Production Version: JSON Schema

For application code, plain-text labels are workable, but structured JSON is often safer.

Expected output:

```json
{
  "category": "BILLING"
}
```

Schema idea:

```json
{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["BILLING", "TECHNICAL", "ESCALATION"]
    }
  },
  "required": ["category"],
  "additionalProperties": false
}
```

This prevents output such as:

```json
{
  "category": "billing/technical"
}
```

or:

```json
{
  "category": "This seems to be billing."
}
```

or:

```text
Sure! Here is the result:
{"category":"BILLING"}
```

A schema gives your backend a predictable result:

```text
Claude response
      ↓
Valid JSON
      ↓
One allowed category
      ↓
Safe router decision
```

## Easy Rule to Remember

If you have rewritten the prompt three times and the answer is still wrong:

```text
Stop adding more words.
        ↓
Look at the exact failure.
        ↓
Add the missing structure.
```

Use this guide:

| Problem | Correct fix |
|---|---|
| Claude returns extra sentences | Add a strict output constraint |
| Different uppercase/lowercase labels | Specify exact values and show an example |
| Claude returns two labels | Add “exactly one” and an ambiguity rule |
| Claude invents JSON fields | Use a JSON Schema / structured output |
| Claude mixes instructions with user data | Use XML tags |
| Claude gives wrong shape despite instructions | Add few-shot examples |
| Prompt is becoming huge | Remove repeated text; keep only rules that solve a known failure |

## Main Takeaway

Do not make prompts longer just because they fail.

Make them **more precise**:

```text
Wrong output format?
→ Add an output constraint.

Exact style or casing unclear?
→ Add a few-shot example.

Mixed instructions and data?
→ Add XML tags.

Machine-readable production output needed?
→ Use structured JSON output.
```

For your production applications, especially classification, routing, extraction, and tool inputs, prefer the smallest prompt that produces stable results. This lowers cost, improves speed, and makes your backend more reliable.

## Corrected System Prompt

The defect is that the original prompt does not define the exact JSON format Claude must return. It says “extract key information,” but it does not specify field names, allowed values, or whether extra text is allowed.

Use this corrected system prompt:

```text

- Do not add Markdown code fences.
- Do not add explanations before or after the JSON.
- Use exactly the field names: category, urgency, summary.
- Do not add extra fields.
- The summary must be one sentence.
- If more than one category appears possible, choose the most likely category.
```
