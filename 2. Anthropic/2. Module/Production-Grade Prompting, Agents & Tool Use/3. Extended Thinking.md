## Simple Summary

**Extended thinking** tells Claude to spend more effort reasoning before it gives the final answer. It can improve difficult planning or multi-step tasks, but it costs extra tokens and can make responses slower—so do not enable it for every request. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

Think of it like this:

```text
Normal request:
Question → Claude answers

Extended thinking:
Question → Claude reasons internally/in a thinking block → Claude answers
```

Use it when careful reasoning matters. Leave it off for simple classification, extraction, formatting, and lookup tasks.

***

## What Extended Thinking Does

When enabled, Claude can create a separate **thinking block** before the final answer block. The API response may contain both:

```text
Response:
1. thinking block
2. final answer block
```

On newer models, the full reasoning content is generally not exposed by default; you can request a readable display summary where supported. Each thinking block also has a `signature`, which is an opaque verification value from the API. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

Simple example:

```text
User:
Plan how to migrate a Magento store with minimum downtime.

Claude:
[Thinking / planning]
- Check dependencies
- Plan database backup
- Choose maintenance window
- Test rollback plan

[Final answer]
1. Take a verified backup...
2. Test the migration in staging...
3. Enable maintenance mode...
```

The important application-level answer is the final answer. The thinking block is mainly part of the model’s reasoning flow and API conversation state.

## When to Use It

| Task type | Use extended thinking? | Why |
|---|---:|---|
| Classifying support tickets | No | The task is mechanical; a constrained prompt or schema is enough |
| Extracting fields from a PDF or support ticket | No | A clear schema is usually more useful than extra reasoning |
| Converting JSON, CSV, or text format | No | It adds cost without meaningful benefit |
| Short factual question | Usually no | It is normally unnecessary |
| Multi-step math or logic | Yes | The model must work through several dependent steps |
| Complex debugging | Often yes | It can reason through causes, constraints, and possible fixes |
| Project planning with dependencies | Yes | It helps plan ordered steps and trade-offs |
| Tool-using agent | Often yes | It can help choose the right tool and plan multiple actions |

The practical rule is:

```text
Simple, fixed-format task
        ↓
Use a clear prompt + output constraint

Hard reasoning or multi-step planning
        ↓
Enable extended thinking
```

This matches Claude’s guidance that the `thinking` setting controls thinking blocks while the `effort` setting controls how much work the model applies to the response. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

***

## Effort Setting: Low, Medium, High

Newer Claude models use **adaptive thinking**. Instead of forcing a fixed number of reasoning tokens, you enable adaptive thinking and select an effort level. Claude then decides when and how deeply to reason based on the task. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

```text
thinking: adaptive
        +
effort: low / medium / high
```

| Effort | Simple meaning | Good use case |
|---|---|---|
| Low | Minimize extra thinking; prioritize speed and lower token use | Straightforward tasks where latency matters |
| Medium | Use a reasonable amount of reasoning when needed | General tasks with some complexity |
| High | Spend more effort on difficult reasoning and planning | Complex debugging, multi-step plans, high-stakes decisions |
| Max, where supported | No practical limit on reasoning depth | Rare, very difficult reasoning tasks |

On current adaptive-thinking documentation, `high` is the default in some configurations, while lower effort levels can reduce or skip extended reasoning for easy requests. [docs.aws.amazon](https://docs.aws.amazon.com/en_en/bedrock/latest/userguide/claude-messages-adaptive-thinking.html)

**Important:** do not use high effort simply because it sounds better.

```text
High effort on simple classification
        ↓
More tokens + more latency
        ↓
Usually no better result
```

For example:

```text
Task: “Classify this ticket as BILLING, TECHNICAL, or ESCALATION.”

Best choice:
- Extended thinking: off
- Strong output constraint: on
- Structured JSON output: preferred in production
```

But:

```text
Task: “Analyze this production incident, identify likely root causes,
rank them by likelihood, create a safe rollback plan, and decide which
tools should run first.”

Best choice:
- Extended thinking: on
- Effort: medium or high
- Tool calls: allowed
- Human approval: required before destructive actions
```

## Important Change: Old vs New Method

Older implementations used a fixed reasoning token budget:

```json
{
  "thinking": {
    "type": "enabled",
    "budget_tokens": 10000
  }
}
```

The newer recommended direction is adaptive thinking with effort:

```json
{
  "thinking": {
    "type": "adaptive"
  },
  "output_config": {
    "effort": "medium"
  }
}
```

`budget_tokens` is deprecated on newer Claude model generations, and newer documentation recommends adaptive thinking plus the separate `output_config.effort` setting instead. The effort value belongs under `output_config`, not inside the `thinking` object. [docs.aws.amazon](https://docs.aws.amazon.com/en_en/bedrock/latest/userguide/claude-messages-adaptive-thinking.html)

## Critical Rule for Tool Use

When extended thinking is used with tools, you must return all received thinking blocks to the API **exactly as received** on the next request.

Do not:

- Remove the thinking block
- Edit the thinking text
- Summarize it
- Reorder it
- Remove its `signature`
- Change earlier request context in a way that invalidates it

Every thinking block includes a signature used by the API to verify that it was generated by Claude. If you modify or drop it during a tool-use loop, the next API call can fail. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

### Correct Agent Flow

```text
1. User sends request
          ↓
2. Claude returns:
   - thinking block
   - tool_use block
          ↓
3. Your application runs the tool
          ↓
4. Your application sends back:
   - the full original assistant message
   - unchanged thinking block(s)
   - unchanged tool-use block(s)
   - new tool result
          ↓
5. Claude continues and returns the final answer
```

### Wrong Flow

```text
1. Claude returns thinking + tool request
          ↓
2. App deletes thinking block to save tokens
          ↓
3. App sends only tool result
          ↓
4. API rejects the next request
```

The rule exists because tool use is part of one continuous reasoning flow. Claude needs its verified earlier reasoning context to continue after the external tool result arrives. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

## Simple Pseudocode

```python
response = client.messages.create(
    model="claude-model",
    system="You are a careful deployment-planning assistant.",
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    tools=tools,
    messages=messages
)

# Keep every content block exactly as Claude returned it.
messages.append({
    "role": "assistant",
    "content": response.content
})

for block in response.content:
    if block.type == "tool_use":
        tool_result = run_tool(block.name, block.input)

        messages.append({
            "role": "user",
            "content": [{
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": tool_result
            }]
        })

next_response = client.messages.create(
    model="claude-model",
    system="You are a careful deployment-planning assistant.",
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    tools=tools,
    messages=messages
)
```

The key line is:

```python
"content": response.content
```

Do not rebuild only the “important” pieces. Preserve the full response content, including any thinking blocks and their signatures, unchanged. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

## Cost and Context Impact

Thinking tokens are billed like output tokens. More reasoning means more token usage and usually more latency. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

```text
More effort
      ↓
More thinking
      ↓
More output tokens
      ↓
Higher cost and longer response time
```

For long-running agents, thinking blocks also become part of the conversation state that must be preserved in tool workflows. Do not simply delete them to reduce context use, because that can invalidate the API request. Instead, design the agent to:

- Keep tools and system prompts stable during the active reasoning chain
- Return the exact previous assistant content while completing tool calls
- Complete the active tool loop before compacting or resetting history
- Summarize or trim history only at safe boundaries between tasks

Preserved-thinking documentation notes that changing the system prompt, tools, or messages before a preserved thinking block can invalidate later blocks. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)

## Easy Memory Trick

```text
Thinking = extra brain work
Effort = how hard Claude works
Tools = actions Claude asks your app to perform
Signature = proof that the thinking block is unchanged
```

And remember:

```text
Hard planning or reasoning?
→ Enable thinking.

Simple extraction or classification?
→ Use output constraints, not thinking.

Thinking plus tools?
→ Send thinking blocks back unchanged.
```

The best production design uses the smallest amount of reasoning that reliably solves the task: lower cost, faster answers, and fewer moving parts.

## Correct Matches

| Task | Correct decision | Why |
|---|---|---|
| Classify 50,000 support tickets into three labels overnight | **Leave it off** | Classification is a simple, repeatable task. Use a strict output format or JSON schema instead. Extended thinking adds token cost with little or no accuracy benefit. |
| Plan a multi-step refactor where each step depends on the previous one | **Enable it, budget for the planning step** | A dependent refactor needs planning, sequencing, risk checks, and reasoning about how one change affects another. Extended thinking can improve the plan. |
| Strip the thinking block out of conversation history to save context before the next tool call | **Never do this** | Thinking blocks must be returned unchanged in a tool-use conversation. Removing, editing, or summarizing them can invalidate their signature and make the next API request fail.  [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking) |

## Easy Way to Remember

```text
Simple repeated work
→ Leave extended thinking off

Hard multi-step planning
→ Turn extended thinking on

Thinking block during a tool loop
→ Never remove or edit it
```

For the 50,000-ticket job, the practical production setup would be:

```text
Batch API
      +
Extended thinking off
      +
Strict category schema
      +
Low-temperature / repeatable configuration
```

This keeps the overnight classification job cheaper, faster, and easier to parse.
