## Stage 1: Identify the Four Bugs

The implementation has one bug in each layer:

1. **Schema layer** — tool description is too vague.
2. **Streaming layer** — partial streamed output can be saved even if the stream fails.
3. **Context/message layer** — thinking blocks are removed even though the agent uses tools with extended thinking.
4. **Memory layer** — every old session transcript is injected into every new session.

***

## 1. Schema Bug

### Problem code

```python
"description": "Gets data."
```

### Layer

**Schema layer**

### What happens at runtime

Claude cannot reliably tell when to use `get_customer_data`, what type of customer data it returns, or when another tool should be used instead, so it may choose the wrong tool or make unnecessary calls.

### Why

Tool selection depends heavily on the tool name and description. “Gets data” does not explain:

- What data it gets
- Which ID is expected
- When the tool should be called
- When the tool should not be called
- What result comes back

***

## 2. Streaming Bug

### Problem code

```python
assistant_content = [b for b in assemble(blocks) if b["type"] != "thinking"]
messages.append({"role": "assistant", "content": assistant_content})
```

### Layer

**Streaming layer**

### What happens at runtime

If the network connection drops or the stream ends before `message_stop`, the code still assembles and saves a partial assistant message, possibly including incomplete text or a half-written `tool_use` JSON block; the next API request can then fail validation.

### Why

The code sets:

```python
stop_seen = False
```

and later sets it to `True` only when:

```python
event.type == "message_stop"
```

But it never checks it before saving the response.

The bad behavior is:

```text
Stream drops early
        ↓
No message_stop event
        ↓
stop_seen remains False
        ↓
Code still appends incomplete blocks to messages
        ↓
Next Claude request contains corrupt history
```

Only `message_stop` proves a streamed response is complete and safe to commit. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

***

## 3. Context / Message Structure Bug

### Problem code

```python
assistant_content = [b for b in assemble(blocks) if b["type"] != "thinking"]
```

### Layer

**Context layer / tool-use message structure**

### What happens at runtime

The code removes thinking blocks before sending the assistant turn back in the next tool-use request; because adaptive thinking is enabled, the next API call can fail with an `invalid_request_error` due to missing or modified thinking-block signatures.

### Why

The agent enables thinking:

```python
thinking={"type": "adaptive"}
```

Then it filters out thinking blocks:

```python
if b["type"] != "thinking"
```

That is unsafe in an extended-thinking tool loop.

```text
Claude returns:
- thinking block
- tool_use block
        ↓
Application removes thinking block
        ↓
Application sends tool result
        ↓
Next request lacks verified reasoning block
        ↓
API may reject request
```

Thinking and redacted-thinking blocks must be preserved exactly as received and in their original order when they are sent back as part of a tool-use conversation. [platform.claude](https://platform.claude.com/docs/en/api/errors)

***

## 4. Memory Bug

### Problem code

```python
def build_session_history(prior_sessions):
  full_history = []
  for session in prior_sessions:
    full_history.extend(session["messages"])
  return full_history
```

### Layer

**Memory layer**

### What happens at runtime

Every new session receives the full transcript of every old session, so token cost and latency grow continuously; eventually the context window fills, leading to incomplete answers, context-limit failures, or worse tool decisions.

### Why

This code treats full old conversation history as permanent live context:

```text
Session 1 history
        +
Session 2 history
        +
Session 3 history
        +
Session 4 history
        =
New session starts with huge prompt
```

This is especially harmful when old sessions contain large tool results, long logs, file contents, PDFs, or extended tool-use conversations.

A better design is:

```text
Raw history and durable facts
→ Save in external storage

Important prior progress
→ Save as a small structured summary

New session
→ Retrieve only relevant facts and summary
```

Context-window documentation explains that growing message history and tool outputs consume context budget, so long-running systems need deliberate context/memory management rather than replaying all earlier transcripts. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## Quick Bug Table

| # | Layer | Bug | Runtime result |
|---:|---|---|---|
| 1 | Schema | `get_customer_data` description is only “Gets data.” | Claude may choose the wrong tool or not know when to use it |
| 2 | Streaming | Does not check `stop_seen` before saving assistant content | Interrupted streams save partial blocks and corrupt the next request |
| 3 | Context | Filters out `thinking` blocks while adaptive thinking and tools are enabled | Next tool-loop request may fail due to missing/changed thinking-block signature |
| 4 | Memory | Replays every prior session transcript in full | Costs and latency grow; eventually context window fills |
