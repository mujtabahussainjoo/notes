## Full Summary: Streaming Responses

Streaming means Claude sends its answer **piece by piece** while it is being created, instead of making the user wait for the complete answer.

It is useful when:
- The answer may be long.
- A user is waiting on a screen.
- You want text to appear quickly, like live typing in ChatGPT.
- You want the interface to feel faster.

For short backend tasks, where nobody is waiting, normal non-streaming requests are usually simpler and safer. Claude streams Messages API output through a sequence of server-sent events. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

***

## Normal vs Streaming Response

### Normal Response

In a normal request, your application waits until Claude completes everything.

```text
Your app sends request
        ↓
Waits silently
        ↓
Claude finishes full response
        ↓
Your app receives one complete message
        ↓
Show or process answer
```

Example:

```python
response = client.messages.create(
    model=model,
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": "Explain how to reset an API key."
        }
    ]
)

print(response.content)
```

This is easy because `response.content` is already complete.

***

### Streaming Response

In streaming, Claude sends parts as soon as they are ready.

```text
Your app sends request
        ↓
Claude sends first words
        ↓
Your app displays them
        ↓
Claude sends more words
        ↓
Your app displays them
        ↓
Claude signals completion
```

Example of what a user sees:

```text
Without streaming:

[User waits several seconds]

"To reset your API key, first open..."

With streaming:

"To reset..."
"To reset your API key..."
"To reset your API key, first open..."
```

The final message is the same. The difference is that with streaming, **your code must collect and rebuild the answer** from many smaller events. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

***

## Main Streaming Events

Claude sends events in a sequence. Your code listens to them and builds the final message.

| Event | Meaning | What your code should do |
|---|---|---|
| `message_start` | A new Claude message starts | Create temporary empty storage |
| `content_block_start` | A new block starts: text, tool call, or thinking | Create a block at that index |
| `content_block_delta` | A small new piece arrives | Add it to the correct block |
| `content_block_stop` | One block is finished | Finalize that block |
| `message_delta` | Message-level updates arrive | Save `stop_reason` and final usage details |
| `message_stop` | Whole message is finished | Now it is safe to save and use the assistant message |

Claude documentation describes streams as a message start event, followed by one or more content blocks with start/delta/stop events, then a final message stop event. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

***

## Simple Text Streaming Example

Imagine Claude is generating this answer:

```text
Your API key can be reset from the developer settings page.
```

It may arrive in pieces:

```text
Event 1:
content_block_start
→ A text block has started

Event 2:
content_block_delta
→ "Your API key"

Event 3:
content_block_delta
→ " can be reset"

Event 4:
content_block_delta
→ " from the developer settings page."

Event 5:
content_block_stop
→ Text block is complete

Event 6:
message_stop
→ Whole assistant response is complete
```

Your application joins the pieces:

```python
answer = ""

for text_piece in text_deltas:
    answer += text_piece
```

Final result:

```text
Your API key can be reset from the developer settings page.
```

## Why Streaming Is More Complex

With normal API calls:

```text
One request
        ↓
One complete response
        ↓
Use it safely
```

With streaming:

```text
One request
        ↓
Many partial events
        ↓
Your code rebuilds the answer
        ↓
Your code must handle connection failures
        ↓
Use only after completion
```

The important risk is that a stream can stop early because of:

- Internet connection loss
- Server timeout
- Browser tab closing
- Client disconnect
- Temporary API/network failure
- Application crash or restart

If this happens, your application may have received only part of the response.

***

## Most Important Rule

```text
Only message_stop means the response is complete.
```

Do not treat:

```text
“The event loop ended”
```

as equal to:

```text
“The response finished successfully”
```

A loop may end because the stream completed, but it may also end because the network failed.

Use this safe rule:

```text
message_stop received?
        │
        ├── Yes → Save full response to conversation history
        │
        └── No  → Discard partial response and retry
```

This prevents broken or incomplete messages from being stored in your conversation history. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

***

## Why Tool Calls Need Extra Care

Streaming is especially risky with tools.

A Claude tool call does not arrive in one complete piece. Its input can arrive as **partial JSON**.

Example final tool call:

```json
{
  "order_id": "10001234",
  "include_tracking": true
}
```

But streaming may send it like this:

```text
Delta 1:
{"order_id":

Delta 2:
"10001234",

Delta 3:
"include_tracking":

Delta 4:
true}
```

After Delta 1, this is not valid JSON:

```json
{"order_id":
```

After Delta 2, this is still incomplete:

```json
{"order_id": "10001234",
```

Only after the block finishes is it safe to parse:

```json
{
  "order_id": "10001234",
  "include_tracking": true
}
```

Claude’s streaming tool documentation notes that tool inputs may be delivered as partial JSON strings. Accumulate them first; do not parse or execute a tool before the tool-use block has finished. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)

***

## Wrong Tool-Streaming Example

This code is unsafe:

```python
for event in stream:
    if event.type == "content_block_delta":
        partial_json += event.delta.partial_json

        # Wrong: JSON may be incomplete.
        tool_input = json.loads(partial_json)
        run_tool(tool_input)
```

Possible failure:

```text
Partial input:
{"order_id": "1000
```

Problems:

- JSON parsing fails.
- Tool receives incomplete arguments.
- A payment, cancellation, or order action could run incorrectly.
- Partial tool data may be saved in history.
- The next Claude API request can fail validation.

***

## Correct Tool-Streaming Example

Safe process:

```text
Receive tool-use start
        ↓
Store tool ID and tool name
        ↓
Keep adding partial JSON fragments
        ↓
Wait for content_block_stop
        ↓
Wait for message_stop
        ↓
Parse complete JSON
        ↓
Run tool
        ↓
Return matching tool_result
```

Simple code idea:

```python
import json

blocks = {}
stop_seen = False
stop_reason = None

with client.messages.stream(
    model=model,
    max_tokens=4096,
    messages=messages,
    tools=tools,
) as stream:

    for event in stream:
        if event.type == "message_start":
            blocks = {}

        elif event.type == "content_block_start":
            blocks[event.index] = init_block(event)

        elif event.type == "content_block_delta":
            apply_delta(blocks[event.index], event.delta)

        elif event.type == "content_block_stop":
            finalize_block(blocks[event.index])

        elif event.type == "message_delta":
            stop_reason = event.delta.stop_reason

        elif event.type == "message_stop":
            stop_seen = True
```

Then check if the full message completed:

```python
if not stop_seen:
    # Important:
    # Do not save incomplete blocks.
    # Do not run a partial tool call.
    # Retry from the last known complete conversation state.
    raise RuntimeError(
        "Stream ended before message_stop. "
        "Discarding partial assistant response."
    )

assistant_content = assemble(blocks)

messages.append({
    "role": "assistant",
    "content": assistant_content
})
```

Only after `message_stop` is it safe to inspect `tool_use` blocks:

```python
if stop_reason == "tool_use":
    for block in assistant_content:
        if block["type"] == "tool_use":
            tool_input = json.loads(block["input_json"])
            tool_result = run_tool(
                tool_name=block["name"],
                tool_input=tool_input
            )
```

## Full Real-Life Example: Order Status Agent

Suppose a customer asks:

```text
Where is my order 10001234?
```

### Step 1: User Message

```text
User:
Where is my order 10001234?
```

### Step 2: Claude Starts Streaming

Claude decides it needs an order lookup tool.

```text
message_start
        ↓
content_block_start
→ Starts a tool_use block
        ↓
content_block_delta
→ Tool name: get_order_status
        ↓
content_block_delta
→ Partial input: {"order_id":
        ↓
content_block_delta
→ Partial input: "10001234"}
        ↓
content_block_stop
→ Tool call block is complete
        ↓
message_delta
→ stop_reason = tool_use
        ↓
message_stop
→ Whole assistant turn is complete
```

### Step 3: Your App Runs the Tool

Only now should your backend run the tool:

```python
order_data = get_order_status("10001234")
```

Backend result:

```json
{
  "status": "shipped",
  "courier": "BlueDart",
  "tracking_number": "BD123456789",
  "estimated_delivery": "2026-09-28"
}
```

### Step 4: Return the Tool Result

Your application returns the result using the same tool-use ID:

```python
messages.append({
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": "toolu_01ABC",
            "content": """
            {
              "status": "shipped",
              "courier": "BlueDart",
              "tracking_number": "BD123456789",
              "estimated_delivery": "2026-09-28"
            }
            """
        }
    ]
})
```

### Step 5: Claude Streams Final Answer

Claude now creates a customer-friendly reply:

```text
Your order has been shipped through BlueDart and is expected
to arrive on 28 September 2026.
```

Again, save it to history only after the final `message_stop`.

## Interrupted Stream Example

Imagine this happens:

```text
message_start
        ↓
content_block_start: tool_use
        ↓
content_block_delta:
{"order_id": "10001
        ↓
Network connection drops
        ↓
No content_block_stop
No message_stop
```

The partial input is invalid:

```json
{"order_id": "10001
```

### Wrong Behavior

```python
# Wrong: saves an incomplete assistant turn.
messages.append({
    "role": "assistant",
    "content": assemble(blocks)
})
```

Then the next request contains malformed history. The Claude API may reject it because the saved tool call is incomplete or incorrectly paired.

### Correct Behavior

```python
if not stop_seen:
    blocks.clear()

    # Do not save partial assistant message.
    # Do not execute tool.
    # Keep previous complete messages unchanged.
    retry_request()
```

Correct recovery flow:

```text
Stream drops before message_stop
        ↓
Discard partial assistant response
        ↓
Keep only last complete conversation history
        ↓
Retry the same request
        ↓
Use the response only if message_stop arrives
```

This prevents the “stream ended → partial tool call was saved → next request fails” problem. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

## Text Streaming vs Tool Streaming

| Situation | Can you show it immediately? | Can you save it immediately? | Can you act on it immediately? |
|---|---:|---:|---:|
| Partial normal text | Yes, if you want a live UI | No, wait for `message_stop` | No external action needed |
| Partial tool input JSON | Usually do not show it to users | No, wait for `message_stop` | No, wait until it is complete |
| Completed text block | You may display it | Still safest to wait for final `message_stop` | No tool action required |
| Completed tool-use block | You may inspect it | Wait for final `message_stop` before durable history save | Run only after complete message handling |
| Full message with `message_stop` | Yes | Yes | Yes, check `stop_reason` first |

## When to Use Streaming

### Use Streaming When

- Users are watching the screen.
- Responses can be long.
- You are building a chat interface.
- You want a fast, live typing experience.
- You stream progress or text to operators.

```text
User-facing chatbot
→ Streaming is useful
```

### Avoid Streaming When

- The response is short.
- It is a backend-only process.
- It is a scheduled nightly job.
- No person is waiting.
- Simplicity and reliability matter more than live output.

```text
Classify 50,000 tickets overnight
→ Use batch processing, not streaming
```

```text
Extract a few fields from one support ticket in a background service
→ Normal non-streamed API call is usually simpler
```

***

## Production Checklist

Before using streaming in production, make sure your code does all of these:

- Create temporary storage for streamed blocks.
- Track blocks by `event.index`.
- Append every incoming delta to the correct block.
- Preserve text, tool-use, and thinking blocks.
- Do not parse partial JSON tool input.
- Do not run tools from incomplete blocks.
- Track `message_delta.stop_reason`.
- Save assistant history only after `message_stop`.
- If the stream fails, discard the partial assistant turn.
- Retry from the last complete conversation state.
- For tool calls, return a `tool_result` with the exact matching tool-use ID.
- If extended thinking is enabled, preserve thinking blocks unchanged in the next request. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

```text
Streaming gives speed to the user,
but gives responsibility to your code.
```

Remember:

```text
Partial text can be displayed.
```
