## Module 2: Easy Final Summary

This module teaches how to move from a simple Claude demo to a **real production application** that works reliably with real users, large inputs, tool calls, long conversations, errors, and risky actions.

The main idea is:

```text
A demo only needs to work once.

A production AI system must work:
- with unexpected user input
- across many users
- across long sessions
- with large files
- with tool failures
- at reasonable cost
- without making harmful changes
```

***

## 1. Fix Prompts by Finding the Real Problem

When Claude gives a wrong answer, do not keep adding more words blindly.

First identify the failure type.

| Problem | Main fix |
|---|---|
| Claude gives the wrong output shape | Add an output constraint |
| Claude changes role, tone, or scope over time | Improve the system prompt |
| Claude understands the task but invents its own format | Add few-shot examples |
| Claude mixes instructions with input data | Use XML tags |
| Claude returns broken JSON | Use structured output / JSON Schema |
| Claude sends bad tool arguments | Use strict tool schemas |

### Example

Bad prompt:

```text
Classify this ticket.
```

Claude may return:

```text
This looks like a billing issue.
```

But your code may require:

```text
BILLING
```

Better prompt:

```text
Classify the ticket into exactly one label:

BILLING
TECHNICAL
ESCALATION

Return only one uppercase label.
Do not add explanations or punctuation.
```

For production JSON, use a schema so the API prevents malformed output before your code receives it. Claude structured outputs can constrain final JSON responses, while strict tool use constrains tool inputs to match a schema. [docs.cloud.google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/structured-outputs)

## 2. Use Thinking Only for Hard Tasks

Extended thinking means Claude spends more effort reasoning before giving its answer.

```text
Simple task
→ No extended thinking needed

Hard multi-step planning
→ Extended thinking can help
```

### Use Extended Thinking For

```text
Complex debugging
Multi-step planning
Hard logic
System design
Dependent tool calls
Risky decision analysis
```

### Do Not Use It For

```text
Ticket classification
Extracting fields
JSON formatting
Simple lookup
Short factual reply
```

Why?

```text
More thinking
      ↓
More tokens
      ↓
Higher cost
      ↓
Longer response time
```

When thinking is enabled with tools, preserve the thinking block exactly as Claude returned it. Removing, editing, summarizing, or changing it can break the next request because the API checks its signature. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/thinking)

***

## 3. Tools: Claude Chooses, Your Code Executes

Claude does not directly run your database query, Magento API request, email action, or file update.

```text
Claude chooses a tool
        ↓
Your backend checks permissions
        ↓
Your backend runs the real action
        ↓
Your backend returns the result
        ↓
Claude continues
```

### Tool-Use Loop

```text
User asks question
        ↓
Claude returns tool_use block
        ↓
Your application runs the tool
        ↓
Your application returns tool_result block
        ↓
Claude answers or requests another tool
```

Every `tool_use` block must receive a matching `tool_result` with the same ID in the immediately following user turn. [platform.claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

### Good Tool Description

Bad:

```text
Use this to get data.
```

Better:

```text
Use this tool to retrieve the current delivery status of a specific order.
Use it when the user asks where an existing order is, whether it has
shipped, or when it will arrive.

Do not use it to cancel orders, change an order, search products, or
retrieve unrelated customer data.
```

The key rule is:

```text
Say when to use the tool.
Say when not to use the tool.
```

If two tools have nearly identical descriptions, Claude cannot reliably choose between them.

## 4. Streaming: Save Only Complete Messages

Streaming lets users see Claude’s response as it is generated.

```text
Without streaming:
User waits
        ↓
Full answer appears

With streaming:
Answer appears little by little
```

Streaming feels faster, but your code must collect many small events and build the final response.

### Important Rule

```text
Only message_stop means the response is complete.
```

If the stream stops because of a network problem:

```text
Partial response
        ↓
Do not save it to conversation history
        ↓
Do not execute partial tool input
        ↓
Discard it
        ↓
Retry from the last complete message
```

This is especially important for tool calls because tool inputs can arrive as partial JSON.

```text
Partial tool JSON:
{"order_id": "1000

This is not safe to run.
```

Wait until the full message completes before saving the turn or running a tool. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/streaming)

## 5. Context: Claude’s Working-Memory Budget

The context window is the total working space Claude has in one request.

```text
System prompt
      +
Conversation history
      +
Tool definitions
      +
Tool calls
      +
Tool results
      +
Images and PDFs
      +
Claude output
      =
Context usage
```

The context window is not free. More content means:

```text
More input tokens
      ↓
More cost
      ↓
More latency
      ↓
Less room for new work
```

### Common Production Problem

Development uses short test tool results:

```text
Tool result: 800 tokens
```

Production uses real documents and logs:

```text
Tool result: 3,200 tokens
```

Then the agent starts choosing worse tools or gives incomplete answers after several turns.

```text
Agent looks confused
        ↓
Team suspects tool schema
        ↓
Real problem may be full context window
```

When tool selection becomes worse after a fixed number of turns, check context size first. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

### Ways to Manage Context

| Method | Use it when | What it does |
|---|---|---|
| Pruning | Agent followed a bad path | Removes unhelpful old turns |
| Compaction | Same task continues but history is large | Replaces old detail with a summary |
| Clearing | New task is unrelated | Starts a clean session |
| Subagent handoff | A large subtask can be isolated | Gives a subtask to a separate context window |
| RAG / retrieval | Large knowledge base exists | Sends only relevant documents instead of everything |

## 6. Workflow vs Agent

Use the simplest pattern that solves the problem.

```text
Single model call
        ↓
Workflow
        ↓
Agent
```

### Use a Workflow When

You know the exact steps.

```text
1. Check login
2. Find order
3. Check return period
4. Create return request
5. Send confirmation
```

This is normal code with fixed rules.

### Use an Agent When

You know the goal but do not know the exact path.

```text
Goal:
Find why checkout is failing.

Possible work:
- Read logs
- Check deployment history
- Check payment settings
- Compare staging and production
- Inspect a code file
```

An agent chooses the next tool based on what it finds.

### Important Agent Rules

```text
Keep the tool list small.
Use clear tool descriptions.
Set a maximum number of tool rounds.
Define clear exit conditions.
Use human approval for risky actions.
```

## 7. Human Approval for Risky Actions

Human-in-the-loop, or HITL, means pausing the agent before a dangerous or irreversible action.

```text
Agent proposes action
        ↓
Human reviews
        ↓
Human approves or rejects
        ↓
Only then can the action run
```

Use approval before actions such as:

```text
Send email
Delete data
Edit production file
Deploy code
Cancel order
Refund money
Create public post
Change customer record
Run database migration
```

### Example

Unsafe:

```text
Agent finds bad production setting
        ↓
Agent changes file automatically
        ↓
File syntax is valid
        ↓
Application breaks because business impact was not checked
```

Safe:

```text
Agent finds possible problem
        ↓
Agent prepares proposed change
        ↓
Agent validates proposal
        ↓
Human approves
        ↓
Agent applies production change
```

A tool can be technically valid but still harmful. Human approval must happen before the real write action.

## 8. Memory: What Survives Sessions

Memory answers:

```text
What should the agent remember after this session ends?
```

| Memory pattern | Best for |
|---|---|
| In-context memory | Short, one-session work |
| External storage | Multi-day cases, customer preferences, project state |
| Summarized memory | Continuing a long task with reduced context cost |
| Stateless | Independent jobs such as classification or formatting |

### Example

Customer support agent over two weeks:

```text
Use external storage.
```

Store:

```text
Customer ID
Case ID
Confirmed findings
Current status
Open tasks
Preferences
Approval history
```

Document formatting job:

```text
Use stateless design.
```

No previous information is needed.

Long coding session that ends permanently:

```text
Use in-context memory.
```

Current discussion and files remain in the active session only.

Do not replay every earlier conversation in each new session. That makes cost and context size grow until the agent fails. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

***

## 9. Skills vs CLAUDE.md

A Skill is reusable specialized guidance.

```text
Memory:
“What happened earlier?”

Skill:
“How should this type of task be done?”
```

### Use a Skill for Specialized Work

Examples:

```text
Magento module review
Payment integration audit
Security checklist
Deployment review
Incident response
Performance investigation
```

A Skill lives in a `SKILL.md` file and loads when the request matches its description. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/skills-guide)

### Use CLAUDE.md for Always-On Rules

Examples:

```text
Use TypeScript strict mode.
Follow Magento coding standards.
Do not change database schema without migration.
Add tests for changed business logic.
Do not deploy production changes without approval.
```

`CLAUDE.md` applies to every project session, while Skills are loaded only when relevant. [code.claude](https://code.claude.com/docs/en/agent-sdk/claude-code-features)

## 10. Images and PDFs Use Context Too

Images and PDFs consume context budget before Claude reads your question.

For images:

\[
\text{Visual tokens} =
\left\lceil \frac{\text{width}}{28} \right\rceil
\times
\left\lceil \frac{\text{height}}{28} \right\rceil
\]

Example:

\[
1000 \times 1000 \text{ pixels}
=
36 \times 36
=
1296 \text{ visual tokens}
\]

Large images can become expensive and reduce space for instructions, tool results, and output.

```text
Large image
      ↓
More visual tokens
      ↓
More cost
      ↓
Less room for the rest of the request
```

Resize images when full high resolution is not needed. Claude supports image blocks through Base64, URLs, and Files API references. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/vision)

***

## 11. Files API and Batch API

### Files API

Use the Files API when the same file is reused.

```text
Upload once
      ↓
Receive file_id
      ↓
Reuse file_id in future requests
```

Good for:

```text
Reference diagrams
Product images
Reusable PDFs
Policy documents
Manuals
```

The Files API lets you upload files and reference them later by `file_id`. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/files)

### Inline Base64

Use Base64 for one-time files.

```text
One screenshot
      ↓
One request
      ↓
Inline Base64 is fine
```

### Message Batches API

Use batch processing for large offline jobs.

```text
5,000 support tickets
        ↓
Submit one batch
        ↓
Receive batch ID
        ↓
Poll status later
        ↓
Download results
```

Use it for:

```text
Nightly classification
Large PDF extraction
Image-quality checks
Prompt evaluation runs
Bulk data cleanup
```

Do not use it for a live user waiting for an answer.

```text
User waiting now
→ Normal API or streaming

Thousands of offline jobs
→ Message Batches API
```

The Message Batches API supports up to 100,000 requests or 256 MB per batch, can take up to 24 hours, and returns results that should be matched using `custom_id` rather than assumed order. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

## Final Production Checklist

Before deploying a Claude-powered application, check:

- Is the prompt short, clear, and structurally correct?
- Are JSON outputs protected with a schema when parsing matters?
- Are tool descriptions clear about when to use and not use each tool?
- Do tool results match the original `tool_use_id`?
- Does streaming save history only after `message_stop`?
- Are thinking blocks preserved unchanged when thinking and tools are enabled?
- Is context size measured with real production-sized files and tool output?
- Are old tool outputs pruned or summarized?
- Is there a clear reason to use an agent instead of a workflow?
- Are exit conditions and maximum tool rounds defined?
- Does every risky write/delete/send action require approval?
- Is memory stored in the right place for the task?
- Are specialized instructions in Skills instead of every prompt?
- Are large images resized before upload?
- Are repeated assets stored using Files API?
- Are large offline jobs submitted through Batch API?
- Are batch results matched by `custom_id`?

## Main Lesson

A reliable Claude system is built from small, deliberate controls:

```text
Clear prompts
      +
Strict output formats
      +
Safe tools
      +
Correct streaming handling
      +
Managed context
      +
Right memory scope
      +
Human approval for risky actions
      +
Correct file and batch strategy
      =
Production-ready AI application
```

You can now take a prototype and turn it into a system that is safer, cheaper, faster, and more reliable under real production use.
