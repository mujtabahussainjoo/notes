## Simple Summary

When building with Claude, you must make two important decisions:

1. **Which model should run the work?**
2. **How will you stop a long conversation or agent session from becoming too large, slow, and expensive?**

A good default is to start with **Sonnet**, measure its quality using real test cases, move up only if needed, and manage the growing conversation context before it reaches its limit. Current Claude documentation lists Fable, Opus, Sonnet, and Haiku model families with different capability, speed, cost, and context-window trade-offs. [platform.claude](https://platform.claude.com/docs/en/models/overview.md)

***

## 1. Model Selection

Different models are suited to different kinds of work.

| Model tier | Simple meaning | Best use |
|---|---|---|
| **Haiku** | Fast and lower-cost | Classification, extraction, short routing tasks, simple support replies |
| **Sonnet** | Balanced default | Most production apps, coding, support agents, tool use, moderate reasoning |
| **Opus** | Stronger for hard work | Difficult coding, complex planning, difficult debugging, demanding agent work |
| **Fable** | Highest capability | Very hard reasoning, advanced coding, research synthesis, complex agent workflows |

The current model overview lists 1M-token context windows for current Fable, Opus, and Sonnet tiers, while Haiku is listed with a 200K-token window. Model IDs and availability can change, so verify them in the documentation before deploying. [platform.claude](https://platform.claude.com/docs/en/models/overview.md)

### Practical Model Rule

```text
Start with Sonnet
        ↓
Test with realistic examples
        ↓
Quality good enough?
        │
        ├── Yes → Keep Sonnet
        │
        └── No → Test Opus or Fable
```

For high-volume simple work:

```text
Start with Sonnet
        ↓
Test Haiku against the same evaluation set
        ↓
Quality still acceptable?
        │
        ├── Yes → Use Haiku to reduce cost and latency
        │
        └── No → Stay with Sonnet
```

Do not choose a larger model only because it is more capable. Do not choose a cheaper model only because it costs less. Use evaluation results.

### Example: Magento Product Support

| Task | Good first choice | Why |
|---|---|---|
| Classify 50,000 support tickets | Haiku or Sonnet | Fixed labels, high volume, low complexity |
| Extract order number, customer issue, and urgency | Haiku or Sonnet | Structured extraction with JSON schema |
| Debug a complicated checkout integration failure | Sonnet | Balanced coding and reasoning |
| Plan a large Magento 2 migration with rollback steps | Opus or Fable, after evaluation | More dependencies, risk, and multi-step planning |
| Research a complex business problem using many documents and tools | Opus or Fable | Strong multi-step analysis and tool planning |

## 2. What Is the Context Window?

The **context window** is Claude’s working memory for one request.

It includes:

```text
System prompt
      +
User messages
      +
Assistant responses
      +
Tool definitions
      +
Tool calls
      +
Tool results
      +
Images and PDFs
      +
Generated output for the current turn
      =
Context window usage
```

Claude’s documentation states that system prompts, message history, tools, tool results, documents, images, output tokens, and extended-thinking tokens all count toward the context budget. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

Think of it as a backpack:

```text
Small conversation
→ Small backpack load

Long chat + many tool results + large files
→ Heavy backpack load

Too much content
→ Context window fills
```

Even if a model has a large context window, every extra token still affects:

- Input cost
- Latency
- Available space for the next tool result
- Ability to keep a session running for many turns

## 3. What Happens When Context Fills?

There are two different cases.

### Case A: Input Is Already Too Large

```text
Your request is bigger than the allowed context window
        ↓
API rejects the request before Claude starts answering
        ↓
You receive a validation error
```

### Case B: Request Starts but Output Hits the Limit

```text
Input fits
        ↓
Claude starts generating
        ↓
Context limit is reached during generation
        ↓
Output stops early
        ↓
stop_reason = model_context_window_exceeded
```

Claude does not silently remove old conversation messages for you. Your application must decide what to keep, summarize, remove, or store outside the live conversation. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## 4. Why Production Fails Earlier

Development test data is often much smaller than real data.

### Development Example

```text
20 receipt-processing turns
      ↓
Each tool result: about 800 tokens
      ↓
20 × 800 = 16,000 tokens
      ↓
Session works fine
```

### Production Example

Real receipts may include:

- Receipt text
- Invoice details
- Transaction records
- Customer messages
- Supporting PDFs
- Bank or tax data

```text
8 receipt-processing turns
      ↓
Each tool result: about 3,200 tokens
      ↓
8 × 3,200 = 25,600 tokens
      ↓
Add system prompt, user messages, tool calls, responses
      ↓
Team budget cap is reached
      ↓
Agent starts failing at turn 8
```

The model did not suddenly become worse. The tool outputs became larger and filled the working memory faster.

```text
Large tool results
        ↓
Context fills
        ↓
Important instructions become less effective or unavailable
        ↓
Tool selection becomes worse
        ↓
Answers become incomplete or wrong
```

If an agent starts selecting wrong tools after a similar number of turns, check **context usage** before rewriting tool schemas.

## 5. Four Ways to Control Context

### 1. Pruning: Remove a Bad Path

Pruning means going back to an earlier point in the conversation and removing what happened after it.

Use it when Claude has gone down an unhelpful route.

```text
Turn 1: User asks to debug payment issue
Turn 2–8: Agent explores wrong module and wrong logs
Turn 9: You discover the direction is wrong
        ↓
Prune back to Turn 1 or Turn 2
        ↓
Continue with the correct approach
```

**Good for:**
- Failed debugging attempts
- Unhelpful back-and-forth
- Wrong assumptions
- Tool output that is no longer useful

**What you lose:** everything after the point where you go back.

***

### 2. Compaction: Summarize Old History

Compaction means replacing old detailed messages with a shorter summary.

```text
Before compaction:

System prompt
+ 30 chat messages
+ 15 tool results
+ long debugging output
+ API responses
= 70,000 tokens
```

```text
After compaction:

System prompt
+ short summary of important work
+ current task
+ latest relevant tool results
= 12,000 tokens
```

Use compaction when:

- You are continuing the same task.
- The conversation is becoming long.
- You need Claude to remember decisions and progress.
- You can safely lose low-value detail.

Claude supports server-side compaction, which can summarize earlier conversation content so an agent can continue beyond the context limit; manual client-side summarization is also possible. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

### Bad Compaction Prompt

```text
Summarize the conversation so far.
```

This may lose important technical details.

### Better Compaction Prompt

```text
Summarize the conversation for a developer continuing this task.

Preserve:
- Current user goal
- Decisions already made
- Files modified and file paths
- APIs and tools called
- Important tool results
- Errors encountered
- Root causes identified
- Fixes attempted
- Current implementation state
- Remaining work
- Next recommended step
- Any constraints that must not change

Do not include unrelated discussion or repeated explanations.
```

The compaction guidance emphasizes preserving state, next steps, and learnings, and supports customizing summarization instructions. [platform.claude](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)

**Important:** summarization can lose details. If a fact is important later, explicitly ask the summarizer to preserve it.

***

### 3. Clearing: Start Fresh

Clearing means starting a completely new conversation.

```text
Old task:
Debug Magento payment gateway problem
        ↓
New task:
Write marketing copy for a product page
        ↓
Do not carry old technical debugging context
        ↓
Start a new session
```

Use clearing when the next job is unrelated.

```text
Different task
        ↓
Old context is not useful
        ↓
Start a new session
```

**What you lose:** all current conversation history.

If something must survive across sessions, store it outside the context window:

```text
Database
File
Project memory
CLAUDE.md
Vector store
User profile
Task-state record
```

***

### 4. Subagent Handoffs: Give a Separate Task to a Separate Agent

A subagent is a separate agent with its own smaller, clean context.

Instead of making the main agent carry every exploration step, give a focused task to a subagent and return only the useful result.

```text
Main agent:
“Fix checkout performance issue.”

        ↓

Subagent 1:
“Inspect database-query problems.
Return only findings and suggested SQL/index fixes.”

        ↓

Subagent 2:
“Inspect frontend JavaScript bundle issues.
Return only findings and suggested build changes.”

        ↓

Subagent 3:
“Review Redis/cache configuration.
Return only relevant risks and fixes.”

        ↓

Main agent:
Combines the summaries into one plan.
```

Use subagents when:

- A task has independent parts.
- Exploration produces lots of messy detail.
- Only a short final result is needed by the parent agent.
- The overall task is too large for one context window.

**What you lose:** the parent agent does not automatically retain all the detailed intermediate reasoning from each subagent. It gets their final summary.

***

## 6. Compare the Four Strategies

| Strategy | What it does | Use it when | What you lose |
|---|---|---|---|
| Pruning | Removes an unhelpful section of conversation | Agent followed the wrong path | Work after the rewind point |
| Compaction | Replaces old detail with a summary | Same task continues but history is large | Fine details not included in summary |
| Clearing | Starts a fully new session | New task is unrelated | All old session information |
| Subagent handoff | Delegates a focused task to separate context | Task is large or has independent research areas | Subagent’s full process and intermediate detail |

## 7. Prompt Caching: Lower Cost for Repeated Content

Prompt caching saves cost and time when the beginning of your request remains the same across many calls.

Good things to cache:

```text
Long system prompt
Large tool definitions
Product catalog documentation
API documentation
Company policy document
Repeated reference material
```

Example:

```text
Every request contains:

- 8,000-token system prompt
- 5,000-token product documentation
- 2,000-token tool definitions
- New user message
```

Without caching:

```text
Every call processes all 15,000 repeated tokens again
```

With caching:

```text
First call:
Processes and caches the stable prefix

Later calls:
Reuse cached prefix
Only process changing user data and new conversation content
```

Claude’s prompt-caching feature uses `cache_control`, supports automatic caching or explicit cache breakpoints, and exposes cache-read and cache-creation token counts in usage data. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

### Simple Cache Concept

```text
Stable system prompt + tools + documents
                ↓
             Cache once
                ↓
New user message each turn
                ↓
Reuse old stable prefix
```

Caching reduces what you **pay to process repeatedly**, but the cached content still counts toward the total context window. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## 8. Token Counting: Check Before It Fails

Token counting means checking how many tokens a request will use before sending it to Claude.

```text
Build request
      ↓
Count tokens
      ↓
Is it within your safe budget?
      │
      ├── Yes → Send request
      │
      └── No → Compact, prune, clear, or reduce tool output
```

This is useful because it helps you find the problem before a production request fails.

Example:

```text
Your internal session budget: 40,000 tokens

Current request:
- System prompt: 4,000
- Tool schemas: 5,000
- Conversation history: 18,000
- Tool results: 11,000
- Expected response reserve: 4,000
-------------------------------
Total: 42,000 tokens
```

Result:

```text
Over internal budget
        ↓
Compact conversation before next model call
```

Claude provides token counting using the same request shape as a messages call, allowing you to inspect token use before running inference. The API response usage fields also report token use and cache-related counts. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## 9. RAG: Keep Large Knowledge Outside Context

**RAG** means retrieving only the relevant information from a large knowledge base instead of putting the whole knowledge base into every prompt.

Example: You have 20,000 Magento support documents.

### Bad Approach

```text
Put all 20,000 documents into the prompt
        ↓
Very expensive
        ↓
Slow
        ↓
Context fills
        ↓
Claude may still miss the relevant line
```

### Better RAG Approach

```text
User asks:
“How do I configure stock alerts in Magento?”

        ↓

Search documentation
        ↓

Retrieve only the 3–5 relevant chunks
        ↓

Send those chunks to Claude
        ↓

Claude answers using the retrieved information
```

***

## 10. Three Places RAG Can Fail

### A. Chunking Problem

**Chunking** means splitting large documents into smaller pieces before storing them for search.

```text
Document:
10,000 words
        ↓
Split into chunks
        ↓
Store chunks for retrieval
```

If chunks are too small:

```text
Important sentence is separated from its explanation
        ↓
Retrieved text lacks useful context
```

If chunks are too large:

```text
One chunk contains many unrelated topics
        ↓
Search result becomes less accurate
```

A practical starting point is sentence- or section-based chunks with a small overlap so facts at the edges are not split apart.

```text
Chunk 1:
Paragraphs 1–4

Chunk 2:
Paragraphs 4–7
           ↑
        overlap
```

***

### B. Retrieval/Search Problem

Semantic search finds content with similar meaning.

But sometimes you need an exact term:

```text
User query:
“Why does error code M2-ERR-4471 happen?”
```

Semantic search may prefer a general “payment failure” document over the exact document that contains `M2-ERR-4471`.

A practical solution is **hybrid search**:

```text
Semantic search
        +
Keyword / exact-text search
        =
Better retrieval
```

For product SKUs, order IDs, error codes, class names, configuration keys, and file paths, exact keyword search is often important.

***

### C. Assembly Problem

Even if retrieval finds the correct chunks, they must be placed into the model request clearly.

Bad assembly:

```text
Here are some documents:
[large unstructured text]
Answer the question.
```

Better assembly:

```text
<instructions>
Answer only using the supplied documentation.
If the documentation does not contain the answer, say so.
</instructions>

<retrieved_documents>
  <document id="1">
  ...
  </document>

  <document id="2">
  ...
  </document>
</retrieved_documents>

<user_question>
How do I configure stock alerts in Magento?
</user_question>
```

Clear structure helps Claude use retrieved text instead of relying on general memory.

## 11. Indexed RAG vs Search Across Rounds

There are two common ways to let an agent work with a large document set.

| Approach | How it works | Best for | Trade-off |
|---|---|---|---|
| Indexed RAG | Build embeddings/search index once, then retrieve relevant chunks | Stable manuals, policies, documentation, repeated lookups | Requires infrastructure, syncing, storage, permissions, and index maintenance |
| Search across rounds | Agent searches or reads current files as needed during the task | Rapidly changing files, multi-step investigation, current codebase search | More model/tool calls, more time and tokens per task |

### Example: Stable Documentation

```text
Product policies change once every few months
        ↓
Build and maintain a retrieval index
        ↓
Fast, cheap repeated searches
```

### Example: Active Git Repository

```text
Code changes every day
        ↓
Use search/read tools against current files
        ↓
Agent sees current code instead of stale indexed chunks
```

For a stable reference corpus, an index is often worth maintaining. For changing source material or multi-step questions, iterative search is usually simpler, though it may cost more per query.

## 12. Practical Agent Design Example

Imagine a Magento support agent that investigates checkout failures.

### Poor Design

```text
1. Send every log file to Claude
2. Send every database query result
3. Keep every old tool result forever
4. Keep every debugging conversation turn
5. Continue until the context window fills
```

Result:

```text
More tokens
      ↓
Higher cost
      ↓
Slower response
      ↓
Context fills
      ↓
Wrong tool choices and incomplete answers
```

### Better Design

```text
1. Use Sonnet as the starting model
2. Use Haiku for simple ticket classification
3. Send only relevant logs, not all logs
4. Limit tool output to needed fields
5. Store raw data outside context
6. Send short summaries of completed investigation steps
7. Compact proactively near an internal token limit
8. Delegate isolated research to subagents
9. Cache stable system instructions and tool schemas
10. Count tokens using realistic production-sized outputs
```

### Example Internal State Summary

Instead of retaining 20 pages of logs:

```text
<investigation_summary>
Issue: Checkout API returns 500 for guest users only.

Confirmed:
- Logged-in checkout works.
- Failure began after payment module version 2.4.3 deployment.
- Error occurs in Vendor\Payment\Model\GuestTokenValidator.
- Stack trace points to null quote ID.
- Database and Redis are healthy.

Files inspected:
- app/code/Vendor/Payment/Model/GuestTokenValidator.php
- app/code/Vendor/Payment/Plugin/CheckoutPlugin.php

Remaining work:
- Compare guest token validation logic with previous module version.
- Test quote ID fallback in staging.
</investigation_summary>
```

This gives Claude the useful state without making it reread every log line.

## Production Checklist

Before launching a multi-turn Claude agent, make sure you have:

- Chosen a starting model using quality, cost, and latency needs.
- Tested with realistic production-sized input and tool outputs.
- Set an internal context budget below the model’s hard limit.
- Used token counting before long or risky requests.
- Logged usage fields such as input, output, and cache token counts.
- Limited tool output to only required fields.
- Decided when to prune, compact, clear, or use subagents.
- Written a detailed compaction prompt that preserves critical task state.
- Stored long-term memory outside the live chat context.
- Cached stable prompts, tool definitions, and repeated reference material.
- Used RAG or search tools instead of injecting entire document collections.
- Added hybrid search for exact identifiers, error codes, SKUs, and paths.
- Checked for context pressure when tool selection worsens after several turns.

## Easy Memory Diagram

```text
Choose a model
      ↓
Measure quality, cost, and speed
      ↓
Keep live context small
      ↓
Store big data outside chat
      ↓
Retrieve only what is needed
      ↓
Compact old history before limits
      ↓
Use subagents for isolated large tasks
      ↓
Count tokens before the request fails
```

The most important idea is:

```text
A larger context window is helpful,
but it is not a replacement for context management.
```

Plan what enters the context, what gets summarized, what stays in external storage, and what should never be sent at all.

## Mechanism: Context Crowding

The failure is **context-window pressure** (also called context crowding).

```text
Turn 1–4:
Large policy document results are kept in conversation history
        ↓
More and more tokens remain in Claude's working context
        ↓
Important system instructions and tool-selection guidance get crowded out
        ↓
Turn 5:
Claude chooses the wrong tool
        ↓
Turn 6:
Wrong path continues
        ↓
Turn 7:
Session ends without a result
```

The tool schema may be correct. The problem is that Claude has too much old tool output in its active working memory. Claude documentation explains that messages, tool definitions, tool calls, and tool results all consume context-window capacity, so long-running tool sessions need explicit context management. [platform.claude](https://platform.claude.com/docs/en/build-with-claude/context-windows)

## One-Line Fix

**B. Prune `fetch_policy_document` results after each turn so that accumulated outputs do not crowd out current instructions, and apply compaction before Turn 5.**

A better practical pattern is:

```text
Fetch large policy document
        ↓
Extract only the relevant policy rules
        ↓
Save a short structured summary
        ↓
Remove or prune the full 2,400-token document result
        ↓
Keep the agent's system prompt and tool guidance visible
```

For example, replace this large tool output:

```text
Full policy document: 2,400 tokens
```

with this smaller retained state:

```text
<policy_summary>
Policy ID: POL-2026-014
Coverage rule:
- Claims above ₹50,000 require manual review.
- Claims submitted after 30 days are rejected unless an exception is approved.
- Use apply_coverage_rule for eligibility decisions.
</policy_summary>
```

This preserves what Claude needs while removing unnecessary detail.

## Why Other Options Are Wrong

| Option | Why it is not the main fix |
|---|---|
| A. Improve tool description | A clearer description can help in a true schema-routing problem, but the pattern here is different: selections were correct until repeated large tool outputs accumulated. The failure begins after context growth. |
| B. Prune and compact | Correct. It directly removes the growing context pressure that caused tool selection to degrade. |
| C. Increase `max_tokens` | `max_tokens` mainly controls how much Claude can generate as output. It does not remove old tool results or restore lost context space. Increasing it can make budget pressure worse. |

## Easy Rule to Remember

```text
Tool selection works early,
then becomes wrong after several large tool results
        ↓
Check context size before rewriting tool schemas.
```

Use pruning for large results that are no longer needed, and compact important findings into a smaller summary before the next tool decision.
